## 一、M0 阶段的目标设计与阶段划分

### 背景 / 问题描述

进入 M0（项目奠基）时容易犯的错误是把它当成"装环境"——装完就进 M1。
但本项目 3~4 个月的周期里，有两个风险**只有在第 1 周验证才便宜**：

| 风险 | 后期发现的代价 |
| --- | --- |
| IL2CPP 下 xLua / protobuf-net 的 AOT 问题 | Editor 正常、打包后崩。若拖到 M6 才发现，可能推翻协议层实现 |
| 插件无法在纯 .NET 服务端运行 | 决定 AI 架构（A1/A2/A3 裁决）。若 M4 才发现，AI 层要重写 |

### 解决方案 / 代码模式

**把风险验证设计成 M0 的一等公民，而不只是"顺手做做"。**

M0 被切成 9 个阶段，其中两个阶段专门用于"引爆风险"：

```
D1~D4   创建工程 + 关键设置      （地基）
D5~D11  导入依赖与插件            （按顺序，避免重复导入）
D12     数据库准备
D13     服务端骨架                ← 零依赖，可与 D1 并行
D14     插件架构边界实验          ← 风险引爆点 1
D15~D16 工程骨架 + Git
D17     IL2CPP 打包验证            ← 风险引爆点 2（M0 的最终关卡）
```

**关键设计：先定"红线"再开工**

| 检查点 | 红线 | 降级动作 |
| --- | --- | --- |
| 第 1 周末 | D17 未通过 | **不进入 M1**，先解决 AOT。这是唯一不能跳过的关卡 |
| 第 1 周末 | D12 未通过 | 可用 SQLite/内存库占位，但 M3 前必须补齐 |

**并行化**：D13（服务端骨架）不需要 Unity 工程存在，因此可以在负责人操作 D1 的同时由 AI 完成，
把 M0 从"串行等待"变成"部分并行"。

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 把 AOT 验证放到项目末期 | 这是最贵的错误。此刻 0 行业务代码时验证，成本是几小时 |
| 导入顺序随意 | YooAsset 与 xLua 会改动资源导入流程，**先装它们**可避免后续资源重复导入 |

| 打包时开着 Development Build | 验证 AOT 要出 **Release 包**，否则裁剪行为不同，验不出来 |

## 二、XML 注释内禁止 `--`（本次真实抓到的缺陷）

### 背景 / 问题描述

生成 5 个 `.csproj` 时，为了让注释好看，我用 `------...------` 画了分隔线。
结果**所有工程文件都无法被 XML 解析器解析**：

```
XML FAIL NBC.Shared.csproj -> not well-formed (invalid token)
MSB4025: 未能加载项目文件。名称不能以“-”字符开头
```

### 根因分析

**XML 规范（1.0）硬性规定：注释内容中不得出现字符串 `--`**，因为 `--` 是注释的结束标记组成部分。

```xml
<!-- 合法注释 -->
<!-- ==== 分隔线 ==== -->          ← 合法（= 号不是 -）
<!-- --------- 分隔线 --------- -->  ← ❌ 非法！内容含 "--"
```

解析器一旦遇到注释内的 `--` 就会报错，**整个工程文件加载失败**。
这也解释了为什么 `Directory.Build.props` 一开始就能通过——它的分隔线用的是 `=`。

### 解决方案 / 代码模式

XML 注释的分隔线**只用 `=` 或 `~`**，绝不用 `-`：

```xml
<!-- ========================================================================
     模块说明
     ======================================================================== -->
```

**修复用状态机而不是正则**（这一点很重要，见下节踩坑）：

```python
def rebuild_comments(text):
    out, i, n = [], 0, len(text)
    while i < n:
        j = text.find("<!-", i)
        if j < 0:
            out.append(text[i:]); break
        out.append(text[i:j])
        k = text.find("->", j + 3)
        if k < 0:
            out.append(text[j:]); break
        inner = text[j + 3:k].rstrip("-")
        inner = re.sub(r"-{2,}", "-", inner)      # 只处理注释内部
        out.append("<!--" + inner + "-->")
        i = k + 2
    return "".join(out)
```

**交付前的只读校验清单**（项目规则 W2）：

| 校验 | 方法 |
| --- | --- |
| XML 合法性 | `xml.etree.ElementTree.parse()` |
| JSON 合法性 | `json.load()`，**用 Python 显式 UTF-8 读** |
| 括号配平 | 统计 `{}` `()` 数量 |
| 编码/BOM | 读前 3 字节判断是否 BOM |
| 结构自检 | 如 `.sln` 的 `Project(` 与 `EndProject` 数量配对 |

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| **用正则修改注释标记本身** | 我第一次写 `re.sub(r"<!--.*?-->", clean)`，其中 `clean` 对整个匹配串（**含 `<!--` 和 `-->`**）做 `-{2,} → -`，结果把 `<!--` 变成 `<!-`、`-->` 变成 `->`，**注释结构被彻底破坏**，后续正则再也匹配不上。教训：**处理定界符包裹的内容时，只对"内部"做替换，绝不动定界符** |
| 破坏后再用同一正则去修 | 结构已损坏，正则匹配不到，越修越乱。此时应改用**状态机**按字符扫描重建 |
| 修复脚本没有自检 | 每次修复后必须重新解析校验，否则会带着更严重的错误进入下一步 |

## 三、PowerShell 读中文文件的编码陷阱（重要，会造成误报）

### 背景 / 问题描述

同一批文件，用 Python 校验 JSON **全部通过**，用 PowerShell 校验却报：

```
Invalid object passed in, ':' or '}' expected. (88)
"NBC 鏈嶅姟绔噺缃..."     ← 明显的乱码
```

看起来像 JSON 语法错误，**实际是编码问题造成的误报**。

### 根因分析

`Get-Content -Raw` 在**没有显式指定编码**时，使用系统默认 ANSI 代码页。
本机（中文 Windows）默认是 **GBK**，而文件是 **UTF-8 无 BOM**。
UTF-8 的中文字节被按 GBK 解读 → 乱码 → 引号/括号配对关系被破坏 → 解析器报"语法错误"。

> 关键认知：**文件是好的，是"读它的方式"错了。** 这类问题最容易被误判为内容缺陷。

### 解决方案 / 代码模式

| 场景 | 正确做法 |
| --- | --- |
| 校验 UTF-8 中文文件 | **优先用 Python**：`io.open(path, "r", encoding="utf-8")` |
| 必须用 PowerShell | 显式加编码：`Get-Content -Raw -Encoding UTF8` |
| 判断是否乱码而非真错 | 看报错信息里是否出现 `鏈嶅姟` 这类**典型 UTF-8→GBK 乱码特征串** |

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 把编码误报当成内容缺陷去"修" | 会去改本来正确的文件，把好文件改坏 |
| 用 `[xml]`/`ConvertFrom-Json` 却不控编码 | 校验结果不可信 |
| 反过来：以为乱码就是文件坏了 | 先用 Python 复验一次再下结论 |

## 五、`.gitignore` 忽略目录的写法陷阱（本次抓到 4 条规则失效）

### 背景 / 问题描述

为 Monorepo（`Client/` Unity + `Server/` .NET）写 `.gitignore` 时，我按"看起来更健壮"的思路写了字符类写法：

```gitignore
Client/[Ll]ibrary/
Client/Temp/ 等
Server/**/bin/
Server/**/obj/
```

写完**语法检查完全通过、没有任何报错**。但用路径模拟验证后发现有 **4 条规则实际失效**：

```
Client/Library/ScriptAssemblies/Assembly-CSharp.dll   → TRACKED!  ❌
Client/UserSettings/EditorUserBuildSettings.asset     → TRACKED!  ❌
Server/NBC.Server.Core/bin/.../NBC.Server.Core.dll    → TRACKED!  ❌
Server/NBC.Server.Core/obj/project.assets.json        → TRACKED!  ❌
```

**含义**：`Library/` 里是 Unity 自动生成的、动辄数 GB 的缓存；`bin/`/`obj/` 是编译产物。
它们被提交进仓库会**立刻把仓库撑爆、且每次提交全是噪音 diff**。

### 根因分析

| 失效写法 | 为什么失效 |
| --- | --- |
| `Client/[Ll]ibrary/` | 尾随斜杠让规则**只匹配"目录本身"**，而 git 匹配路径时面对的是**目录内的文件路径**（如 `Client/Library/Artifacts/x`）。git 不会因为父目录命中就忽略子文件 —— 于是整个目录被漏掉 |
| `Server/**/bin/` | `**/` 在 gitignore 中的语义与直觉不同；`bin` 本来就是"任意层级下的目录名"，**裸写 `bin/` 即可正确匹配任意层级**，加 `**/` 反而不可靠 |

**关键认知**：`.gitignore` 的规则失效是**静默的** —— 没有报错、没有警告，
只有在 `git status` 里看到一大堆不该出现的文件时才会发现，而那时可能已经提交了。

### 解决方案 / 代码模式

**正确写法：忽略目录用「目录名 + 斜杠」，不要用字符类 + 斜杠。**

```gitignore
# ✅ 正确：匹配该目录自身及其下所有内容
Client/Library/
Client/Temp/
Client/UserSettings/

# ✅ 正确：裸目录名的规则可匹配任意层级
bin/
obj/

# ❌ 错误：字符类 + 尾部斜杠会漏掉目录内文件
Client/[Ll]ibrary/
Server/**/bin/
```

**并且必须做路径模拟验证**（项目规则 W6）。核心脚本：

```python
import io, os, fnmatch

rules = []           # 按顺序保留"最后匹配优先"语义
for ln in io.open(".gitignore", encoding="utf-8"):
    ln = ln.rstrip("\n")
    if not ln.strip() or ln.lstrip().startswith("#"):
        continue
    neg = ln.startswith("!")
    rules.append((neg, (ln[1:] if neg else ln).strip()))

def is_ignored(path):
    path = path.replace("\\", "/")
    state = False
    for neg, pat in rules:
        base = pat.rstrip("/")
        is_dir_rule = pat.endswith("/") or ("/" not in pat and "." not in pat)
        hit = False
        if is_dir_rule:                                   # 目录规则：匹配自身及子孙
            segs = base.split("/")
            if len(segs) == 1:
                hit = base in path.split("/")
            else:
                hit = (path == base or path.startswith(base + "/"))
        else:                                             # 文件规则
            if "/" in base:
                hit = fnmatch.fnmatch(path, base)
            else:
                hit = fnmatch.fnmatch(os.path.basename(path), base)
        if hit:
            state = not neg
    return state
```

**然后准备两组断言清单**：

| 清单 | 内容 | 期望 |
| --- | --- | --- |
| `must_track` | 源码、配置模板、asmdef、`Packages/manifest.json`、`ProjectSettings/*.asset`、文档 | 全部 **不被忽略** |
| `must_ignore` | `Library/`、`Temp/`、`Logs/`、`bin/`、`obj/`、`Builds/`、`*.Local.json`、生成的 `.csproj`/`.sln` | 全部 **被忽略** |

两组都通过才算 `.gitignore` 正确。

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 以为"语法没错"就等于"规则生效" | gitignore 失效是静默的。**必须按路径模拟，而不是读一遍觉得对** |
| 把"看起来更健壮"的写法当成更安全 | `[Ll]ibrary/` 这种"兼容大小写"的写法**恰恰是错的**，反而漏掉整个目录 |
| 只测一层路径 | 必须测"目录内的深层文件"（`Client/Library/Artifacts/abc`），只测 `Client/Library` 会误判为正确 |
| Monorepo 里忽略规则写得太窄 | `Server/**/bin/` 只覆盖 Server 下；用裸 `bin/` 才对任意层级都生效 |

## 六、用 asmdef 的 `noEngineReferences` 把架构约束变成编译错误

### 背景 / 问题描述

需求文档里写了一条硬约束：**逻辑层（Model）禁止引用 `UnityEngine`**（§4.2 R1、DET-02）。
原因是帧同步要求所有端算出完全相同的结果，而 `UnityEngine` 的 `Vector3` / `Mathf` 内部都是 `float`，
浮点不保证跨端一致 → 只要逻辑层碰了 UnityEngine，就可能引入不确定性。

问题在于：**"写在文档里的约束"没有任何强制力**。开发两三个月后，某个新脚本顺手写了
`using UnityEngine;`，没有任何提示，直到 M4 帧同步出现偶发不同步才暴露 —— 而那种问题极难排查。

### 根因分析

| 约束形式 | 强制力 | 发现问题的时间点 |
| --- | --- | --- |
| 写在需求文档里 | ❌ 无 | 靠人记得；忘了就违反 |
| 写在代码审查清单里 | ⚠️ 弱 | 靠每次审查；漏一次就放过 |
| **编译期检查（asmdef）** | ✅ 强 | **写下的那一刻就编译失败** |
| 单元测试断言 | ✅ 强（可补充） | 跑测试时；能覆盖"间接引用" |

### 解决方案 / 代码模式

Unity 的程序集定义（`.asmdef`）有一个字段 **`noEngineReferences`**：
设为 `true` 后，该程序集**无法访问任何 UnityEngine API**，编译直接报错。

本项目的程序集划分：

| 程序集 | 目录 | `noEngineReferences` | 理由 |
| --- | --- | --- | --- |
| `NBC.Framework` | `_Project/Framework/` | `false` | 框架底座要操作 GameObject / MonoBehaviour |
| **`NBC.Model`** | `_Project/Game/Model/` | **`true`** | **逻辑层，必须纯 C#** |
| `NBC.Game` | `_Project/Game/`（View/Controller/Service） | `false` | 表现与调度层，需要引擎 API |
| `NBC.Editor` | `_Project/Editor/` | `false` | 编辑器工具（`includePlatforms: ["Editor"]`） |
| `NBC.Tests.EditMode` / `PlayMode` | `_Project/Tests/…` | `false` | 测试程序集（测试需要 UnityEngine.TestRunner） |

**asmdef 的关键写法要点**（[Unity 2022.3 官方格式文档](https://docs.unity.cn/Components/AssemblyDefinitionFileFormat.html) 已核实）：

```json
{
    "name": "NBC.Model",
    "references": [ "NBC.Framework" ],
    "includePlatforms": [],
    "noEngineReferences": true,
    "autoReferenced": true
}
```

| 要点 | 说明 |
| --- | --- |
| `references` 可用**程序集名**或 `GUID:xxx` | 本项目统一用**程序集名**（可读、可手写、不怕 GUID 变化）；⚠️ **同一个列表里不能混用两种形式** |
| `noEngineReferences` 默认为 `false` | 必须显式写 `true` 才生效 |
| 目录归属 | asmdef 覆盖**它所在目录及其所有子目录**（除非子目录另有 asmdef） |
| `includePlatforms: ["Editor"]` | 编辑器专用程序集；漏了它出包时会带上编辑器代码并报错 |

**付出的代价与应对**（这是关键：约束有代价，必须给出替代方案，否则开发会绕开它）：

| Model 层原本想用 | 改用 | 归属 |
| --- | --- | --- |
| `Debug.Log` | 自研 `Log` 接口（Framework 提供实现） | M1 |
| `Vector3` / `Mathf` | 自研 `FixVector3` / `FixMath`（定点） | M1 |
| `ScriptableObject` 配置类 | 放 `NBC.Game` 层作数据容器，读出后转成 Model 的纯数据对象 | M1 |
| `MonoBehaviour` | 纯 C# 类，由 `NBC.Game` 层的驱动脚本持有 | M1 |

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 以为"写进文档"就等于"会被遵守" | 文档约束无强制力。**能量化成编译错误或测试断言的约束才算真约束** |
| 只加 `noEngineReferences` 不给替代方案 | 开发会被迫"绕开"（比如把逻辑挪回 Game 层），约束形同虚设。**必须同时提供 Log / 定点数学等替代品** |
| asmdef 的 `references` 混用名称与 GUID | 官方明确要求同一列表形式统一，混用会出问题 |
| 忘了 `includePlatforms: ["Editor"]` | 出包时把编辑器代码打进包，报错或包体膨胀 |
| 目录名含 `Tests` 却不建测试 asmdef | Unity 会按测试程序集规则处理该目录下的脚本，可能报 NUnit 相关错误 |

## 七、NuGet 包版本锁定与"依赖闭包"（Unity 侧最容易漏的一环）

### 背景 / 问题描述

M0 要"冻结依赖版本"，而"最新稳定版"这种写法有三个问题：
① 不是可复现的（明天构建可能拉到不同版本）② 无法判断兼容性 ③ 面试时讲不出为什么选它。

于是我去查了各包的真实版本与**依赖关系**，结果发现一个会导致 Unity 编译失败、但很容易漏掉的点。

### 根因分析

**NuGet 包管理的是"包"，Unity 管理的是"DLL" —— 两者的"依赖闭包"概念不对等。**

服务端用 `<PackageReference>`，NuGet 会自动把传递依赖一起还原，所以只写一个包名就够。
但 **Unity 不认 NuGet**，需要手动把 DLL 拖进 `Assets/`。此时如果只拖主包、
忘了传递依赖，编译就会报"找不到类型"。

以 `protobuf-net 3.2.30` 为例，它的 `.nuspec` 显示依赖关系是：

| 目标框架 | 依赖 |
| --- | --- |
| `.NETStandard2.0` | `protobuf-net.Core` + `System.Reflection.Emit` + `System.Reflection.Emit.Lightweight` |
| **`.NETStandard2.1`** | **只有 `protobuf-net.Core`** ← 本项目走这条 |

而 `protobuf-net.Core 3.2.30` 的 `.nuspec`：

| 目标框架 | 依赖 |
| --- | --- |
| `.NETStandard2.0` | `System.Collections.Immutable` + `System.Memory` |
| **`.NETStandard2.1`** | **只有 `System.Collections.Immutable 7.0.0`** |

**结论**：Unity 侧必须放 **3 个 DLL**：
`protobuf-net.dll` + `protobuf-net.Core.dll` + `System.Collections.Immutable.dll`。
只放第一个 → 编译失败。

顺带一个重要发现：**`netstandard2.1` 目标不依赖 `System.Reflection.Emit`** ——
而 `Reflection.Emit` 在 IL2CPP（AOT）下不可用。所以走 `netstandard2.1` 对 Unity 更友好。

### 解决方案 / 代码模式

**要点 1：判断一个 NuGet 包能否用于 Unity，看它有没有 `netstandard2.x` 目标。**

查法（不用打开 Visual Studio，直接打 NuGet 的 flat-container API）：

```
https://api.nuget.org/v3-flatcontainer/<包名小写>/index.json    # 版本列表
https://api.nuget.org/v3-flatcontainer/<包名小写>/<版本>/<包名小写>.nuspec   # 依赖与 license
```

> 国内如遇重定向，可用镜像域名 `nuget.azure.cn`（本次即如此）。

**要点 2：把"依赖闭包"写进依赖清单，而不是只写主包。**

本项目的 `Docs/05-依赖清单.md` 因此把原来的 1 行 protobuf-net 拆成 3 行
（`C7` / `C7a protobuf-net.Core` / `C7b System.Collections.Immutable`），并在 Unity 放置说明里明确"三个一起放"。

**要点 3：选版本时不追新，选"已验证可用于目标框架"的。**

| 版本 | 判断 |
| --- | --- |
| `protobuf-net 3.2.30`（选用） | ✅ 有 `netstandard2.1` 目标，且该目标不依赖 `Reflection.Emit` |
| `protobuf-net 3.4.x`（最新） | 未核实，且本项目不需要新特性 —— **"能打包运行"比"用最新版"重要** |

本次锁定的版本（全部经 `.nuspec` 核实）：

| 包 | 版本 | 许可 | 备注 |
| --- | --- | --- | --- |
| Dapper | 2.1.86 | Apache-2.0 | 服务端数据访问 |
| MySqlConnector | 2.5.0 | **MIT** | 含 `net8.0` 目标；真异步 |
| protobuf-net | 3.2.30 | Apache-2.0 | 含 `netstandard2.1` |
| protobuf-net.Core | 3.2.30 | Apache-2.0 | 传递依赖，Unity 侧必须一起放 |
| xUnit | 2.9.3 | Apache-2.0 | 服务端单测 |
| NPOI | 2.8.0 | **Apache-2.0** | 取代 EPPlus（Polyform Noncommercial，商用需付费） |

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 以为"装了主包就能用" | NuGet 会自动拉传递依赖，**Unity 不会**。清单里必须登记依赖闭包 |
| 用"最新稳定版"当作锁定 | 不可复现，且无法预判兼容性。**要写精确版本号** |
| 只看版本号不看 `TargetFramework` | 一个包可能只有 `net6.0` 目标，Unity（.NET Standard 2.1）用不了 |
| 选许可受限的库 | EPPlus 5+ 是 Polyform Noncommercial，商用要付费；改用 Apache-2.0 的 NPOI 更稳 |

## 八、测试账号密码哈希：让脚本"开箱可用"

### 背景 / 问题描述

`Docs/08-数据库脚本.sql` 里最初写的是**占位哈希串**（格式对、长度 64，但不是真实哈希）。
这意味着：跑完脚本后测试账号**登不上去**，而 M3 首次联调时你会在"账号密码错误"上浪费时间去猜是代码问题还是数据问题。

### 解决方案 / 代码模式

**把占位串换成真实计算的哈希**，并**显式写清算法约定**，让服务端实现有唯一标准：

```python
hash = hashlib.sha256((salt + "123456").encode("utf-8")).hexdigest()   # 小写十六进制，64 字符
```

产出（明文密码统一 `123456`）：

| 账号 | salt | password_hash（前 16 位） |
| --- | --- | --- |
| test01 | `6f1a2b3c4d5e6f70` | `6a94b5966341a30b…` |
| test02 | `7a2b3c4d5e6f7081` | `cedc18947cb79327…` |
| test03 | `8b3c4d5e6f708192` | `0733ea2d54931910…` |
| test04 | `9c4d5e6f708192a3` | `2560cab1006a2eee…` |

并在脚本里加了**双向自校验**：

```python
assert hashlib.sha256((salt + PWD).encode()).hexdigest() == h      # 同算法可复现
assert hashlib.sha256((salt + "wrong").encode()).hexdigest() != h  # 错密码不命中
```

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 用占位哈希当真实数据 | 会让"数据问题"伪装成"代码问题"，M3 联调时最耗时的一类误判 |
| 没写清拼接顺序 | `salt + password` 与 `password + salt` 结果完全不同；不写明就会双端不一致 |
| 改完脚本不做静态校验 | 见下条 —— 我的校验器自己就出了 bug |

## 九、校验器本身也会误报（第二次踩到）

### 背景 / 问题描述

写 SQL 静态校验脚本时，用正则拆分 INSERT 的值个数：

```python
nval = len([v for v in re.split(r",(?![^']*')", row) if v.strip()])   # ❌ 有 bug
```

结果把正确的脚本报成 `MISMATCH account 列=3 值=1`。
**如果直接相信这个结果，我就会去"修"一个本来正确的 SQL 文件，把它改坏。**

### 根因分析

那个正则的本意是"逗号后面如果不是引号区间，就当作分隔符"，
但 `(?![^']*')` 这种负向先行断言在**单行内多个引号对**时会误判，
导致本该切分的逗号没被切开（或反之）。

**更根本的问题**：用正则处理"带引号的结构化文本"本身就是错的选择。
引号是有状态的（进/出引号），**正则没有状态**，所以永远会有边界情况。

### 解决方案 / 代码模式

**改用状态机（有状态扫描）**，这是处理引号/括号/注释这类结构的唯一可靠方式：

```python
def split_quote_aware(s):
    parts, cur, inq = [], "", False
    for ch in s:
        if ch == "'":
            inq = not inq
            cur += ch
        elif ch == "," and not inq:
            parts.append(cur.strip()); cur = ""
        else:
            cur += ch
    if cur.strip():
        parts.append(cur.strip())
    return parts
```

改完后复核：**列数与值数完全匹配**（account 3/3、player_profile 10/10），
**说明 SQL 脚本本身一直是对的，是校验器错了。**

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 把校验器的输出当成事实 | 校验器是代码，代码会有 bug。**报错时要先确认"是数据错了还是校验器错了"** |
| 用正则解析有状态结构 | 引号、括号、注释都需要状态机。正则适合"无状态"的匹配 |
| 同一类错误重复犯 | 本次是**第二次**（第一次是 XML 注释那次，正则改动定界符）。**规律：涉及成对符号/定界符时，一律用状态机** |
| 只查一处就下结论 | 应同时打印原文人工核对。这次靠"打印原文 + 状态机复核"才定位清楚 |

## 十、PowerShell 脚本的编码陷阱：无 BOM 的 `.ps1` 会被按 ANSI 解码

### 背景 / 问题描述

为减少手工步骤，我把 M0 的"建目录 + 搬文件"写成 `Tools\Prepare-M0.ps1`，注释与输出都用中文。
写完做语法解析检查，**报了 11 个语法错误**：

```
行 144: Unexpected token '_Project\Configs';  l = 'Assets\_Project\Configs锛堢敓鎴愮殑' ...
行 144: The hash literal was incomplete.
行 166: Unexpected token 'AsmDefs\Game.asmdef'; ...
```

而用 `[System.Text.Encoding]::UTF8.GetString()` 读同一个文件，**替换字符数为 0、中文完全正常** ——
**文件是合法 UTF-8，是 PowerShell 读错了。**

更坑的是：我把它改成 UTF-8 **带 BOM** 后语法通过了；
但下一次用编辑工具改这个文件时，**BOM 被工具按无 BOM 写回**，脚本又坏了。
**也就是说"靠 BOM 兜住中文"这个方案在我的工作流下是不可靠的。**

### 根因分析

Microsoft 官方文档 [about_Character_Encoding](https://learn.microsoft.com/zh-cn/powershell/module/Microsoft.PowerShell.Core/About/about_character_encoding) 明确写了：

> 在 Windows PowerShell 中……**ANSI 也是 PowerShell 引擎从文件读取源代码时使用的内容。**
> 如果需要在脚本中使用非 Ascii 字符，请使用 BOM 将它们另存为 UTF-8。
> **如果没有 BOM，Windows PowerShell 会将脚本误解为使用过时的"ANSI"代码页进行编码。**

| 事实 | 值 |
| --- | --- |
| 本机 PowerShell | **5.1**（`$PSVersionTable.PSVersion` = 5.1.26100.9444，且**没有 `pwsh`**） |
| PS 5.1 读无 BOM 脚本源码的编码 | **系统 ANSI 代码页（本机 = GBK）** |
| PS 7+ 的默认 | `utf8NoBOM`（所以这个坑只在 PS 5.1 出现） |

所以：UTF-8 的中文字节被按 GBK 解码 → 字符串字面量里的引号/括号配对关系被破坏 → 解析失败。

**关键认知：文件编码的正确性，取决于"谁来读它"。**
同一个无 BOM UTF-8 文件：给 Roslyn（C# 编译器）读完全没问题，给 PowerShell 5.1 读就崩。

### 解决方案 / 代码模式

**本项目采用的方案：PowerShell 脚本正文全 ASCII（编码无关）。**

| 方案 | 可靠性 | 评价 |
| --- | --- | --- |
| **正文全 ASCII**（采用） | ✅ 任何编码、任何编辑器、任何 PS 版本都正确 | 中文说明移到 `Docs/`，脚本只留英文注释与输出 |
| 含中文 + UTF-8 **带 BOM** | ⚠️ 依赖工具每次都保留 BOM | 本次实测被编辑工具打回无 BOM，**不可靠** |
| 含中文 + 无 BOM | ❌ PS 5.1 直接解析失败 | 不可用 |

保留后续可扩展性：脚本顶部放一个 `$M` 消息表（默认 ASCII），谁想要中文输出就填表**并另存为 UTF-8 with BOM**。

验证脚本是否符合约定的命令：

```powershell
# 1) 非 ASCII 字节数应为 0
$b = [System.IO.File]::ReadAllBytes('Tools\Prepare-M0.ps1')
($b | Where-Object { $_ -gt 127 }).Count

# 2) 语法解析（0 个错误）
$errs = $null
[void][System.Management.Automation.Language.Parser]::ParseFile(
    (Resolve-Path 'Tools\Prepare-M0.ps1'), [ref]$null, [ref]$errs)
$errs.Count

# 3) 干跑验证（不应真的改任何东西）
powershell -NoProfile -ExecutionPolicy Bypass -File Tools\Prepare-M0.ps1 -WhatIf
```

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 只看"文件是不是合法 UTF-8" | **不够**。文件合法代表"能被正确解码"，不代表"消费方会用正确编码解码" |
| 以为 BOM 方案能兜住中文 | 一旦编辑工具按无 BOM 回写就失效。**要选"结构上不可能出错"的方案，而不是"配好了就对"的方案** |
| 不带参数调用脚本，还想拿退出码 | 用 `powershell -File xxx.ps1` 才能可靠拿到 `$LASTEXITCODE` |
| 给 `Join-Path` 传 `..\x` 这类相对路径 | 它**不做规范化**，会产出 `Assets\..\x` 这种难读且容易误判的路径。要么传绝对路径，要么在调用处 `Join-Path` 好 |

## 十一、NuGet 还原被 TLS 阻塞：一个被推迟的依赖问题

### 背景 / 问题描述

上一轮我锁定了依赖版本，这一轮想**实测** NuGet 对 `protobuf-net 3.2.30` 的真实依赖解析结果，
以便确定 Unity 侧到底要放哪些 DLL。在系统临时目录建了一个 `netstandard2.1` 探针工程做 `dotnet restore`（**不碰项目工程**）：

```
error NU1301: 无法加载源 https://api.nuget.org/v3/index.json 的服务索引。
error NU1301:   The SSL connection could not be established, see inner exception.
error NU1301:   Authentication failed, see inner exception.
error NU1301:   安全包中没有可用的凭证
```

换国内镜像源 `nuget.azure.cn` **同样失败**。

### 根因分析

不是"整机断网"：

| 证据 | 说明 |
| --- | --- |
| `web_fetch` 能正常访问 `nuget.azure.cn` | 网络本身可通 |
| `dotnet restore` 报 SSL + "安全包中没有可用的凭证" | **dotnet 进程的 TLS 握手失败**，像是证书信任链或代理凭据问题 |
| 全局 NuGet 缓存 `~\.nuget\packages` | 只有 9 个 SDK 运行时包，**业务依赖一个都没有** |
| 已配置的第二个源 "Microsoft Visual Studio Offline Packages" | 本地离线目录里同样没有这些包 |

**关键认知：一个"被推迟的阻塞点"。**
M0 的服务端骨架刻意不含任何 NuGet 包，所以 `dotnet build` 现在能过；
但 **M1 一打开 `PackageReference` 就会失败**。如果现在不记录，到 M1 会突然卡住并误以为是代码问题。

### 解决方案 / 代码模式

**先记录，再给用户多个可选方向**（不自己硬闯网络，也不接触凭据 —— 规则 13、7）：

| # | 方案 | 成本 | 备注 |
| --- | --- | --- | --- |
| 1 | 在系统凭据/代理里放行 dotnet | 需用户排查 | 报错含"凭证"，像证书信任问题 |
| 2 | **用 Visual Studio 的 NuGet 图形界面还原** | 低（推荐先试） | VS 用自己的证书栈，可能不受限 |
| 3 | 手动下载 `.nupkg`（本质是 zip）解压取 `lib/netstandard2.1/*.dll` | 中 | **对客户端影响小**（Unity 本来就要手工放 DLL），主要影响服务端 |
| 4 | 配置可用的私有/离线源 | 中 | — |
| 5 | 检查根证书 / 系统时间偏差 | 低 | TLS 握手里常见原因 |

**同时调整了 M0 的结论口径**，避免虚假的"通过"：

| 结论 | 说明 |
| --- | --- |
| ✅ 不阻塞 M0 收关 | M0 骨架不含 NuGet 包；Unity 侧 DLL 靠手工放置 |
| ⚠️ 必须在 M1 开工前解决 | M1 要引 Dapper / MySqlConnector / protobuf-net / xUnit / NPOI |
| 📌 已记入依赖清单 §三·补 与 M0 验收清单 | 不让它悄悄溜过去 |

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 以为"`dotnet build` 通过 = 依赖没问题" | M0 骨架**故意不含包**，所以这个"通过"不能证明还原可用。**要区分"当前能编译"和"依赖链可用"** |
| 依赖"标准做法"（`dotnet restore`） | 环境受限时标准做法直接不可用。**先探测能力边界，再选路线**，不要反复重试同一个失败命令 |
| 只给结论不给方向 | 遇到环境限制时，应给出**多个带成本评估的选项**让用户决策，而不是自己硬试或直接放弃 |

## 十二、程序集名必须从 DLL 元数据读，不能从包名推断

### 背景 / 问题描述

`link.xml` 的 `<assembly fullname="..." />` 必须写**真实程序集名**，否则 Unity **静默忽略**该条目，
只在 IL2CPP 出包后表现为崩溃（风险 R4）。而"真实程序集名"不能从 NuGet 包名可靠推断。

### 解决方案 / 代码模式

写了一个**只读**验证脚本 `Tools\Verify-PluginDlls.ps1`，用 .NET 的 `AssemblyName` API 读 DLL 元数据：

```powershell
$an = [System.Reflection.AssemblyName]::GetAssemblyName($dllPath)
$an.Name      # 真实程序集名
$an.Version   # 版本
```

它做四件事：
1. 列出目标目录下所有 DLL 的**真实程序集名**（不是文件名）
2. 校验 protobuf-net 的**依赖闭包**（3 个 DLL 是否放齐）
3. 逐条比对 `link.xml` 条目，报出**匹配不到**的（即静默失效的那些）
4. **反向检查**：对未进 `link.xml` 的 protobuf/lua 类程序集，直接打印该补的那一行

**验证脚本本身也做了功能测试**：把任意 DLL 重命名成 `protobuf-net.dll` 放进去，
脚本报出的程序集名是它**内部真实的**名字（`ILLink.CodeFixProvider`）——
这恰好证明了"它在读元数据而不是文件名"，也顺便演示了"靠文件名猜程序集名会错"。

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 从包名推断程序集名 | 会错。本次测试就构造了一个反例（文件名 `protobuf-net.dll`，程序集名 `ILLink.CodeFixProvider`） |
| `link.xml` 写错了没提示 | Unity 不报错、不警告，**条目被静默忽略**。必须有工具主动比对 |
| 用二进制 `.nupkg` 取文件清单 | `web_fetch` 对 `application/octet-stream` 直接拒绝，拿不到。**换思路：在能访问文件的地方（用户机器）读元数据**，比远程猜更可靠 |
| PowerShell 输出用 `Format-Table -AutoSize` 处理长字符串 | 列宽会溢出、与下一列挤在一起。**长字段用显式 `-f` 定宽格式** |

## 十三、分层诊断：把"SSL 失败"拆成 DNS → TCP → TLS → HTTP → 代理

### 背景 / 问题描述

上一轮发现 `dotnet restore` 报：

```
error NU1301: The SSL connection could not be established
error NU1301: Authentication failed / 安全包中没有可用的凭证
```

**"SSL 失败"这个报错本身不能定位原因**。它至少可能是六种情况之一：
DNS 解析错、防火墙拦截、TLS 被中间人/证书链问题、代理未开、代理端口没监听、进程被网络沙箱限制。
而**这六种的修法完全不同** —— 如果直接按"证书问题"去折腾，可能几小时都碰不到真正原因。

### 解决方案 / 代码模式

**按网络栈自下而上分层探测**，看"第一处失败的层"是哪一层：

```
DNS 解析  →  TCP 443  →  TLS 握手  →  HTTP  →  代理  →  目标端点
```

| 第一处失败的层 | 结论 |
| --- | --- |
| DNS | hosts 文件 / DNS 服务器问题 |
| TCP | 防火墙 / 无路由 |
| **TCP 通但 HTTP 失败** | TLS 被拦 / 证书信任 / 网络沙箱 |
| 直连失败但走代理成功 | 需要打开系统代理 |
| 代理端口无监听 | 代理客户端在跑，但代理功能是关的 |

实现要点（`Tools\Test-Network.ps1`）：

| 层 | 探测方式 |
| --- | --- |
| DNS | `[System.Net.Dns]::GetHostAddresses()` |
| TCP | `TcpClient.BeginConnect()` + `AsyncWaitHandle.WaitOne(6000)` 做超时控制（`Test-NetConnection` 较慢且依赖模块） |
| TLS/HTTP | `Invoke-WebRequest -Method Head -UseBasicParsing`，并**打印 `InnerException`** |
| 代理 | 同时看**环境变量** + **WinINET 注册表**（`ProxyEnable`/`ProxyServer`）+ **WinHTTP**（`netsh winhttp show proxy`）—— 三者可能不一致 |
| 代理是否真在跑 | `Get-NetTCPConnection -LocalPort <port> -State Listen` + 取 `OwningProcess` 反查进程名；**光看进程存在是不够的** |

**本机实测结果**（这一轮的实际产出）：

| 层 | 结果 |
| --- | --- |
| DNS | ✅ 三个目标都解析出 IP |
| TCP 443 | ✅ 可达 |
| **TLS/HTTP** | ❌ 全部失败，内层「安全包中没有可用的凭证」 |
| 代理监听 | ❌ **无任何端口在监听** |
| 代理进程 | ⚠️ `clash-verge-service`、`verge-mihomo` 在运行，但配置里 `mixed-port: 7890` 而 7890 无监听 |

**结论**：Clash Verge 的**进程在跑，但代理功能没开**；同时 AI 环境的网络沙箱本身也拦掉所有直连 HTTPS。
两者叠加，所以必须**在沙箱外的普通 PowerShell 里再跑一次**才能区分、才能确定 M1 的真实条件。

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 拿一个模糊报错去直接修 | "SSL 失败"必须先**分层定位**。先找"第一处失败的层"，再谈修法 |
| 看到代理进程在跑就以为代理可用 | **进程存在 ≠ 端口在监听**。必须查监听端口 |
| 只查环境变量就判断代理配置 | 环境变量、WinINET 注册表、WinHTTP 三处可能互相不一致，要都看 |
| **在受限环境里做连通性诊断并直接下结论** | 沙箱内**所有**直连 HTTPS 都会失败，所以诊断结果**无法区分"沙箱限制"与"真机网络问题"**。必须在**目标环境**（用户自己的 shell）里跑 |
| 把"该 URL 从本进程可达"当成"浏览器能访问" | 浏览器有自己的代理与 TLS 栈，两者独立，不能互推 |

## 十四、项目目标变更：新增规则 15「以培养用户能力为目标」

### 背景 / 问题描述

项目负责人于 2026-09-16 新增一条全局规则：

> 本项目的目的也包括教会用户相关操作和知识以及技能，提升用户开发能力，**尽量避免使用一键脚本，即使它能够提高工作效率**。

这条规则**与工程效率取向正好相反**，而且**回头否定了我此前的一项产出**：
为了让卡了 5 轮的 M0 更容易启动，我写过 `Tools\Prepare-M0.ps1`（一键建 14 目录 + 搬 9 个文件）。
从效率看它是对的，从新规则看它是错的。

### 根因分析

| 视角 | 对"一键脚本"的判断 |
| --- | --- |
| 工程效率 | ✅ 好事：减少手工、降低出错、可重复 |
| **本项目目标** | ❌ 坏事：**用户看不到中间动作，也就学不到东西** |

关键区别在于**目标函数不同**：这个项目的交付物不只是"能跑的游戏"，还包括"用户的能力增长"。
当两者冲突时，**教学目标优先**。

### 解决方案 / 代码模式

**不能只把规则当口号**（否则下次我会以"这次特殊"为由再写一个）。因此定了一条可裁决的判据：

> **这个工具是在"替用户完成流程"，还是在"帮用户观察与判断"？**
> 把多个步骤打包成一次执行、使中间动作与中间结果不再出现在用户眼前 → **一键脚本，禁止**
> 只输出信息供用户判断、不代替用户做任何修改动作 → **允许保留**

## 十五、🎓 本次新概念（复习用，1~3 条）

### 1. XML 注释不能包含 `--`

- **这是什么**：XML 规范规定注释内容里不许出现连续两个连字符，因为 `--` 参与构成注释结束标记。
- **为什么这么做**：XML 允许注释出现在标签内部等任意位置，若允许 `--`，解析器无法安全地定位注释结尾。
- **不这么做会怎样**：`.csproj` 这类**工程文件直接加载失败**（`MSB4025`），项目连编译都进不去——一个"为了好看"的分隔线能让整个工程打不开。

### 2. 编码是"读取方式"的属性，不是"文件内容"的属性

- **这是什么**：同一串字节，按 UTF-8 解读是"服务端"，按 GBK 解读是"鏈嶅姟绔"。文件没变，变的是解码器。
- **为什么这么做**：Windows 中文环境的 PowerShell 默认 ANSI 代码页是 GBK，而现代源码/配置普遍是 UTF-8 无 BOM，两者默认不匹配。
- **不这么做会怎样**：会把**正常的 UTF-8 文件误判为语法错误**（如 JSON 校验失败），然后去"修"一个本来正确的文件，把好文件改坏。

### 3. 处理"定界符包裹的内容"时，只能替换内部，不能动定界符

- **这是什么**：用正则/字符串替换批量修改 `<!-- ... -->`、`"..."`、`( ... )` 这类成对结构时，替换范围必须排除定界符本身。
- **为什么这么做**：定界符一旦被改动，结构就失去可识别性，后续任何基于定界符的匹配都会失效——**错误会从"内容错"升级为"结构坏"**。
- **不这么做会怎样**：本次就发生了：`<!--` 被压成 `<!-`，注释不再可识别，修复脚本越修越乱，最后必须改用**状态机逐字符重建**才恢复。

### 4. `.gitignore` 规则失效是静默的，必须做路径模拟

- **这是什么**：忽略规则写错时 git **不报错、不警告**，只会安静地不生效；要靠"模拟 git 的匹配逻辑 + 两组断言清单"才能查出来。
- **为什么这么做**：`.gitignore` 的匹配语义细节很多（目录规则 vs 文件规则、`**` 的行为、尾随斜杠的影响、最后匹配优先），光靠读一遍判断不可靠。
- **不这么做会怎样**：本次 4 条规则静默失效，其中 `Client/Library/` 是 Unity 的 GB 级缓存目录——一旦提交，仓库立刻被撑爆，且每次提交全是噪音 diff。

### 5. 忽略目录要用「目录名 + 斜杠」，不要用「字符类 + 斜杠」

- **这是什么**：`Client/Library/` 能忽略目录内所有文件；而"看起来更兼容大小写"的 `Client/[Ll]ibrary/` 只匹配目录本身，**目录内的文件会被漏掉**。
- **为什么这么做**：git 匹配路径时面对的是**目录内的文件路径**，它不会因为父目录命中就自动忽略子文件。
- **不这么做会怎样**：整个 `Library/`、`bin/`、`obj/` 被误提交——比"没写忽略规则"更糟，因为它给了你"我已经配好了"的错觉。

### 6. 把架构约束编译期化（`noEngineReferences`）

- **这是什么**：Unity 的 `.asmdef` 有个 `noEngineReferences` 开关，打开后该程序集**完全无法访问 UnityEngine API**。
- **为什么这么做**：帧同步要求逻辑层纯 C#（不能有 `float`），而"写在文档里"和"靠代码审查"都没有强制力；编译错误才有。
- **不这么做会怎样**：某天有人顺手写了 `using UnityEngine;`，几个月后表现为"偶发不同步"——而 `float` 的跨端差异不会崩，只会算出略微不同的结果，这类 bug 极难定位。

### 7. 依赖闭包：NuGet 管"包"，Unity 管"DLL"

- **这是什么**：一个库的"可用"不只取决于主包，还取决于它**传递依赖**的那些包。NuGet 会自动拉齐，Unity 不会。
- **为什么这么做**：Unity 没有 NuGet 集成，只能手动放 DLL；漏一个传递依赖就编译报错，而错误信息指向的是"找不到某个类型"，很难联想到是"少放了一个包"。
- **不这么做会怎样**：本次 `protobuf-net` 实际需要 **3 个 DLL**（主包 + `.Core` + `System.Collections.Immutable`）。只放主包会在接入当天卡住，且容易误判成版本不兼容。

### 8. 处理成对符号/定界符时，一律用状态机而不是正则

- **这是什么**：引号、括号、注释都是**有状态**的结构（进/出配对）；正则没有状态，所以必然有边界情况处理不了。
- **为什么这么做**：本次用 `re.split(r",(?![^']*')", ...)` 拆分 SQL 的值，把**正确的脚本报成了错误**——如果我信了它，就会去改坏一个好文件。
- **不这么做会怎样**：**同一类错误本次犯了两次**（第一次是正则改动 XML 注释的定界符 `<!--`）。而且更危险的是"校验器误报"会诱导你去修改本来正确的东西。**校验器也是代码，它也会错；报错时要先分清是数据错还是校验器错。**

### 9. 文件编码的正确性取决于"谁来读它"

- **这是什么**：同一个无 BOM 的 UTF-8 文件，C# 编译器（Roslyn）按 UTF-8 读没问题，**PowerShell 5.1 却按 ANSI(GBK) 读**，于是中文字符串字面量被破坏、脚本报语法错误。
- **为什么这么做**：编码不是文件自身的属性，而是"解码方"的约定。判断某个文件能否含非 ASCII，要看**消费它的程序用什么编码读**。
- **不这么做会怎样**：本次 `Prepare-M0.ps1` 因中文注释在 PS 5.1 下解析失败，报一堆 `Unexpected token`，而文件本身完全合法——**第一眼根本看不出是编码问题**，会误以为是语法写错了。

### 10. 选方案要选"结构上不可能出错"的，而不是"配好了就对"的

- **这是什么**：同一个目标常有多种做法，其中一些依赖"每次操作都记得做对"，另一些从结构上就排除了出错可能。
- **为什么这么做**：本次给 `.ps1` 加 UTF-8 BOM 确实能跑，但只要**编辑工具按无 BOM 回写一次就失效**——而这在我的工作流里必然发生。最终改为"脚本正文全 ASCII"，从结构上消除了这个问题。
- **不这么做会怎样**：会反复陷入"修好 → 被工具改坏 → 再修"的循环。**判据：如果一个方案需要"每次都记得做对某件事"才能成立，那它在长期使用中一定会失效。**

---

### 11. 区分"当前能编译"和"依赖链可用"

- **这是什么**：`dotnet build` 通过只能证明**当前**代码与**当前**引用集能编译；如果代码刻意还没引任何外部包，这个"通过"完全不能证明 NuGet 还原是可用的。
- **为什么这么做**：M0 骨架故意不含 `PackageReference`，所以 build 能过 —— 但 `dotnet restore` 其实是坏的。若不区分这两件事，会把一个环境问题误判为"已经没问题了"，直到 M1 突然卡住。
- **不这么做会怎样**：依赖问题被推迟到代价更高的阶段才暴露。**要主动去探测能力边界**（如用一个最小工程试还原），而不是等它自己爆。

### 12. 程序集名来自元数据，不从文件名/包名推断

- **这是什么**：`.dll` 文件**内部**记录着自己的程序集名与版本，与文件名无关。用 `[System.Reflection.AssemblyName]::GetAssemblyName()` 可以读出来。
- **为什么这么做**：配置类工具（如 Unity 的 `link.xml`）匹配的是**程序集名**，写错会被**静默忽略**、不报错，只在最终产物里表现为崩溃。
- **不这么做会怎样**：本项目就做过反例演示——把任意 DLL 改名为 `protobuf-net.dll` 放进去，它内部真实名字是别的，靠文件名猜必然出错，而这个错误会在 IL2CPP 出包后才发作。

---

### 13. 分层诊断：模糊报错先定位到"第一处失败的层"

- **这是什么**：把一条端到端链路（DNS → TCP → TLS → HTTP → 代理 → 端点）逐层单独探测，找出最先失败的那一层。
- **为什么这么做**：像"SSL 失败"这种报错可能对应七八种完全不同的原因，而修法互不相通。分层之后每条结论都是可行动的。
- **不这么做会怎样**：会按猜测去"修证书""换源""重装 SDK"，耗时且大概率修不到点上。本次靠分层才定位出「TCP 通、TLS 失败、代理无监听」这个组合。

### 14. 进程存在 ≠ 服务可用

- **这是什么**：判断某个服务是否可用，要看它**是否在监听端口/端口是否响应**，而不是看进程是否存在。
- **为什么这么做**：本次 `verge-mihomo`、`clash-verge-service` 两个进程都在运行，但**没有任何端口在监听**——代理实际是关闭的。只看进程会得出"代理在跑"的错误结论。
- **不这么做会怎样**：会把"代理没开"误判为"代理有问题"，进而去改代理配置，方向完全错。

### 15. 受限环境里的诊断结果不能代表目标环境

- **这是什么**：AI 运行在带约束的沙箱里；如果沙箱本身阻断了某类操作（如所有直连 HTTPS），那么在沙箱里做的诊断**无法区分"沙箱限制"与"真机问题"**。
- **为什么这么做**：诊断的目的地是**最终要跑代码的那个环境**。本次 M1 的还原要在用户的普通 PowerShell 里跑，所以必须在那边验证。
- **不这么做会怎样**：会把沙箱限制误报成"你的机器有网络故障"，让用户去排查一个并不存在的问题；反之也可能把一个真问题当成沙箱噪音而忽略。**正确做法：把诊断脚本交给用户在其环境里跑，并明确说明"脚本本身区分不了这两者"。**

---

### 16. 目标函数不同，同一个做法会从"对"变成"错"

- **这是什么**：评价一个做法好不好，取决于**目标函数**。同一个"一键脚本"，以"交付速度"为目标是最优解，以"培养人的能力"为目标就是负分。
- **为什么这么做**：本项目同时有两个目标（做出作品 + 提升用户能力），二者会在具体做法上冲突。**必须显式写出冲突时的优先级**，否则每次都会按"更省事"来选。
- **不这么做会怎样**：会持续用"效率"为理由做出与教学目标相反的决定，而且每次都有充分理由，问题不会暴露，只会积累。

### 17. 规则要配"可机械裁决的判据"，否则会被绕过

- **这是什么**：一条原则若只有口号（"尽量避免一键脚本"），执行时总会遇到"这次算不算例外"的模糊地带。
- **为什么这么做**：给判据（*它是在替用户做事，还是在帮用户看清事情？*）之后，每个新工具都能被一致地归类，不需要每次重新争论。
- **不这么做会怎样**：例外会越来越多，最后规则名存实亡。本次就是靠判据才能把"网络诊断脚本"与"一键准备脚本"分开处理。

### 18. 删除自动化必须伴随教学化改写

- **这是什么**：删掉一个替用户做事的工具时，要同时提供**逐步指引**（每步在干什么 / 怎么验证 / 失败先看什么），而不是简单地"把脚本删了，你自己做"。
- **为什么这么做**：否则成本只是从"机器替你做"转移成"你无从下手"，用户既没省事也没学到东西。
- **不这么做会怎样**：本次若只删 `Prepare-M0.ps1` 而不把 M0 手册 §1.3 改写成教学版，那 23 个动作就变成无说明的清单，用户仍然学不到，还可能做错。

### 第 3 轮补充：服务端骨架的架构意图（写给未来的自己）

| 文件 | 意图 |
| --- | --- |
| `NBC.Shared\SharedInfo.cs` | **不是业务代码**，作用是"证明共享层装配正确"——服务端与 Unity 客户端都应能编译到它 |
| `NBC.Server.Core\TickScheduler.cs` | 累加器切定长逻辑帧的实现骨架（DET-03 / LOCK-01），含"补帧上限"防雪崩 |
| `NBC.Server.Core\INetTransport.cs` | **单机模式成立的关键**：单机 = 换一个 `LocalTransport` 实现，不是另写一套逻辑（§13.5） |
| `NBC.Server.Game\BattleInstance.cs` | 三种同步模式共用同一个战斗实例，差异在下发策略（§6.1 策略模式） |
| `NBC.Server.Tests\SkeletonSelfCheck.cs` | 无 xUnit 的占位自检，机械证明 `NBC.Shared` 能被纯 .NET 程序集引用（§4.2 R5） |
