## 一、项目工作规则（pi 版）的跨项目继承问题

### 背景 / 问题描述

本项目（`3D联网战斗Demo`）在与项目负责人连续 5 轮需求讨论、产出一份 2400 行需求文档之后，
负责人问了一句："你现在能够读到 PI-Agent 遵守的全局规则吗？"

结果：**AI 一直在绕开负责人已有的工作方法论工作**。规则文件确实存在于本机，
但 AI 从未加载过它，导致多轮对话违反了其中若干条硬性规定。

### 根因分析

| 层 | 事实 |
| --- | --- |
| 规则文件位置 | `C:\Users\李云峰\.pi\agent\skills\project-rules\SKILL.md`（130 行，14 条规则） |
| 为什么没自动加载 | 该 skill 的 `description` 里写死了触发范围：**「RPG_Git / RPG1 Unity project」**；而本项目是 `3D联网战斗Demo`，属于**另一个项目目录**，因此 DSH/pi 的技能加载机制不会把它纳入本项目会话的技能目录 |
| 为什么 AI 没主动发现 | 技能目录只暴露"与当前项目相关"的技能摘要；跨项目的全局规则不在其中，需要**主动去文件系统里找** |
| 同目录还有什么 | `~/.pi/agent/skills/` 下另有 7 个角色 Agent 规则（anim / net / resource / ui / level / shader / integrator），以及 `E:\U3D Projects\RPG_Git\DeepSeekOutput\`（57 个知识点总结文件） |

### 解决方案 / 代码模式

**不能假设"规则会自动生效"，要显式确认规则的适用范围与实际加载情况。**

处理方式（本次采用）：

1. **先查证再回答**，不凭印象说"我读到了"或"我没有"：
   ```powershell
   # 1) 找候选位置（环境变量 + 常见规则文件名 + 用户目录）
   Get-ChildItem env: | Where-Object { $_.Name -match 'PI_|AGENT|RULE' }
   Get-ChildItem $HOME -Force | Where-Object { $_.Name -match 'pi.?agent|agent.?rule' }
   ```
   命中：`C:\Users\李云峰\.pi`、`C:\Users\李云峰\AppData\Roaming\Pi Agent Desktop`

2. **读取规则文件正文**，逐条做"适用性对照表"（适用 / 不适用 / 已改写）。

3. **发现规则与需求冲突时，不做单方面裁决**，而是列方案让负责人拍板：
   规则 12（不重复造轮子）vs 需求 11（点名用自研框架底座）—— 这两条**不可能同时满足**。

4. **写一份本项目内的裁剪版规则文件**（`Docs\00-项目工作规则.md`），
   把"适用/不适用/例外"固化下来，避免后续再次漏规则。**不改动 `~/.pi` 下的全局 skill。**

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 只凭技能目录判断"有没有规则" | 技能目录是**按项目过滤过的**，跨项目规则不会出现。必须去文件系统里找 |
| 把"能读到文件"当成"规则已生效" | 两者是两件事：文件可读 ≠ 自动化加载。要向负责人说清区别 |

| 一次性把 14 条规则当成全部适用 | 规则里有 RPG 专属内容（环境速查段），需要逐条裁剪而不是照搬 |

## 二、规则 12「不重复造轮子」与需求 11「用指定自研框架」的冲突与仲裁

### 背景 / 问题描述

- **规则 12**：禁止自行新写同类基础能力（**资源加载框架、热更、网络、对象池、寻路、加密、UI 框架**），优先用 YooAsset / HybridCLR / Mirror 等成熟方案。
- **需求 11**：点名要用唐老师那套**自研框架底座**（其中就包含对象池、UI 框架、资源加载）。
- **需求 5**：热更新"**这部分不用框架**"。

三条要求放在一起**逻辑上不可能同时满足**：执行规则 12 就要弃用指定框架 → 违背需求 11。

### 根因分析

这类冲突的本质是**两套约束体系的作用域重叠**：

| 约束 | 来源 | 作用域 |
| --- | --- | --- |
| 规则 12 | 负责人的**工作方法论**（跨项目通用） | 所有项目 |
| 需求 11 / 5 | **本项目的技术需求大纲**（面试作品的技术主张） | 本项目 |

方法论关心"效率与工程规范"，需求大纲关心"面试要展示什么能力"（自研框架本身是被考察项）。
**两者目标不同，因此在"哪些基础能力该自研"上必然打架。**

### 解决方案 / 代码模式

采用**「原则 + 书面例外清单」**（负责人确认的方案 B）：

```
默认：一律用现成方案（规则 12）
例外：仅下列 5 项自研，每项必须有书面理由，且必须登记
```

| 例外 | 自研内容 | 理由 |
| --- | --- | --- |
| E1 | 唐老师框架底座 | 需求 11 点名指定 |
| E2 | 网络传输层 + 三种同步策略 | 需求 11 排除 Mirror；需求 2 无现成方案 |
| E3 | Lua + AB 的**业务侧**热更管理 | 需求 5"不用框架" |
| E4 | 定点数学 `Fix64` | 无现成方案 |
| E5 | 确定性 A\* / 流场 | 已购插件是浮点+异步，不满足帧同步确定性 |

**支撑这套裁决的判据表**（可复用到其他项目）：

| 信号 | 结论 |
| --- | --- |
| 有活跃维护、兼容当前引擎版本的成熟方案，且**不影响"确定性/服务端权威"** | 用现成 |
| 该能力是**面试/交付物的核心技术主张** | 自研（否则没内容可讲） |
| **需求文档点名要求** | 按需求文档，但必须**写明这是有意偏离通用规则** |
| 现成方案**技术指标不达标**（如浮点不满足帧同步） | 自研（此时属"现成方案确实不满足需求"） |

**新增例外的强制流程**（防止"我想自己写"变成理由）：
评估现成方案为什么不满足 → 写入例外表 → 在需求文档 §17 记录决策 → 更新依赖清单。

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 把冲突当成"二选一" | 实际可以"原则 + 例外清单"，既守方法论又保技术主张 |
| 例外只说口头理由 | 必须**书面登记**（含对应规则点名项），否则以后无法自证合规 |
| 忽略"例外会扩散" | 必须在流程上设门槛（评估 → 登记 → 记录），否则例外会越来越多 |

## 三、YooAsset 与需求 5「用 AB 包、不用框架」的边界划分

### 背景 / 问题描述

需求 5 原文：「热更新部分使用 Lua 脚本语言、**AB 包**，**这部分不用框架**」。
而规则 12 明确点名"资源加载框架、热更"**禁止自写**，推荐 YooAsset。
两者对"AB 这一层谁来做"给出了相反的要求。

### 根因分析

需求 5 的"AB 包"和"不用框架"是两个不同粒度的要求：

| 需求要素 | 粒度 | 可由谁实现 |
| --- | --- | --- |
| "使用 AB 包" | **格式/机制** | 只要产物是 AssetBundle 即可 —— YooAsset 底层**就是** AssetBundle |
| "不用框架" | **业务编排** | 指热更的业务流程（何时检查、怎么提示、失败怎么办）不要交给游戏框架 |

关键认知：**YooAsset 不是"游戏框架"，它是"资源管线库"**。它封装的是构建/依赖/版本/下载/校验，
不包含游戏的业务编排 —— 因此它不违反"这部分不用框架"。

### 解决方案 / 代码模式

**用「职责分层」把两者切开**，而不是二选一：

```
┌────────────────────────────────────────────────────┐
│ 自研：业务侧热更管理（需求 5 "不用框架" 所指）        │
│  · 更新流程编排（检查→下载→校验→切换→启动）           │
│  · 更新 UI（进度/速度/剩余时间/可跳过）               │
│  · 强制更新 vs 可选更新（minClientVersion）           │
│  · 原子性切换与回滚（失败可回退旧版本运行）           │
│  · 更新日志、与游戏流程衔接（热更完才初始化 Lua）      │
├────────────────────────────────────────────────────┤
│ YooAsset：资源/AB 底层（规则 12 要求用现成方案）      │
│  · Bundle 构建与依赖分析、资源清单与版本号            │
│  · 下载器（并发 + 断点续传 + 失败重试）               │
│  · 内置校验（CRC/哈希）、缓存目录、StreamingAssets 内置包│
│  · 资源加载句柄、引用计数、卸载、场景加载              │
└────────────────────────────────────────────────────┘
```

配套要求：**业务层不得出现 YooAsset 类型** —— 全部经 `AssetManager` / `YooAssetAdapter` 适配层暴露
（可用 `grep YooAsset` 做机械校验，只应出现在适配层）。

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 把"第三方库"等同于"框架" | 判断标准应是：**它是否接管你的游戏架构/业务流程**。YooAsset 只管资源管线，不算游戏框架 |
| 只做分层不落成文档 | 分层必须写进需求文档（§11.2 职责分层 + §11.2.2 用词说明），否则以后会被质疑"用了框架" |
| 原子性更新容易漏 | 必须明确"全部就绪才激活新版本，失败要能回退旧版本"——这是热更系统最重要的正确性要求 |
| 打包动作交给 AI | 按规则 13，打内容包必须**负责人手动执行**，AI 只给操作步骤 |

## 🎓 本次新概念（复习用，1~3 条）

### 1. 规则生效的两个条件：可读 ≠ 已加载

- **这是什么**：一个规则文件"存在于磁盘上"和"被当前会话自动加载"是两件事。后者取决于该规则的**触发范围声明**（如 skill 的 `description` 里写的项目名）。
- **为什么这么做**：规则按项目作用域过滤是有意设计——否则 RPG 项目的打包规则会污染无关项目。
- **不这么做会怎样**：你会以为"规则在生效"，实际全程违规；反过来也会以为"没规则"，然后自己另发明一套，导致同一台机器上两套工作方式互相冲突。

### 2. 职责分层（Layered Responsibility）化解"用不用框架"之争

- **这是什么**：把一件完整功能按**粒度**切成上下两层，底层交给成熟库、上层业务编排自研，用适配层隔开。
- **为什么这么做**：需求里"用 X 但不用框架"这类看似矛盾的话，通常是指**不同粒度**；分层后两者可以同时成立。
- **不这么做会怎样**：只能在"全用"和"全自研"之间二选一，要么违背需求，要么白写一遍别人已经写好的基础能力（本项目的 AB 构建/下载/校验约值 1 周工时）。

### 3. 例外清单（Exception Register）是让原则可持续的机制

- **这是什么**：默认遵守原则，但把"经批准的偏离"逐条登记（含理由、对应规则条款、决策记录）。
- **为什么这么做**：任何绝对化的工程原则在真实项目里都会遇到反例；全部禁止会僵化，随便开口子会失控。
- **不这么做会怎样**：例外只存在于口头和记忆里 → 换人/过几个月后无人能解释"为什么这里自己写了"，合规性无法自证；且例外会无声扩散。
