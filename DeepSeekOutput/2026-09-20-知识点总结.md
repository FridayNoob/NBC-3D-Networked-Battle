## 一、ECall：托管代码与 Unity 原生引擎的那条边界（本次核心）

### 背景 / 问题描述

架构裁决 A1/A2/A3（AI 分两套实现、帧同步不由服务端跑 AI、寻路分两套）全部建立在
一个前提上：**Behavior Designer 和 Unity NavMesh 无法在本项目的纯 .NET 服务端进程里工作**。

但这个前提原来只是"文档推断"。M0 的 D14 就是把它变成实测。原计划是"在服务端工程里引用
Behavior Designer 的 dll，看编译报什么错"。**实际执行时改成了更根本的做法**：
不引用插件，**直接引用 Unity 自己的程序集**。

### 根因分析：分界线其实有三层，不是"能/不能"

用一个 9 级探针（`Server\_unity-ref-probe\`，.NET 8.0.21）测出来的结果：

| 分层 | 能否在纯 .NET 进程里工作 | 实测证据 |
| --- | --- | --- |
| **纯托管数学**（`Vector3` / `Quaternion` / `Mathf`） | ✅ **能，结果完全正确** | `magnitude=5`、`Normalize=(0.6,0.8,0)`、`Mathf.Sqrt(16)=4` |
| **类型元数据**（反射拿 `Type`、读基类链） | ✅ **能** | `MonoBehaviour` 的基类链 `Behaviour → Component` 可读出 |
| **引擎对象 / 原生调用** | ❌ **不能** | `new GameObject()`、`go.name`、`Time.deltaTime` 全部抛异常 |

失败异常原文：

```text
System.Security.SecurityException: ECall methods must be packaged into a system module.
```

**为什么会这样（白话版）**：

Unity 的托管程序集（`UnityEngine.CoreModule.dll` 等）里，凡是要落到 C++ 引擎里的方法，
都标了 `[MethodImpl(MethodImplOptions.InternalCall)]` —— 简称 **ECall**，
意思是"**这个方法不在这里实现，由运行时内部提供**"。

- 在 **Unity 自己的运行时**里：这些 ECall 被转到原生引擎，正常工作。
- 在**独立 .NET 进程**（`dotnet run`）里：CLR 里**没有**这些内部实现 → 调用时抛 `SecurityException`。

> **一句话**：`Vector3` 的加法是**纯 C# 写的**，所以在哪儿都能算；
> `new GameObject()` 要**问 C++ 引擎要一块对象内存**，而 CLR 里没有引擎，所以炸。

### 解决方案 / 代码模式

**① 关键认知：这是运行时错误，不是编译错误。**

```powershell
# 引用 UnityEngine.CoreModule 后 dotnet build —— 0 错误，能编译通过！
# 问题只在真正调用引擎的那一刻才炸。
```

所以 —— **"编译成功"不能用来证明"服务端能跑行为树"**。
反过来说，如果只做"引用 dll 看编译报错"的实验，会得到一个**假结论**（"能编译通过，那就没问题？"）。

**② 9 级探针必须用反射调用，不能顺序调用。**

```csharp
// ❌ 顺序调用：一次异常会中断后面所有级别，
//    分不清"是这一级失败"还是"因为上一级失败而没能跑到"
try { L3(); } catch { } try { L4(); } catch { }   // 脆弱

// ✅ 反射调用：每一级被隔离，异常包在 TargetInvocationException 里
var mi = typeof(Program).GetMethod(name, BindingFlags.Static | BindingFlags.NonPublic);
try { var r = mi.Invoke(null, null); } 
catch (TargetInvocationException tie) { /* 精确定位到这一级 */ }
```

**③ `<Private>true</Private>` 不能省 —— 否则实验失去意义。**

```xml
<Reference Include="UnityEngine.CoreModule">
  <HintPath>C:\...\UnityEngine\UnityEngine.CoreModule.dll</HintPath>
  <Private>true</Private>   <!-- 必须：把 dll 复制到输出目录 -->
</Reference>
```

只写 `<Reference>` 时会得到 `FileNotFoundException: 找不到 UnityEngine.CoreModule` ——
那只能证明"**我没把 dll 放过去**"，证明不了任何关于 Unity 的事实。
**要让实验有意义，必须先让运行时真的能加载到它。**

**④ 想量"引用一个模块会拖进几个模块"，要读元数据而不是猜。**

用 `System.Reflection.Metadata` 读 `AssemblyRef` 表并求传递闭包（Unity 安装目录下共 87 个模块 dll）：

| 起点 | Unity 侧传递闭包 | 数量 |
| --- | --- | --- |
| `UnityEngine.CoreModule` | CoreModule、SharedInternalsModule | **2** |
| `UnityEngine.IMGUIModule` | + InputLegacy、TextRendering、TextCoreTextEngine、TextCoreFontEngine | **7** |
| `UnityEngine.AIModule` | AIModule、SharedInternalsModule、CoreModule | **3** |

**工程含义**：服务端引用任何一个 Unity 模块，都要把整个闭包补全，否则得到 `CS0012`。
**这不是"多加一行 HintPath"的小事，而是"要拖进多少引擎代码"的成本** ——
这就是本项目坚持 `NBC.Shared` 用 `netstandard2.1`、`NBC.Model` 设 `noEngineReferences: true` 的原因。

**⑤ 同一套元数据扫描还能回答"某类型在哪个模块"（排查 `CS0012`/`CS0234` 最快的办法）。**

实测速查（**全部来自元数据，不是记忆**）：

| 类型 | 所在模块 |
| --- | --- |
| `Object` / `GameObject` / `Component` / `MonoBehaviour` / `ScriptableObject` / `Transform` | `UnityEngine.CoreModule` |
| `Vector3` / `Quaternion` / `Mathf` / `Time` / **`Debug`** / `Application` / `Resources` / `Camera` / `Material` | `UnityEngine.CoreModule` |
| `GUI` / `GUILayout` / `GUIStyle` / `Event` | `UnityEngine.IMGUIModule` |
| `Input` / `Touch` | `UnityEngine.InputLegacyModule` |
| **`NavMesh` / `NavMeshAgent`（命名空间是 `UnityEngine.AI`！）** | **`UnityEngine.AIModule`** |
| `Animator` / `Animation` | `UnityEngine.AnimationModule` |
| `Rigidbody` / `Collider` / `Physics` | `UnityEngine.PhysicsModule` |

### 踩坑记录

| 坑 | 真相 |
| --- | --- |
| 以为"编译通过 = 能运行" | **这是本次最大的认知修正**。发布 IL2CPP 包和引用程序集都是"编译期正常"，问题在运行时 |
| 以为 `UnityEngine.Debug` 在 `IMGUIModule` | **错，它在 `CoreModule`**。`IMGUIModule` 里是 `GUI` / `GUILayout` / `Event` |
| 以为 `NavMesh` 的命名空间是 `UnityEngine` | **错，是 `UnityEngine.AI`**，在 `AIModule` 里 |
| 想用 PowerShell 的 `Assembly.LoadFrom(...).GetExportedTypes()` 扫类型 | **不行**：pwsh 的加载上下文解析不了 `netstandard 2.1`，抛 `FileNotFoundException`。**要读元数据就用 `System.Reflection.Metadata`** |
| 原计划"引用插件 dll 看报错"就够了 | 那样测的是"**这个插件**行不行"，结论会被插件版本影响。**向下挖一层测 Unity 程序集本身，结论更硬、换插件也不失效** |

## 二、`.gitignore` 的语义陷阱，以及"验证方式本身出错"的两次翻车

### 背景 / 问题描述

D16 要 `git init` + 首次提交。提交前必须确认 `.gitignore` 真的有效，
否则 `Library/`（几 GB）会被提交进去。

于是开始验证 —— 结果**验证过程本身连续翻车两次**，这比 `.gitignore` 的知识更值得记。

### 根因分析 + 解决方案

**陷阱 1：`.gitignore` 不支持"行尾注释"——`#` 只在行首才是注释。**

```gitignore
# ❌ 错的：整行（含注释文字）被当成一个"永远匹配不到"的取反模式，等于白写
!**/Packages/          # 注意：Unity 的 Packages 目录要保留

# ✅ 对的：注释独占一行
# 注意：Unity 的 Packages 目录要保留
!**/Packages/
```

本次在 `Server\.gitignore` 里真的发现了这样一行 —— 它**静默失效**，不报错、不警告。

**陷阱 2：Windows 上 `core.ignoreCase = true`，所以 `**/packages/` 会连 Unity 的 `Packages/` 一起忽略。**

实测：

```text
core.ignoreCase = true
Packages/manifest.json  <=  .gitignore:4:**/packages/     ← 大写 Packages 也被匹配了
```

**正解不是去取反**，而是**把作用域限死**：本项目的 Unity 工程在 `Client/`，
`Server/` 下不存在 `Packages/` —— 所以在 `Server\.gitignore` 里写 `**/packages/` 就足够了，不需要 `!` 取反。

**陷阱 3（本次推翻了两个"我自己写下的错误结论"）：**

我之前在根 `.gitignore` 里写过两条"写法警告"，本次用真实 git 实测**全部推翻**：

| 我原来写的 | 实测真相 |
| --- | --- |
| "`Client/[Ll]ibrary/` 这种字符类+尾部斜杠**会漏掉目录内的文件**" | ❌ **错**。`[Ll]ibrary/` 正确忽略了 `Library/ScriptAssemblies/Assembly-CSharp.dll` |
| "`**/bin/` 反而**可能匹配不到**" | ❌ **错**。`**/bin/` 正确忽略了 `Server/NBC.Host/bin/Debug/host.exe` |

**为什么错**：git 对"**已被忽略的目录**"**根本不会向下遍历**，所以目录内文件自动一并忽略 ——
不存在"只匹配目录本身、漏掉内部文件"这回事。

**真正的教训（比这两个结论本身更值钱）**：

> **这两个错误结论来自一个我自己写的"路径模拟校验脚本"。**
> 我拿一个自己写的模拟器，去否定了真实工具的语义，还把它当成事实写进了配置文件注释。
> **校验器本身也要先被校验** —— 能用真实工具（`git check-ignore -v`）验证时，永远不要相信自己的模拟器。

### 踩坑记录（**这一天连续踩了两次"验证本身出错"**）

| 坑 | 说明 |
| --- | --- |
| ① 用"路径模拟脚本"代替真实工具 | 见上。写模拟器很容易漏掉真实工具的语义（"被忽略目录不遍历"、"ignoreCase"） |
| ② 改用 `git check-ignore -v` 后**又被它误导** | `git check-ignore -v` 会把**被取反规则（`!xxx`）命中**的路径**也打印出来，且退出码为 0**。我据此把 `.gitignore` 末尾的取反保命规则 `!Server/**/*.csproj`、`!*.asmdef` 误判成"这些文件被忽略了" |
| ✅ **正确判据：地面真值** | 要验证的是"**这些文件最终会不会进仓库**"，所以判据应该是：`git add --dry-run .` 或 `git status --porcelain -uall` —— **该保留的必须出现，该忽略的必须不出现**。换成它之后，22 项应保留 + 17 项应忽略**全部符合预期** |
| 项目还没有 `.git` 仓库时跑 `git check-ignore` | 确实会失败。**但"命令失败"不等于"文件被正确忽略"** —— 当时我误读了退出码，得出了错误结论。正解：在临时目录里 `git init` 一个最小仓库来验证规则语义 |

> **这一天的最大收获**：不是"我修好了 `.gitignore`"，而是发现**我连着两次相信了错误的验证方式**。
> 第一次是"自己写的模拟器"，第二次是"一个真实但不适合这个问题的工具"。
> **判据选错，比不验证更危险** —— 不验证只是不知道，判据选错会得到"确信的错误答案"。

## 三、XML 里 `--` 是非法字符（同一个坑踩了两次）

### 背景 / 问题描述

给 `probe.csproj` 写注释时，顺手写了复现命令 `dotnet run --project ...`。
构建直接失败：

```text
error MSB4025: 未能加载项目文件。名称不能以"e"字符(十六进制值 0x65)开头。...
```

### 根因分析

**XML 注释 `<!-- ... -->` 内部不允许出现 `--`。** 这是 XML 规范的硬性规定（`--` 是注释结束符的一部分）。
`dotnet run --project` 里正好有 `--`。

本项目**之前已经因为同样原因踩过一次**（`.csproj` 里用 `------` 做分隔线导致 `MSB4025`），
当时的对策是在 `.csproj` 里改用 `=====` 做分隔线。所以：

### 解决方案 / 代码模式

| 场景 | 规则 |
| --- | --- |
| `.csproj` / `.props` / `.targets` 的 XML 注释 | **禁止出现 `--`**。分隔线用 `=`；命令行用 `-p` 之类的单横线写法，或干脆写成"把工作目录切到某处再执行 `dotnet run`" |
| 想写 `<!-- ---- 分节 ---- -->` | ❌ 会 `MSB4025`。写成 `<!-- ==== 分节 ==== -->` |

> **记忆点**：**改了 `.csproj` 之后一定要真跑一次 `dotnet build`** —— 这个错误在编辑器和 Markdown 预览里看不出来。

## 三之二、"0 个错误"不等于成功：MSBuild 多节点在沙箱下的静默失败

### 背景 / 问题描述

收尾复核时跑 `dotnet build NBC.sln`，输出是：

```text
生成失败。
    0 个警告
    0 个错误
```

**退出码 1，但一条错误信息都没有。** 而 D13 记录里这个命令是**成功过**的。

### 根因分析（三步定位）

| 步 | 动作 | 结果 |
| --- | --- | --- |
| 1 | 提高详细度重跑（`-v n` / `-v diag`） | 失败点是 `_GetAllRestoreProjectPathItems`，**子 MSBuild 节点返回失败但不记录任何错误** |
| 2 | 找出触发条件 | `-m`（默认并行）失败；**`-m:1`（单节点）成功**。逐工程试：只有含 **≥2 个 `ProjectReference`** 的工程（Game / Host / Tests）会失败 |
| 3 | **最小对照实验** | 在 `%TEMP%` 新建 A/B/C 三个工程（C 引用 A + B，共 20 行代码）：`-m:1` ✅ 成功、`-m:2` / `-m` ❌ 同样静默失败 |

**结论**：这是**运行环境**的限制，**与本项目完全无关** ——
MSBuild 在 `-m` 下会启动**进程外工作节点**，节点间靠**命名管道**通信；
DSH 的受限沙箱不允许打开命名管道，子节点起不来，于是任务返回失败却不记录错误。

### 解决方案 / 代码模式

```powershell
dotnet build NBC.sln -m:1     # ✅ AI 在沙箱里代跑构建时用这条
dotnet build NBC.sln          # ✅ 用户在自己终端里用这条（正常环境不受限）
```

**可复用的排查手法（比这次的结论更值钱）**：

| 手法 | 说明 |
| --- | --- |
| **看退出码，不只看输出** | `0 个错误` 完全可能是失败。**只有退出码为 0 才算成功** |
| **换 `-m:1` 试一次** | 并行构建失败时的第一反应 |
| **写最小对照工程** | 把嫌疑从"我的项目"摘出去的最快办法。**20 行代码就能决定是该改项目还是改环境** |
| 提高详细度（`-v n` → `-v diag`）定位到**哪个 target/task** 失败 | 这次因此定位到 `_GetAllRestoreProjectPathItems` 与"子节点失败" |

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 看到"生成失败 + 0 个错误"先怀疑自己的工程 | 这会让人去删 `obj`、改 `csproj`，**全是无用功**。先做最小对照实验 |
| 拿"之前成功过"当"现在也该成功" | D13 成功是在**不同环境**（用户自己的终端）下得到的。**环境变了，结论就要重新验证** |
| 用 `-v q`（静默）排查失败 | 静默模式连失败原因都不打印。排查时应先提高详细度，**定位之后再回到静默模式做日常构建** |

## 四、方法论：把"文档断言"升级为"实测证据"的标准动作

### 背景 / 问题描述

需求文档 §5.4.5 里原本写着"Behavior Designer **引用不了**"。
实测后发现这句话**过头了**（能引用、能编译），准确的说法是"**能引用、纯托管能跑，一碰引擎对象就抛 `ECall`**"。

### 解决方案 / 代码模式（可复用的四步）

| 步 | 动作 | 本次做法 |
| --- | --- | --- |
| 1 | **先问"这个断言的最底层机制是什么"**，再设计实验 | 不问"这个插件行不行"，而问"**Unity 程序集在 .NET 里行不行**" |
| 2 | **把被测对象分层**，而不是给一个"能/不能" | 分三层：纯托管数学 / 类型元数据 / 引擎对象与原生调用 |
| 3 | **让每一层独立失败**（反射隔离） | 9 级探针，异常逐个定位 |
| 4 | **写下"这个实验没有证明什么"** | 没直接引用插件 dll；没测 IL2CPP/AOT 侧（那是 D17） |

**结论收窄不是退步，而是变强**：
原来是"我说编译不过"（一个可能被反驳的断言）；
现在是"**我实测过：编译能过、托管部分能跑，但一碰引擎对象就炸**"（解释了**为什么**，而不只是断言）。

> **面试迁移**：任何"我用了 X 技术"的说法，都值得追问一句"**你怎么知道它一定/一定不能？**"
> 能拿出一段自己写的探针 + 逐字输出，说服力和"我看文档说"完全不是一个量级。

## 五、`mysql.exe` 打不开中文路径：把 `errno` 号当线索用

### 背景 / 问题描述

执行 D12（建库建表）时，在 `mysql>` 交互里敲：

```text
mysql> source E:/U3D Projects/0_MyFile/3D联网战斗Demo/Docs/08-数据库脚本.sql
ERROR: Failed to open file 'E:\U3D Projects\0_MyFile\3D联网战斗Demo\Docs\08-数据库脚本.sql', error: 42
```

**文件明明存在，路径也没写错。**

### 根因分析（先排除，再定位）

| 步 | 动作 | 结果 |
| --- | --- | --- |
| 1 | 排除"文件本身有问题" | 大小 9553 字节、**无 BOM**、**合法 UTF-8**、LF；自带 `CREATE DATABASE` / `USE` → **脚本完全正常** |
| 2 | 读懂 `error: 42` | Windows CRT（ucrt）里 **42 = `EILSEQ`（非法字节序列）**，指向**字符编码转换失败**，**不是"文件不存在"** |
| 3 | **最小对照实验** | `cmd /c 'more < "<同一个中文路径>"'` → **退出码 0，读出全部 188 行** ✅。即：**cmd 能打开这个路径，只有 `mysql.exe` 自己打不开** |
| 4 | 试 8.3 短路径 | `for %I in ("<长路径>") do @echo %~sI` 返回的还是**中文长名** → E: 盘**没启用 8.3 别名**，此路不通 |

**结论**：`mysql.exe` 的 `source` 会把文件名从**客户端字符集**转换到**操作系统字符集**，
路径里含中文（`3D联网战斗Demo`）时转换失败 → `fopen` 返回 NULL → `EILSEQ`。
**这是 MySQL 客户端在 Windows 上的已知限制，与脚本内容、与路径写法都无关。**

> **这里最值钱的技能：`errno` 号本身就是线索。**
>
> | errno | 符号 | 含义 | 排查方向 |
> | --- | --- | --- | --- |
> | 2 | `ENOENT` | 文件不存在 | 核对盘符/路径/工作目录 |
> | 13 | `EACCES` | 权限不足 | 文件只读？被占用？ |
> | **42** | **`EILSEQ`** | **非法字节序列** | **编码问题**（路径/内容里的非 ASCII 字符） |
>
> 同样是"打不开文件"，**2 和 42 的排查方向完全相反**。
> 只看"Failed to open file"就去改路径，会白折腾很久。

### 解决方案 / 代码模式

**✅ 方式 A（推荐）：改用 cmd 的输入重定向，绕过 mysql 自己的 `fopen`**

```bat
cd /d "E:\U3D Projects\0_MyFile\3D联网战斗Demo"
mysql -u root -p --default-character-set=utf8mb4 < "Docs\08-数据库脚本.sql"
```

- **必须在 `cmd` 里执行**：cmd.exe 是 Unicode 感知的，重定向时由 **cmd 打开文件**并把句柄交给 mysql，
  完全绕开了出问题的那段代码。
- 数据正确性：mysql 从 stdin **读原始字节**，按 `--default-character-set=utf8mb4` 解释 → 中文不会乱码。
- **优点**：永远跑的是 `Docs` 下那份**唯一源文件**，不存在副本脱节。

**方式 B（还想用 `source`）：把脚本复制到纯 ASCII 路径**

```bat
mkdir C:\nbc
copy "E:\...\Docs\08-数据库脚本.sql" C:\nbc\nbc_db.sql
```
```text
mysql> source C:/nbc/nbc_db.sql
```
- 目录名**和**文件名都要 ASCII（任一段含中文都可能触发同一个错）。
- **缺点**：副本会与原文件**脱节** —— 改了 `Docs` 下的原文件却忘了重新复制，就会跑到旧数据上。

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 把 `error: 42` 当成"路径写错" | 于是反复改路径、改斜杠、加/去引号 —— **全是无用功**。42 是编码问题，不是路径问题 |
| 在 **PowerShell** 里用 `<` 重定向 | PowerShell 5.1 **不支持** `<`（报"`<` 运算符保留给未来使用"）。要重定向就开 `cmd` |
| 想用 8.3 短路径绕开 | 实测 E: 盘没开 8.3 别名，`%~sI` 返回的还是长名 → 不可用（**先验证，别假设**） |
| 忘了 `.sql` 文件不能有 BOM | 有 BOM 时 mysql 第一条语句会报 **1064**。本项目脚本是 UTF-8 **无 BOM**，改动时别加上 |
| 以为"cmd 能打开"就代表"mysql 也能" | 两者用的是**不同的文件打开路径**：cmd 用 Unicode API，mysql 用自己的字符集转换。**这正是最小对照实验的价值** |

## 七、xLua 的 `DllNotFoundException: xlua`：文档写错一步，坑就真的踩到了

### 背景 / 问题描述

按 M0 手册 **D6** 手动导入 xLua 后，Unity Console 刷出一片红色：

```text
DllNotFoundException: xlua assembly:<unknown assembly> type:<unknown type> member:(null)
XLua.LuaEnv..ctor () (at Assets/ThirdParty/XLua/Src/LuaEnv.cs:66)
XLuaTest.NoGc..ctor () (at Assets/ThirdParty/XLua/Examples/05_NoGc/NoGc.cs:73)
XLuaTest.LuaBehaviour..cctor () (at .../02_U3DScripting/LuaBehaviour.cs:30)
```

### 根因分析：三步，且第三步才是真凶

| 步 | 动作 | 结果 |
| --- | --- | --- |
| 1 | 读报错位置 | `LuaEnv.cs:66` 在调 `LuaAPI.xlua_get_lib_version()`；`LuaDLL.cs:39` 写着 `const string LUADLL = "xlua"` → **是 C 原生库找不到**，与 C# 编译无关 |
| 2 | 磁盘核对 | `Assets\ThirdParty\XLua\` 有 378 个文件（Src / Examples / Tutorial / Editor / Resources / Doc 全在）→ **看着很齐全**；但**整个工程搜不到任何 `xlua.dll`** |
| 3 | 找原料出处 | 用户下载的 `xLua-master\` 里：**`Assets\Plugins\`（含 `x86_64\xlua.dll`）与 `Assets\XLua\` 是【平级】的**。而**手册 D6 原文写的是"`Client\Assets\ThirdParty\XLua\` 下应有 `Src`、`Plugins`、`Examples` 等"** —— 把 `Plugins` 说成在 `XLua` **里面** |

**真凶是文档，不是操作。** 我（AI）在写 D6 时**没有实测过 xLua 的目录结构**，
凭"插件一般自带 Plugins 子目录"的印象写了一句，用户照着做就必然漏掉原生库。

> **教训**：**文档里的"目录结构"只要没实测过，就是写给用户的一个坑。**
> 凡是"某文件在哪"这类断言，都应该用 `Get-ChildItem` / `tar` 之类**问出答案**，而不是从记忆里取。

### 解决方案 / 代码模式

**① 复制原生库（含一个容易漏的细节）**

```powershell
$src = 'E:\U3D Projects\0_MyFile\xLua-master\Assets\Plugins'
$dst = 'E:\U3D Projects\0_MyFile\3D联网战斗Demo\Client\Assets\Plugins'
Copy-Item "$src\x86_64"      $dst -Recurse -Force   # 目录本体
Copy-Item "$src\x86_64.meta" $dst -Force            # ⚠️ 目录自己的 .meta 是【兄弟文件】，必须单独复制
```

- **`.meta` 必须一起搬**：Unity 靠它里面的**平台设置**决定这个原生库给哪个平台用；
  只搬目录不搬 `.meta`，Unity 会新生成一个默认设置的 `.meta`，可能把库判到错误平台。
- **只取 `x86_64`**：本项目只做 PC（需求 §12），`x86`/`Android`/`iOS`/`WebGL`/`WSA`/`arm64`/`xlua.bundle` 共用不上（约 6 MB）。

**② 版本握手：C# 与原生库必须是同一棵源码树**

```csharp
// XLua/Src/LuaEnv.cs:62
const int LIB_VERSION_EXPECT = 105;
// 不匹配 → throw new InvalidProgramException("wrong lib version expect:105 but got:...")
```

所以从别的项目（本机还有 `LearnXLua\`、`LearnLuaBag\`）拿 `xlua.dll` 会**换一种错**：
从 `DllNotFoundException` 变成 `InvalidProgramException`。
**"看起来同名就拿来用"是错的** —— 二进制和源码之间有版本契约。

### 顺着排查挖出来的第二个坑（更隐蔽）：`link.xml` 静默失效

跑 `Tools\Verify-PluginDlls.ps1` 时发现 `link.xml` 里两条 xLua 条目：

```xml
<assembly fullname="XLua" preserve="all" />
<assembly fullname="XLua.Example" preserve="all" />
```

**它们永远匹配不到任何程序集。** 因为 **xLua 整棵源码树里没有任何 `.asmdef`** ——
它的 C# 全部编译进 Unity 自动生成的 **`Assembly-CSharp`**。

用元数据扫描取证（`System.Reflection.Metadata` 读 `Library\ScriptAssemblies`）：

| 程序集 | 类型总数 | `XLua*` 类型数 |
| --- | --- | --- |
| `Assembly-CSharp.dll` | 742 | **109**（含 `XLua.LuaEnv` / `DelegateBridge` / `ObjectTranslator`） |
| `Assembly-CSharp-Editor.dll` | 70 | 5 |

**Unity 对不匹配的 link.xml 条目不报错、不警告** —— 保护**静默失效**，
只会在 IL2CPP 包里表现为崩溃或数据异常。这正是本项目 `link.xml` 注释里早就警告过的那类 bug，
结果自己踩了。

**修法**：改成 `<assembly fullname="Assembly-CSharp" preserve="all" />`。
**为什么这样是安全的**：本项目业务代码**都带 asmdef**（`NBC.Framework`/`NBC.Game`/`NBC.Model`/`NBC.Editor`），
所以 `Assembly-CSharp` 里**只有 xLua 自己的代码 + Examples + Tutorial**，不会把业务代码一起冻住。

### 第三个坑：**校验工具自己的扫描范围有盲区**

原来的 `Verify-PluginDlls.ps1` 只扫 `Client\Assets` 下的 DLL，
所以它**认不出 `Assembly-CSharp`**（那是 Unity 编译产物，在 `Library\ScriptAssemblies`）——
修好 link.xml 后它反而会误报"NO matching DLL"。
已给脚本加了一段"**Unity 编译产物索引**"（仅用于校验 link.xml 名称，不混进插件 DLL 清单）。

> **这已经是今天第二次"验证工具本身需要被修正"**（第一次是 `.gitignore` 那两次翻车）。
> 规律很清楚：**凡是"校验器"，都要先问一句"它的输入范围够不够覆盖我要校验的东西"**。

### 踩坑记录（含第二轮：DLL 到位了却还是 `DllNotFoundException`）

把 `xlua.dll` 复制到位后**依然**报 `DllNotFoundException`，只是调用点变成了
`CSObjectWrapEditor.Generator..cctor`（静态构造函数）。**这次不能靠猜，要靠证据把它钉死。**

| 步 | 验证动作 | 结论 |
| --- | --- | --- |
| 1 | 文件在不在、字节对不对 | ✅ `Assets\Plugins\x86_64\xlua.dll` 存在，与源文件 **SHA256 完全一致** |
| 2 | `.meta` 的平台设置对不对 | ✅ 复制过来的 meta 里 `Editor: enabled 1, CPU x86_64, OS Windows`、`Win64: enabled 1` |
| 3 | **PE 头**：位数与依赖（读 `PEReader`） | ✅ `Machine=Amd64`（x64 位对）；依赖字符串只有 `KERNEL32`/`WS2_32` → **静态链接 CRT，不缺运行时** |
| 4 | **自己 `LoadLibraryW` 直接加载**（决定性实验） | ✅ `handle` 非 0、`GetLastError=0`、导出表里有 `xlua_get_lib_version` → **DLL 本身、位数、含中文的路径全都没问题** |
| 5 | 读 `Editor.log` 的会话边界 | 🔑 `Initialize engine version` **只出现 1 次** → **整个日志是一个会话**，用户是在 **Unity 开着的时候**复制 DLL 的，**从未重启** |
| 6 | 读 `libxlua.so.meta` | 🔑 `Editor: enabled 1, OS: AnyOS` → 解释了日志里的 `found 2 plugins`（Unity **确实登记了**插件） |

**两个叠加的根因**：

1. **原生插件是在会话启动时登记搜索路径的**。开着 Unity 才把 DLL 放进去 → Mono 的原生库搜索路径没更新 →
   `[DllImport("xlua")]` 解析不到（虽然 Unity 的插件列表里已经"看得见"它）。
2. **C# 静态构造函数一旦抛异常，该类型在【当前域】内永久损坏**。之后任何调用都重抛
   `TypeInitializationException`，**静态构造不会再执行** → `Assets → Refresh`、重新导入**全都无效**，
   **只有域重载 / 重启 Unity 才能恢复**。

**修法**：关掉 Unity → 重新打开工程 → 再跑 `XLua → Generate Code`。

> **可复用的排查范式**（本次真正值钱的部分）：
> 当"某组件说找不到某文件"时，**不要只在组件内部打转** ——
> 用**最底层的方式**（这里是 `LoadLibraryW` + `GetProcAddress`）直接验证那个文件能不能用。
> 能加载 ⇒ 排除文件/位数/路径/依赖，问题在调用方；
> 不能加载 ⇒ 拿到 Win32 错误码，直接定位。
> 这和本次的 MSBuild 最小对照实验、`mysql` 的 `errno` 判读是**同一招**：
> **把"嫌疑对象"和"运行环境"分开验证。**

### 收尾实测：重启后一次通过，并确认了两个布局事实

**重启 Unity 后 `XLua → Generate Code` 直接成功** ✅ —— 反证了上面的判断（插件登记时机 + 静态构造毒化）。

顺手确认了两个"以后会疑惑"的布局事实（都是**实测**，不是推断）：

| 事实 | 实测结果 |
| --- | --- |
| 生成产物落在哪 | **`Assets\XLua\Gen\`（108 个文件）** —— 是 xLua 的**默认路径**（`GeneratorConfig.common_path`），**不在** `ThirdParty\XLua\` 下面。别以为是放错了 |
| 项目里有几份 `link.xml` | **3 份**，Unity 会**全部合并**：① `Assets/link.xml`（我们手写）② `Assets/XLua/Gen/link.xml`（xLua 生成，精到 `<type>`）③ `Packages/com.arongranberg.astar/link.xml`（A\* 自带）。**②每次 Generate Code 都会被覆盖，不要手改** |

生成的那份 `link.xml` 实测声明了 5 个程序集：`mscorlib`、`UnityEngine.CoreModule`、
`UnityEngine.AnimationModule`、`UnityEngine.ParticleSystemModule`、**`Assembly-CSharp`** ——
确认了正文里那个判断（xLua 的代码确实在 `Assembly-CSharp` 里）。

> 这也给出了 M5 的收窄路径：等我们信任 xLua 生成的那份之后，就可以把
> `Assets/link.xml` 里那条粗粒度的 `Assembly-CSharp preserve="all"` 删掉。

### 其余踩坑记录

| 坑 | 说明 |
| --- | --- |
| **文档写错目录结构** | 写出"`Plugins` 在 `XLua` 里面"这种没实测的断言 → 用户必然漏文件。**根因在文档，不在操作** |
| 用"文件数量看着齐全"当"导入完成" | `XLua\` 有 378 个文件，看着很全 —— 但**原生库根本不在这个目录里**，数量核对发现不了 |

| 在"找不到文件"上只怀疑路径 | 本次路径完全没问题（**含中文的路径 `LoadLibraryW` 都加载成功**）—— 必须做最小对照才能排除 |

> **一句话记忆点**：**报错说"找不到文件"时，先确认"这个文件应该在哪个目录"—— 而这个答案必须来自实测，不能来自文档或记忆。**
> **补一句**：如果文件确实在、也确实是好的，那么问题就在**调用方**（Unity 的加载时机 / 被毒死的静态构造），**这时候刷新是没用的，要重启。**

## 八、D17 第一次出包：`protobuf-net` 在 IL2CPP 下挂了 —— 而根因**不是**我们以为的那个

### 背景 / 问题描述

M0 的最后一关 **D17（IL2CPP 出包 + AOT 探针）** 第一次跑：

| 项 | 结果 |
| --- | --- |
| 出包 / 启动 | ✅ 成功（IL2CPP，Release，WindowsPlayer x86_64） |
| **xLua** | ✅ **通过** —— Lua 求和 1..10 = **55** |
| **protobuf-net** | ❌ **失败** |

### 根因分析：**先纠正一个错误假设，这比修 bug 更重要**

我们文档里（需求文档 **R4**、`link.xml` 的注释、D17 排查表）一直假设：
> IL2CPP 会把反射要用的元数据**裁剪**掉 → 所以要用 `link.xml` **保留**程序集。

**实测把这个假设推翻了。** 真实报错是：

```text
NotSupportedException: ...RuntimeParameterInfo.cpp(23) :
  Unsupported internal call for IL2CPP:RuntimeParameterInfo::GetTypeModifiers
  - "This icall is not supported by il2cpp."
  at ProtoBuf.Meta.MetaType.ResolveTupleConstructor(...)
  at ProtoBuf.Meta.RuntimeTypeModel.FindOrAddAuto(...)
  at ProtoBuf.Meta.MetaType.ApplyDefaultBehaviour(...)
  at ProtoBuf.Meta.RuntimeTypeModel.GetSerializer[T]()
  at ProtoBuf.Serializer.Serialize[T](...)
```

**这不是"东西被删了"，而是"这个功能 IL2CPP 根本没实现"** —— `RuntimeParameterInfo.GetTypeModifiers` 是一个 icall，
IL2CPP 没提供它，所以一调用就抛异常。

| 假设 | 实测 |
| --- | --- |
| "元数据被裁剪掉了" | ❌ 错。**加多少 `link.xml` 都没用** —— 因为不是缺东西，是缺功能 |
| 失败在"序列化" | ❌ 错。失败在 **`RuntimeTypeModel` 运行时自动构建类型模型**（`GetSerializer[T]` 之前） |
| "protobuf-net 装了就能用" | ❌ 错。它默认走**自动发现**（扫特性、解析元组构造函数），这条路在 IL2CPP 下必炸 |

**为什么会踩到那个 icall**：`ApplyDefaultBehaviour` 处理成员时，遇到**重复字段**（我们 DTO 里的 `List<int>`）
会去解析"元素类型"，进而走 `ResolveTupleConstructor` → `IsPublicSetter` → 读参数的 custom modifiers → 命中未实现的 icall。
**所以只要消息里有集合字段，默认路径就炸。**

> **教训**：**排查方向错了，花的时间全是白费。**
> 报错第一行已经写明"**Unsupported internal call**"，而我们（包括文档）却一直按"裁剪"理解。
> **读原文明辨"缺东西"还是"缺功能"，能省掉一整天。**

### 解决方案 / 代码模式

**① 修复思路：不让 protobuf-net 自动发现，改用显式 `TypeModel`**

```csharp
var model = RuntimeTypeModel.Create("NBC.ProbeExplicitModel");
model.AutoAddMissingTypes = false;            // 缺类型时别再去自动发现
model.AutoAddProtoContractTypesOnly = true;

var mt = model.Add(typeof(ProbeMessage), false);   // ★ false = 不做默认行为扫描
mt.Add(1, nameof(ProbeMessage.Id));
mt.Add(2, nameof(ProbeMessage.Name));
// ... 逐个显式声明
model.Freeze();

model.Serialize(stream, obj);                  // 用模型，而不是静态 Serializer
```

**② 但真正值钱的是"一次出包测 4 条路"，而不是反复试**

一次 IL2CPP 出包要 5~15 分钟，所以不能"改一版试一版"。我把探针改成**可行性矩阵**：

| 用例 | 要回答的问题 |
| --- | --- |
| T1 默认API · 纯标量（无集合） | 集合是不是触发条件？ |
| T2 默认API · 标量 + **可写** List | "只读集合"是不是触发条件？ |
| T3 默认API · 原 DTO（含只读 List） | 复现失败（基线） |
| T4 **显式 TypeModel** · 原 DTO | 绕开自动发现是否可行（**核心问题**） |

每条独立 `try/catch`，任一条失败不影响其余；摘要给屏幕、明细给日志。
**一次出包拿到 4 个数据点**，足以决定"继续用 protobuf-net 还是换库"。

**③ 矩阵结果（第 2 次出包实测）：两条路都不通**

```text
[NBV0][Protobuf] 可行性矩阵：
  [通过] T1 默认API·纯标量         序列化往返数据一致
  [失败] T2 默认API·可写List       异常 NotSupportedException: ...GetTypeModifiers
  [失败] T3 默认API·原DTO(只读List) 异常 NotSupportedException: ...GetTypeModifiers
  [失败] T4 显式TypeModel·原DTO    异常 NotSupportedException: ...GetTypeModifiers
```

| 用例 | 结果 | 学到什么 |
| --- | --- | --- |
| T1 纯标量 | ✅ | **标量成员没问题** —— 不是"protobuf-net 完全不能用" |
| T2 可写 `List<int>` | ❌ | **集合是触发条件，与"只读"无关** |
| T3 只读 `List<int>` | ❌ | 复现基线 |
| **T4 显式 `TypeModel`** | ❌ | **`Add(typeof(T), false)` + `AutoAddMissingTypes=false` 也绕不过去** —— `mt.Add(fieldNo, memberName)` 解析集合元素类型契约时仍会走到 `ResolveTupleConstructor` |

**结论**：**protobuf-net 3.2.30 在 Unity 2022.3 + IL2CPP 下，只要消息含 repeated 字段就必然抛异常。**
而网络协议**必然**有 repeated 字段（技能列表、快照实体列表、输入队列）→ **它不满足本项目的 AOT 要求**。

> **这一步真正的价值不是"找到了修法"，而是"用一次出包把一条技术路线彻底否掉"，并留下可复现的证据。**
> 如果不做这个矩阵，我们会在"显式模型应该能行吧"的猜测里反复出包试错 —— 每次 5~15 分钟，还未必有结论。

**④ 两个把"浪费一次出包"概率降到最低的手法（这次都用了）**

| 手法 | 做法 | 收益 |
| --- | --- | --- |
| **先从 DLL 元数据里读出 API 签名**，再写代码 | 用 `System.Reflection.Metadata` 扫 `RuntimeTypeModel` / `MetaType` 的**方法签名与参数类型** | 避免"凭记忆写 API → 编译失败 → 白等一次出包" |
| **在 .NET 里先把改动编译一遍** | 临时 csproj 引用**真实的 protobuf-net DLL + Unity 引擎程序集**，把改过的 `.cs` 编进去 | 编译错误当场暴露（本次结果：**0 错误 0 警告**） |

**⑤ 顺手纠正的一个"过时知识"**

网上很多"protobuf-net 预编译"的文章讲的是 v2 的做法：`Compile(assemblyName, path)` 生成一个**序列化器 DLL** 放进工程。
**实测 v3.2.30 的签名是 `Compile(CompilerOptions) → TypeModel`，没有落盘重载**；而且该 DLL 里**不含** `BuildTools`（源生成器是独立包）。
→ **老文章的做法不能照搬**，方案要重新设计。

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| **把"icall 未实现"当成"元数据被裁剪"** | 方向完全错。前者加 `link.xml` 无用，后者才有用。**报错原文第一行就写着 `Unsupported internal call`** |
| 想靠 `link.xml` 修 AOT 问题 | `link.xml` 只影响**裁剪**，管不了"功能未实现" |
| 照搬网上 v2 时代的预编译流程 | v3 的 API 变了（`Compile(CompilerOptions)`），必须先**读签名**再动手 |
| 改一版就出一次包试 | 一次 5~15 分钟；应设计成"一次测多条路"的矩阵 |
| 凭记忆写第三方 API | 用元数据扫签名 + 本地预编译，成本几分钟，省一次出包 |

> **一句话记忆点**：**AOT 报错先分清是"缺东西"（裁剪 → `link.xml`）还是"缺功能"（icall 未实现 → 只能换调用方式）。**
> **分不清这两者，会在错误的路上把时间烧光。**

### 结论：换库（2026-09-20 决定）

**序列化库由 `protobuf-net 3.2.30` 换成 `Google.Protobuf 3.21.1`。**

| 项 | 内容 |
| --- | --- |
| 触发 | D17 第 2 次出包，4 条路矩阵实测：`T1 纯标量 ✓ \| T2 可写List ✗ \| T3 只读List ✗ \| T4 显式TypeModel ✗` |
| 判定 | protobuf-net 在 Unity 2022.3 + IL2CPP 下，**只要消息含 `repeated` 字段就必崩**，且**不是裁剪问题** |
| 决定 | 换 **Google.Protobuf 3.21.1**（`protoc` 编译期生成显式 C#，**零运行时反射**） |

#### 为什么"能修"和"值得修"是两件事

严格说，**protobuf-net 还剩一条没验证的路**：`protobuf-net.BuildTools` 源生成器
（Unity **官方支持 Roslyn 源生成器**）。但它要：自取 NuGet 里的 analyzer DLL + 打 `RoslynAnalyzer` 标签 +
与 Unity 的 Roslyn 版本匹配，**可行性未知**。

而此刻的处境是：**协议层一行代码都还没写**（M0 还在收尾）。此时换库的成本 ≈ **改一个探针**；
等到 M3 协议层成型再换，成本就是**推翻整层协议实现**。

> **决策原则**：**"能不能修"是技术问题，"值不值得修"是时机问题。**
> 当一条路的可行性未知、而另一条路是行业标准且此刻成本最低时，**应该换，而不是赌**。
> 这不是"逃避难题" —— 判断依据是**实测数据**（4 条路矩阵），不是感觉。

#### 换库后的收益（都是可验证的）

| 维度 | protobuf-net | Google.Protobuf |
| --- | --- | --- |
| Unity 侧 DLL | **4 个**（主包 + `.Core` + `Immutable` + `Unsafe`） | **2 个**（`Google.Protobuf` + `Unsafe`） |

## 🎓 本次新概念（复习用）

### 1. ECall（`MethodImplOptions.InternalCall`）—— "这个函数不在 C# 里实现"

- **这是什么**：Unity 托管程序集里，凡是要落到 C++ 引擎里的方法都标了 `InternalCall`。
  在 Unity 运行时里它们被转到原生引擎；在独立 .NET 进程里 CLR 找不到实现，调用时抛
  `SecurityException: ECall methods must be packaged into a system module.`
- **为什么这么做**：Unity 的核心（对象系统、时间、渲染、物理）本来就在 C++ 侧，
  C# 只是壳。用 ECall 让 C# 侧代码"看起来"是普通方法，实际转发给引擎。
- **不这么做（不知道它）会怎样**：会得出"编译通过 = 服务端能跑行为树"的**错误结论**，
  一直要到 M4 把行为树接进服务端时才炸，那时架构已经很难改了。

### 2. `AssemblyRef` 表 / 程序集传递闭包 —— "引用一个 dll 到底会拖进多少东西"

- **这是什么**：每个 .NET 程序集的元数据里有一张 `AssemblyRef` 表，记录"我引用了哪些程序集"。
  从入口程序集出发反复展开这张表，就是**传递闭包**。
- **为什么这么做**：Unity 把引擎拆成 87 个模块（`CoreModule`、`AIModule`、`IMGUIModule`…），
  引用一个模块往往要连带引用它依赖的模块，否则编译报 `CS0012`。
- **不这么做（不知道它）会怎样**：会以为"引用 Unity 就加一行 `<Reference>`"，
  结果在服务端拖进一堆引擎代码；或者靠记忆猜"这个类型在哪个模块"，然后在 `CS0234` 上反复试错。
  正解：用 `System.Reflection.Metadata` 读元数据，**问出答案而不是猜答案**。

### 3. `.gitignore` 的语义细节 —— "注释、大小写、目录不遍历、以及怎么验证它"

- **这是什么**：`.gitignore` 有四条容易致命的细节：
  ① `#` **只在行首**才是注释（**没有行尾注释**）；② Windows 上 `core.ignoreCase=true`，规则大小写不敏感；
  ③ **已被忽略的目录，git 不会向下遍历**，所以目录内文件自动一并忽略；
  ④ **验证它要用地面真值**（`git add --dry-run .` / `git status --porcelain -uall`），
  而不是 `git check-ignore -v` —— 后者会把被 `!` 取反命中的路径也打印出来且退出码为 0，极易误读。
- **为什么这么做**：`.gitignore` 语法极简，没有"注释到行尾"的便利，也不做大小写区分；
  而"会不会进仓库"是**最终效果**，只有 `git add --dry-run` 这类命令才直接回答它。
- **不这么做（不知道它）会怎样**：
  写了 `!**/Packages/  # 注释` 这种**静默失效**的规则（没有任何报错），
  直到某天发现 Unity 的 `Packages/` 被忽略、工程拉下来跑不起来；
  或者像我这次一样 —— **连着两次相信了错误的验证方式，得到"确信的错误答案"**。
  **判据选错，比不验证更危险。**
