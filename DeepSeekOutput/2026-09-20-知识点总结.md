## 一、ECall：托管代码与 Unity 原生引擎的那条边界（本次核心）

### 背景 / 问题描述

架构裁决 A1/A2/A3（AI 分两套实现、帧同步不由服务端跑 AI、寻路分两套）全部建立在
一个前提上：**Behavior Designer 和 Unity NavMesh 无法在本项目的纯 .NET 服务端进程里工作**。

但这个前提原来只是"文档推断"。M0 的 D14 就是把它变成实测。原计划是"在服务端工程里引用
Behavior Designer 的 dll，看编译报什么错"。**实际执行时改成了更根本的做法**：
不引用插件，**直接引用 Unity 自己的程序集**。

### 根因分析：分界线其实有三层，不是"能/不能"

用一个 9 级探针（`Server\_unity-ref-probe\`，.NET 8.0.21）测出来的结果：

| 分层 | 能否在纯 .NET 进程里工作 | 实测证据 |
| --- | --- | --- |
| **纯托管数学**（`Vector3` / `Quaternion` / `Mathf`） | ✅ **能，结果完全正确** | `magnitude=5`、`Normalize=(0.6,0.8,0)`、`Mathf.Sqrt(16)=4` |
| **类型元数据**（反射拿 `Type`、读基类链） | ✅ **能** | `MonoBehaviour` 的基类链 `Behaviour → Component` 可读出 |
| **引擎对象 / 原生调用** | ❌ **不能** | `new GameObject()`、`go.name`、`Time.deltaTime` 全部抛异常 |

失败异常原文：

```text
System.Security.SecurityException: ECall methods must be packaged into a system module.
```

**为什么会这样（白话版）**：

Unity 的托管程序集（`UnityEngine.CoreModule.dll` 等）里，凡是要落到 C++ 引擎里的方法，
都标了 `[MethodImpl(MethodImplOptions.InternalCall)]` —— 简称 **ECall**，
意思是"**这个方法不在这里实现，由运行时内部提供**"。

- 在 **Unity 自己的运行时**里：这些 ECall 被转到原生引擎，正常工作。
- 在**独立 .NET 进程**（`dotnet run`）里：CLR 里**没有**这些内部实现 → 调用时抛 `SecurityException`。

> **一句话**：`Vector3` 的加法是**纯 C# 写的**，所以在哪儿都能算；
> `new GameObject()` 要**问 C++ 引擎要一块对象内存**，而 CLR 里没有引擎，所以炸。

### 解决方案 / 代码模式

**① 关键认知：这是运行时错误，不是编译错误。**

```powershell
# 引用 UnityEngine.CoreModule 后 dotnet build —— 0 错误，能编译通过！
# 问题只在真正调用引擎的那一刻才炸。
```

所以 —— **"编译成功"不能用来证明"服务端能跑行为树"**。
反过来说，如果只做"引用 dll 看编译报错"的实验，会得到一个**假结论**（"能编译通过，那就没问题？"）。

**② 9 级探针必须用反射调用，不能顺序调用。**

```csharp
// ❌ 顺序调用：一次异常会中断后面所有级别，
//    分不清"是这一级失败"还是"因为上一级失败而没能跑到"
try { L3(); } catch { } try { L4(); } catch { }   // 脆弱

// ✅ 反射调用：每一级被隔离，异常包在 TargetInvocationException 里
var mi = typeof(Program).GetMethod(name, BindingFlags.Static | BindingFlags.NonPublic);
try { var r = mi.Invoke(null, null); } 
catch (TargetInvocationException tie) { /* 精确定位到这一级 */ }
```

**③ `<Private>true</Private>` 不能省 —— 否则实验失去意义。**

```xml
<Reference Include="UnityEngine.CoreModule">
  <HintPath>C:\...\UnityEngine\UnityEngine.CoreModule.dll</HintPath>
  <Private>true</Private>   <!-- 必须：把 dll 复制到输出目录 -->
</Reference>
```

只写 `<Reference>` 时会得到 `FileNotFoundException: 找不到 UnityEngine.CoreModule` ——
那只能证明"**我没把 dll 放过去**"，证明不了任何关于 Unity 的事实。
**要让实验有意义，必须先让运行时真的能加载到它。**

**④ 想量"引用一个模块会拖进几个模块"，要读元数据而不是猜。**

用 `System.Reflection.Metadata` 读 `AssemblyRef` 表并求传递闭包（Unity 安装目录下共 87 个模块 dll）：

| 起点 | Unity 侧传递闭包 | 数量 |
| --- | --- | --- |
| `UnityEngine.CoreModule` | CoreModule、SharedInternalsModule | **2** |
| `UnityEngine.IMGUIModule` | + InputLegacy、TextRendering、TextCoreTextEngine、TextCoreFontEngine | **7** |
| `UnityEngine.AIModule` | AIModule、SharedInternalsModule、CoreModule | **3** |

**工程含义**：服务端引用任何一个 Unity 模块，都要把整个闭包补全，否则得到 `CS0012`。
**这不是"多加一行 HintPath"的小事，而是"要拖进多少引擎代码"的成本** ——
这就是本项目坚持 `NBC.Shared` 用 `netstandard2.1`、`NBC.Model` 设 `noEngineReferences: true` 的原因。

**⑤ 同一套元数据扫描还能回答"某类型在哪个模块"（排查 `CS0012`/`CS0234` 最快的办法）。**

实测速查（**全部来自元数据，不是记忆**）：

| 类型 | 所在模块 |
| --- | --- |
| `Object` / `GameObject` / `Component` / `MonoBehaviour` / `ScriptableObject` / `Transform` | `UnityEngine.CoreModule` |
| `Vector3` / `Quaternion` / `Mathf` / `Time` / **`Debug`** / `Application` / `Resources` / `Camera` / `Material` | `UnityEngine.CoreModule` |
| `GUI` / `GUILayout` / `GUIStyle` / `Event` | `UnityEngine.IMGUIModule` |
| `Input` / `Touch` | `UnityEngine.InputLegacyModule` |
| **`NavMesh` / `NavMeshAgent`（命名空间是 `UnityEngine.AI`！）** | **`UnityEngine.AIModule`** |
| `Animator` / `Animation` | `UnityEngine.AnimationModule` |
| `Rigidbody` / `Collider` / `Physics` | `UnityEngine.PhysicsModule` |

### 踩坑记录

| 坑 | 真相 |
| --- | --- |
| 以为"编译通过 = 能运行" | **这是本次最大的认知修正**。发布 IL2CPP 包和引用程序集都是"编译期正常"，问题在运行时 |
| 以为 `UnityEngine.Debug` 在 `IMGUIModule` | **错，它在 `CoreModule`**。`IMGUIModule` 里是 `GUI` / `GUILayout` / `Event` |
| 以为 `NavMesh` 的命名空间是 `UnityEngine` | **错，是 `UnityEngine.AI`**，在 `AIModule` 里 |
| 想用 PowerShell 的 `Assembly.LoadFrom(...).GetExportedTypes()` 扫类型 | **不行**：pwsh 的加载上下文解析不了 `netstandard 2.1`，抛 `FileNotFoundException`。**要读元数据就用 `System.Reflection.Metadata`** |
| 原计划"引用插件 dll 看报错"就够了 | 那样测的是"**这个插件**行不行"，结论会被插件版本影响。**向下挖一层测 Unity 程序集本身，结论更硬、换插件也不失效** |

## 二、`.gitignore` 的语义陷阱，以及"验证方式本身出错"的两次翻车

### 背景 / 问题描述

D16 要 `git init` + 首次提交。提交前必须确认 `.gitignore` 真的有效，
否则 `Library/`（几 GB）会被提交进去。

于是开始验证 —— 结果**验证过程本身连续翻车两次**，这比 `.gitignore` 的知识更值得记。

### 根因分析 + 解决方案

**陷阱 1：`.gitignore` 不支持"行尾注释"——`#` 只在行首才是注释。**

```gitignore
# ❌ 错的：整行（含注释文字）被当成一个"永远匹配不到"的取反模式，等于白写
!**/Packages/          # 注意：Unity 的 Packages 目录要保留

# ✅ 对的：注释独占一行
# 注意：Unity 的 Packages 目录要保留
!**/Packages/
```

本次在 `Server\.gitignore` 里真的发现了这样一行 —— 它**静默失效**，不报错、不警告。

**陷阱 2：Windows 上 `core.ignoreCase = true`，所以 `**/packages/` 会连 Unity 的 `Packages/` 一起忽略。**

实测：

```text
core.ignoreCase = true
Packages/manifest.json  <=  .gitignore:4:**/packages/     ← 大写 Packages 也被匹配了
```

**正解不是去取反**，而是**把作用域限死**：本项目的 Unity 工程在 `Client/`，
`Server/` 下不存在 `Packages/` —— 所以在 `Server\.gitignore` 里写 `**/packages/` 就足够了，不需要 `!` 取反。

**陷阱 3（本次推翻了两个"我自己写下的错误结论"）：**

我之前在根 `.gitignore` 里写过两条"写法警告"，本次用真实 git 实测**全部推翻**：

| 我原来写的 | 实测真相 |
| --- | --- |
| "`Client/[Ll]ibrary/` 这种字符类+尾部斜杠**会漏掉目录内的文件**" | ❌ **错**。`[Ll]ibrary/` 正确忽略了 `Library/ScriptAssemblies/Assembly-CSharp.dll` |
| "`**/bin/` 反而**可能匹配不到**" | ❌ **错**。`**/bin/` 正确忽略了 `Server/NBC.Host/bin/Debug/host.exe` |

**为什么错**：git 对"**已被忽略的目录**"**根本不会向下遍历**，所以目录内文件自动一并忽略 ——
不存在"只匹配目录本身、漏掉内部文件"这回事。

**真正的教训（比这两个结论本身更值钱）**：

> **这两个错误结论来自一个我自己写的"路径模拟校验脚本"。**
> 我拿一个自己写的模拟器，去否定了真实工具的语义，还把它当成事实写进了配置文件注释。
> **校验器本身也要先被校验** —— 能用真实工具（`git check-ignore -v`）验证时，永远不要相信自己的模拟器。

### 踩坑记录（**这一天连续踩了两次"验证本身出错"**）

| 坑 | 说明 |
| --- | --- |
| ① 用"路径模拟脚本"代替真实工具 | 见上。写模拟器很容易漏掉真实工具的语义（"被忽略目录不遍历"、"ignoreCase"） |
| ② 改用 `git check-ignore -v` 后**又被它误导** | `git check-ignore -v` 会把**被取反规则（`!xxx`）命中**的路径**也打印出来，且退出码为 0**。我据此把 `.gitignore` 末尾的取反保命规则 `!Server/**/*.csproj`、`!*.asmdef` 误判成"这些文件被忽略了" |
| ✅ **正确判据：地面真值** | 要验证的是"**这些文件最终会不会进仓库**"，所以判据应该是：`git add --dry-run .` 或 `git status --porcelain -uall` —— **该保留的必须出现，该忽略的必须不出现**。换成它之后，22 项应保留 + 17 项应忽略**全部符合预期** |
| 项目还没有 `.git` 仓库时跑 `git check-ignore` | 确实会失败。**但"命令失败"不等于"文件被正确忽略"** —— 当时我误读了退出码，得出了错误结论。正解：在临时目录里 `git init` 一个最小仓库来验证规则语义 |

> **这一天的最大收获**：不是"我修好了 `.gitignore`"，而是发现**我连着两次相信了错误的验证方式**。
> 第一次是"自己写的模拟器"，第二次是"一个真实但不适合这个问题的工具"。
> **判据选错，比不验证更危险** —— 不验证只是不知道，判据选错会得到"确信的错误答案"。

## 三、XML 里 `--` 是非法字符（同一个坑踩了两次）

### 背景 / 问题描述

给 `probe.csproj` 写注释时，顺手写了复现命令 `dotnet run --project ...`。
构建直接失败：

```text
error MSB4025: 未能加载项目文件。名称不能以"e"字符(十六进制值 0x65)开头。...
```

### 根因分析

**XML 注释 `<!-- ... -->` 内部不允许出现 `--`。** 这是 XML 规范的硬性规定（`--` 是注释结束符的一部分）。
`dotnet run --project` 里正好有 `--`。

本项目**之前已经因为同样原因踩过一次**（`.csproj` 里用 `------` 做分隔线导致 `MSB4025`），
当时的对策是在 `.csproj` 里改用 `=====` 做分隔线。所以：

### 解决方案 / 代码模式

| 场景 | 规则 |
| --- | --- |
| `.csproj` / `.props` / `.targets` 的 XML 注释 | **禁止出现 `--`**。分隔线用 `=`；命令行用 `-p` 之类的单横线写法，或干脆写成"把工作目录切到某处再执行 `dotnet run`" |
| 想写 `<!-- ---- 分节 ---- -->` | ❌ 会 `MSB4025`。写成 `<!-- ==== 分节 ==== -->` |

> **记忆点**：**改了 `.csproj` 之后一定要真跑一次 `dotnet build`** —— 这个错误在编辑器和 Markdown 预览里看不出来。

## 三之二、"0 个错误"不等于成功：MSBuild 多节点在沙箱下的静默失败

### 背景 / 问题描述

收尾复核时跑 `dotnet build NBC.sln`，输出是：

```text
生成失败。
    0 个警告
    0 个错误
```

**退出码 1，但一条错误信息都没有。** 而 D13 记录里这个命令是**成功过**的。

### 根因分析（三步定位）

| 步 | 动作 | 结果 |
| --- | --- | --- |
| 1 | 提高详细度重跑（`-v n` / `-v diag`） | 失败点是 `_GetAllRestoreProjectPathItems`，**子 MSBuild 节点返回失败但不记录任何错误** |
| 2 | 找出触发条件 | `-m`（默认并行）失败；**`-m:1`（单节点）成功**。逐工程试：只有含 **≥2 个 `ProjectReference`** 的工程（Game / Host / Tests）会失败 |
| 3 | **最小对照实验** | 在 `%TEMP%` 新建 A/B/C 三个工程（C 引用 A + B，共 20 行代码）：`-m:1` ✅ 成功、`-m:2` / `-m` ❌ 同样静默失败 |

**结论**：这是**运行环境**的限制，**与本项目完全无关** ——
MSBuild 在 `-m` 下会启动**进程外工作节点**，节点间靠**命名管道**通信；
DSH 的受限沙箱不允许打开命名管道，子节点起不来，于是任务返回失败却不记录错误。

### 解决方案 / 代码模式

```powershell
dotnet build NBC.sln -m:1     # ✅ AI 在沙箱里代跑构建时用这条
dotnet build NBC.sln          # ✅ 用户在自己终端里用这条（正常环境不受限）
```

**可复用的排查手法（比这次的结论更值钱）**：

| 手法 | 说明 |
| --- | --- |
| **看退出码，不只看输出** | `0 个错误` 完全可能是失败。**只有退出码为 0 才算成功** |
| **换 `-m:1` 试一次** | 并行构建失败时的第一反应 |
| **写最小对照工程** | 把嫌疑从"我的项目"摘出去的最快办法。**20 行代码就能决定是该改项目还是改环境** |
| 提高详细度（`-v n` → `-v diag`）定位到**哪个 target/task** 失败 | 这次因此定位到 `_GetAllRestoreProjectPathItems` 与"子节点失败" |

### 踩坑记录

| 坑 | 说明 |
| --- | --- |
| 看到"生成失败 + 0 个错误"先怀疑自己的工程 | 这会让人去删 `obj`、改 `csproj`，**全是无用功**。先做最小对照实验 |
| 拿"之前成功过"当"现在也该成功" | D13 成功是在**不同环境**（用户自己的终端）下得到的。**环境变了，结论就要重新验证** |
| 用 `-v q`（静默）排查失败 | 静默模式连失败原因都不打印。排查时应先提高详细度，**定位之后再回到静默模式做日常构建** |

## 四、方法论：把"文档断言"升级为"实测证据"的标准动作

### 背景 / 问题描述

需求文档 §5.4.5 里原本写着"Behavior Designer **引用不了**"。
实测后发现这句话**过头了**（能引用、能编译），准确的说法是"**能引用、纯托管能跑，一碰引擎对象就抛 `ECall`**"。

### 解决方案 / 代码模式（可复用的四步）

| 步 | 动作 | 本次做法 |
| --- | --- | --- |
| 1 | **先问"这个断言的最底层机制是什么"**，再设计实验 | 不问"这个插件行不行"，而问"**Unity 程序集在 .NET 里行不行**" |
| 2 | **把被测对象分层**，而不是给一个"能/不能" | 分三层：纯托管数学 / 类型元数据 / 引擎对象与原生调用 |
| 3 | **让每一层独立失败**（反射隔离） | 9 级探针，异常逐个定位 |
| 4 | **写下"这个实验没有证明什么"** | 没直接引用插件 dll；没测 IL2CPP/AOT 侧（那是 D17） |

**结论收窄不是退步，而是变强**：
原来是"我说编译不过"（一个可能被反驳的断言）；
现在是"**我实测过：编译能过、托管部分能跑，但一碰引擎对象就炸**"（解释了**为什么**，而不只是断言）。

> **面试迁移**：任何"我用了 X 技术"的说法，都值得追问一句"**你怎么知道它一定/一定不能？**"
> 能拿出一段自己写的探针 + 逐字输出，说服力和"我看文档说"完全不是一个量级。

## 🎓 本次新概念（复习用）

### 1. ECall（`MethodImplOptions.InternalCall`）—— "这个函数不在 C# 里实现"

- **这是什么**：Unity 托管程序集里，凡是要落到 C++ 引擎里的方法都标了 `InternalCall`。
  在 Unity 运行时里它们被转到原生引擎；在独立 .NET 进程里 CLR 找不到实现，调用时抛
  `SecurityException: ECall methods must be packaged into a system module.`
- **为什么这么做**：Unity 的核心（对象系统、时间、渲染、物理）本来就在 C++ 侧，
  C# 只是壳。用 ECall 让 C# 侧代码"看起来"是普通方法，实际转发给引擎。
- **不这么做（不知道它）会怎样**：会得出"编译通过 = 服务端能跑行为树"的**错误结论**，
  一直要到 M4 把行为树接进服务端时才炸，那时架构已经很难改了。

### 2. `AssemblyRef` 表 / 程序集传递闭包 —— "引用一个 dll 到底会拖进多少东西"

- **这是什么**：每个 .NET 程序集的元数据里有一张 `AssemblyRef` 表，记录"我引用了哪些程序集"。
  从入口程序集出发反复展开这张表，就是**传递闭包**。
- **为什么这么做**：Unity 把引擎拆成 87 个模块（`CoreModule`、`AIModule`、`IMGUIModule`…），
  引用一个模块往往要连带引用它依赖的模块，否则编译报 `CS0012`。
- **不这么做（不知道它）会怎样**：会以为"引用 Unity 就加一行 `<Reference>`"，
  结果在服务端拖进一堆引擎代码；或者靠记忆猜"这个类型在哪个模块"，然后在 `CS0234` 上反复试错。
  正解：用 `System.Reflection.Metadata` 读元数据，**问出答案而不是猜答案**。

### 3. `.gitignore` 的语义细节 —— "注释、大小写、目录不遍历、以及怎么验证它"

- **这是什么**：`.gitignore` 有四条容易致命的细节：
  ① `#` **只在行首**才是注释（**没有行尾注释**）；② Windows 上 `core.ignoreCase=true`，规则大小写不敏感；
  ③ **已被忽略的目录，git 不会向下遍历**，所以目录内文件自动一并忽略；
  ④ **验证它要用地面真值**（`git add --dry-run .` / `git status --porcelain -uall`），
  而不是 `git check-ignore -v` —— 后者会把被 `!` 取反命中的路径也打印出来且退出码为 0，极易误读。
- **为什么这么做**：`.gitignore` 语法极简，没有"注释到行尾"的便利，也不做大小写区分；
  而"会不会进仓库"是**最终效果**，只有 `git add --dry-run` 这类命令才直接回答它。
- **不这么做（不知道它）会怎样**：
  写了 `!**/Packages/  # 注释` 这种**静默失效**的规则（没有任何报错），
  直到某天发现 Unity 的 `Packages/` 被忽略、工程拉下来跑不起来；
  或者像我这次一样 —— **连着两次相信了错误的验证方式，得到"确信的错误答案"**。
  **判据选错，比不验证更危险。**
