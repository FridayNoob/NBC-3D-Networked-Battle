## 一、M2 要达成什么

**一句话**：在**完全不需要网络**的前提下，做出"**接到一个任务 → 打一局 PVE → 任务完成 → 交付 → 奖励真的发下来**"的可演示闭环。

### 1.1 验收标准（源自 `Docs\20` §三 M2 行）

| # | 完成标准 | 对应任务 | 验证方式（可测） |
| --- | --- | --- | --- |
| V1 | **条件系统**落地：事件 → 进度 → 达成回调，且**不认识"任务/成就"这两个词** | **A1** | EditMode 测试；`Shared\Quest\` 里搜不到 "Quest" 字样（机械检查） |
| V2 | 任务运行时：接取 → 进度 → 完成 → 交付 → 发奖 | **A2** | EditMode 端到端用例（假表 + 假发奖口） |
| V3 | 新增配置表 `Quest` / `QuestCondition` / `Reward`（+ `Monster`，PVE 要用） | **A3** | ConfigKit 校验通过、三份产物一致、报错定位照旧 |
| V4 | 单机 PVE 最小战斗：属性 + 伤害结算 + 死亡事件 | **B** | EditMode 战斗结算用例 + PlayMode 冒烟 |
| V5 | 用**真实战斗事件**驱动任务条件（不是测试里手搓 `Notify`） | **C** | 端到端用例：打够怪 → 任务自动完成 |
| V6 | 任务 UI：接取 / 追踪 / 交付 | **D** | 面板 EditMode 用例（逻辑）+ 你点击验证（预制体） |

### 1.2 M2 的红线（**明确不做**，来自 `Docs\20` §二）

任务链、多分支、日常/周常、自动寻路引导；多阶段 BOSS、难度分级、随机词缀；成就、PVP、好友、聊天（M4/M5）。

## 二、任务拆分

> 约定：🤖 = AI 写代码/文档；👤 = 必须你在 Unity 里操作。

### A 组 · 任务与条件系统（**纯逻辑，单机闭环**）

| # | 任务 | 内容 | 谁 | 验收 |
| --- | --- | --- | --- | --- |
| **A1** | **条件系统核心** | 落在 **`Client\Assets\_Project\Shared\Quest\`** —— 因为它是**双端共享**的候选（服务端 M4 要校验任务进度）。四件东西：`EConditionEvent`（事件类型）/ `ConditionDef`（条件定义）/ `ConditionProgress`（进度，**钳位**）/ `ConditionTracker`（订阅→累加→达成回调）。<br>**三条写死的语义**：① `TargetId == 0` = **任意目标** ② 进度**钳位在需求值**，于是"达成只回调一次"**不需要额外标志位**（只在"跨越那一刻"回调）③ 注册时可选择**是否清零进度** —— 这一个 `bool` 就是"任务（接取才计数）"与"成就（一直生效）"的**唯一差别** | 🤖 | EditMode 全绿；`Shared\Quest\` 源码里**没有** "Quest"/"Achievement" 字样（机械检查，证明通用性） |
| **A2** | **任务运行时** | `Game\Quest\`：`QuestRuntime`（接取/进度/完成/交付）+ `ConditionEventBridge`（`EventCenter` → `ConditionTracker` 的桥）+ `IQuestRewardSink`（发奖接缝：M2 内存实现，M4 换服务端权威）。<br>**报错形态**：玩家操作类（重复接取、条件没达成就要交付）**返回原因字符串**而不是抛异常 —— 这是"玩家能触发的错误"，不该用异常控流程 | 🤖 | EditMode 端到端用例：接取→打够→完成→交付→奖励到账 |
| **A3** | **配置表** | 新增 `Quest` / `QuestCondition` / `Reward` / `Monster` 四张表（CSV 在 `Configs\Design\`），跑 `ConfigKit.Cli` 生成三份产物。<br>⚠️ **这是 C 组通用性的第一次实战检验**：加表**不改一行工具代码**（包括 `ConfigImporter`，它按 `<表>Config` 反射找类型） | 🤖 写 + 👤 点导入菜单 | ConfigKit 校验通过；生成物入库可 diff；SO 资产由你点菜单生成 |
