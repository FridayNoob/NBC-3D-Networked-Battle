## 四、M1 沉淀的 8 条方法论（跨模块反复出现）

| # | 母题 | 出现过的模块 |
| --- | --- | --- |
| 1 | **静默失败最危险**（出错但不报错） | A3 string key · A5 `float` 当等待 · A8 兜底字符串 · A9 `Find` 返回 null · E1 `N/A` vs `0` · C2 空格子当 0 |
| 2 | **把不可控环境变成可注入参数** | A5 `Tick(dt)` · A7 假输入源 · A8 探针 · **E1 `IPerfCounterSource`** · **C2 `ITableSource`** · **C4 `IConfigSource`** |
| 3 | **"没报错"可能是"实验没跑"** | A1 基线全 0 · A2 asmdef 实验 inconclusive · **C2 `NU1301` 实测** |
| 4 | **验证器本身必须先被验证**（W9） | A2 阳性对照 · A8 产物字符串表 · A10 检查命中注释 · **C2/C4 共 6 次命中注释** |
| 5 | **断言里的数字必须算出来** | D2 相对误差界 · E1 三次栽在阈值（最终"把阈值从断言里去掉"） |
| 6 | **写可以手写，验必须用真工具** | **C2 手写 JSON → 用 `System.Text.Json` 反向解析** |
| 7 | **报告/输出类方法不该改数据** | **C2 `Render` 就地排序 → 调用方遍历时抛异常** |
| 8 | **"删除类"改动必须回读确认** | **C4 我的清理编辑报了成功但代码还在**，只以"另一条测试红了"的面目出现 |

> 📌 第 4 条值得单独说：**"机械检查命中注释"在 M1 里栽了 6 次**
> （`#US` 堆、grep 命中注释、FSM-09、`Math\.` 正则、架构守卫、生成物断言）。
> 这已经不是巧合，而是"**用裸词/正则做检查**"这个做法的固有缺陷 ——
> 正确做法是：**能剥注释就剥、能用调用点形式就别用裸词、能用编译器就别用 grep**。

## 八、数据收集方法（**可重跑**，不靠手抄）

```powershell
# 用例数（显式 UTF-8 读，因为本机 Get-Content 行数不可信 —— W3a）
Get-ChildItem -Recurse -Filter *.cs Client\Assets\_Project\Tests\EditMode |
  ForEach-Object { [regex]::Matches([IO.File]::ReadAllText($_.FullName,[Text.Encoding]::UTF8),'(?m)^\s*\[Test\]').Count } |
  Measure-Object -Sum

# 规模
Get-ChildItem -Recurse -Filter *.cs Client\Assets\_Project\Framework |
  Measure-Object   # 文件数；行数用 ReadAllLines 累加

# 提交数 / 待推送
git rev-list --count HEAD
git rev-list --count origin/main..HEAD
```

⚠️ **本机两条环境规矩**（`Docs\11` §四之二/§四之三）：`dotnet build` 加 `-m:1`；
`dotnet run` 配 `--no-build`。**不要用 `Get-Content` 数行**（W3a：它静默吞换行）。
