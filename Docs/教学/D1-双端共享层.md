# ① 问题是什么

游戏逻辑里有一部分**两端都要用**：

- 定点数学（`Fix64`）—— 帧同步的地基
- 战斗核心逻辑 —— 服务端算一遍校验客户端
- 协议定义

> **帧同步**：客户端把"玩家按了什么"发给服务端，两边**各跑一遍同一份逻辑**，
> 结果对不上就是有人作弊或者有 bug。所以**两端必须跑同一份代码**。

## 那"同一份代码"到底怎么共享？

最直觉的做法是**两边各放一份**。这是最危险的：

> 你改了客户端那份、忘了改服务端那份 → 两边算出来的结果**不一样** →
> 帧同步立刻失效。而且这种 bug **不会报错**，只会表现为"玩着玩着就不同步了"、
> 复现还时有时无。**极难定位。**

另一种做法是**服务端编成 DLL 丢给 Unity**。能用，但：改一行代码要重新编 DLL、
两边打断点时源码路径对不上、IL2CPP 下多一个待验证项。

**所以选第三种：只有一份源码，两边都去编它。**

# ② 最小例子

```
Client/Assets/_Project/Shared/          ← 唯一源码在这里
    NBC.Shared.asmdef                   ← Unity 用这个编译它
    SharedInfo.cs
    （后面 D2 会加 Fix64.cs 等）

Server/NBC.Shared/NBC.Shared.csproj     ← 服务端不存源码，引用上面那个目录
```

服务端工程里就这一行是关键的：

```xml
<ItemGroup>
  <!-- ★ 唯一源码：Unity 侧 -->
  <Compile Include="..\..\Client\Assets\_Project\Shared\**\*.cs" />
</ItemGroup>
```

还有一行同样重要：

```xml
<!-- 关掉默认编译项，否则服务端目录里再放 .cs 会被**偷偷编进去** -->
<EnableDefaultCompileItems>false</EnableDefaultCompileItems>
```

**为什么要关默认编译？** 因为 SDK 默认会把工程目录下的 `.cs` 全编进来。
不关的话，哪天有人"顺手"在服务端目录里放一份拷贝，它**会被编进去**，
于是就有了两份代码 —— 而且**没有任何报错**。这正是我们要防的漂移。

# ③ 抓到的真隐患：服务端可以写出 Unity 编不过的代码

**这一节是 D1 最有价值的部分。**

## 现象

改之前，服务端工程的 `LangVersion` 没写，用的是 **SDK 默认值**。
而 SDK 默认值**允许 C# 10 语法**。

Unity 2022.3 只支持 **C# 9**。

> **`LangVersion`**：告诉编译器"按哪个版本的 C# 规则检查"。
> 版本越高，能用的语法越多；**用高版本语法写的代码，低版本编译器直接不认**。

于是就有了这个局面：

```
服务端：LangVersion = 默认（C# 10+）  → 能编 C# 10 语法
Unity ：C# 9                          → 编不了 C# 10 语法
        ↓
服务端**可以**写出"服务端编得过、Unity 编不过"的共享代码
而且**没有任何东西会拦住它**
        ↓
错误只在"打开 Unity"的那一刻才暴露 —— 在错误的地方、错误的时间
```

## 这不是假想，是已经躺在仓库里的

改动前的 `SharedInfo.cs` 第一行是：

```csharp
namespace NBC.Shared;        // ← 文件作用域命名空间，这是 C# 10 语法
```

（老写法是 `namespace NBC.Shared { ... }` 把整个文件包起来。）

它**一直在服务端编得过**，因为服务端允许 C# 10。
但只要真的把它共享给 Unity，**立刻就编译失败** —— 而它恰好就是"证明共享层装配正确"的那个文件。

## 修法：把服务端的语言版本钉到 Unity 的水平

```xml
<LangVersion>9.0</LangVersion>
```

**效果**：**"服务端编得过"这件事本身就代表"Unity 也能编过"。**

这和编译闸门 `ApiProbe.csproj` 的 `<LangVersion>9.0</LangVersion>` 是**同一个理由** ——
闸门早在 A1 就定下了这条，只是服务端的共享工程漏了。

## 顺带炸出第二件事：`ImplicitUsings`

钉完 `LangVersion 9.0`，构建立刻报了一堆：

```
error CS8773: 功能"全局 using 指令"在 C# 9.0 中不可用。请使用语言版本 10.0 或更高版本。
```

来源是一个我没写过的文件：`obj\...\NBC.Shared.GlobalUsings.g.cs`。

> **`ImplicitUsings`**：SDK 的一个开关，会自动生成一个文件，里面是一堆 `global using`。
> 而 `global using` 是 **C# 10** 特性。

**但这里的关键不是"绕过报错"**：**Unity 根本没有隐式 using**。
也就是说，共享代码里本来就必须把 `using` 写全 —— 关掉它只是让两边环境一致。

```xml
<ImplicitUsings>disable</ImplicitUsings>
```

# ④ 为什么用测试钉住这些约定

D1 的约定**全是配置文件层面的**，而**编译器只能挡住一部分**：

| 约定 | 编译器会报吗 |
| --- | --- |
| `NBC.Shared` 不许引用 `UnityEngine` | ❌ 不会（`noEngineReferences` 是 Unity 侧的设置，服务端看不见） |
| 服务端必须引用 Unity 侧目录 | ❌ 不会 |
| **服务端目录里不许再出现 .cs** | ❌ **完全不会** —— 但那一刻双端就开始漂移了 |
| 服务端 `LangVersion` 必须是 9.0 | ❌ 不会 |

所以写成一个测试类（8 条），用**读文件 + 断言**的方式钉死：

```csharp
[Test]
public void ServerProject_DirectoryContainsNoSourceFiles()
{
    string dir = Path.GetDirectoryName(ServerSharedCsproj);
    string[] sources = Directory.GetFiles(dir, "*.cs", SearchOption.AllDirectories);

    List<string> real = new List<string>();
    for (int i = 0; i < sources.Length; i++)
    {
        if (sources[i].Contains("\\obj\\")) continue;   // SDK 自动生成的不算
        real.Add(Path.GetFileName(sources[i]));
    }

    CollectionAssert.IsEmpty(real,
        "服务端共享目录里不该再存 .cs（唯一源码在 Unity 侧）。发现：" + string.Join(", ", real.ToArray()));
}
```

这套手法和 `FrameworkLayeringTests`（断言 asmdef 引用必须为空）是**同一个思路**：
**约定被人改坏时，测试当场变红。**

## ⚠️ 一个必须排除的东西：注释

有一条测试是"共享源码里不许出现 `UnityEngine`"。
第一版**直接把注释行也算进去了** —— 而解释这条规则的注释里**就有这个词**：

```csharp
/// 本程序集【禁止】引用 UnityEngine（帧同步确定性的硬前提）
```

于是报了假违规。加上"排除 `//` 与 `///`"才是有效检查：

```csharp
if (trimmed.StartsWith("//")) continue;
```

> 这已经是本项目**第 3 次**"验证方法本身要先被验证"。
> （前两次：拿 ASCII 搜 DLL 只能验类型名/成员名，搜不到字符串字面量；
> FSM-09 的机械检查第一次命中 7 处全是注释。）

# ⑤ 自测 4 题

**1.** 为什么不做"两边各放一份源码"？
**2.** `EnableDefaultCompileItems>false` 是为了防什么？
**3.** 服务端 `LangVersion` 不钉会怎样？（举出仓库里**实际发生**的那一例）
**4.** 为什么"共享源码里不许出现 `UnityEngine`"这条要排除注释行？

<details>
<summary>点开看答案</summary>

**1.** 两份拷贝一定会**漂移**。你改了客户端忘了改服务端，两边算出来的结果不一样，
帧同步立刻失效 —— 而且**不会报错**，只表现为"玩着玩着就不同步了"，极难定位。

**2.** 防"服务端目录里又被放进一份 .cs"。不关的话 SDK 会**偷偷把它编进来**，
于是就有了两份代码，且没有任何报错。

**3.** 服务端可以写出 C# 10 语法的共享代码，而 **Unity（C# 9）编不过**，且没有任何东西拦得住。
**实际发生的那一例**：`SharedInfo.cs` 用了 C# 10 的**文件作用域命名空间**（`namespace NBC.Shared;`）——
服务端一直编得过，一旦共享给 Unity 就会编译失败。

**4.** 因为解释这条规则的注释里**就有 `UnityEngine` 这个词**。
不排除的话，检查会把"说明文字"当成"违规代码"，得到一堆假违规。
</details>

# ⑥ 30 秒验证

**测试**：Test Runner → EditMode → Run All，`SharedLayerTests` **8** 条绿，总数 **278/278**。

**服务端侧（不用开 Unity，随时能跑）**：

```powershell
dotnet build Server\NBC.Shared\NBC.Shared.csproj -m:1
```

它编的就是 Unity 侧那份源码 —— **编得过，就说明服务端能复用共享逻辑**。

**负向对照**（证明 `LangVersion` 真的在起作用）：

在 `Client\Assets\_Project\Shared\` 里新建一个 `__probe.cs`，内容只有一行：

```csharp
namespace NBC.Shared.Probe;
```

再构建服务端 —— 应当当场报：

```
error CS8773: 功能"文件范围内的命名空间"在 C# 9.0 中不可用。
```

删掉文件，构建恢复绿色。

> ⚠️ **验证产物时要确认它是本次生成的。**
> 我第一次验"产物里有 `SharedInfo`"时，构建其实是**失败**的，我读的是**上一次的旧 DLL** ——
> 那次结论**无效**。后来改成**先核对产物时间戳晚于构建开始时间**，才是有效证据。

# ⑦ 一分钟面试版

> 帧同步要求客户端和服务端跑**同一份**战斗逻辑，所以共享代码怎么组织是个真问题。
>
> 我排除了两种做法：**两边各放一份**会漂移 —— 改了客户端忘了改服务端，两边算出来不一样，
> 帧同步悄悄失效而且不报错；**服务端编 DLL 给 Unity** 能用，但改一行要重编、断点路径对不上、
> IL2CPP 多一个待验证项。
>
> 最后选的是**一份源码放 Unity 侧，服务端用 `Compile Include` 引用它** ——
> 只有一份代码，改一处两边都变。代价是服务端构建依赖客户端目录，这个取舍我写在架构文档里了。
>
> 顺手抓到一个已经躺在仓库里的隐患：**服务端原来的 `LangVersion` 用 SDK 默认、允许 C# 10，
> 而 Unity 2022.3 只到 C# 9** —— 也就是说服务端**可以**写出"服务端编得过、Unity 编不过"的共享代码，
> 而且没有任何东西拦得住。事实上共享层那个文件当时就用了 C# 10 的文件作用域命名空间。
>
> 修法是**把服务端的语言版本钉到 9.0**，这样"服务端编得过"本身就代表"Unity 也能编过"；
> 钉完又暴露出 SDK 默认开的隐式 using 也是 C# 10 特性（Unity 没有隐式 using，
> 共享代码本来就必须写全）。
>
> 另外这些约定**编译器大多挡不住**（比如"服务端目录里不许再出现 .cs"），
> 所以我写了 8 条读配置文件做断言的测试把它们钉死 —— 约定被改坏时测试当场变红。

# 附：术语速查

| 术语 | 一句白话 |
| --- | --- |
| **共享层 / 双端共享逻辑** | 客户端和服务端都要跑的那部分代码（定点数学、战斗核心、协议） |
| **帧同步** | 两端跑同一份逻辑、喂同样的输入，靠"结果一致"互相校验 |
| **漂移（两份拷贝）** | 两份本该一样的代码慢慢变得不一样 —— 而且没有任何报错 |
| **`LangVersion`** | 让编译器按哪个版本的 C# 规则检查 |
| **`ImplicitUsings`** | SDK 开关：自动生成一个装满 `global using` 的文件（C# 10 特性） |
| **`Compile Include`** | .csproj 里手动指定"要编译哪些文件" |
| **`EnableDefaultCompileItems`** | SDK 开关：是否自动把工程目录下的 `.cs` 全编进来 |
| **`noEngineReferences`** | asmdef 上的开关：这个程序集不许引用 `UnityEngine` |
| **机械保证** | 不靠人记得，而靠"改错了就编译不过 / 测试变红" |
