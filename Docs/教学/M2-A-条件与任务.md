## ① 问题是什么（不用代码）

### 1.1 先说"任务系统"到底在做什么

你在别的游戏里一定见过这种东西：

> **初次狩猎**：击杀 3 只野狼，并带回 2 张狼皮 —— 奖励：经验 100、金币 50、狼牙 ×2

玩家做的事是：**接任务 → 打怪 → 交任务 → 拿到奖励**。
程序要做的事，拆开其实只有三句：

1. **记住**"玩家现在有哪几个任务、每个做到哪一步了"
2. **知道**"游戏里刚发生了一件事，它算不算任务进度"
3. **判断**"这个任务是不是做完了，做完了该给什么"

### 1.2 最容易走进的坑：把任务写死在代码里

新手（包括我早期）通常这么写：

```csharp
// ❌ 任务 A 的判定散落在战斗代码里
void OnMonsterDied(Monster m)
{
    if (m.Id == 6001)
    {
        m_killWolfCount++;
        if (m_killWolfCount >= 3) { ShowTip("初次狩猎：可以交任务了"); }
    }
}
```

这段代码**能跑**，但四个问题会陆续找上门：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 任务内容（杀哪种怪、杀几只）**写在代码里** | 策划想改一个数字，得找程序员、改代码、重新出包 |
| 2 | **战斗代码认识任务** | 战斗模块里堆满 `if (m_killWolfCount >= 3)`；再来 20 个任务就是 20 段这种代码 |
| 3 | 判断**散布在各处** | "这个任务为什么没完成"要翻战斗、翻背包、翻 NPC 对话 |
| 4 | **没法复用** | 成就系统要"累计击杀 10 只"，你会发现几乎是同一段逻辑，但只能复制一份 |

### 1.3 于是有了两层：**条件系统** 与 **任务系统**

这是本模块**唯一**需要先记住的一句话：

> **条件系统负责"做到了没有"，任务系统负责"该不该发奖"。**

```
        游戏里发生的事（打死了怪 / 捡到物品 / 走进区域）
                        │
                        ▼
        ┌────────────────────────────────────────┐
        │  条件系统（条件系统 / ConditionTracker）│  ← 只管计数与达成
        │  "击杀怪物 ×3（目标 6001）：2/3"        │
        └────────────────┬───────────────────────┘
                         │ 达成时喊一声
                         ▼
        ┌────────────────────────────────────────┐
        │  任务系统（任务系统 / QuestRuntime）    │  ← 只管接取/交付/发奖
        │  "3001 的两条条件都满了 → 可交付"       │
        └────────────────────────────────────────┘
```

**为什么这个拆分值钱**：成就系统在 M4 要进来。成就也是
"达成条件 → 做点什么"，区别只有**两头**：

| | 任务 | 成就 |
| --- | --- | --- |
| **什么时候开始算** | **接取之后**才算 | **一直**在算 |
| **达成后做什么** | 去交任务 → 发奖励 | 立刻解锁 + 弹个提示 |

中间"订阅事件 → 累加 → 判定达成"那一层**一模一样**。
所以 M4 的成就不需要重新写一套，它只是**同一套条件系统的第二个使用者**。

## ② 一个最小例子（先看差别）

### 2.1 "击杀 3 只野狼"这件事，两种写法

```csharp
// ❌ 错的写法：任务知识散在代码里
if (monsterId == 6001 && ++m_killCount >= 3) { CompleteQuest(3001); }

// ✅ 对的写法：条件是一条**数据**
ConditionDef def = new ConditionDef(EConditionEvent.KillMonster, 6001, 3);
//                                  ↑ 做了什么          ↑ 做在谁身上  ↑ 多少次
tracker.Register(4001, def, resetProgress: true);
tracker.Notify(EConditionEvent.KillMonster, 6001, 1);   // 打死一只就喂一次
```

第二条写法的关键不在"短"，而在于：

- **`ConditionDef` 是从配置表读出来的**（`QuestCondition` 表的一行），策划能自己改
- 战斗代码**只需要喊一句**"我打死了一只 6001"，它**根本不知道任务是什么东西**

### 2.2 用一句话说清"打架和任务怎么连起来"

```
战斗模块：Trigger(BattleEvents.MonsterDied, 6001)     ← 只报告事实
                  │
                  │  桥（ConditionEventBridge）把事实翻译成条件事件
                  ▼
条件系统：Notify(EConditionEvent.KillMonster, 6001, 1) ← 只认条件事件
                  │
                  ▼
任务系统：3001 的两条条件都满了 → 状态变成"可交付"
```

这条链上**没有任何一个模块知道它的下游**：
战斗不知道条件系统，条件系统不知道任务，任务不知道 UI。

## ③ 需求到底要什么（M2 的验收线）

`Docs\20` §三 把 M2 的验收写成了一句话：

> **单机一局 PVE 里接到并完成一个任务，奖励真的发下去。**

把它拆成可测的条目（就是 `Docs\22` 里的 V1~V3）：

| # | 要求 | 为什么它必须可测 |
| --- | --- | --- |
| V1 | 条件系统 **不认识"任务/成就"这两个词** | 否则 M4 服务端校验任务进度时会被迫认识客户端任务系统 |

| V3 | 新增 4 张配置表**不改工具代码** | 这是 C 组"通用工具链"的第一次实战检验 |

⚠️ **"奖励真的发下去"这句里的"真的"很重要**：
下面 ⑤ 会看到，测试里我刻意**不看"Grant 被调用过"**，而是看**到账的数字**。

## ④ 做法：分层与关键决定

### 4.1 为什么条件系统住在**共享层**（`Shared\Condition\`）

`Shared\` 是本项目里"**一份源码、双端都编**"的地方（M1-D1 定的）：
Unity 侧由 `NBC.Shared.asmdef` 编，服务端由 `NBC.Shared.csproj` 把**同一批文件** `<Compile Include>` 进去。

为什么条件系统要放这儿？因为 **M4 要在服务端校验任务进度**：

> 客户端说"我打了 3 只野狼"，服务端凭什么信？它得**自己**再算一遍。

如果条件逻辑只在客户端，服务端就只剩两条路：要么复制一份（**两份拷贝一定会漂移**，而漂移不报错），
要么相信客户端（**那就是作弊**）。放共享层之后，服务端拿到的是**同一个 `ConditionTracker`**。

📌 **代价也如实记**：共享层里不许有 `UnityEngine`、不许有浮点（D2 的确定性要求）、
不许有事件中心。所以条件系统只能对外暴露一个朴素的 `Notify(事件类型, 目标, 次数)` ——
"怎么从游戏事件翻译过来"就变成了客户端那边的一座桥（见 4.6）。

### 4.2 决定一：进度**钳位**，于是"达成只回调一次"不需要标志位

**钳位**是"封顶"的意思：进度最高就是需求值，不会涨到 5/3、100/3。

```csharp
// 需求 3，已经打了 2 只，又来 100 只
ConditionProgress after = new ConditionProgress(2 + 100, 3);
// 内部的钳位： Current 最终是 3，不是 102
```

不钳位的话会怎样？要判断"这次跨过线了吗"，你得额外存一个 `bool m_met`，
每次 `Notify` 都要读它、判断、再写它 —— **多一个状态，就多一个能不同步的地方**
（尤其是进度要存进数据库的时候：进度和标志位可能只写进去一个，
于是出现"进度满了但没解锁"这种查一天都查不出来的状态）。

钳位之后，判定变成一句纯算术：

```csharp
if (!before.IsMet && after.IsMet) { 回调一次 }
```

📌 **代价（如实记）**：钳位会**丢掉"超额完成"的信息**。
如果将来要做"击杀 10 只额外奖励"这种阶梯奖励，得另外记原始计数。
M2 没有这个需求，所以选简单的那个。

### 4.3 决定二：`resetProgress` 那个 bool，就是"任务"与"成就"的**唯一差别**

```csharp
public void Register(int conditionKey, ConditionDef def, bool resetProgress)
```

| 使用者 | 传什么 | 含义 |
| --- | --- | --- |
| **任务** | `true` | 接取时清零 → "**接了之后**打的怪才算" |
| **成就** | `false` | 保留既有进度 → "**一直**在算" |

⚠️ 这里有个**很容易漏掉的细节**，它是本轮最值钱的一条经验：

```csharp
if (resetProgress) { store.SetProgress(key, 0); return; }

// 不清零时：如果**本来就已经达成**，当场回调一次
int current = store.GetProgress(key);
if (current >= def.RequiredCount) { 回调(); }
```

为什么必须补这段？因为**成就的进度是要存库的**：

> 玩家昨天已经杀了 12 只怪（成就要求 10 只）。今天登录，注册成就条件时进度是 12/10。
> 如果不当场回调，玩家得**再杀一只**才会解锁成就。

现象是"成就解锁晚了一只怪"，看起来像玄学 —— 而原因只是"注册时没检查已达成"。
这条现在有专门的用例（`Register_WithoutReset_WhenAlreadyMet_FiresImmediately`）。

### 4.4 决定三：一次 `Notify` 只认"派发开始那一刻"的登记表

**契约**：回调里新登记的条件，**不会被这一次事件影响**。

```csharp
// 达成回调里接下一个任务
tracker.ConditionMet += (key, progress) =>
{
    if (key == 1) { tracker.Register(2, 下一个任务的条件, true); }
};
tracker.Notify(EConditionEvent.KillMonster, 6001, 1);
// 条件 2 的进度是 0，不是 1
```

不这么定会怎样？玩家**交完任务的同一只怪**会把刚接的新任务计上一次 ——
"我刚接的任务怎么就已经 1/3 了"，而且**只在这个顺序下复现**，几乎不可能靠手测抓到。
（这条和 A3 事件中心的"派发中增删监听"是**同一类语义**，本项目一贯是把它**写死成契约 + 用例钉住**。）

### 4.5 实现细节：为什么要"先收集、后派发"

`ConditionTracker.Notify` 分两段写，不是绕远路：

```
第一段：遍历登记表，只做"读 + 写进度"，把**恰好达成的**收集到一个小列表
第二段：遍历那个小列表，逐个回调 —— 此刻回调里增删登记表都安全
```

**理由是踩过的坑**：M1-C2 我写过"一边遍历诊断集合、一边调用渲染（渲染会动那个集合）"，
运行期直接抛 `Collection was modified`（`InvalidOperationException`）。
这里形状一模一样：达成回调里**很可能**去注销/登记别的条件
（交任务、接下一个任务、发奖励触发 `CollectItem` 再 `Notify` 一次）。

📌 顺带一个好习惯：**回调里能"再喂事件"也是被支持的**，而且有用例钉住
（`Callback_MayNotifyReentrantly`）—— 因为"发奖励 → 奖励里有物品 → 又是一次 CollectItem"
是真实会发生的链。

### 4.6 客户端这边：用"注册映射"的桥，而不是一个写死的 `switch`

```csharp
m_bridge = new ConditionEventBridge(m_tracker);
m_bridge.Bind<int>(BattleEvents.MonsterDied,          // 哪个事件
                   EConditionEvent.KillMonster,        // 算成哪种条件事件
                   monsterId => monsterId);            // 怎么从载荷里取"目标编号"
```

写成一个 `switch (eventId)` 也能跑，但每加一条链路都要改桥本身，
而"加链路的人"往往在做战斗、根本不知道任务模块在哪。改成注册映射之后：

- **生产事件的模块完全不知道任务存在**（它只管发自己的事件）
- 装配处写**一行**就接通一条新链路
- 桥本身对"有哪些事件"**零知识** —— 于是它不需要随着玩法长大而变

⚠️ 桥订阅了事件中心，所以**必须有人 `Dispose`**（A4/A8 那两轮反复踩的同一个坑：
订阅不退订 = 对象"死了"还在被回调）。有用例专门验 Dispose 之后不再转发。

### 4.7 任务运行时：两处刻意做成"全有或全无"

| 操作 | 顺序 | 不这么做会怎样 |
| --- | --- | --- |
| `Accept` | **先解析全部条件 → 再统一登记** | 否则"登记到第三条才发现表里没这行"，前两条已经留下 —— 一个**半接取**的任务：UI 上看不见它，它却在后台**悄悄累计进度** |
| `Submit` | **先查奖励表 → 再改状态** | 否则玩家处于"任务没了、奖励也没到"的状态（最气人的一类 bug） |

### 4.8 错误处理的分工：玩家能触发的 → 返回值 + 原因；程序错误 → 异常

```csharp
// 玩家点的按钮：失败是**正常业务流程**
public readonly struct QuestActionResult { public bool Ok; public string Reason; }

// 程序自己的 bug：越早炸越好，而且不该被 catch 掉当业务分支
throw new InvalidOperationException("条件 4001 已经登记过了，不能重复登记。");
```

而且被拒绝的原因**不只放在返回值里**，还会广播出去：

```csharp
EventCenter.Instance.Trigger(QuestEvents.Rejected, new QuestRejectedPayload(questId, reason));
```

**为什么**：调用方很可能是 UI，它多半只判了"成功/失败"就完事。
玩家点了按钮却什么都没发生，是最难排查的一类问题（"我点了呀" → "后台说不能点" →
中间**没有任何东西告诉玩家**）。广播出去，UI 就能把原因显示在玩家眼前 ——
这和 A9 那条"**让错误自己说出来**"是同一条原则。

### 4.9 配置表：第一次出现"`enum:` 指向共享层"

```csv
id,eventType,targetId,requiredCount,note
编号,事件类型（见 EConditionEvent）,目标编号（0 = 任意）,需要数量,说明
int,enum:NBC.Shared.Condition.EConditionEvent,int,int,string
key,,"min(0)","range(1,9999)","len(1,32)"
4001,KillMonster,6001,3,击杀野狼
```

三件事值得记：

| # | 事 | 为什么 |
| --- | --- | --- |
| 1 | 枚举类型名**可以带命名空间** | 条件系统住在共享层，而生成的配置类型在 `NBC.Game.Config` —— 不带命名空间找不到 |
| 2 | 生成的 C# 里是**全限定名** | `public NBC.Shared.Condition.EConditionEvent eventType;` 编译闸门（同时编 Shared 与 Game）真的编过 |
| 3 | 字段名**不能叫 `event`** | `event` 是 C# 关键字，`public E... event;` 直接编不过 → 本表用 `eventType`。**这类问题只有让编译器说话才会发现** |

✅ **加这 4 张表没有改一行工具代码**（含 `ConfigImporter`，它按 `<表>Config` 反射找类型）——
C 组做成通用工具链的回报在这里第一次兑现。

## ⑤ 自测 5 问（先自己答，再看折叠答案）

<details><summary><b>问 1</b>：为什么条件系统要放在共享层，而不是客户端？</summary>

因为 **M4 要在服务端校验任务进度**。客户端说"我打了 3 只野狼"，服务端不能信，
得自己再算一遍。共享层是"一份源码、双端都编"的地方（M1-D1），
服务端因此拿到的是**同一个 `ConditionTracker`**，而不是一份会漂移的拷贝。

代价：共享层不许碰 `UnityEngine`、不许有浮点，所以它只能暴露朴素的
`Notify(事件类型, 目标, 次数)` —— "怎么从游戏事件翻译过来"落在客户端那座桥上。
</details>

<details><summary><b>问 2</b>：进度为什么要钳位？不钳位会出什么问题？</summary>

钳位 = 进度封顶在需求值（最高 3/3，不会 102/3）。

不钳位的话，要判断"这一次有没有跨过线"，就得额外存一个 `bool m_met` 标志位。
**多一个状态就多一个能不同步的地方** —— 尤其进度要落库时，
"进度"和"标志位"可能只写进去一个，于是出现"进度满了但没解锁"。

钳位之后判定退化成纯算术：`!before.IsMet && after.IsMet` → 回调一次。
代价是丢掉"超额完成"的信息（阶梯奖励要用就得另记原始计数）。
</details>

<details><summary><b>问 3</b>：任务和成就共用条件系统，差别到底在哪一行代码？</summary>

就在 `Register(conditionKey, def, resetProgress)` 的**第三个参数**：

- 任务传 `true`（接取时清零 → 接了之后打的怪才算）
- 成就传 `false`（保留进度 → 一直在算）

⚠️ 还有一个配套细节：**传 `false` 且注册时就已经达成时，要当场回调一次**。
否则"昨天已经打了 12 只、今天登录"的成就得再打一只才解锁 —— 现象像玄学。
</details>

<details><summary><b>问 4</b>：`Accept` 为什么必须"先校验全部条件、再统一登记"？</summary>

否则会出现**半接取**的任务：条件是边解析边登记的，
如果登记到第三条才发现"条件表里没这行"，前两条已经留在条件系统里了。

那个任务的症状极难查：**UI 上看不见它**（状态没变成已接取、没进活动列表），
但它**在后台悄悄累计进度** —— 打怪的时候会涨。
</details>

<details><summary><b>问 5</b>：`ConditionEventBridge` 为什么用 `Bind<T>(...)` 注册映射，而不是一个 `switch`？</summary>

因为"加链路的人"往往在做战斗/背包，**根本不知道任务模块在哪**。
写死 `switch` 的话，每加一条链路都要改桥本身，桥就变成了"每个人都要动"的热点文件。

注册映射之后：生产事件的模块**完全不知道任务存在**（它只管发自己的事件），
装配处写一行就接通一条链路，桥本身对"有哪些事件"零知识。
</details>

| 3 | **负向对照**：把 `QuestCondition.csv` 里某个 `requiredCount` 改成 `0`，重跑导出 | 报错定位到**文件+表+行+列**，退出码 **2**，**一个文件都不产出** |

> （这也是 M1 里 W9 那条"验证器本身要先被验证"）。

## ⑦ 一分钟面试版（可以直接背）

> "M2 我做了任务系统，第一件事是**把它拆成两层**：
> **条件系统**只管'玩家做到了没有'（订阅事件 → 累加 → 判定达成），
> **任务系统**只管'该不该发奖'（接取 → 交付 → 发奖）。
>
> 这么拆的原因是 M4 要做成就，而成就和任务的中间那层**一模一样**，
> 只有两头不同：任务要'接取之后才计数'，成就'一直在算'。
> 所以我把这个差别收敛成 `Register` 的一个 `bool` 参数 —— 成就进来时不用写第二套逻辑。
>
> 第二个决定是条件系统放在**双端共享层**：因为任务进度在服务端要**重新校验一遍**
> （客户端说自己打完了不算数）。共享层是'一份源码、双端都编'，
> 服务端拿到的是同一个实现，不会漂移。
>
> 有三个语义是我刻意写死的：
> ① 进度**钳位** —— 于是'达成只回调一次'**不需要标志位**，少一个能不同步的状态；
> ② 注册时可以不清零，但**已达成要当场回调** —— 否则成就得等玩家再打一只才解锁；
> ③ 一次事件只认'派发开始那一刻'的登记表 —— 否则交完任务的同一只怪会算进刚接的新任务。
>
> 还有一处是我觉得最能体现工程习惯的：**Accept 和 Submit 都是全有或全无**。
> Accept 先把所有条件解析完再统一登记，避免'半接取'的任务（UI 看不见、后台却在涨进度）；
> Submit 先查奖励表再改状态，避免'任务没了、奖励也没到'。
>
> 最后，这一轮的验证我是'两条腿走路'：Unity 侧 489 条 EditMode 全绿；
> 另外写了个 **.NET 8 探针**把共享层的纯逻辑在**第二种运行时**上真跑一遍（22/22）——
> 因为'双端共享'这句话不能只靠声称。那个探针还当场抓出我自己写错的一个用例。"

## ⑧ 本轮踩的坑（**如实记，这一节比结论有用**）

### 坑 1 · 我的"阳性对照"自己红了 —— 而它暴露的是**检查器有个洞**

**现象**：负责人跑 Unity 得到 **488 绿 1 红**，红的是
`SharedConditionGeneralityTests.Checker_ActuallyDetectsBusinessWords`：

```
断言样例: "if (quest != null) { }"   ← 小写 quest
匹配逻辑: code.Contains("Quest")     ← 大小写敏感
Expected: True / But was: False
```

**最省事的修法**：把样例改成大写 `Quest`，一秒变绿。

**但那是个假绿**：真实检查（"共享层不许出现 Quest/Achievement"）改之前一直是**绿的**，
可它漏得掉 `questId` / `questRuntime` / `achievementOf` 这类**驼峰写法** ——
而那正是"通用层沾上业务词"最常见的形态。

**正解**：改**检查器**（大小写不敏感），并且让**真实检查和阳性对照走同一个函数**。
原先真实检查自己写了一份 `Contains`，两处规则不一致 ——
那才会出现"对照通过、真检查有洞"这种最难发现的情况。

📌 **这是本项目"机械检查"相关教训的第 7 次**，前 6 次都是"命中注释"。
这次是**新形态**：**只测了大小写一致的那一半**。
一句话总结：**阳性对照要覆盖"最可能漏掉的形态"，而不是最容易写的形态。**

### 坑 2 · 我写错的重入用例：看着在测重入，其实**空过**

```csharp
// ❌ 第一版
tracker.Register(1, new ConditionDef(CollectItem, 0, 1), true);
tracker.ConditionMet += (key, p) => { if (key == 1) { tracker.Notify(CollectItem, 7002, 1); } };
tracker.Notify(KillMonster, 6001, 1);   // ← 喂的是**另一个条件**的事件
```

条件 1 是"捡物品"，可我喂的是"击杀" —— 条件 1 **永远不会达成**，
回调永远不触发，于是"重入"这件事**一次都没发生过**，用例却会绿。

**谁抓到的**：`.NET 8` 探针（它在 Unity 之前先跑了一遍）。
修法是让回调里喂**另一个条件**关心的事件，并断言两条条件都达成。

📌 教训：**"回调里再喂事件"这类用例，要断言"重入真的发生了"**，
不能只断言"最后状态对"。

### 坑 3 · 同一份共享源码，两端的 nullable 规则不同

| 环境 | 可空引用类型 |
| --- | --- |
| Unity（`NBC.Shared.asmdef`） | **没开** |
| 服务端（`Server\Directory.Build.props`） | `<Nullable>enable</Nullable>` |

于是两头都不干净：服务端冒出一批 `CS86xx`；
而如果为了消警告去写 `string?` / `List<T>?`，**Unity 侧**又会因为
"可空注解出现在未开启可空上下文的文件里"报 `CS8632`。

**做法**：在这 6 个文件顶部显式写 `#nullable disable`，并注明理由 ——
**把环境差异钉死在一处**，让两端看到同一套规则。
（这正是 D1 那条"不许漂移"的同一条思路：漂移不报错，所以更要主动堵。）

### 坑 4 · csproj 注释里不能有**连续两个减号**（W1，第 2 次踩）

`Server\_condition-probe\ConditionProbe.csproj` 连报两次 `MSB4025`：

1. 第一版在 XML 注释里画了 `-----` 分隔线
2. 第二版写了 `dotnet` 命令，而命令的长开关（`--project`、`--no-build`）本身就是连续减号

**规矩收紧为**：csproj 注释里**一律不写命令行**，改去 md 里写。
（XML 注释里无法转义 `--`，所以这不是"注意点"，是**硬约束**。）
