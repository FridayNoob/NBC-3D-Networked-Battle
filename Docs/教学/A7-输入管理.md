## ① 问题是什么

玩家按下了 W。我们要让**服务端**知道这件事。

朴素做法：逻辑层直接读 `Input.GetKey(KeyCode.W)` 然后移动。这在单机没问题，在联网项目里必死，原因有两条：

1. **服务端没有键盘。** 它要重放你的操作，手里只能有"数据"。
2. **自动化测试按不了键盘。** `Input.GetKey` 依赖真实设备，你在跑测试时没法让它返回 true。

所以真正的问题不是"怎么读键盘"，而是：

> **怎么把键盘，变成一个可传输、可重放、可测试的值。**

## ② 最小例子

```csharp
// ❌ 逻辑层直接读设备 —— 不可传输、不可重放、不可测
if (UnityEngine.Input.GetKey(KeyCode.W))
    transform.position += forward * speed * Time.deltaTime;

// ✅ 采集 → 命令 → 逻辑层
var src = new LegacyInputSource();   // 设备相关，关在底层
src.Poll();
var cmd = new InputCommand(tick: 42, moveX: src.MoveX, moveY: src.MoveY, 0u, 0u);
// cmd 是纯数据：能发服务端、能存录像、能在测试里手写出来
Move(cmd.MoveY / 1000f);
```

一句话记住：**`int` 能过网线，`KeyCode` 不能。**

## ③ 原版错在哪（缺陷编号 P-14）

唐老师框架 `InputMgr.cs`，56 行，核心就这一句：

```csharp
private void CheckKeyCode(KeyCode key)          // 每帧被调 4 次（WASD）
{
    if (Input.GetKeyDown(key)) EventTrigger("某键按下", key);
    if (Input.GetKeyUp(key))   EventTrigger("某键抬起", key);
}
```

三个病，而且**全都不报错**：

1. **每帧 8 次 `Input.GetKey*`**（4 键 × 2），扫的是一组写死的键。你想加一个技能键？改框架。
2. **无条件发事件** —— 一个监听者都没有的时候，字典查找和委托链照样白跑一遍。而且工具选错了：每帧一条的**命令是数据**，不是"低频的游戏事件"。
3. **事件名是硬编码中文字符串**（FW-12）。`EventTrigger("某键按下")` 打错一个字，静默不触发。

还有第 4 条，文档里没写但我认为是根子：**它把"读设备"和"想做什么"焊死在一起了。** 正因为焊死了，所以它既发不给服务端，也测不了。

## ④ 重写

拆成三层，每层只干一件事。

### 第一层 `IInputSource` —— 采集，设备相关

```csharp
void Poll();
int  MoveX { get; }                     // -1000..1000
int  MoveY { get; }
bool WasActionPressed(InputActionId a); // 本帧刚按下
bool WasActionReleased(InputActionId a);// 本帧刚松开
bool IsActionHeld(InputActionId a);     // 持续按住
```

注意：**接口里一个 `KeyCode` 都不出现。** 这是整个抽象的成败点 —— 一旦接口里冒出 `KeyCode`，这个抽象就是假的，将来换新输入系统还是得改接口。

### 第二层 `LegacyInputSource` —— 唯一的设备实现

`KeyCode` 全部关在这个类里。看它的按键查询是怎么写的：

```csharp
public bool WasActionPressed(InputActionId action)
{
    KeyCode key;
    return m_mapping.TryGetKey(action, out key) && UnityEngine.Input.GetKeyDown(key);
}
```

`TryGetKey` 失败就直接 false，**根本不查键**。这个短路不是微优化，它让"没绑定的动作"零成本。

### 第三层 `InputManager` —— 生成命令，设备无关

```csharp
public InputCommand Tick(int tick)     // 签名就是设计
```

为什么是 `Tick(int tick)` 而不是协程、不是 `Update`？和 A5 的 `SceneLoader` 完全是同一个理由：**帧号变成了注入的参数**。测试里直接 `Tick(1)`、`Tick(2)`，不需要真实帧、不需要真键盘。**真按键在自动化测试里造不出来，注入一个假 `IInputSource` 可以。**

然后是三条关键设计决定，每条我都告诉你"不这么做会怎样"。

**(a) 移动轴量化成整数 `[-1000, 1000]`，不是 float。**

浮点在不同平台 / AOT 下不保证一致，而且**序列化后不是精确相等的**。`InputCommand.Equals` 是逐字段比较 —— 靠这个才能断言"同样的按键产生同样的命令"。摇杆本来是模拟量？量化到 8~16 位是真实联机游戏的常规做法。（M4 帧同步若需要更强一致性会换自研定点数 `Fix64`，但"量化整数"这条思路不变。）

**(b) 命令同时带"按下边沿"和"抬起边沿"。**

```csharp
public readonly uint ActionBits;         // 本帧新按下
public readonly uint ActionReleaseBits;  // 本帧新松开
```

只发"按下"是一种**很常见的偷懒**，后果是逻辑层不知道玩家什么时候松手 —— 表现就是**"松手了还在开火"**。两条边沿都有，逻辑层才能精确重建持续状态：

```
held = held | pressed;    // 记下新按下的
held = held & ~released;  // 抹掉松开的
```

**(c) 只查"游戏显式登记过的动作"。**

这是 P-14 的直接修法。原版扫 4 个写死的键、调 8 次 `GetKey`；现在只问游戏真正关心的动作。这条有专门的测试 `Tick_OnlyQueriesTrackedActions` 和 `Tick_QueriesScaleWithTrackedActions_NotWithAHardcodedKeyList` —— 拿假源**数调用次数**来断言，而不是看结果对不对。因为"结果对"可能只是碰巧对。

### 两个必须写死的边界，不能靠猜

- **`Pause()` 的确切语义**：不查任何键 + 产出**空命令**写进 `Current`（这样网络层按 tick 轮询时时序不会错位）+ **不触发** `CommandGenerated`。三条各有测试。
- **框架只给 WASD 默认值，不给动作绑定。** "技能1 = 哪个键"是**游戏层**概念。框架里写死就等于把业务烧进框架 —— 那正是 FW-12 要修的病。⚠️ 但注意：**有默认值 ≠ 硬编码**，关键是**能不能被覆盖**。原版把 WASD 烧在 `CheckKeyCode` 里，连覆盖的机会都没给。

### 附带一个 `InputActionId`

和 A3 的 `EventId` 同款写法 —— 私有构造 + `Declare(index, name)`：

- 索引是**稠密的 0..31**，因为命令用 32 位掩码表示动作。
- 两个动作抢同一个索引 → 在**声明处**抛异常，而不是运行期才发现"按技能1 触发了技能2"。
- ⚠️ `default(InputActionId).Index == 0`，所以**不能用 `default` 当"无动作"哨兵**。这条也有专门测试。

## ⑤ 自测 5 题

先自己想，答案在下面。

1. 逻辑层为什么不能直接 `Input.GetKey`？说两条，第二条要和"测试"有关。
2. `MoveX` 为什么是 `int` 而不是 `float`？如果做成 float，**最先坏掉的是哪个断言**？
3. 命令里为什么必须同时有 `ActionBits` 和 `ActionReleaseBits`？只留前者，玩家会看到什么现象？
4. 如果往 `IInputSource` 里加一个 `KeyCode CurrentKey { get; }`，A7 这个设计还剩多少价值？
5. `Pause()` 之后 `Current` 是空命令但**不发** `CommandGenerated` —— 为什么不干脆什么都不做（连 `Current` 也不更新）？

<details>
<summary>点开看答案</summary>

1. ① 服务端没有键盘，`GetKey` 是设备查询不是数据；② 自动化测试造不出真按键。
2. 浮点跨平台序列化不是精确相等 → `InputCommand.Equals`（逐字段比较）这个断言最先坏。
3. 只留按下 → 逻辑层不知道松手 → **"松手了还在开火"**。重建持续状态必须两条边沿。
4. 那个抽象基本废了 —— 换新输入系统还得改接口，等于没抽象。`KeyCode` 必须留在实现侧。
5. 网络层是**按 tick 轮询** `Current` 的。不更新的话，禁用期间 `Current` 停在禁用前那一帧，网络层会把**旧命令反复当成新命令**发出去 → 时序错位。

</details>

## ⑦ 一分钟面试版

> 输入层我做了"采集"和"命令"的分离。采集是 `IInputSource`，接口里**不出现任何 `KeyCode`**，旧输入系统的实现把键位映射关在自己内部 —— 将来换 Unity 新输入系统只需要新写一个实现类，上层一行不改。
>
> 命令是 `InputCommand`，纯值类型：帧号 + 量化成整数的移动轴 + 按下位掩码 + 抬起位掩码。轴用整数是因为浮点跨平台序列化不保证精确相等，而联机要求"同样的输入序列得到同样的结果"。
>
> 生成命令的是 `InputManager.Tick(int tick)`，不是协程 —— 帧号是注入的参数，测试里注入假 `IInputSource` 就能断言"按下技能键 → 命令第 N 位为 1"，不需要真键盘。
>
> 我改掉的原版问题是：它每帧对 4 个写死的键调 8 次 `GetKey`，然后**无条件**发中文字符串事件。现在只查游戏显式登记过的动作，而且每帧的命令**不走事件中心** —— 事件中心是给低频"游戏事件"的工具，命令是数据。

## 附：本节出现的术语速查

| 术语 | 一句白话 |
| --- | --- |
| **采集层 / 命令层** | 采集层问"键盘现在什么状态"（设备相关）；命令层答"这一帧玩家想做什么"（设备无关，可发服务端） |
| **量化整数** | 把 -1..+1 的模拟轴乘 1000 存成 `int`，避开浮点跨平台不一致 |
| **边沿（edge）** | "这一帧刚发生变化"的事件：按下边沿 / 抬起边沿。区别于"当前是否按住"的状态 |
| **稠密索引** | 0,1,2,3… 中间不留空，因为位掩码需要连续的位号 |
| **位掩码（bit mask）** | 用一个 `uint` 的第 i 位表示"第 i 个动作本帧发生了"，一次比较代替 32 次遍历 |
| **帧号（tick）** | 逻辑帧的编号。命令带上它，服务端才能知道这条命令属于哪一帧 |
