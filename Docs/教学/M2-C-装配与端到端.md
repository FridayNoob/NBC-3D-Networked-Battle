## ① 问题是什么（不用代码）

M2 前两块（条件/任务、战斗）各自都能测了，但**没人把它们接起来**。这一轮要回答的是：

> **"玩家按下 J 之后，一直到最后奖励到账"，这条链上每一环由谁负责？**

这条链一共六站：

```
按下 J
  → 输入命令（A7，做成可传输的值）
  → 翻译成"放哪个技能"（SkillCaster）
  → 技能结算（BattleWorld：查表、命中、扣血、广播）
  → 事件桥把它变成"条件事件"（ConditionEventBridge）
  → 条件累加（ConditionTracker）
  → 任务状态变化 + 发奖（QuestRuntime → IQuestRewardSink）
```

每一站都有主人。**但"谁按什么顺序把它们造出来、谁把线接上"——没有人管。**

这件事有个名字：**装配（composition）**。它极易被忽略，因为"接起来"听起来不像"功能"。
可一旦没有它，你会得到一堆各自测得很绿的模块，**合起来按不动**。

## ④ 做法与关键决定

### 4.1 `AssetConfigSource`：M1-C4 那道缝的**兑现**

M1-C4 里 `ConfigMgr` 只定义了接缝，并写明：

> "真正的实现（走资源层）等打包做完再接，**一行都不用改 `ConfigMgr`**"

这个文件就是那次兑现——**`ConfigMgr` 确实一行都没改**（`git log` 可对）。四个要点：

| # | 选择 | 理由 |
| --- | --- | --- |
| 1 | 只用框架的 `AssetManager` 接缝，**不认识第三方** | 所以它住在 `NBC.Game`；三层各管一段：`NBC.Boot` 装加载器、本文件把表名翻译成地址、`ConfigMgr` 管缓存与查询 |
| 2 | 用**异步**（`LoadAssetAsync`）而不是受限的同步接口 | 同步接口在播放模式下会打警告（ADR-001 决策 5）；启动时一次加载 7 张表正是最不该阻塞主线程的一段，而 `IConfigSource` 本来就是回调式 → **用异步零成本** |
| 3 | 判成功用 **`IsValid`**（成功 && 资产非 null），**不看句柄是不是 null** | M1-B5 我把"句柄非 null 但资产为 null"报成过 ✅。框架已把这个教训写进属性 |
| 4 | 句柄**一直持有、不 Dispose** | 配置表进程内常驻；这是**有意为之**，不是漏了。将来做热重载时才需要真释放路径 |

⚠️ 还有一条是**排查方向**问题：没装底层加载器时，报错必须指向"**组合根没跑**"，
而不是"表不存在"——这两件事的排查方向完全相反。这条现在有用例盯着。

### 4.2 `GameTables`：**"这个游戏要哪几张表"的唯一清单**

`ConfigMgr` 的语义是"同步查表 + 启动预加载"，所以启动时必须有人把表读进来 ——
而那个人需要知道**到底要几张**。散在启动流程里的后果：

> M3 加了 `Dungeon` 表 → 忘了改启动流程 → **忘了不报错** →
> 直到某个功能第一次用到那张表才炸（而那时你早忘了自己加过表）

抽成一份清单之后，加表改一处，而且**它本身就是"这个游戏有哪些表"的文档**。

### 4.3 `BattleSession`：装配层，**不含任何逻辑**

判据一句话：

> **这个类里出现任何"判断"或"计算"，就说明它放错了地方。**

它只做三件事：① 按依赖顺序造对象 ② 把事件桥接上 ③ 给调用方一层门面
（接任务 / 进关卡 / 放技能 / 交任务）。

**为什么是纯 C# 类而不是 MonoBehaviour**：因为整条闭环要能在 EditMode 里跑。
MonoBehaviour 那侧（读键盘、`OnGUI` 画状态）是**另一件事**，
两者分开之后，"闭环对不对"和"能不能点着玩"变成两个可以各自验证的东西。

⚠️ 一个刻意的简化：**目标选择是"打第一只活着的怪"**（没有点选/锁定 UI），
并且立了一条不变量：**`CurrentTargetInstanceId` 要么是 0，要么指向一只活怪**。
（这条是**被一条红逼出来的**：原来打完不换目标，UI 会显示一个已经不在场上的目标。）

### 4.4 演示壳子为什么在 `NBC.Boot`（**编译不过才想明白**）

我原打算把 `M2DemoBehaviour` 放 `NBC.Game`，**编译不过**：它要调 `AssetBootstrapper`，
而程序集依赖是单向的：

```
NBC.Boot  →  NBC.Framework.YooAsset / NBC.Framework / NBC.Game
```

`NBC.Game` 想用 `AssetBootstrapper` 就是**反向依赖 + 循环引用**。

**这不是妥协，而是分层本来就该这样**：**"把谁装到谁身上"是组合根的活**，
`NBC.Game` 里只有业务逻辑。壳子只干三件"只有 Unity 才能干"的事：
按时机跑异步装配、每帧喂输入、把状态画出来。

### 4.5 本轮新加的两道"过期检查"（**都是被坑出来的**，见 §⑧）

| 检查 | 在哪 | 查什么 |
| --- | --- | --- |
| **配置资产过期** | `Editor\ConfigStalenessCheck.cs`（新菜单） | 逐表比 `.tsv` 与 `<表>Config.asset` 的 mtime，报「最新 / 过期 / 缺资产」 |
| **演示数据预检** | `M2DemoBehaviour.VerifyConfiguredIds` | 启动时把要用的 id 全查一遍（英雄/技能/怪/任务/奖励），缺哪个就**当场说清 + 给两步处理办法** |

差别要说清：前者查**文件时间**（只在编辑器里有意义，且是启发式）；
后者查**数据**（**打包后的 Player 里也有效**）。两个都要。

## ⑤ 自测 5 问（先自己答，再看折叠答案）

<details><summary><b>问 1</b>：为什么"装配"要单独一层，散在 MonoBehaviour 的 <code>Start</code> 里不行吗？</summary>

短期行，长期不行。三个理由：

1. **漏接一根线不报错**：少一行 `Bind` 只是"某个功能静默不生效"，而那是最难查的一类问题
2. **没法在 EditMode 测整条闭环**：MonoBehaviour 需要帧循环、需要键盘、需要场景
3. **逻辑会顺着这里长出来**：一旦装配和逻辑混在一个 `Start` 里，下一个改动者就会在里面加 `if`

判据：**装配层里出现"判断/计算"就是放错了地方。**
</details>

<details><summary><b>问 2</b>：为什么 <code>AssetConfigSource</code> 用异步，而不用那个"同步加载"接口？</summary>

因为 `AssetManager.LoadAsset<T>` 是**受限接口**（ADR-001 决策 5）：它阻塞主线程，
播放模式下还会打警告，只该用于编辑器工具或极小资源。

配置表虽然小，但**启动时一次要读 7 张**，正是最不该阻塞的一段；
而 `IConfigSource` 的接口本来就是回调式的（成功/失败各一个回调），
所以用异步**零成本**。
</details>

<details><summary><b>问 3</b>：端到端用例里为什么特别强调"没有一句手搓的 <code>Notify</code>"？</summary>

因为"条件系统能累加进度"和"**真实游戏事件能驱动条件系统**"是两件事。

如果端到端用例里手搓 `Notify(KillMonster, 6001, 1)`，它验的就只是"条件系统 + 任务运行时"，
而**接线那一半（事件桥）根本没被测**——恰恰那一半最容易漏（少 Bind 一行，什么都不报）。

现在进度来自 `BattleEvents.MonsterDied` 与 `WorldEvents.AreaEntered` 两个**真事件**，
所以用例红了能指向接线，而不只是逻辑。
</details>

<details><summary><b>问 4</b>：`ConfigStalenessCheck` 比文件时间，这个判据有什么问题？</summary>

它是**启发式**，两个方向都有边界（已写在文件头）：

- **假阳性**：碰一下 TSV 但内容没变，也会被报成"过期"（无害，点一下导入就好）
- **假阴性**：手工改过 `.asset` 而源表没动，**查不出来**（那种情况只能看 Git diff）

第一次真跑就撞上了假阳性：7 张表全报过期，其中只有 `Quest`/`QuestCondition`
内容真的变了，其余 6 张只是"被重写过、内容没变"。

📌 所以它**不是精确工具**，作用只是"**让一个静默的坑变得看得见**"——
而且它给的动作（全部重新导入一遍）是**正确的**。
</details>

<details><summary><b>问 5</b>：为什么"演示数据预检"查数据，而"过期检查"查文件时间？两者不能合并吗？</summary>

不能，它们**运行环境不同**：

- 过期检查跑在**编辑器**里：能看到 `Assets/` 下的 `.tsv` 文件，所以能比时间
- 数据预检跑在**运行时**：打包之后 `.tsv` 根本不在包里，只能查"资产里有没有这个 id"

而且数据预检**更直接**：它问的是"我需要的那个 id 在不在"，
而不是"文件时间对不对"（后者只是前者的一个间接信号）。
</details>

## ⑧ 本轮踩的四道坎（**这一节比结论有用**）

### 坎 1 · 我把 `Simulate Package Root` 默认成空串，而代码和提示自相矛盾

**现象**：Play 后报 `[YooAssetProvider] 编辑器模拟模式必须提供模拟清单目录`。

**两层原因**：
1. 字段默认空串，而**底层报错只说"必须提供目录"，没说怎么弄出那个目录**
2. 我的提示写着"留空表示用默认"，而代码对空串直接 `return string.Empty` —— **提示说 A、代码做 B**

📌 这是本里程碑**第二次**同一类错误（上一次是 `SkillCaster.Bind` 注释说"装配时就报错"却只查了一半）。
**注释写着 A、代码做的是 B，比没有注释更危险** —— 它会让后来的人相信那句话，不再读代码。

### 坎 2 · **"读了源码"还不够，要读对代码路径**（本轮最值钱的一条）

我上一版把约定路径写成 `Bundles/<平台>/<包名>/Simulate`，依据是源码里
`BundleSimulateBuilder.SimulateBuild` 写死 `PackageVersion = "Simulate"`。

**但窗口走的是另一条路**：`EditorSimulateBuildPipelineViewer.ExecuteBuild` 用的是
`buildParameters.PackageVersion = _buildVersionField.value` ——也就是**窗口上那个"构建版本"文本框**
（默认日期时间串），于是输出是 `.../2026-09-23-833/`。而 `BundleSimulateBuilder`
**只有运行时反射入口会调**（`EditorSimulateBuildInvoker`），窗口根本不碰它。

**证据链**：`OutputCache/buildInfo.log` 里 `pipeline 'EditorSimulateBuildPipeline'` +
`Create package manifest file: '.../2026-09-23-833/...'`；两个入口的源码对照。

> 📌 **同一个功能有两个入口时，只读其中一个就会得出一个"看起来有据可查"的错结论。**
> 所以改法不是"把路径写对"，而是**别让人填**：留空就自动挑最新的一份清单，
> 并且把"用的是哪一份、什么时候建的"打出来。

### 坎 3 · 配置资产是**旧快照**，而"忘了点导入菜单"不报错

**现象**：`配置表 Quest 里没有任务 3004`。

**硬证据**：3004 在资产里出现 **0 次**；资产 mtime `09/22 23:30`，而 TSV mtime `09/23 13:20`。

配置表流水线是**两步、第二步要人手点**：

```
CSV →[ConfigKit.Cli]→ TSV/.cs →[Tools/NBC/配置表/导入 TSV → SO]→ <表>Config.asset
```

而"忘了点第二步"**不报任何错**：`ConfigMgr` 照样能加载、照样能查表，只是那份资产是旧的。

📌 **和坎 1 是同一个形状**：**"手工步骤 + 没有提示" = 一定会在某天以别的 bug 的面目出现。**
（坎 1 的模拟清单也是"快照"。）

**改法**：加了过期检查菜单（编辑器）+ 数据预检（运行时），并把失败形状
从"运行到一半才炸"改成"**启动就说清 + 给两步处理办法**"。

### 坎 4 · 导入菜单**随机挑错类型**（一个不确定性 bug）

**现象**：报 `HeroConfig 上没有 LoadFromTsv(string)`，还建议我重跑 ConfigKit（**把人带偏了**）。

**线索就在现象里**：**只有 `HeroConfig` / `SkillConfig` 失败**，另外 5 张都成功 —— 为什么正好这两个？

因为工程里有**两个**同名类型：

| 类型 | 有没有 `LoadFromTsv` |
| --- | --- |
| `NBC.Game.Config.HeroConfig`（生成物） | ✅ |
| `NBC.Tests.EditMode.ConfigMgrTests+HeroConfig`（测试假类型） | ❌ |

而 `FindType` 的判据是"**任意已加载程序集里第一个**同名且是 ScriptableObject 的类型"——
测试程序集在编辑器里是加载着的，`GetAssemblies()` 顺序不保证 → **随机**。

**改法**：判据收紧为"名字像 **且** 真的有 `LoadFromTsv(string)`"（那正是导入器需要的东西）；
多个候选就**报歧义不猜**；一个可导入的都没有时把"同名但不可导入"的**列出来**。
顺带删掉了 `ImportOne` 里那段"再判一次 `load == null`"——判据已在筛选时用过，
再判就是**永远走不到的分支**。
