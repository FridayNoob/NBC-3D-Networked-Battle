# ① 问题是什么

游戏要加载资源：模型、贴图、音效、场景。原框架用一个 `ResMgr`：

```csharp
public T Load<T>(string name) where T : Object
{
    return Resources.Load<T>(name);
}
```

`Resources` 是 Unity 最省事的加载方式。**但这个项目不能用它**，原因有两条：

**① 直接违反需求 5（热更新）。**
`Resources` 目录下的东西在**打包时被固化进包体**，不能增量下发。
想改一个数值、换一张图，就得**重新出一个整包** —— 对联网游戏是不可接受的。

**② 框架层无法按需卸载单个资源。**
（这里要说准确，不能夸大：对 `GameObject` 它返回的是 `Instantiate` 出来的实例，
调用方可以销毁实例；对 `TextAsset`/`AudioClip` 它返回的是**共享资源**，
而框架**不持任何引用计数**、也**从不调 `Resources.UnloadAsset`**。
所以准确说法是：**框架层无法卸载单个资源**，只能靠 `Resources.UnloadUnusedAssets` 这种
**全局**兜底 —— 代价是全场景扫描。）

> **一句话**：`Resources` 不是"写错了"，而是"**目标不匹配**"。
> 教学框架定位是单机小游戏，`Resources` 是最省事的选择；本项目要求 AB + 热更。

# ② 最小例子

```csharp
// 三种消费方式，**同一个对象**（不是三套 API）
AssetHandle<Sprite> handle = AssetManager.Instance.LoadAssetAsync<Sprite>("UI/Icon_HP");

handle.OnComplete += h => image.sprite = h.Asset;   // ① 回调
if (handle.IsDone) { ... }                          // ② 轮询
Sprite s = await handle;                            // ③ await

handle.Dispose();                                   // 用完释放（引用计数 -1）
```

**为什么三种都要有？** 因为调用场景不同：UI 代码喜欢回调、帧驱动逻辑适合轮询、
流程编排用 `await` 最清楚。**但如果做成三套 API，就会有三种用法要维护、三处会不一致。**
所以做成"一个对象、三种读法"。

# ④ 做法

## 4.1 ADR-001 的核心：**依赖倒置**

```
NBC.Framework        ← 定义 IAssetProvider / IAssetLoadOperation / ISceneLoadOperation
    ↑                （框架**一个 YooAsset 类型都不认识**）
NBC.Framework.YooAsset  ← 唯一引用 YooAsset 的程序集（适配层）
    ↑
    NBC.Game         ← 业务只认识 AssetManager
```

三个关键点：

**① 框架侧只定义"接口"，不定义"实现"。**
`IAssetProvider` 就是那道缝。换资源方案（YooAsset → Addressables → 自研）时，
只需**新写一个实现类**，上层一行不改。

**② 适配层独立成一个程序集。**
`NBC.Framework.YooAsset` 是全工程**唯一**引用 YooAsset 的地方。
换方案时**删掉这一个程序集**就行。

**③ `NBC.Framework` 的 `references` 必须为空**，有测试机械保证。

> ⚠️ 这条守卫是被"加强"过两次的：
> 最初只断言"`NBC.Framework` 不引用 **`NBC.*`**" —— 但 `YooAsset` 不是 `NBC.*`，
> 也就是说**把 YooAsset 塞进 Framework，那条测试照样是绿的**。
> 后来改成"**必须为空**"（底座不依赖任何东西，含第三方）。

> 📌 这个思路在 A9 又用了一次：UI 需要 UGUI，而 UGUI 必须显式引用。
> 为了**不动这条守卫**，UI 单独成了 `NBC.Framework.UI` 程序集（`Docs\02` 决策 7）。
> **"不许为了让自己代码过而改守卫"** —— 这是那条自律的第一次实践。

## 4.2 可测性红利：为什么这层能在 EditMode 里测透

`AssetManager` 的全部逻辑（缓存、引用计数、释放）都在框架侧，
**它只通过 `IAssetProvider` 跟外面打交道**。

于是测试里塞一个**假加载器**就能：

- **精确控制**"什么时候加载完、加载到什么、什么时候失败"
- 断言引用计数、缓存命中、释放时机 —— 全都**确定、不 flaky**
- **完全不需要 YooAsset、不需要打包**

> **这就是"依赖倒置"不只是架构好看的证据**：
> 21 条 EditMode 测试**一条都不需要真实的资源系统**。
> （对比：如果没有这道缝，这些测试全得进 PlayMode 真打包，慢而且不稳。）

## 4.3 三级释放（ADR-001 决策 1）

```csharp
public void Dispose();          // ① 引用计数 -1（只减不释放）
public int ReleaseUnused();     // ② 把计数为 0 的条目真正放掉
public void UnloadAll();        // ③ 全放（切游戏模式 / 退出时）
```

**为什么 `Dispose` 不立刻释放？**
因为同一次加载可能被多个地方用（缓存命中时计数会到 2、3…）。
立刻放掉的话，第二个使用者手里就成了死引用。

**为什么要有 `ReleaseUnused` 这个独立入口？**
因为"什么时候集中清理"是个**策略问题**，不该由每次 `Dispose` 决定。
比如"切场景后统一清一次"是合理的；"每帧清一次"是浪费。

## 4.4 ⚠️ 一处**有意偏离**原框架：不再自动实例化 GameObject

原框架有个**隐式契约**：`Load<GameObject>` 返回的是**实例**（内部替你 `Instantiate` 了）。

**本项目不复刻它**：`LoadAssetAsync<GameObject>` 返回**原始 prefab**，要实例请自己 `Instantiate`。

**判定依据**：

| 问题 | 结论 |
| --- | --- |
| 那 6 个调用点在哪？ | 全在**我们正在重写的模块**里（A2 已完成、A8/A9 已完成）——**没有兼容包袱** |
| 哪边更好？ | 显式 `Instantiate` 更清楚，而且**能和对象池配合**：`new GameObjectPool("Bullet", () => Object.Instantiate(prefab), 64)` —— 池本来就通过工厂拿对象，正好对上 |
| 隐式实例化的坏处？ | "我加载了个预制体"和"我创建了个实例"是两件事，混在一起会让人误以为拿到了共享资源 |

> ⚠️ 这是**明说出来的偏离**，写在 `Docs\06` §13.7 和 §6.2 的更正里。

## 4.5 不做 `Resources` 兜底

`FW-M05` 的措辞里有"`Resources` 兜底"。

**本项目不做。** 理由：兜底会让"资源没打进去"这种真问题**在开发期被掩盖**，
到了线上（没有 `Resources` 目录）才爆。**宁可开发期就红。**

（这条也是**经批准**的偏离。）

## 4.6 同步加载保留但受限

同步加载在编辑器里很常用（工具、测试），但**在 Player 里调用会打警告**。
因为同步加载会**卡住主线程**，移动端上几 MB 的包就是明显的卡顿。

# ⑤ B3：那段三轮才对上的排错过程（**这一节最值钱**）

B3 是"把 YooAsset 真的跑起来"。冒烟测试第一次跑：**3 条里 2 条红**。
最后是**第三轮才对**。中间两次的结论都被推翻了 —— 过程比结果更有教育意义。

## 第一轮：表象是"静默 no-op"

```
Resource package 'DefaultPackage' is already initialized.
  at YooAsset.ResourcePackage.InitializePackageAsync (ResourcePackage.cs:101)
```

当时看到 TearDown 里"先 `ResetAll()` 再 `ShutdownInstalled()`" ——
**通过单例去找加载器时它已经没了** → `ShutdownInstalled()` 变成**静默 no-op**（什么都没做）→
下一个用例撞上"already initialized"。

**第一轮的结论：修 TearDown 顺序。** ❌ **这个结论后来被推翻了。**

## 第二轮：顺序修好了，暴露出更深的问题

修好顺序之后，出现了新错误：

```
YooPackageInvalidException: Active package manifest not found
  at YooAsset.ResourcePackage (ResourcePackage.cs:1002)
```

现象很怪：`InitializeStatus == Succeeded`，但 `ActiveManifest == null` —— **状态是"成功"，但东西不在**。

**第二轮的结论：`YooAssets.Destroy()` 之后重新初始化会得到畸形状态，所以不要销毁。**
（方向对了，但**根因还没找到**。）

## 第三轮：真正的根因 —— **v3 的初始化是三段式**

去读 YooAsset 源码，才明白：

| 你调的方法 | 它实际做了什么 |
| --- | --- |
| `InitializePackageAsync` | **只建文件系统**（内部步骤：`SetPlayMode → CheckOptions → CreateCore → InitFileSystem → Done`）——**不加载清单** |

而 `SetActiveManifest`（把清单设为"当前生效的"）**全局只有一个调用点**：

```
LoadPackageManifestOperation.cs:91
```

**也就是说：不调 `LoadPackageManifestAsync`，清单永远不会被设上，
`ActiveManifest` 永远是 null —— 哪怕 `InitializeStatus` 是 Succeeded。**

**修法**：初始化补上后两步：

```csharp
await package.InitializePackageAsync(options);                    // ① 建文件系统
string version = await package.RequestPackageVersionAsync();       // ② 问版本
await package.LoadPackageManifestAsync(                            // ③ 加载清单 ← 关键
    new LoadPackageManifestOptions(version, 60));
```

再顺手做两件事：
1. **`InitializeAsync` 改为幂等**（已经初始化成功的包直接复用）
2. 测试之间**不再销毁资源系统**（它是**进程级子系统**，本来就不该每个用例拆掉重建）

**结果：PlayMode 41/41 全绿，而且编辑器模拟模式下真的加载到资源并断言了内容。**

## ⚠️ 从这三轮里提炼的两条

### 教训 1：**看到"某样东西是 null"，第一反应该是"谁负责把它设上"**

前两轮我一直在问"**我哪里把它弄丢了**"。
但正确的问题是：

> **`ActiveManifest` 是谁负责设的？它什么时候被调？**

一旦这么问，去源码里搜 `SetActiveManifest`，**立刻**就找到了 —— 只有一个调用点。
**"我弄丢了什么"是个死胡同；"谁负责设它"才能定位到根因。**

### 教训 2：**每次都要重新读错误信息，不要套用上次的结论**

第二轮的错误和第一轮**不是同一个问题**。
如果我还按"哦这是那个 TearDown 顺序问题"去想，就会在错误的方向上继续折腾。

> **每一条新的错误信息都要当成新信息去读**，而不是"我见过类似的，应该还是那个原因"。

### 教训 3（关于测试）：**进程级子系统不该每个用例拆掉重建**

`YooAssets` 是**进程级**的（全局单例、有自己的线程/状态）。
把它当成"每个用例都要重置的东西"，本身就是个错误前提 ——
这跟 A1 的"EditMode 不调 `Awake`"有点像：**你对被测对象的生命周期假设错了**，
后面所有现象都会很怪。

# ⑥ 一个必须记住的 YooAsset v3 事实

**装的 3.0.5 是重构过的 v3 API。**

网上和教程里大量的 v2.3 写法（`InitializeAsync` / `EditorSimulateModeParameters` / `RawFileHandle`）
在 3.0.5 里被 `#if YOOASSET_LEGACY_API` 包着，**默认不参与编译**。

也就是说：**照 v2.3 教程写，压根编译不过。**

> 📌 这一条**编译闸门会当场挡住**：闸门引用了真实的 `YooAsset.dll`，
> 于是"v3 的类型名/成员名到底叫什么"由**编译器**来回答，不用开 Unity 试。
> 这是本项目最有价值的一次闸门扩展。

另外两条容易踩的：

| 事实 | 说明 |
| --- | --- |
| `Dispose()` == `Release()` | YooAsset 里 `Dispose()` 的实现就是调 `Release()` —— **两个都调等于释放两次** |
| `await handle` 是合法的 | `AsyncOperationBase.GetAwaiter()` 返回**公开的** `OperationAwaiter` 结构，所以跨程序集 `await` 没问题 |

# ⑦ 自测 5 题

**1.** 为什么不能用 `Resources`？说两条。
**2.** 为什么适配层要**单独一个程序集**？
**3.** `Dispose()` 为什么不立刻释放资源？
**4.** 看到 `ActiveManifest` 是 null，正确的第一个问题是什么？
**5.** 为什么"两边各写一份资源加载代码"不行，而"依赖倒置"行？

<details>
<summary>点开看答案</summary>

**1.** ① `Resources` 的内容打包时固化，**不能热更**（直接违反需求 5）；
   ② 框架层**无法按需卸载单个资源**（它不持引用计数、从不 `UnloadAsset`），只能全局兜底。

**2.** 因为它是**全工程唯一引用 YooAsset 的地方**。换资源方案时**删掉这一个程序集**即可，
   `NBC.Framework` 保持零依赖（有测试机械保证）。

**3.** 因为同一个资源可能被多个地方用（缓存命中时计数会到 2、3…）。
   立刻放掉的话，第二个使用者手里就成了死引用。
   "什么时候集中清理"是**策略问题**，所以留了独立的 `ReleaseUnused()`。

**4.** **"`ActiveManifest` 是谁负责设上的？它什么时候被调？"**
   —— 而不是"我哪里把它弄丢了"。
   去源码搜 `SetActiveManifest`，立刻发现只有一个调用点（在 `LoadPackageManifestOperation` 里），
   于是根因（初始化是三段式，少调了第三步）就出来了。

**5.** 因为"各写一份"意味着**两个实现都要维护**，而且行为会慢慢分叉。
   依赖倒置是"**一份接口 + 一个可替换的实现**"：换的时候是**替换**，不是**并存**。
</details>

# ⑧ 一分钟面试版

> 资源层我用的是 YooAsset，但**框架侧一个 YooAsset 类型都不认识**。
> 原框架的 `ResMgr` 基于 `Resources`，问题是内容打包时固化、不能热更，而且框架层无法按需卸载单个资源。
>
> 我的做法是**依赖倒置**：框架侧只定义 `IAssetProvider` 和加载操作的接口，
> 适配层 `NBC.Framework.YooAsset` 是**全工程唯一引用 YooAsset 的程序集**。
> 换资源方案时删掉这一个程序集就行。而且 `NBC.Framework` 的 asmdef 引用列表**必须为空**，
> 有测试机械保证 —— 这条守卫我还加强过一次：最初它只断言"不引用 `NBC.*`"，
> 但 YooAsset 不是 `NBC.*`，也就是说**把 YooAsset 塞进框架，那条测试照样绿**。
>
> 这套设计的**回报是可测性**：`AssetManager` 的缓存和引用计数逻辑全在框架侧，
> 测试里塞一个假加载器就能精确控制"什么时候加载完、什么时候失败"，
> 21 条测试**一条都不需要真实的资源系统、不需要打包**。
> 释放做成三级：`Dispose` 只减引用计数、`ReleaseUnused` 集中放掉零引用的、`UnloadAll` 全放。
>
> 有一处**有意偏离**原框架：`LoadAssetAsync<GameObject>` **不再自动实例化**，
> 返回原始 prefab。因为原来那 6 个调用点全在我正在重写的模块里，**没有兼容包袱**；
> 而且显式实例化能和对象池配合 —— 池本来就通过工厂拿对象。
>
> B3 那段排错我想说一下，因为它教了我两件事。冒烟测试三轮才对：
> 根因是 **v3 的初始化是三段式** —— `InitializePackageAsync` **只建文件系统、不加载清单**，
> 而 `SetActiveManifest` 全工程只有一个调用点，在 `LoadPackageManifestOperation` 里。
> 所以不调 `LoadPackageManifestAsync`，`ActiveManifest` 永远是 null，**哪怕状态是 Succeeded**。
>
> 前两轮我一直问"我哪里把清单弄丢了"，那是死胡同。
> 正确的问法是"**这份清单是谁负责设上的、什么时候被调**" —— 一搜源码就找到了。
> 第二件事是：**每一条新的错误信息都要当成新信息读**，不要因为"看起来像上次那个问题"就套用旧结论。

# 附：术语速查

| 术语 | 一句白话 |
| --- | --- |
| **AB 包 / AssetBundle** | Unity 的可增量下发的资源打包格式 |
| **热更新** | 不重新出整包就能更新内容 |
| **依赖倒置** | 高层定义接口，低层去实现；高层不认识低层 |
| **适配层（adapter）** | 把第三方库翻译成本项目接口的那一层 |
| **引用计数** | 记录一个资源被多少地方在用；减到 0 才真正释放 |
| **幂等（idempotent）** | 同样的调用做多次，结果和做一次一样 |
| **进程级子系统** | 全局单例、生命周期跟整个进程走的东西（如 YooAsset 的资源系统） |
| **no-op** | 什么都不做的调用。**静默 no-op 是最危险的** |
| **清单（manifest）** | 描述"这个包里有哪些资源、地址是什么"的元数据 |
| **冒烟测试** | 只验"整条链路通不通"的最少量测试 |
