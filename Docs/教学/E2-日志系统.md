# ① 问题是什么

游戏跑起来之后，**唯一能告诉你"刚才发生了什么"的东西就是日志**。

没有日志系统的时候，典型的做法是到处 `Debug.Log`。然后很快遇到三个问题：

**① 刷屏淹掉关键信息。**
战斗逻辑每帧刷几十条，网络收发包每帧又刷几十条 ——
真正重要的那条"资源加载失败"被埋在几千行里，**等于没有**。

**② 想关掉的时候关不干净。**
"把日志关掉"听起来简单，但如果是散落各处的 `Debug.Log`，你只能一个个删。

**③ 玩家/测试机上的日志拿不到。**
Console 里的东西**只在那台机器上**。玩家报"打到第三关崩了"，你手里什么都没有。

**所以需要**：**能分级、能按来源开关、能落盘**。

---

# ② 最小例子

```csharp
// 记一条
LogSystem.Instance.LogInfo(LogChannel.Battle, "命中：" + damage);

// 单独关掉网络收发（FW-M11 点名要的那个开关）
LogSystem.Instance.SetChannelEnabled(LogChannel.Network, false);

// 热路径上的正确写法：先问，再拼字符串
if (LogSystem.Instance.IsEnabled(LogLevel.Info, LogChannel.Battle))
{
    LogSystem.Instance.LogInfo(LogChannel.Battle, "位置 " + pos);   // 只有真要记才拼
}

// 挂一个落盘目标（带滚动）
LogSystem.Instance.AddSink(new FileLogSink(Application.persistentDataPath + "/Logs"));

// 退出前必须刷，否则最后几条会丢
LogSystem.Instance.Flush();
```

# ③ 需求要什么

`FW-M11` 列了四件事：

| 要求 | 做法 |
| --- | --- |
| **分级** | `MinLevel` 以下直接丢掉 |
| **文件落盘** | `FileLogSink`，超长自动滚动 |
| **战斗中滚动日志** | 内存里的**环形缓冲**，最新的在最前，给游戏内控制台面板读 |
| **网络收发日志开关** | **频道**维度（General / Network / Battle / Asset / Ui） |

# ④ 做法

## 4.1 ⚠️ 关键：为什么需要"频道"这个**第二个**维度

这是这一块最容易被做漏的地方。

只想"分级"的话很简单：Debug / Info / Warning / Error，一条 `MinLevel` 就完事。
但需求点名要"**网络收发日志开关**" —— 而这件事**级别过滤做不到**：

> 网络的正常日志是 `Info`，战斗的正常日志**也是 `Info`**。
> 按级别往下压，会把两个一起关掉。

**级别回答的是"这条有多严重"，频道回答的是"这条是谁发的"。** 两个问题，两个维度。

所以有专门一条测试钉住它：

```
DisablingNetworkChannel_DoesNotAffectOtherChannels
    → 关掉 Network 之后，Battle 的 Info 照常记录
```

## 4.2 ⚠️ 过滤必须发生在**字符串拼接之前**

这是性能上的硬要求，而且**很容易写错**：

```csharp
// ❌ 拼接白做了 —— 关掉日志也照样每帧分配一个字符串
LogSystem.Instance.LogInfo(LogChannel.Battle, "位置 " + pos);

// ✅ 热路径必须这样写
if (LogSystem.Instance.IsEnabled(LogLevel.Info, LogChannel.Battle))
{
    LogSystem.Instance.LogInfo(LogChannel.Battle, "位置 " + pos);
}
```

C# 会**先把参数算出来**再传给方法。所以即使日志被过滤掉了，那个 `"位置 " + pos`
**也已经分配过了** —— 在每帧几十条的热路径上，这是稳定的 GC 压力（需求 ⑩ OPT-26 说的就是这个）。

**所以 `IsEnabled` 不是"给调用方参考"的**，是**必须提供的短路入口**。

⚠️ 而它既然被用来做判断，就有一条隐含契约：**它的预测必须和 `Write` 的实际行为完全一致**。
不然"先问再拼"就是错的（问了说不记、结果记了；或者说记、结果没记）。
有测试逐个组合验这一点：

```
IsEnabled_MatchesActualWriteBehavior
    → 4 个级别 × 3 个频道 = 12 种组合，每种都比对"预测"与"实际"
```

## 4.3 `ILogSink`：把"记什么"和"记到哪"分开

```
        LogSystem                    ← 只管：要不要记、记什么
            │
      ┌─────┼──────────┐
      ▼     ▼          ▼
FileLogSink  UnityConsoleLogSink  MemoryLogSink（测试用）
```

好处直接体现在**测试怎么组织**上：

| 测什么 | 用什么 sink | 为什么 |
| --- | --- | --- |
| 过滤、频道、滚动缓冲、统计 | `MemoryLogSink` | **不碰文件系统**，快、确定 |
| 真的落盘、滚动、编码 | 真实临时目录 | **碰文件系统才算测到落盘** |

**两个文件分开**，哪边红了立刻知道是"过滤逻辑错"还是"写文件错"。

> ⚠️ 说实话：这道缝**主要价值是测试与将来的扩展**（比如把日志发给服务端），
> 不像 `IInputSource` 那样是明确的架构替换点。**别把它说成后者。**

## 4.4 滚动日志：环形缓冲

内存里存最近 N 条（默认 200），满了覆盖最旧的。

```csharp
private void PushToRing(in LogEntry entry)
{
    if (m_ringCount < m_ring.Length)
    {
        m_ring[(m_ringStart + m_ringCount) % m_ring.Length] = entry;
        m_ringCount++;
        return;
    }

    // 满了：覆盖最旧的那条，并把起点往后挪一格
    m_ring[m_ringStart] = entry;
    m_ringStart = (m_ringStart + 1) % m_ring.Length;
}
```

`CopyRecent` 给的是**新的在前**（控制台面板从上往下显示，不必再转一次）。

⚠️ 环形缓冲最容易写错的就是**绕圈之后的顺序**，所以有专门一条测试
`RingBuffer_PreservesOrderAcrossWraparound` 填满再绕两圈，逐条比对。

## 4.5 ⚠️ 文件滚动：**同一个测试两轮才对**（这一节最值钱）

### 第一轮：时序边界

`Write` 原本**写完再检查**长度：

```csharp
m_writer.WriteLine(line);
if (m_writer.BaseStream.Length >= m_maxFileBytes) Rotate();   // ❌ 写之后
```

后果：如果**最后一次写**刚好触发滚动，当前文件 `nbc.log` 就被改名归档成 `nbc.1.log`，
而**不留新的当前文件** —— 那一刻正在 `tail` 日志的人会看到"**文件突然不见了**"。

**教训**：这类 bug 的性质是"**时序上的边界**" —— 不是算错了，而是
"**在某个特定时刻，状态不符合直觉**"。从代码上看不出来，
但一句朴素的断言就能抓到：**"滚动之后，当前文件该不该在？"**

### 第二轮：**缓冲让"长度"这个量不可信**

把检查挪到写之前，"当前文件永远存在"这条不变式成立了 —— **但滚动再也不发生了**（`RotationCount` 一直是 0）。

根因：`StreamWriter` 是**带缓冲**的，内容要等缓冲满（默认 1 KB）才落到流上，
所以 `BaseStream.Length` **落后于**实际写入量。

⚠️ **而且这暴露了第一版"能过"是侥幸**：它只在"某次写恰好触发缓冲 flush"的那一刻
才可能看到长度超标 —— 20 条日志刚好跨过一次 flush，**于是它看起来能工作**。
顺序一改，侥幸没了，问题才现形。

> **这个 bug 一直都在，只是被"刚好合适的测试数据量"掩盖了。**

**修法**：**自己记字节数**，不依赖被缓冲的量：

```csharp
m_writtenBytes += m_encoding.GetByteCount(line) + NewlineByteCount;

// 三个配套细节，缺一个都会出别的毛病：
// ① EnsureOpen 时从**已有文件的真实长度**起步
//    —— 否则"追加到一个本来就很大的日志"会永远不滚动
// ② Rotate 时归零
//    —— 否则下一次写会立刻又滚，变成无限滚动
// ③ 用编码算字节数，不是 line.Length
//    —— 中文字符 1 个 char 是 3 个字节
```

**验证**：用 PowerShell 复刻同一套逻辑跑 20 条（上限 200 字节）——
**旧逻辑 0 次滚动，新逻辑 6 次滚动**，当前文件存在、字节 177、归档文件正好 3 个。

### 两轮的教训不一样，都值得记

| 轮次 | 教训 |
| --- | --- |
| 第一轮 | **时序边界**：某个特定时刻状态不符合直觉。朴素断言就能抓到 |
| 第二轮 | **缓冲让一个数值变得不可信** —— 依赖**被中间层缓冲过**的值做判断，是在**赌"它什么时候刷新"**。**赌赢了也还是错的** |

## 4.6 一个刻意的环境判断：EditMode 下**不挂**控制台 sink

```csharp
protected override void OnInit()
{
    if (Application.isPlaying)
    {
        AddSink(new UnityConsoleLogSink());
    }
}
```

**为什么**：EditMode 测试里，**任何一条没被 `LogAssert.Expect` 声明的 `Error` 都会让用例失败**。
如果控制台 sink 在 EditMode 也自动挂上，那么"测 LogSystem 自己"的用例
会**因为自己写进去的 Error 而变红** —— 那是测试环境被自己的输出污染。

> 这和 A5 的 `SceneLoader`、A8 的 `AudioManager` 是同一个套路：
> **`Application.isPlaying` 挡住 EditMode**。
> 加一条测试把它钉住：`InEditMode_NoConsoleSinkIsAutoAttached`。

## 4.7 已知局限（写清楚，不藏）

| # | 局限 | 说明 |
| --- | --- | --- |
| 1 | **同步 I/O** | 每条日志一次系统调用，高频刷会把帧率吃光。真要高频记录应改成"写进环形缓冲，退出/出错时一次性 dump"（属 M5 优化） |
| 2 | **没有线程安全** | 目前只有主线程在记。将来网络线程要记，得加锁或改成"每线程队列 + 主线程合并" |
| 3 | 环形缓冲溢出**不提示** | 用 `TotalCount` 和 `RingCount` 的差值能看出来，但不去打扰使用者 |

# ⑤ 自测 4 题

**1.** 为什么"分级"不够，还需要"频道"？举出需求里点名的那件事。
**2.** 为什么 `IsEnabled` 不是"给调用方参考"的，而是**必须提供**的？
**3.** 环形缓冲最容易写错的是什么？怎么测它？
**4.** 为什么不能用 `m_writer.BaseStream.Length` 判断"该不该滚动"？

<details>
<summary>点开看答案</summary>

**1.** 因为需求点名要"**网络收发日志开关**"，而网络的正常日志和战斗的正常日志**都是 `Info`** ——
   按级别压会把两个一起关掉。**级别回答"有多严重"，频道回答"谁发的"，是两个问题。**

**2.** 因为 C# **先把参数算出来**再传进方法。所以 `LogInfo(ch, "位置 " + pos)` 里那句拼接
   **即使日志被过滤也照样发生** —— 热路径上就是稳定的 GC 压力。
   `IsEnabled` 让调用方**在拼接之前**短路。
   ⚠️ 配套契约：它的预测必须和 `Write` 的实际行为**完全一致**，有测试逐个组合验。

**3.** **绕圈之后的顺序**（取模、起点、覆盖最旧三件事凑在一起）。
   测法：填满再绕两圈，然后**逐条比对**期望的序号。

**4.** 因为 `StreamWriter` 是**带缓冲**的，`BaseStream.Length` **落后于**实际写入量。
   拿它做判断等于**赌"缓冲什么时候刷新"** ——
   而且这个设计曾经"看起来能工作"，只是因为测试数据量刚好跨过一次 flush。
   **赌赢了也还是错的。** 所以改成自己记字节数。

# ⑦ 一分钟面试版

> 日志我做了两件事：**分级**和**频道**。
>
> 只做分级是不够的 —— 需求点名要"网络收发日志开关"，而网络的正常日志和战斗的正常日志
> **都是 Info**，按级别压会把两个一起关掉。**级别回答"有多严重"，频道回答"谁发的"，是两个问题。**
>
> 第二个设计点是**过滤必须发生在字符串拼接之前**。C# 会先把参数算出来再传进方法，
> 所以 `LogInfo(ch, "位置 " + pos)` 里那句拼接**即使日志被过滤也照样分配字符串** ——
> 热路径上就是稳定的 GC 压力。所以我提供 `IsEnabled` 让调用方在拼接前短路，
> 而且有测试逐组合验证"它的预测和实际记录行为完全一致"。
>
> 输出目标我抽成了 `ILogSink`：内存 sink 用来测过滤和滚动（快、不碰文件系统），
> 真实临时目录用来测落盘。**两个文件分开，红了立刻知道是哪一层错。**
>
> 落盘这块我踩了个值得说的坑：**同一个测试两轮才对**。
> 第一轮是时序问题 —— 原本"写完再检查长度"，于是最后一次写触发滚动时，
> 当前文件被归档却**不留新的当前文件**，正在 tail 日志的人会看到文件突然不见了。
> 改成"写之前检查"之后，**滚动再也不发生了** —— 因为 `StreamWriter` 有缓冲，
> `BaseStream.Length` 落后于实际写入量。
>
> 而且这暴露了第一版"能过"其实是**侥幸**：它只在某次写恰好触发缓冲 flush 的那一刻
> 才可能看到长度超标，测试数据量刚好跨过一次 flush，所以它看起来能工作。
> **依赖一个被中间层缓冲过的值做判断，是在赌它什么时候刷新 —— 赌赢了也还是错的。**
> 最后改成自己记字节数，并且处理了三个配套细节：追加已有文件时从真实长度起步、
> 滚动时归零、用编码算字节数而不是字符数。

# 附：术语速查

| 术语 | 一句白话 |
| --- | --- |
| **分级（Level）** | 这条日志有多严重：Debug / Info / Warning / Error |
| **频道（Channel）** | 这条日志是谁发的：General / Network / Battle / Asset / Ui |
| **sink** | 日志的"出口"。文件、控制台、内存都是一种 sink |
| **环形缓冲（ring buffer）** | 固定容量的缓冲，满了就覆盖最旧的 —— 天然只保留"最近 N 条" |
| **滚动（rotation）** | 文件太大就换一个，旧的保留有限个 —— 磁盘占用有上限 |
| **短路** | 先判断"要不要做"，再做昂贵的那件事（比如拼字符串） |
| **缓冲（buffering）** | 内容先攒在内存里，攒够一批再真正写出去。**代价是"已写多少"这个量会滞后** |
