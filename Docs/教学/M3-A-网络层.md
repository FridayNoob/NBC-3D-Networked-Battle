## ① 问题是什么（先不看代码）

单机游戏里，"怪物掉血了"这句话只有一个人听得见 —— 你自己。联机之后，同一件事要让**两台机器达成一致**，
于是冒出一串新问题，而且它们**互相纠缠**：

| # | 问题 | 不管它会怎样 |
| --- | --- | --- |
| 1 | **TCP 是字节流，不是消息流** | 你发三条，对面可能一次收到（粘包）、也可能半条半条到（拆包）→ "偶尔卡住 / 偶尔读到垃圾" |
| 2 | **谁的算数？** | 客户端自己算伤害 = 可以改内存作弊；两端各算一次 = 偶尔算出不同结果 |
| 3 | **对面还在吗？** | 拔网线、崩溃、进程被杀 —— 没有心跳，对局里会留着永远不动的"僵尸玩家" |
| 4 | **怎么验证？** | 客户端在 Unity 里、服务端在 .NET 里，**我改完一行，怎么知道两边都还对？** |

⚠️ 这一课**故意只做前 3 件里最基础的部分**：把"能通"证明掉（握手 + 心跳 + 30Hz 主循环）。
同步逻辑（房间、快照、伤害）是 S4 之后的事 —— 顺序反了的话，一旦不通，你分不清是"同步写错了"还是"根本没连上"。

## ② 最小例子：两种写法的差别

**❌ 常见写法**（教程里到处都是，问题也最多）：

```csharp
// 业务代码里直接 new 一个 TcpClient，收到字节就当成一条消息
var client = new TcpClient("127.0.0.1", 7777);
var stream = client.GetStream();
byte[] buf = new byte[1024];
int n = stream.Read(buf, 0, buf.Length);
var msg = Parse(buf, n);        // ← 这一行永远在对不对之间摇摆
```

三处硬伤：
① `Read` 一次拿到的**不保证是一条消息**（粘包/拆包），`Parse` 的结果取决于运气；
② 业务层从此**认识 socket** —— 想换 UDP、想在测试里不发网络，全都得改业务代码；
③ 这段代码**在 Unity 的 EditMode 里跑不了**，只能"开两个客户端点点看"。

**✅ 我们的写法**（三层，各管一件事）：

```
业务/会话层   NetSession          ← 协议语义：这是 HandshakeAck，那是 Pong
   ↓ ITransport（接缝，认识"一条条载荷"，不认识 socket）
传输层        TcpTransport        ← 字节流 ↔ 载荷：粘包/拆包在这里被吃掉
   ↓ 同一份 FrameCodec（双端共享）
线            长度前缀 [4 字节小端][载荷]
```

关键就一句：**"消息在哪儿结束"必须自己带信息**（长度前缀），而且这件事**双端必须用同一份代码**。

## ③ 需求到底要什么（这一版协议的 8 个决定）

来自 `Docs\25` §三（D1~D8），这里只留会写进代码的那些：

| 决定 | 内容 | 为什么 |
| --- | --- | --- |
| **D1 传输** | **TCP + 4 字节小端长度前缀 + protobuf 载荷** | M3 是**状态同步**，"可靠 + 有序"最要紧；几十行就能跑通，不引第三方 |
| **D2 tick** | 服务端 **30 Hz** | 客户端 60fps、服务端 30Hz 下发，2~4 人完全够 |
| **D3 权威** | 服务端算伤害/位置/掉落；客户端**只发意图** | 这是"服务器权威"的定义，也是 M4 的 PVP 能直接复用的前提 |
| **D4 预测** | **M3 不做客户端预测**（有意） | 先正确、后手感。预测+回滚属于 M4 的帧同步 |
| **D5 粒度** | 每 tick **全量快照** + 事件 | 2~4 人、实体少 → 全量最省心；差分/压缩留 M5 |
| **D6 房间** | 一个房间 = 一个副本实例，2~4 席位 | 最简单又能演示组队 |
| **D7 共享** | 协议 + M2 已有的伤害结算/条件系统 | 白拿的东西不要重写 |
| **D8 两客户端** | 一个 Editor + 一个打包版 | Unity 里同时 Play 两个实例做不到 |

⚠️ 协议版本号有**两处**要一致：`Protocol\nbc_m3.proto` 顶部的 `CONTRACT_VERSION` 与
`Shared\Net\NetContract.cs` 的 `Version`。它们由 `ProtocolTests` **直接读那个 .proto 文件**比对 ——
"改了协议忘了升版本"是典型的**静默漂移**：两端都能编过，只有联机时才暴露。

## ④ 做法：五个决定，每条都带"不这么做会怎样"

### 决定 1 · 分帧放**共享层**（`Shared\Net\FrameCodec.cs`）

和条件系统、伤害结算是同一条判据：**两端必须算出同一个结果的东西，才放共享层**。
分帧是"两边各写一份就一定会对不上"的典型：长度字节序、上限、对 0 长度帧的处理，
只要有一点不同，联机就表现为"偶尔卡住"，**而且单端测试全绿**。

三条写死的约定：

| 约定 | 不这么做会怎样 |
| --- | --- |
| **长度是小端、手写四行字节**（不用 `BitConverter`） | `BitConverter` 取决于**宿主字节序**：本机 x86 是小端，换到大端平台两端互相读成天文数字 |
| **0 长度帧合法** | protobuf 空消息序列化出来就是 0 字节；把它当非法 = **静默丢消息** |
| **超过上限 = 协议违规，直接断开** | 长度前缀可以撒谎；不设上限就是"一句 N 让本端 `new byte[N]` 吃光内存" |

### 决定 2 · 接缝放**引擎无关**的程序集（`NBC.Framework.Net`）

最初我按 A/B 组的老分法，把 `ITransport` 放进 `NBC.Framework`、实现放进适配程序集。
**改掉的理由不是审美，是可验证性**：

| 放法 | 后果 |
| --- | --- |
| 接缝在 `NBC.Framework` | 网络层挂上 UnityEngine 依赖 → **我在沙箱里一行都跑不了**，只能等负责人开 Unity |
| 接缝 + 实现在 `NBC.Framework.Net`（`noEngineReferences: true`，只引 `NBC.Shared`） | `Server\_condition-probe`（.NET 8）能把这批源码**直接编进去真开端口跑**：回环、粘包、对端关闭当天就有证据 |

代价（如实记）：网络层用不了框架的日志/事件中心 —— 报错走 `Closed` 的人话原因，够用。
附带好处：`noEngineReferences: true` 把"网络层偷偷用 UnityEngine"变成**编译错误**。

> 📌 一条可复用的判据：**"这段代码我能不能自己在没有编辑器的环境里跑一遍？"**
> 如果答案是不能，那它的设计就该再想一想。

### 决定 3 · **拉模式（Pump）**，而不是"网络线程 + 回调"

`Pump()` 由调用方每帧调一次，一切都在那个线程上发生（非阻塞 `Poll` 收发）。买到三样：

| 买到的 | 说明 |
| --- | --- |
| **无锁** | 状态只有一个线程碰过 —— "加锁漏了一处"这类 bug 不存在 |
| **可复现** | 测试里手工 `Pump()` 到某个状态，**不需要 sleep 碰运气** |
| **同源** | 客户端与服务端是同一个形状，联调时不用在两种心智模型之间切换 |

代价：IO 及时性取决于 Pump 频率（30Hz 主循环完全够 M3）。

### 决定 4 · 两端的**形状**不一样（别合并）

| 端 | 接口 | 为什么不同 |
| --- | --- | --- |
| 客户端 | `ITransport`（连/发/收/关） | 它只有**一条**连接 |
| 服务端 | `INetTransport`（每条带 `sessionId`，还要接受新连接） | 它有 **N 条**连接，且要能踢人 |

分帧**同一份**，形状**各自**。硬要合并的结果是两边都变别扭（客户端被迫处理 sessionId，服务端被迫假装只有一条连接）。

### 决定 5 · 顺序敏感的四处（这一课最值钱的部分）

| # | 细节 | 顺序/做法错了会怎样 |
| --- | --- | --- |
| 1 | **断开前先冲发送队列**（`Flush` → `Shutdown(Send)` → `Close`） | "你被断开，因为协议版本不一致"这条说明**到不了客户端**，只表现为"连接莫名其妙断了" |
| 2 | **收到 0 字节 = 对端关了** | `Poll(SelectRead)` 为真但 `Available == 0` 就是 FIN。漏掉它的表现是"对方早退了，本端一直以为自己还连着" |
| 3 | **心跳超时要真的断开** | 只把状态标成"掉线"、留着半死 socket，下一次 `Send` 会以为还连着 —— 那正是"偶尔丢一条"的来源 |
| 4 | **握手也要有超时** | 连上了但服务端不说话（版本不兼容 / 对面不是本协议）→ 界面永远停在"连接中"，日志什么都没有 |

另外两条工程习惯：

* **`NoDelay = true`（关 Nagle）**：Nagle 会攒小包，最多压到 ~200ms 才发 → 对 30Hz 动作战斗就是"操作忽然一顿一顿的"
* **收到先入队，`Pump()` 返回后再处理**：回调是在传输层内部触发的，在那里直接改会话状态 = "在收发过程中改状态表"

## ⑤ 自测若干问（先自己答，再看）

<details><summary>1. 为什么分帧必须双端同一份代码，而不是"各写一份、测试都过"？</summary>

因为分帧的**每个约定**（字节序、上限、0 长度帧是否合法）都只影响"两端**一起**工作时"的行为。
单端测试里没有对端，所以任何一份都能"自洽地通过"。而两端一旦不一致，症状是"偶尔卡住/偶尔读到垃圾"，
**不崩、不报错**，只有联机才暴露 —— 典型的静默失败。
</details>

<details><summary>2. 为什么服务端和客户端不共用一个传输接口？</summary>

因为要解决的问题不同：客户端是"一条连接"，服务端是"N 条连接 + 接受新连接 + 踢人 + 心跳清理"。
共用会让两边都别扭。真正该共享的是**分帧**（同一份 `FrameCodec`），不是"连接的形状"。
</details>

<details><summary>3. `Pump()` 模式和"网络线程 + 回调"比，卖掉了什么？买到了什么？</summary>

卖掉的是 IO 及时性（只在你调 `Pump()` 时处理），买到的是**无锁**、**可复现**、**两端同源**。
30Hz 的主循环下，及时性完全够 —— 这是**有意**的取舍，不是没想到多线程。
</details>

<details><summary>4. 为什么"断开前要先冲发送队列"？顺序反了会怎样？</summary>

`Close()` 之后 socket 就没了，**队列里的字节永远发不出去**。
而"为什么踢你"这条 `HandshakeAck{accepted=false}` 恰恰是那时队列里唯一的东西 ——
顺序反了，客户端只看到"连接被关"，永远不知道原因。排查成本极高（现象与原因隔了一条网线）。
</details>

<details><summary>5. 为什么 `NetSession` 的时间要从外面喂（`Pump(deltaMs)`）？</summary>

因为它要拿时间做三件事：心跳节奏、握手超时、心跳超时判定。
如果内部直接读 `DateTime.Now`，测试"过了 5 秒"就得 `Thread.Sleep(5000)`（慢且 flaky）。
注入之后，"过了 5 秒"就是一行 `session.Pump(5001)`。
（编辑器窗口那边反过来要**夹住 delta**：编辑器卡顿会让 delta 变成好几秒 → 会判出**假掉线**。）
</details>

<details><summary>6. "一处规则、两个实现"具体指这次哪件事？</summary>

服务端"收 → 路由 → 回包/断开"这段逻辑有**两个调用点**：`NBC.Server.Host` 和端到端探针。
如果探针里再抄一份，那么探针验的就是**抄本**，而真正跑在生产里的那份没人验。
所以它被提成 `ServerMessagePump`（Core 里唯一实现），两边都用它。
</details>

## ⑥ 30 秒验证（你自己能跑，含负向对照）

### A. 端到端探针（不用 Unity、不用开编辑器）

```powershell
cd "E:\U3D Projects\0_MyFile\3D联网战斗Demo"
dotnet build Server\NBC.sln -m:1
dotnet build Server\_net-probe\NetProbe.csproj -m:1
dotnet run --project Server\_net-probe\NetProbe.csproj --no-build
```

**应当看到：`通过 17，失败 0。 结果：✅ 全绿`**

这 17 条里**负向对照**是故意做的，用来证明"检查真的在工作"：

| 负向对照 | 期望结果 |
| --- | --- |
| 客户端报协议版本 999 | 收到 `accepted=false` 的**说明**，然后连接被断开（顺序不能反） |
| 没握手就直接发 Ping | 被断开，原因是"还没握手就发了 Ping" |
| 发一条 0 长度帧 | 判协议违规（不是静默忽略） |
| 发一个撒谎的长度前缀（声称 512KB+1） | 判违规断开，**不照着它攒内存** |
| 客户端连上后一句话不说 | 250ms 后服务端按**心跳超时**踢掉并释放席位 |

### B. 两个**真进程**互通（S3 的验收本体）

```powershell
# 窗口 1：起服务端
Server\NBC.Server.Host\bin\Debug\net8.0\NBC.Server.Host.exe --port=7799

# 窗口 2：当客户端连过去
dotnet run --project Server\_net-probe\NetProbe.csproj --no-build -- --connect=7799
dotnet run --project Server\_net-probe\NetProbe.csproj --no-build -- --session=7799
```

服务端那边应当打印：

```
[就绪] 已监听 7799
[接入] 会话 1 来自 127.0.0.1:xxxxx
[提示] 会话 1 握手成功 → 玩家 1（客户端 v1，tick 30Hz）
[断开] 会话 1（玩家 1）：对端关闭了连接（收到 0 字节）
```

### C. Unity 里点着看（`Tools/NBC/网络/网络调试窗口`）

先起服务端（同 B 的窗口 1），再打开窗口点「连接」。应当看到：
状态 `Online`、玩家 id、RTT（几十毫秒以内，本机通常是 0~2ms）、
心跳"已发/已收"两个数字**每秒各 +1**。

**负向对照**：不起服务端直接点「连接」→ 状态应当是 `Failed`，
原因写着 **`连接 127.0.0.1:7777 失败：对端没有在监听（连接被拒绝）`**
（而不是一直停在"连接中"）。这条最能证明"人话原因"是真的有用。

## ⑦ 一分钟面试版

> M3 我做了网络层：**自研 TCP 传输 + 客户端会话 + 服务端 30Hz 主循环**。
>
> 分帧用**长度前缀 + 手写小端**，放在**双端共享**的那一层 —— 因为分帧是"两端各写一份必然对不上"的典型，
> 而且错了不报错，只在联机时表现为偶尔卡住。
>
> 架构上我留了传输**接缝**：客户端 `ITransport`、服务端 `INetTransport`（形状不同，因为一个是单连接、一个是 N 连接），
> 分帧同一份。接缝刻意放在**引擎无关**的程序集里 —— 这样我在没有 Unity 的环境里也能把真 socket 跑起来，
> 反过来逼着网络层不许碰 UnityEngine。
>
> 收发是**拉模式 `Pump`**：无锁、可复现、两端同源，代价是 IO 及时性取决于帧率，30Hz 够用。
>
> 细节上我踩过并修掉四处**顺序敏感**的坑：断开前必须先冲发送队列（否则"你为什么被踢"到不了客户端）、
> 收到 0 字节要当成对端关闭、心跳超时要真的断 socket、握手也要有超时。
>
> 验证上我不满足于"能编过"：**45 条共享层/传输层探针 + 17 条端到端探针（真 socket + 真 protobuf）
> + 两个真进程互通**，客户端会话还额外对着真服务端跑了一遍；Unity 侧 **628 条 EditMode 用例**。
> 版本不一致会被拒、没握手会被踢、撒谎的长度前缀会断开，这些都是**负向对照**，专门证明检查在工作。
