# ① 问题是什么

游戏里到处都要"通知"：玩家死了要通知 UI、通知音效、通知任务系统。

最朴素的写法是**直接引用**：`UIManager.Instance.ShowDeathPanel()`。
但那样 `BattleLogic` 就得认识 `UIManager` —— 一个逻辑模块认识 UI，是**依赖方向错了**。
而且"死亡"要通知的东西会越来越多，每加一个都要去改 `BattleLogic`。

于是有了**事件中心**：发布者只管喊一声"英雄死了"，谁关心谁自己来听。
发布者**不认识任何订阅者**。

原框架就是这么个东西，但它的 key 是**字符串**：

```csharp
EventTrigger("英雄死亡", data);
AddEventListener("英雄死亡", OnHeroDied);
```

# ② 最小例子

```csharp
// 声明事件（拼错编译不过）
public static class BattleEvents
{
    public static readonly EventId HeroDied = EventId.Declare("Battle.HeroDied");
    public static readonly EventId DamageDealt = EventId.Declare("Battle.DamageDealt");
}

// 订阅 / 退订（要传同一个方法，委托相等性）
EventCenter.Instance.AddEventListener<DamageInfo>(BattleEvents.DamageDealt, OnDamage);
EventCenter.Instance.RemoveEventListener<DamageInfo>(BattleEvents.DamageDealt, OnDamage);

// 触发
EventCenter.Instance.Trigger(BattleEvents.HeroDied);
EventCenter.Instance.Trigger(BattleEvents.DamageDealt, info);
```

**核心区别**：事件标识是一个**编译期常量**，不是字符串。
`EventId.Declare` 是唯一的创建入口（构造函数是私有的），所以**拼错名字编译不过**。

# ③ 原版错在哪（3 条）

## FW-06：用 `string` 作 key

```csharp
EventTrigger("英雄死亡", data);
```

字符串的问题：**拼错不报错，只是静默不触发**。
`"英雄死亡"` 和 `"英雄 死亡"`（多了个空格）是两个完全不同的事件，
而编译器**一个字都不会说**。

排查这种 bug 有多痛苦？你的回调就是不执行，Console 干干净净，
你会去怀疑"是不是没注册成功""是不是顺序问题"——**就是不怀疑拼写**。

## FW-07：同一个 key 用不同类型监听/触发 → NRE

事件中心内部大概是这样：

```csharp
private Dictionary<string, IEventInfo> eventDic;

public void AddEventListener<T>(string name, UnityAction<T> action)
{
    if (eventDic.ContainsKey(name))
        (eventDic[name] as EventInfo<T>).actions += action;   // ← 类型不对就是 null
    else
        eventDic.Add(name, new EventInfo<T>(action));
}
```

**如果先注册了 `EventInfo<int>`、后来用 `EventInfo<string>` 触发**：
`as` 转换失败拿到 `null` → 后面 `.actions` 就是 **NullReferenceException**。
而且**报错点在事件中心里面**，离"你传错类型了"很远。

## P-16 + P-18：两个"没人知道会怎样"

- **P-16**：触发一个**没有任何监听者**的事件 → 原版**静默返回**，什么反馈都没有。
- **P-18**：`EventTrigger` 在**当前调用栈里同步 `Invoke`**。于是"**在回调里增删监听**"会改到正在派发的委托链 —— 而**没人知道具体行为是什么**（增了会收到本次吗？删了还会收到本次吗？）。

> ⚠️ 注意最后这条的措辞：原版的问题**不是"错了"，而是"没人知道它会怎样"**。
> 需求文档 `FW-M02` 其实已经预见了这个问题，把"异步派发队列"列为 P0。

# ④ 做法

## 4.1 `EventId`：把字符串变成编译期常量

```csharp
public readonly struct EventId : IEquatable<EventId>
{
    private readonly string m_name;

    private EventId(string name) { m_name = name; }   // ← 唯一入口是 Declare，外部造不出来

    public static EventId Declare(string name) { return new EventId(name); }

    public bool IsValid { get { return !string.IsNullOrEmpty(m_name); } }
    // == / != / Equals / GetHashCode ...
}
```

两个设计点：

**① 私有构造 + `Declare`**：外部**无法凭空造一个事件标识**。
你必须先 `Declare` 出一个静态字段，然后大家用它。这跟 A7 的 `InputActionId`、A10 的状态标识是同一个思路。

**② 结构体（`readonly struct`）**：事件标识会被频繁当字典键用。
如果是 `class`，每次查字典可能触发哈希/装箱开销；结构体是**值语义、零分配**。

**③ 没有字符串重载。**
如果保留 `Trigger("英雄死亡")` 这种重载，**大家还是会用字符串** ——
那这次改造就白做了。所以**旧的字符串入口一个不留**。

## 4.2 派发语义：**钉成契约，写进测试**

这是 P-18 的真正修法。做法是：**在派发开始时，对监听名单做一次"写时复制"快照**。

> **写时复制（copy-on-write）**：要改的时候先拷一份再改，正在用的那份不动。
> 这里更简单：派发时**先把当前的委托抓到一个局部变量**，之后无论别人怎么增删，本次派发用的都是那个快照。

于是两条语义就被**钉死**了：

| 情形 | 行为 |
| --- | --- |
| 派发中**新增**监听者 | **不会**收到本次事件；从下一次开始收到 |
| 派发中**移除**监听者 | **仍会**收到本次事件（名单在派发开始时就锁定了） |

> **⚠️ 这两条和 C# 原生 `event` 的行为完全一致。**
> 选"和语言一致"是刻意的：**你不需要再背一套新规则**。
>
> **为什么必须写成测试？** 因为第 2 条很容易被当成 bug。
> 而关键在于：**"行为有测试盯着"和"碰巧如此"是两回事**。
> 原版的问题从来不是"它错了"，而是**没人知道它会怎样**。

⚠️ 这里还有一处**经批准偏离需求**：`FW-M02` 原文要求"异步派发队列"（走队列、下一帧再处理），
本项目**保留同步派发**，改为"把语义钉成契约 + 配测试"。
理由：同步派发让"触发之后立刻能观察到结果"，调试和测试都更简单；
而队列会引入"派发延迟一帧"这个到处都要考虑的因素。
**这是明说的偏离，写在 `Docs\06` §11.4，不是偷偷改的。**

## 4.3 三层防护（都是原版没有的）

| # | 防护 | 不做的后果 |
| --- | --- | --- |
| 1 | **未注册事件告警**（每个 id 只报一次，可整体开关） | 原版静默 → 表现为"这个回调怎么不执行"，排查成本极高 |
| 2 | **派发深度上限（8 层）** | A 触发 B、B 触发 A 的无限递归 → **栈溢出**，而栈溢出的报错几乎无法定位 |
| 3 | **异常隔离**（catch + `LogException`） | 错误被吞掉，或者破坏事件中心自身状态 |

**第 1 条的"每个 id 只报一次"很关键**：如果不做去重，
一个每帧触发的未注册事件会**刷爆 Console**，反而把真正的问题淹掉。

**第 2 条的 8 层**：正常业务不会嵌套 8 层。
超过就说明**有人在事件回调里写了循环触发**，这时**响亮地报错**比"跑到栈溢出"有用得多。

## 4.4 一个热路径上的取舍（要能讲出来）

派发时**不调** `GetInvocationList()`。

`GetInvocationList()` 能得到逐监听者的名单（于是可以做"每个监听者单独 try/catch"），
但它**每次派发都会分配一个 `Delegate[]`**。在每帧几十次事件的热路径上，那是**稳定的 GC 压力**。

**代价**：某个监听者抛异常会**中断本次派发的后续监听者**（和 C# 原生 `event` 一致）。

**取舍理由**：异常本身是 bug，**应当响亮地暴露**；而 GC 是每帧都在付的成本。

## 4.5 `EventChannelStat`：给 PerfHUD 看的

```csharp
public void CopyChannelStats(List<EventChannelStat> buffer);
```

每个事件通道的**监听者数量**，给 E1 的性能面板用。

> 和 A2 的 `PoolStats` 是同一个思路：**给数字，不给容器。**

# 附：术语速查

| 术语 | 一句白话 |
| --- | --- |
| **事件中心 / 发布订阅** | 发布者只管喊一声，订阅者自己来听；发布者不认识订阅者 |
| **`readonly struct`** | 不可变的值类型；当字典键不分配堆内存 |
| **写时复制（快照）** | 派发时先把名单抓一份，之后别人怎么改都不影响本次 |
| **委托链** | C# 的 `+=` 把多个方法串起来，按顺序调用 |
| **`GetInvocationList()`** | 把委托链拆成一个数组。能逐个调用，但**要分配内存** |
| **栈溢出** | 递归太深把调用栈撑爆。报错信息几乎无法定位 |
| **热路径** | 每帧都会跑很多次的那段代码。它的 GC 成本会被帧数放大 |
