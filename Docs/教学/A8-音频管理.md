## ① 问题是什么

游戏里要放音效。听起来是"播一下就行"，但在一个要跑几百个音效的战斗场景里，有三个真问题：

1. **播一个音效会不会创建一个对象？**
   原版是：每次播放 `AddComponent<AudioSource>()`，播完 `Destroy`。
   打击音一秒十个 → 每秒十次组件创建 / 销毁 → GC 抖动 + 帧率毛刺。
   正确做法来自一个判断：**音效是高频、同构、可复用的东西** —— 恰好是对象池最典型的场景。

2. **切场景了，音频系统还活着吗？**
   原版 `new GameObject()` 没有 `DontDestroyOnLoad` → 切场景对象被销毁，但**字段还持着引用**
   （Unity 伪 null）→ 下次播放往已销毁对象上 `AddComponent` → `MissingReferenceException`。
   玩家的体感是"**进第二关就没声音了，还报错**"。

3. **玩家说"音乐太吵"，你能只调音乐吗？**
   原版只有两个 float（`bkValue` / `soundValue`），连 UI 音效都只能挤在 `soundValue` 里。
   要**按用途分组**，玩家才能分开调。

> **一句话**：音频模块要解决的不是"怎么播声音"，而是
> **"播几百次不出事、切场景不崩、音量能分开调"**。

## ② 最小例子

```csharp
// ❌ 原版思路：播一次建一个
var go  = new GameObject();                  // 切场景就没了
var src = go.AddComponent<AudioSource>();    // 每次都是新组件
src.clip = clip; src.Play();
Destroy(src, clip.length);                   // 播完销毁 → 下次再来一遍

// ✅ 池化：播完"还回去"
var handle = AudioManager.Instance.Play(
    AudioPlayRequest.Sound3D(clip, hitPoint));   // 取出 → 播 → 播完自动回池
// handle 用来 Stop / 查询；素材由调用方自己加载（理由见 ④）
```

差别就一句话：**原版是"用完就扔"，现在是"用完还回去"。**

## ③ 原版错在哪

先强调一件事：**这一轮我没有照抄审计描述，而是把 docx 解出纯文本、把 139 行真代码整段读了。**

```csharp
// :27-34  Update
private void Update()
{
    for( int i = soundList.Count - 1; i >=0; --i )
        if( !soundList[i].isPlaying )
        { GameObject.Destroy(soundList[i]); soundList.RemoveAt(i); }
}

// :97-105  PlaySound
if(soundObj == null) { soundObj = new GameObject(); soundObj.name = "Sound"; }  // ← 没有 DontDestroyOnLoad
ResMgr.GetInstance().LoadAsync<AudioClip>("Music/Sound/" + name, (clip) =>
{
    AudioSource source = soundObj.AddComponent<AudioSource>();                  // ← 每次新建组件
    ...
});
```

三条真实问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| ① | **音效对象不复用**：`AddComponent` + `Destroy` 循环，没有池、没有并发上限 | 密集音效时组件创建 / 销毁抖动 |
| ② | **宿主未 `DontDestroyOnLoad`**：`soundObj` / `BkMusic` 都没做（对比 `MonoController.cs:18`、`UIManager.cs:40,50` 都做了） | 切场景后 `MissingReferenceException` |
| ③ | **`Update` 无有效性防御**：直接访问 `soundList[i].isPlaying` | 元素被外部销毁 / 随场景销毁时抛异常 |

### ⚠️ 但有两句话是错的，必须更正

需求文档和审计报告都写过：

| 错误说法 | 事实 |
| --- | --- |
| "`Destroy(AudioSource)` **与缓存池冲突**" | **缓存池全程没参与音频路径** —— 音频只从 `ResMgr` 取 `AudioClip`。谈不上冲突 |
| "`Destroy(AudioSource)` **等价于销毁其 gameObject**" | **Unity 官方文档相反**：传 Component 时 "removes the component from the GameObject and destroys it" —— **宿主还活着**，不存在连锁销毁 |

> **所以"该回池"的真正理由是 ①（不复用），不是"和池冲突"。**
> 这条更正的价值不在于抠字眼：如果按"和池冲突"去改，你会去改池；
> 按"不复用"去改，你才会去做**播放器池**。**错误的归因会把你带到错误的修法上。**

## ④ 改造后的做法

分三层，每层只干一件事。

### 1. `AudioVoice` —— 一个可复用的播放器

一个 GameObject + 一个 AudioSource。它和原版的区别就一句：**会被回收，不会被销毁。**

```csharp
public void StopAndReset()   // 回池
{
    m_source.Stop();
    m_source.clip = null;
    m_source.loop = false;
    m_go.SetActive(false);   // 闲置时不参与场景音频更新
    Id = 0;                  // ⚠️ 关键：已经发出去的旧句柄自动失效
}
```

`Id = 0` 这个细节值得单说：**播放器会被复用，但编号永不复用。**
旧句柄（Id=7）在新音效（Id=8）上 `Stop` 时不会误伤 —— 这就是 **ABA 问题**的解法。
（有专门测试：`Stop_WithStaleHandle_DoesNotStopTheNewVoice`。）

> 📌 顺手对照 A7：`InputActionId` 的 **`0` 是合法索引**，绝不能当空值哨兵；
> 而这里的 **`0` 就是"无效句柄"**。两个类型取舍相反，因为一个是"稠密下标"、
> 一个是"外部发放的凭据"——**凭据天然需要一个"没拿到"的表示，下标没有这个余地。**

### 2. `AudioManager` —— 池 + 规则

- **池直接复用 A2 的 `ObjectPool<AudioVoice>`**。分工写清楚：**并发上限由 `AudioManager` 管，池只负责复用**。
- 宿主 `[NBC]AudioHost` **创建那一刻**就 `DontDestroyOnLoad`。
  ⚠️ 只在 `Application.isPlaying` 时调 —— EditMode 下调它会报错，而 EditMode 测试需要宿主存在（否则池逻辑没法测）。
- `Tick()` 每帧回收：**先查 `IsAlive`**，再问探针"还在播吗"。

### 3. 音量分组

```
最终音量 = 分组音量 × 单次音量          静音时是 0
```

- 三个分组 **BGM / SFX / UI**，各自独立可调、可静音。
- 静音**记住原音量**：`IsMuted` 和 `Volume` 分开存，取消静音能恢复。
- ⚠️ **一个很容易写错的点**：调分组音量时要**重算**，用的必须是**单次音量**。
  如果拿"当前最终音量"再乘一遍 → 每调一次就小一截（0.5 → 0.25 → 0.125…）。
  所以 `AudioVoice` 存了 `RequestVolume`。这条有专门测试
  （`SetBusVolume_RecomputesPlayingVoicesWithoutCompounding`）。

### 池满的规则（**写死，避免猜**）

1. 在正在播的里面找**优先级最低**的；**同级取最老的**（按发放顺序）
2. 它的优先级**严格低于**新请求 → **抢占**它（停掉、复用）
3. 否则 → **丢掉新请求**，返回无效句柄，计数

> ⚠️ 「**严格更低**」四个字是关键：**同级不抢**。
> 否则两个同优先级的音效会互相踩，表现是"密集打击音时后一个把前一个吃掉" ——
> 比丢一个音效更难查。
> 推论：`Critical` **永远不会被抢占**（没有比它更高的），这正是它存在的意义 ——
> 剧情语音不该被打击音吃掉。

### 三个刻意的设计选择

**(a) 只收 `AudioClip`，不收资源地址。**

`FW-M08` 的原文是"背景音乐 + 3D 音效池 + 音量分组 + 回池"，**没有"按地址加载"**。
原版把加载和播放焊在一起，正是它不好测的原因之一 —— 一调 `ResMgr` 就得起整个资源系统。
拆开后 `AudioManager` 是纯播放层，EditMode 里 `AudioClip.Create(...)` 就能测。
**代价**：调用方要多写"加载 → 播放 → 在 `VoiceEnded` 里释放素材句柄"。

**(b) `Tick()` 不带 `deltaTime`。**

A5 / A7 需要时间，所以把时间做成参数。这里**不需要**："播完了没有"**由探针回答**，
不由"我们记的秒数"推算 —— 自己算时间会和 `AudioSource` 的真实进度**漂移**
（改 pitch、暂停、编辑器卡顿都会偏）。
**不引入第二份时间，就不会有不一致。**

**(c) `IAudioPlaybackProbe` 我在文件头明说它是"测试缝"，不假装是架构。**

`AudioSource.isPlaying` 在 EditMode 下**永远是 false 且不会推进**，不注入就根本测不了"播完回池"。
它**不像** `IInputSource` 那样是"将来换后端"的真抽象。
好处是：不但能测，还能**数出探针被问了几次** —— 于是"起播那一帧不判定"也成了可断言的事实。

### 顺带一个事件设计的坑

结束通知分了 **4 种原因**：`Finished` / `Preempted` / `Stopped` / `Lost`。

看着像过度设计，但调用方要靠这个事件**释放素材句柄**（选择 a 的代价）——
**只在"自然播完"时通知的话，被抢占和被停掉的音效就会漏通知 → 句柄泄漏。**

> 而这正是我**第一版写错的地方**：缓冲"本帧结束的播放器"时**只存了句柄、没存原因**，
> 派发时写死传 `Finished`。后果是"宿主都没了"被上报成"自然播完了"。
> 详见 `Docs\06` §16.6 —— **和 FW-09 本身是同一类病：看起来在正常运行，实际上信息已经丢了。**

## ⑤ 自测 5 问

先自己想，答案在下面。

1. 原版 `Destroy(AudioSource)` 到底销毁了什么？为什么"与缓存池冲突"这个说法不成立？
2. 为什么 `StopAndReset()` 里要把 `Id` 归零？不归零会发生什么？
3. 池满了，新来的音效优先级和池里最低的一样高。会发生什么？为什么这么设计？
4. 调分组音量时，如果不存 `RequestVolume`、直接拿当前音量乘，会出现什么现象？
5. `Tick()` 为什么不需要 `deltaTime`？（提示：想想 A5 的 `SceneLoader` 为什么需要）

<details>
<summary>点开看答案</summary>

1. 只销毁 `AudioSource` **组件**，宿主 GameObject 还活着。缓存池**全程没参与**音频路径
   （音频只从 `ResMgr` 取 `AudioClip`），所以谈不上"冲突"。
   真正的问题是**不复用** —— 而归因不同，修法就不同。
2. 播放器会被复用，但**句柄不能复用**。不归零的话，旧句柄的 Id 会和某个新音效撞上 →
   `Stop(旧句柄)` 会**误停一个不相干的新音效**（ABA 问题）。
3. **丢弃新请求**（返回无效句柄、`DroppedCount++`）。
   因为同级抢占会让两个同优先级音效互相踩，表现是"密集打击音时后一个吃掉前一个" ——
   那比丢一个音效更难查。
4. 每调一次分组音量，音量就**复合相乘一次**，越调越小（0.5 → 0.25 → 0.125…）。
   所以必须存下**单次音量**再重算。
5. 因为"播完了没有"是**问探针**得到的，不是"我们记的秒数"推算的 —— **没人需要时间参数**。
   A5 需要 `deltaTime`，是因为"超时"本身就是一个时间判断。

</details>

## ⑦ 一分钟面试版

> 音频模块我做的是"**播放器池 + 音量分组**"。
> 原框架每次播音效都 `AddComponent<AudioSource>()`，播完 `Destroy` 组件 ——
> 密集战斗时就是持续的组件创建销毁抖动。我改成从对象池取一个复用播放器，
> 播完 `StopAndReset` **回池、不销毁任何东西**；连播 200 次，
> 创建过的播放器数不超过并发上限 16。
>
> 第二个问题是宿主生命周期：原版的 `soundObj` 没有 `DontDestroyOnLoad`，
> 切场景后对象没了但字段还持着引用，下次播放就 `MissingReferenceException`。
> 我把宿主做成**创建即保护**，并且 `Tick` 里先做有效性检查 ——
> 宿主被外部销毁只会上报 `Lost`，不会抛异常。
>
> 音量按用途分 BGM / SFX / UI 三组，最终音量 = 分组音量 × 单次音量，静音时保留原值。
> 池满时按优先级抢占，**同级不抢** —— 否则同优先级的密集音效会互相踩。
>
> 一个设计取舍：**音频层只收 `AudioClip`、不碰资源加载**。
> 原框架把加载和播放焊在一起，结果这层根本没法单元测试。
> 拆开之后我用一个可注入的"还在播吗"探针，把"播完回池"这条逻辑变成了
> 确定性的 EditMode 测试 —— 而且能断言"**探针被问了几次**"。

## 附：本节出现的术语速查

| 术语 | 一句白话 |
| --- | --- |
| **播放器池（voice pool）** | 预先建好一批"挂好 AudioSource 的对象"，用的时候取、用完还，而不是每次新建 |
| **回池（recycle）** | 停止播放并复位，把对象放回闲置集合。**不等于销毁** |
| **宿主（host）** | 承载这些播放器的那一个常驻 GameObject。它的生命周期决定"切场景后还有没有声音" |
| **`DontDestroyOnLoad`** | Unity 的 API：让对象在场景切换时**不被销毁**。**只对根对象生效** |
| **伪 null（fake null）** | Unity 的 `Object` 重载了 `==`：被销毁的对象与 `null` 比较返回 true。所以 `x != null` 能测出"已销毁" |
| **音量分组（bus）** | 按用途划分的独立音量通道（BGM / SFX / UI），玩家分开调 |
| **优先级抢占** | 并发满了以后，用更重要的音效**顶掉**最不重要的一路 |
| **ABA 问题** | 同一个"槽位"被复用后，旧凭据会误指新数据。这里靠"编号永不复用"避免 |
