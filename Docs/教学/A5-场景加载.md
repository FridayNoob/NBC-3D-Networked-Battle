# ① 问题是什么

切场景（主城 → 战斗）要几秒。这几秒里玩家得**看到进度条**，不能干等着。

原框架用协程做这件事：

```csharp
while (!ao.isDone)
{
    EventTrigger("进度条更新", ao.progress);
    yield return ao.progress;
}
```

它**看起来**很合理：等进度、发进度、再等。**但它有两个问题，而且都不报错。**

---

# ② 最小例子

改造后：

```csharp
SceneHandle handle = SceneLoader.Instance.LoadAsync("BattleScene");

// 由 MonoManager 每帧驱动（运行时）；测试里自己调
SceneLoader.Instance.Tick(deltaTime);

EventCenter.Instance.AddEventListener<SceneProgressInfo>(SceneEvents.ProgressChanged, OnProgress);

```

# ③ 原版错在哪（FW-11）

## 那个 `yield return ao.progress` 根本不是"等待"

`yield return` 后面跟的东西叫**等待指令**（yield instruction）。
Unity 官方文档 [Yield instruction reference](https://docs.unity3d.com/Manual/coroutines-yield-instructions.html)
列出的**运行时**等待指令**只有 7 个**：

```
AsyncOperation          WaitForEndOfFrame      WaitForFixedUpdate
WaitForSeconds          WaitForSecondsRealtime WaitUntil
WaitWhile
```

**`float` 不在其中。**

所以 `yield return ao.progress` 里的 `ao.progress`（一个 0~1 的数字）**不构成任何等待** ——
协程会**立刻**继续执行。那个 `while` 实际上就是：

> **每一帧轮询一次 `isDone`，并且每一帧发一条进度事件。**

一个本来想表达"等进度更新"的写法，实际语义是"**每帧广播一次**"。

## 顺带叠加的第二个问题

```csharp
EventTrigger("进度条更新", ao.progress);   // ← T 被推断成 float
```

原版的事件中心按**类型**建通道。如果监听方是按 `int`（百分比）注册的，
就会命中 **FW-07**（同 key 不同型 → NRE）。
也就是说 **FW-11 和 FW-07 会叠加爆发**：一个负责"每帧发"，另一个负责"发就崩"。

## 后果盘点

| 问题 | 表现 |
| --- | --- |
| 每帧发一次进度 | 一次加载发**几百条**事件；进度条 UI 每帧重排 |
| `float` 当成等待时长 | 语义完全错位（读代码的人会以为它在等） |
| 缺超时 | 场景卡住就**永远卡住**，玩家看着进度条不动，也没有任何提示 |
| 进度不带场景地址 | 并发加载两个场景时，分不清这条进度是谁的 |

# ④ 做法

## 4.1 核心修法：**把时间从 Unity 手里拿回来**

```csharp
public void Tick(float deltaTime);
```

不再写协程，而是做一个 **`Tick` 驱动的状态机**：

| 场景 | 谁调用 `Tick` |
| --- | --- |
| 游戏运行时 | `MonoManager`（A4）每帧调用（`OnInit` 里注册） |
| **单元测试** | **测试自己调**，可以精确控制"过了多少秒" |

**这条设计的价值非常直接**：

> **超时逻辑（30 秒）如果必须真等 30 秒才能测，那它多半不会被测。**
> 抽成 `Tick` 之后，一次 `Tick(31f)` 就测完了 —— 而且**完全确定，不会 flaky**。

> **flaky**：同样的代码，有时通过有时失败。多半来自依赖真实时间/顺序。

⚠️ 这和 A7（输入）、A8（音频）、A10（状态机）是**同一个手法**：
**把不可控的环境（时间 / 设备 / 帧循环）变成可注入的参数。**

> 反例：A8 的 `Tick()` 就**不带** `deltaTime` —— 因为那里"播完了没有"由**探针**回答，
> 不需要自己算时间。**要不要注入时间，取决于这个模块需不需要"时间"这个概念。**

## 4.2 `OnInit` 里用 `Application.isPlaying` 挡住 EditMode

```csharp
protected override void OnInit()
{
    if (Application.isPlaying)
    {
        MonoManager.Instance.AddUpdateListener(OnUpdate);
    }
}
```

为什么要有这个判断？

- EditMode 下 `Update` **不执行**（A1 的 5 对照实验实测），注册了也没用
- 更糟的是：`MonoManager.Instance` 会**平白创建一个宿主 GameObject** —— 测试里留下一堆垃圾

## 4.3 进度**只在真的变化时**广播

```csharp
if (Mathf.Abs(progress - m_lastPublished) < ProgressEpsilon)   // 0.001
{
    return;   // 变化太小就不发
}
```

**效果**：一次加载的事件条数从"**几百条**"降到"**几条到几十条**"。

这是 FW-11 最直接的修复证据，有专门一条测试盯着它：

```
Load_DoesNotPublishProgressOnEveryTick
    → 连续 10 帧进度不变，证明只发 1 条而不是 10 条
```

## 4.4 超时：**并且要把卡住的场景卸掉**

```csharp
m_elapsed += deltaTime;
if (m_elapsed > DefaultTimeoutSeconds)   // 默认 30 秒
{
    // ① 上报失败
    // ② ⚠️ 卸载那个场景 —— 否则它一直占着内存
}
```

**"卸载"这一步最容易被忘**：只报个失败就完事的话，那个加载了一半的场景**还挂在内存里**，
玩家重试几次就把内存吃光了。

## 4.5 进度事件带上**场景地址**

```csharp
public readonly struct SceneProgressInfo
{
    public readonly string Location;   // ← 哪个场景的进度
    public readonly float Progress;
}
```

因为**可能同时加载两个场景**（比如"战斗场景 + 战斗 UI 场景"）。
不带地址的话，进度条会显示成一个来回跳的乱数。

## 4.6 场景一律走**资源层**（YOO-08）

原版直接用 `SceneManager.LoadSceneAsync`。改造后一律：

```
SceneLoader → AssetManager.LoadSceneAsync → IAssetProvider → YooAsset
```

**好处**：将来换资源方案，**场景加载零改动**。
（这也让场景加载能在 EditMode 里用假加载器测 —— 不需要真的打包。）

# ⑤ 一处**如实的降级**（不装成"能用"）

`ISceneLoadOperation.WaitForAsyncComplete()` 在适配层里**做不到真的等待**：

YooAsset 有意把 `SceneHandle.WaitForAsyncComplete()` 设成了 `internal`
（`SceneHandle.cs:49-51`，注释写明"场景加载不支持异步转同步"）。

所以适配层的实现选择：

```csharp
public void WaitForAsyncComplete()
{
    Debug.LogWarning("[YooAssetSceneOperation] 场景加载不支持异步转同步，这个调用不会真的等待。");
    // 然后返回
}
```

**为什么不假装成功？**
因为"静默降级"是本项目最忌讳的。如果它什么都不说就返回，
调用方会以为"等到了"，然后在场景还没好的时候去访问它 —— **又是一次静默失败**。

> **能做的事就做；不能做的，响亮地说出来。**

# ⑥ 自测 4 题

**1.** `yield return ao.progress` 为什么不是"等待"？它实际在做什么？
**2.** 为什么把超时逻辑抽成 `Tick(deltaTime)` 之后才**测得动**？
**3.** 超时之后为什么必须**卸载**那个场景？
**4.** `WaitForAsyncComplete` 做不到时，为什么选"打警告"而不是"悄悄返回"？

<details>
<summary>点开看答案</summary>

**1.** 因为 `yield return` 后面跟的必须是**等待指令**，而 Unity 只认 7 种，`float` 不在其中。
   所以协程立刻继续 —— 那个 `while` 实际是"**每帧轮询 `isDone` + 每帧广播一条进度**"。

**2.** 因为超时是"过了 30 秒就失败"。如果时间来自真实世界，测试就得**真等 30 秒**
   （而且不稳定）。把 `deltaTime` 做成参数后，一次 `Tick(31f)` 就测完，且完全确定。

**3.** 因为那个场景**已经加载了一部分并占着内存**。只报失败不卸载的话，
   玩家重试几次就把内存吃光 —— 表现为"越玩越卡，最后崩"。

**4.** 因为"静默降级"最危险：调用方会以为等到了，然后在场景还没好的时候访问它，
   **又是一次静默失败**。打警告至少让人当场知道"这个调用在这里不成立"。
</details>

# ⑦ 一分钟面试版

> 原框架切场景的协程里写着 `yield return ao.progress`。
> 但 `yield return` 后面必须跟**等待指令**，Unity 官方只认 7 种，
> **`float` 不在其中** —— 所以那一行**不构成任何等待**，协程立刻继续。
> 那个 `while` 实际上是"每帧轮询 + **每帧广播一条进度事件**"，
> 一次加载发几百条，进度条每帧重排。而且如果监听方按 `int` 注册，还会叠加另一个 NRE 问题。
>
> 我的修法是**把时间从 Unity 手里拿回来**：不写协程，改成 `Tick(deltaTime)` 驱动的状态机。
> 运行时由公共宿主每帧调；**测试里自己调**。
> 这条的价值很直接：**超时逻辑如果必须真等 30 秒才能测，那它多半不会被测** ——
> 抽成 `Tick` 之后一次 `Tick(31f)` 就测完，而且完全确定不 flaky。
>
> 顺带修了几件事：进度**只在真的变化时**才广播（事件数从几百条降到几条）；
> 加上 30 秒超时，**并且超时后要把那个卡住的场景卸掉**（不卸的话它一直占内存）；
> 进度事件带上场景地址（并发加载时能分清是谁的）；
> 场景加载一律走资源层，将来换资源方案零改动。
>
> 还有一处**如实的降级**值得一提：YooAsset 有意把场景的"异步转同步"设成了 internal，
> 所以适配层做不到真的等待。我让它**打一条警告再返回**，而不是假装成功 ——
> 因为调用方会以为等到了，然后在场景还没好的时候去访问它，那又是静默失败。
> **能做的就做，不能做的响亮地说出来。**

# 附：术语速查

| 术语 | 一句白话 |
| --- | --- |
| **等待指令（yield instruction）** | `yield return` 后面能跟的那几种特殊对象；Unity 只认 7 种 |
| **轮询（polling）** | 每帧去问一次"好了没"，而不是等通知 |
| **`Tick(deltaTime)`** | 把"过了多少时间"当参数传进来，而不是自己去读真实时间 |
| **flaky** | 同样的代码有时过有时不过，多半因为依赖真实时间或顺序 |
| **降级（degradation）** | 某个能力做不到时，退而求其次的做法。**关键是别装成做到了** |
| **`internal`** | C# 访问修饰符：只有同一个程序集里能访问 |
