# ① 问题是什么

## 先看一个具体场景

帧同步的战斗里，客户端 A 和客户端 B 都要算"角色往哪走"：

```csharp
Vector3 delta = direction * speed * Time.deltaTime;
position += delta;
```

用 `float` 算。**在单机上完全没问题。** 但在帧同步里：

> 服务端要拿客户端 A 的操作**自己算一遍**，用来校验 A 有没有作弊。
> 如果服务端算出来的位置和 A 算出来的**差了一点点**，那就"对不上"——轻则误判作弊，重则两端画面越跑越远。

**而 `float` 恰好会差那一点点。** 原因：

- **IEEE 754 只规定了加减乘除的舍入，没规定 `Sin`/`Sqrt`/`Atan2` 这些函数** ——
  不同运行时的实现可以不一样（.NET vs Mono vs IL2CPP，甚至同一个 Mono 的不同优化开关）
- **x86 和 ARM 的浮点中间精度可能不同**（一个用 80 位寄存器算完再存回 64 位）
- **编译器可能做"融合乘加"（FMA）**，把 `a*b+c` 算成一次运算，舍入点就变了

**一次不同，之后每一步都会放大** —— 两个玩家的位置越差越远，几分钟后就完全对不上。

## 所以要什么

**要一个"位级别确定"的数**：在任何平台、任何编译器、任何优化开关下，同样的输入一定得到**完全相同的二进制结果**。

**定点数**就是这个答案：用整数运算模拟小数。

# ② 最小例子

```csharp
// Q32.32：64 位整数，小数点固定在第 32 位
Fix64 a = Fix64.FromInt(3);          // 原始值 3 * 2^32
Fix64 b = Fix64.Half;                // 0.5
Fix64 c = a * b;                     // 1.5
Fix64 d = c / a;                     // 0.5

// 向量
FixVector3 pos = new FixVector3(Fix64.One, Fix64.Zero, Fix64.Zero);
FixVector3 dir = target - pos;
FixVector3 step = dir.Normalized() * speed;

// 三角（CORDIC，纯整数）
Fix64 angle = FixMath.Atan2(dir.Y, dir.X);
Fix64 s = FixMath.Sin(angle);
```

**关键数字**：

```
1.0  →  0x00000001_00000000   (1L << 32 = 4294967296)
0.5  →  0x00000000_80000000
-2.25 → 0xFFFFFFFD_C0000000
```

**范围**约 ±21 亿，**精度** 1/2³² ≈ 2.3e-10。

# ④ 做法

## 4.1 表示法：Q32.32，以及它换掉了什么

```
┌────────────── 64 位 ──────────────┐
│  32 位整数部分  │  32 位小数部分   │
└───────────────────────────────────┘
```

**和 `float` 的取舍**：

| | `float` | `Fix64` |
| --- | --- | --- |
| 范围 | ±3.4e38 | ±21 亿 |
| 精度 | 相对（越小越准） | **绝对**（恒定 2.3e-10） |
| 确定性 | ❌ | ✅ |

**范围小了这么多，为什么能接受？**
游戏里的坐标、速度、时间都在几万以内，**不需要浮点那种指数范围**；
需要的恰恰是**确定性**和**恒定精度**。

## 4.2 溢出：**饱和，不回绕、不抛异常**

```csharp
public static Fix64 operator +(Fix64 a, Fix64 b)
{
    long result = unchecked(a.m_raw + b.m_raw);

    // 有符号加法溢出判据：两个操作数符号相同、且与结果符号不同
    if (((a.m_raw ^ result) & (b.m_raw ^ result)) < 0L)
    {
        return a.m_raw >= 0L ? MaxValue : MinValue;   // 饱和
    }

    return new Fix64(result);
}
```

三种做法，选了第三种：

| 做法 | 后果 |
| --- | --- |
| **回绕（wrap）** | `最大值 + 1` 突然变成**最小值** —— 在位移里表现为"角色瞬移到地图另一头"，而且**不报错** |
| **抛异常** | 这是逐帧跑的仿真代码，服务端为了一个数值溢出崩掉，代价太大 |
| **饱和（saturate）** | 确定性（同样输入必得同样结果），行为可预期（"顶到上限"） |

⚠️ **代价**：溢出**不报错**，会被悄悄夹住。所以要有测试守边界。
**唯一的例外是除以 0** —— 那是逻辑错误，当场抛。

## 4.3 ⚠️ 乘除法需要 **128 位中间结果**（这段最容易写错）

两个 Q32.32 的原始值相乘是 **Q64.64**。直接写：

```csharp
long result = (a.m_raw * b.m_raw) >> 32;   // ← 错！a*b 那一步就溢出了
```

**而 `Math.BigMul` 在 netstandard2.1 / Unity 里没有**（那是 .NET Core 3.0+ 才有的）。
所以只能手写：**把 64 位拆成两个 32 位"肢"**，做四次乘法再拼接：

```csharp
ulong aLo = ua & 0xFFFFFFFFUL;
ulong aHi = ua >> 32;
ulong bLo = ub & 0xFFFFFFFFUL;
ulong bHi = ub >> 32;

ulong p0 = aLo * bLo;
ulong p1 = aHi * bLo;
ulong p2 = aLo * bHi;
ulong p3 = aHi * bHi;

ulong lo = p0;
ulong hi = p3;

// 把 (p1 + p2) << 32 累加进去
ulong mid = (lo >> 32) + (p1 & 0xFFFFFFFFUL) + (p2 & 0xFFFFFFFFUL);
lo = (lo & 0xFFFFFFFFUL) | (mid << 32);
hi += (p1 >> 32) + (p2 >> 32) + (mid >> 32);

// 要 (hi:lo) >> 32。hi 的高 32 位非 0 就说明超过 64 位 → 饱和
if ((hi >> 32) != 0UL) return negative ? long.MinValue : long.MaxValue;
ulong magnitude = (hi << 32) | (lo >> 32);
```

**除法更麻烦**：`(a << 32) / b` 里的 `a << 32` 本身就会溢出。
做法是**二进制长除法**：先算整数部分，再逐位求 32 位小数：

```csharp
ulong quotient = ua / ub;
ulong remainder = ua % ub;

if (quotient > 0x7FFFFFFFUL) return negative ? long.MinValue : long.MaxValue;

ulong fraction = 0UL;
for (int i = 0; i < 32; i++)
{
    remainder <<= 1;        // ⚠️ 每步只左移 1 位，所以不会溢出
    fraction <<= 1;
    if (remainder >= ub) { remainder -= ub; fraction |= 1UL; }
}
```

⚠️ 代价是 **32 次循环**。除法本来就不是最热的运算，用确定性换这点开销是划算的。

## 4.4 ⚠️ `Floor` 和 `ToInt` 是**两回事**（这里踩过坑）

```csharp
Fix64 v = Fix64.FromRaw(-(Fix64.OneRaw * 3 / 2));   // -1.5

Fix64.Floor(v)   // -2   ← 朝**负无穷**
v.ToInt()        // -1   ← 朝**零**
```

**两个都要有，别混用**（网格对齐用 `Floor`，转整数下标用 `ToInt`）。

**踩的坑**：`ToInt` 第一版我写的是 `m_raw >> 32`。看起来天经地义，但
**C# 的 `>>` 对负数是算术右移，也就是朝负无穷** —— 于是 `(-1.5).ToInt()` 给了 **-2**，而契约是 -1。

**这个 bug 有个可怕的特点**：`ToInt()` 在正数上**完全正确**，只在负数上错。
看代码看不出来，看那几个顺手的用例也看不出来。

> **顺带纠正一个相关的错**：`Floor` 用**掩码**写更准也更简单 ——
> `raw & ~(2^32 - 1)`。补码下掩掉低位永远是"往更小那边靠"。
> 我第一版写的是 `raw >> 32` 再判断负数减 1，**那一步是多余的**（右移已经朝负无穷了），
> 结果是 `floor(-1.5)` 得到 **-3**。

## 4.5 `FixMath`：**CORDIC**，以及为什么不能用查表

**CORDIC 的核心思想**：用"旋转一串预先算好的固定角度"来逼近目标角度，
而这些角度的**正切值恰好是 2 的幂** —— 于是"乘以 `tan`"退化成**移位**，不需要乘法器。

```csharp
// 旋转模式：已知角度求 cos/sin
Fix64 x = K;            // K 是 CORDIC 增益的倒数，先乘掉它
Fix64 y = Fix64.Zero;
Fix64 z = angle;

for (int i = 0; i < 32; i++)
{
    Fix64 xShift = ShiftRight(x, i);   // 即 x * 2^-i
    Fix64 yShift = ShiftRight(y, i);

    if (z.RawValue >= 0)
    {
        x = x - yShift;
        y = y + xShift;
        z = z - AtanTable[i];
    }
    else
    {
        x = x + yShift;
        y = y - xShift;
        z = z + AtanTable[i];
    }
}
// 结果：(x, y) 就是 (cos, sin)
```

**只需要 32 个 `atan(2^-i)` 常量**，全是整数移位和加减。

### ⚠️ 为什么**不用**查表，也**绝对不能**运行时生成表

**运行时生成表是绝对不行的**：

```csharp
// ❌ 这样写会毁掉帧同步
for (int i = 0; i < 1024; i++)
    table[i] = Fix64.FromDouble(Math.Sin(i * step));
```

因为 **`Math.Sin` 在不同运行时的实现可能不同** ——
服务端的 .NET 和客户端的 Mono/IL2CPP 会算出**不同的表**，
于是两端从第一步就不一样。而且这种 bug **只在联机时暴露、几乎查不出来**。

硬编码表也可以（但几百上千个采样值太占地方），CORDIC 更省、精度也更高。

**所以常量是"离线生成后硬编码"的**：

```
.dsh-tmp/fixprobe -- constants     ← 生成器（用 Math.Atan 各算一次）
        ↓ 输出的常量粘进源码
FixMath.AtanTableRaw[32]           ← 运行时读的是同一串二进制
```

## 4.6 两条"让错误不可能发生"的设计

| 设计 | 理由 |
| --- | --- |
| `FixVector3` **没有** `ToVector3()` / `FromVector3()` | `NBC.Shared` 不认识 `UnityEngine`（服务端没有 Unity）。转换由表现层**单向往外**做：逻辑 → 表现。**绝不反过来**，否则会把不确定性引回逻辑层 |
| `DeterminismGuardTests` 4 条**机械守卫** | "不许有浮点"编译器完全不管。所以读源码断言：无 BCL 数学调用、浮点只许出现在转换边界、无 `UnityEngine` |

**边界在哪**（这是允许的）：
```csharp
public static Fix64 FromDouble(double value)   // ← 外部浮点进来的唯一闸门
public double ToDouble()                       // ← 出去给表现层的唯一闸门
```

**进去之后就全是整数运算了。**

# ⑤ ⭐ 这一轮最有价值的东西：**数值对拍探针**

定点数的 bug 有个共同特点：**在顺手写的几个用例上全对，在日常数值上错**。

所以除了手写测试，我另写了一个 .NET 探针（`.dsh-tmp\fixprobe\`，**不属于交付物**），
**随机跑几百万组输入，和 `double` 对拍，把误差量出来**。

## 实测数字

| 项 | 误差 | 样本 |
| --- | --- | --- |
| 乘法（相对） | ≤ 4.9e-11 | 200 万 |
| 除法（**绝对**） | ≤ 1 个 raw ULP | 200 万 |
| `sin` / `cos` | ≤ 6.4e-9 / 6.9e-9 | 100 万（含几十圈大角度） |
| `atan2` | ≤ 1.45e-9 弧度 | 100 万 |
| `asin` / `acos` | ≤ 2.5e-9 / 2.2e-9 | 20 万 |
| 向量长度（相对） | ≤ 3.97e-7 | 20 万 |
| 归一化后长度误差 | ≤ 6.985e-10 | 2 万 |

## 探针抓到的 4 个问题（**3 个是真 bug**）

**① `Floor` / `Ceiling` 对所有负的非整数都错。** `floor(-1.5)` 得到 -3。
（多减了一步；`>>` 本来就是朝负无穷。）

**② `ToInt` / `ToLong` 用了算术右移。** 契约是"向零截断"，实际给了朝负无穷。

**③ `CordicVector` 的 z 累加符号反了。** `Atan2` 在**接近垂直**的向量上给出**符号相反**的结果（差 π），而其它输入全都正常。

**④ 我的判据写错了一次（不是代码错）**：除法的判据本来写成"相对误差 < 1e-7"，
在一个结果为 0.001 的样本上误报。但**定点数的固有量化是绝对量**（2⁻³²）——
结果越小相对误差越大，**那是表示法的性质**。正确的不变式是"**绝对误差 ≤ 1 个 ULP**"。

## ⚠️ 最关键的一条教训：**探针有覆盖盲区**

`ToInt` 那个 bug（②）是**手写测试**抓到的，**探针没抓到** ——
因为**探针压根没测 `ToInt`**。

> **再强的随机测试也覆盖不到它没调用的函数。**

发现之后我做了两件事：
1. 把 `ToInt` / `ToLong` 加进探针
2. 做**负向对照**：临时把 `ToLong` 改回算术右移 → 200 万样本里报 **999,961 处不一致**；
   恢复后全绿。**这才证明"扩展后的探针确实抓得到它"。**

## 一次"值不值得"的实测决策

`Sqrt` 原本只有"整数平方根 + 左移 16 位"，绝对误差 2⁻¹⁶。
`Asin/Acos` 走 `sqrt(1 - v²)`，于是角度误差被它卡在 1.4e-5。

加**一次牛顿迭代**（多一乘一除）：

| 项 | 加之前 | 加之后 |
| --- | --- | --- |
| 开方误差 | 1.526e-5 | **~1e-9** |
| 归一化长度误差 | 1.526e-5 | **6.985e-10** |
| `asin` / `acos` | 1.365e-5 | **2.5e-9 / 2.2e-9** |

**"值不值得"是量出来的，不是拍的。** 相应地，`Fix64Tests` 里的精度断言**被收紧了** ——
不是为了让测试过，是因为实现真的变好了。

# ⑥ 自测 5 题

**1.** `float` 为什么不能用在帧同步里？说出三条以上具体原因。
**2.** 定点数溢出的三种处理方式各有什么后果？本项目为什么选饱和？
**3.** 为什么乘除法需要 128 位中间结果？`Math.BigMul` 为什么不能用？
**4.** `Floor(-1.5)` 和 `(-1.5).ToInt()` 分别是什么？为什么两个都要有？
**5.** 为什么"查表"必须**硬编码**，不能运行时用 `Math.Sin` 生成？

<details>
<summary>点开看答案</summary>

**1.** ① IEEE 754 不规定 `Sin`/`Sqrt` 等函数的实现，不同运行时可以不一样；
   ② x86 与 ARM 的浮点中间精度可能不同；③ 编译器可能做融合乘加（FMA），改变舍入点。
   **而且一次不同之后每一步都会放大。**

**2.** **回绕**：最大值+1 变成最小值 → 位移里表现为"角色瞬移"，且不报错；
   **抛异常**：逐帧仿真代码为数值溢出崩掉，代价太大；
   **饱和**：确定性且行为可预期（"顶到上限"）。

**3.** 两个 Q32.32 的原始值相乘是 **Q64.64**，`a * b >> 32` 里的 `a * b` 就已经溢出了。
   而 `Math.BigMul` 是 .NET Core 3.0+ 才有的，**netstandard2.1 / Unity 里没有**，

   两端从第一步就不一样。硬编码之后，两端读的是同一串二进制。

# ⑧ 一分钟面试版

> 帧同步要求"同样的输入序列 → 同样的结果"。所以我不能用 `float`：
> IEEE 754 只规定了加减乘除的舍入，**没规定 `Sin`/`Sqrt` 这些函数的实现** ——
> .NET、Mono、IL2CPP 可能给出不同结果；再加上 x86 和 ARM 的中间精度差异、
> 编译器的融合乘加，一次不同之后每一步都会放大。
>
> 我用的是 **Q32.32 定点数**：64 位整数，小数点固定在第 32 位。
> 范围从 float 的 3.4e38 缩到 ±21 亿，但游戏里的坐标速度时间都在几万以内，
> 真正需要的是**确定性**和**恒定精度**。
>
> 有几个地方值得说：
> **溢出我选饱和**，不回绕也不抛异常 —— 回绕会让"变大"突然变成负数，
> 在位移里就是"角色瞬移到地图另一头"，而且不报错；抛异常则让服务端为一次数值溢出崩掉。
> **乘除法要手写 128 位中间结果**，因为两个 Q32.32 相乘是 Q64.64，
> 而 `Math.BigMul` 在 netstandard2.1 里没有，只能把 64 位拆成两个 32 位肢来算。
> **三角函数用 CORDIC**，只需要 32 个 `atan(2^-i)` 常量，纯整数移位加法。
> 这里有个关键点：**常量必须离线生成后硬编码** —— 如果运行时用 `Math.Sin` 生成表，
> 服务端和客户端会得到**不同的表**，那就正好毁掉帧同步，而且几乎查不出来。
>
> 验证上我做了件比较实在的事：写了个 .NET 探针，**随机跑几百万组输入和 `double` 对拍，
> 把误差量出来**，而不是"看起来对"。它抓到过三个真 bug ——
> 比如 `ToInt` 用了算术右移，在正数上完全正确、只在负数上错；还有 CORDIC 向量模式
> 在接近垂直的向量上符号反了。
>
> 不过我也发现探针有盲区：`ToInt` 那个 bug 是**手写测试**抓到的，
> 因为**探针压根没测 `ToInt`** —— 再强的随机测试也覆盖不到它没调用的函数。
> 补上之后我做了负向对照：把实现改回错的，200 万样本里报 100 万处不一致，
> 这才证明"扩展后的探针确实抓得到它"。

# 附：术语速查

| 术语 | 一句白话 |
| --- | --- |
| **定点数** | 用整数模拟小数：约定小数点在某个固定位置 |
| **Q32.32** | 64 位里 32 位整数 + 32 位小数 |
| **原始值（raw）** | 定点数内部存的那个整数。`1.0` 的原始值是 `1 << 32` |
| **饱和（saturate）** | 溢出时停在最大/最小值，而不是回绕 |
| **回绕（wrap）** | 溢出后从另一端重新开始（最大+1 变成最小） |
| **ULP** | 最小可表示单位。这里 1 ULP = 2⁻³² |
| **CORDIC** | 用固定角度的旋转序列逼近目标角度；因为 `tan(atan(2^-i)) = 2^-i`，乘法退化成移位 |
| **增益 K** | CORDIC 每步旋转都会把向量拉长一点，K 是这个累积倍率的倒数 |
| **牛顿迭代** | 用 `y' = (y + x/y)/2` 逼近平方根；**误差平方级收敛**，一步就很准 |
| **位级别确定** | 同样输入得到完全相同的二进制，不是"约等于" |
| **融合乘加（FMA）** | 把 `a*b+c` 当一次运算算，舍入点变了 —— 浮点不确定性的来源之一 |
| **`noEngineReferences`** | asmdef 开关：这个程序集不许引用 `UnityEngine` |
| **对拍** | 用另一套实现（这里是 `double`）算同样的输入，比对差异 |
| **覆盖盲区** | 再强的随机测试也测不到它没调用的函数 |
