# ① 问题是什么

游戏里有两类东西**反复出生和死亡**：子弹、特效、伤害飘字、敌人。

不用池的话，每发子弹都是 `Instantiate` + `Destroy`。而 Unity 的 `Instantiate`/`Destroy` 是**不便宜**的：
它们要分配内存、初始化组件、注册进场景；`Destroy` 之后还要等**垃圾回收**。
一秒几十发子弹就是每秒几十次这种操作 → **帧率一阵一阵地卡**（GC 尖峰）。

> **对象池**的思路很简单：**别删，收起来。**
> 用完的子弹不是销毁，而是"放回架子上"；下次要用直接从架子上拿。
> 架子上放多少是**固定上限**。

**用"造/砸"改成了"取/还"，创建次数从"跟使用次数同阶"降到"跟并发峰值同阶"。**

# ② 最小例子

```csharp
// 纯 C# 对象池：工厂由调用方注入
var pool = new ObjectPool<MyObj>("MyObj", () => new MyObj(), maxSize: 64);

MyObj a = pool.Get();
pool.Release(a);          // 回池，不销毁

// GameObject 池
var bullets = new GameObjectPool("Bullet",
    () => Object.Instantiate(bulletPrefab), maxSize: 64);

GameObject go = bullets.Spawn();
bullets.Despawn(go);
```

看关键数字（本项目实测）：

| 方式 | 100 万次取放耗时 |
| --- | --- |
| 原框架（`List.RemoveAt(0)`） | 慢 |
| 现在的池 | **快 21.1 倍** |

# ③ 原版错在哪（5 条）

原框架的 `PoolMgr`：

```csharp
public class PoolData
{
    public GameObject fatherObj;
    public List<GameObject> poolList;          // ← P-11：public 容器

    public GameObject GetObj()
    {
        GameObject obj = poolList[0];
        poolList.RemoveAt(0);                  // ← FW-04：O(n)！
        obj.SetActive(true);
        return obj;
    }

    public void PushObj(GameObject obj) { poolList.Add(obj); }   // ← FW-05：无上限
}
```

| 编号 | 问题 | 后果 |
| --- | --- | --- |
| **FW-04** | `poolList.RemoveAt(0)` | 每取一个都要把后面所有元素往前挪 → **O(n)**。池越大越慢，而且**池越大本来是为了更快**，结果反过来了 |
| **FW-05** | `PushObj` 只 `Add`，**没有上限** | 战斗结束回到主城，池里躺着几千个闲置对象，**永远不释放** —— 内存只涨不跌 |
| **P-04** | `Clear()` 只 `poolDic.Clear()` | 名字叫"清空"，**实际什么都没销毁** —— 池里的 GameObject 变成场景孤儿。而注释写着"主要用在场景切换时" |
| **P-10** | 池空时异步补货的新对象**没有 `SetParent(poolObj)`** | 那段时间它是**场景根对象**，不受池管理，`Clear()` 也清不到它 |
| **P-11** | `public List<GameObject> poolList` / `public GameObject fatherObj` | 谁都能拿到容器直接改，绕过所有父子关系维护 |

# ④ 做法

## 4.1 三条接口决策（当时由负责人拍板）

| # | 决策 | 为什么 |
| --- | --- | --- |
| 1 | **工厂由调用方注入**（`Func<T>`），池不认识"怎么造对象" | 池是通用工具。让它自己 `new` 或 `Instantiate`，就等于把"造什么"烧进池里 |
| 2 | **不要中心化的 `PoolMgr` 单例** | 谁用谁自己持有一个池。中心化会让"谁在什么时候释放了什么"变得无法追踪 |
| 3 | **同步 `Get` / `Release`** | 异步补货（原版那样）会让"取的时候可能还没造好"变成一个到处都要处理的状态 |

## 4.2 O(1)：用 `Stack` + `HashSet`

```csharp
private readonly Stack<T> m_pool = new Stack<T>();     // 闲置的
private readonly HashSet<T> m_inUse = new HashSet<T>(); // 在外的
```

- **取**：`m_pool.Pop()` —— **O(1)**
- **还**：`m_inUse.Remove(item)` 判断"是不是真的在外面"（**O(1)**），把重复归还/归还别人的对象**当场报错**

> ⚠️ `HashSet` 那个判断很关键。不加的话，"**同一个对象归还两次**"会让池里出现两份引用，
> 于是同一个对象被两个地方同时"取到" —— 那是**极难查的灵异 bug**。

## 4.3 上限与失效校验

```csharp
public void Release(T item)
{
    ...
    // FW-05：容量上限。满了就丢弃，而不是无限增长。
    if (m_maxSize > 0 && m_pool.Count >= m_maxSize)
    {
        m_totalDestroyed++;
        DestroyItem(item);
        return;
    }

    m_pool.Push(item);
}
```

另外 `Get()` 里有一处**校验**：从栈顶往下找第一个"仍然有效"的对象，失效的直接丢掉不算复用。

```csharp
while (m_pool.Count > 0)
{
    T candidate = m_pool.Pop();
    if (m_isValid == null || m_isValid(candidate)) { item = candidate; break; }
    m_totalDestroyed++;
}
```

**这是为谁准备的？** 为"A8 音频播放器"那种情况：宿主 GameObject 被外部销毁了，
池里那个引用就变成了 Unity 的"伪 null"。
> **伪 null**：Unity 重载了 `==`，被销毁的对象与 `null` 比较会返回 true。
> 所以 `isValid` 很容易写：`v => v.IsAlive`。

## 4.4 `PoolStats`：把"内部状态"变成一份**快照**

P-11 的修法是"容器 `private`"，但**调试面板还是需要看数字**。
所以对外给一个**只读快照**：

```csharp
public PoolStats GetStats();
```

`PoolStats` 是结构体，包含 `TotalCreated` / `TotalSpawned` / `TotalDespawned` / `TotalDestroyed` /
`PeakInUse` / `PeakInPool` 等。

> **这就是"能不能观测"和"能不能乱改"的分界**：
> 给数字，不给容器。

## 4.5 `IPoolable`：让对象自己知道"我出池了/回池了"

```csharp
public interface IPoolable
{
    void OnSpawned();
    void OnDespawned();
}
```

池在 `Get`/`Release` 时会检查对象有没有实现它，有就调一下。
用途：清状态（比如把血条重置、把粒子停掉）。**可选接口**，不实现就跳过。

## 4.6 `GameObjectPool` 为什么单独一层

`ObjectPool<T>` 管的是"取和还"；`GameObjectPool` 额外管**父子关系**（P-10 的修法）：

```csharp
// 任何进池的对象都先挂到池根下 —— 包括"新建出来的"
private GameObject CreateIdleObject()
{
    GameObject go = m_factory();
    go.transform.SetParent(Root, false);
    go.SetActive(false);
    return go;
}
```

为什么要挂？**为了在 Hierarchy 里一眼看得出"这些东西归池管"**，
而且 `Clear()` 能一次清干净（不然场景根上散着一堆孤儿）。

# ⑤ 一个方法论教训：那次"没报错"的实验

A2 里还做过一次 **asmdef 反向引用实验**，结论是 **inconclusive（没有信息量）**，
但当时差点被当成"验证通过"。

**原计划**：把 `NBC.Game` 加进 `Framework.asmdef` 的 references，期待 Unity 报循环引用。

**当时看到的**：Unity **没有报错**。

**进一步测量后发现：这次实验根本没跑起来。** 证据是三条时间戳：
`Framework.asmdef` 的修改时间、`Library/ScriptAssemblies` 的产物时间、
以及 Unity 的日志时间 —— 三者对不上，说明 **Unity 压根没重新编译**。

> ⚠️ **"没报错"可能是"实验没跑"，而不是"验证通过"。**
> 这是本项目第二次踩这个坑（第一次是 A1 那个基线全 0 的对照实验）。

**整改（Plan B）**：不再依赖 Unity 的编译行为，改成**用测试断言配置本身** ——
这就是 `FrameworkLayeringTests`：读 `Framework.asmdef` 的文本，断言 `references` 必须为空。

⚠️ 而且它带一条**阳性对照**：故意断言"`NBC.Game` 的引用里**有** `NBC.Framework`" ——
这条必须通过。为什么？

> **没有阳性对照的断言可能是"永远通过"的假绿。**
> 如果我的解析器写错了、什么都读不出来，那么"引用为空"这条也会通过 —— 但那是假的。
> 阳性对照就是用来证明"**解析器真的能读出东西**"的。

# ⑥ 自测 4 题

**1.** 原框架的池为什么"越大越慢"？
**2.** 为什么"归还两次"必须当场报错？
**3.** `isValid` 校验是给谁准备的？为什么 Unity 的"伪 null"让这件事变简单？
**4.** 为什么"引用为空"那条断言必须配一条阳性对照？

<details>
<summary>点开看答案</summary>

**1.** 因为取的时候用的是 `List.RemoveAt(0)` —— 移除第 0 个要把后面**所有元素往前挪**，是 O(n)。
   池越大，每次取要挪的元素越多。

**2.** 不报错的话，池里会出现**两份对同一个对象的引用**，
   于是同一个对象可能被两个地方同时"取到" —— 两边互相改状态，表现为极难查的灵异 bug。

**3.** 给"宿主被外部销毁"的情况准备的（比如 A8 的音频播放器随场景被销毁）。
   因为 **Unity 的 `Object` 重载了 `==`**：被销毁的对象与 `null` 比较返回 true，
   所以校验能写成很简单的 `v => v.IsAlive`，不需要额外记录"谁被销毁了"。

**4.** 因为"**永远通过**"的断言也是一种假绿。
   如果解析器写错了、什么都读不出来，"引用为空"照样通过。
   阳性对照（断言某个**存在**的引用能被读出来）证明解析器真的在工作。
</details>

# ⑦ 一分钟面试版

> 原框架的对象池有五个问题：取对象用 `List.RemoveAt(0)` 是 O(n)，
> 池越大越慢；没有容量上限，战斗结束回主城池里躺着几千个对象永远不释放；
> `Clear()` 名字叫清空实际什么都不销毁，池里的 GameObject 变成场景孤儿；
> 异步补货的新对象没设父节点，那段时间不受池管理；还有内部容器是 `public` 的。
>
> 我重写成 `Stack` + `HashSet`：取是 O(1)，还的时候用 `HashSet` 判断"是不是真的在外面"，
> **重复归还当场报错** —— 不报的话池里会出现两份引用，同一个对象被两处同时取到，那是灵异 bug。
>
> 三条接口决策：**工厂由调用方注入**（池不认识怎么造对象）、**不要中心化单例**
> （谁用谁自己持有，中心化会让"谁释放了什么"无法追踪）、**同步 Get/Release**
> （异步补货会让"取的时候可能还没造好"变成到处都要处理的状态）。
>
> 对外只给 `PoolStats` 快照，不给容器 —— **给数字，不给容器**。
>
> 另外有个方法论教训：我本来想用"给 asmdef 加反向引用、看 Unity 报不报错"来验证分层，
> 结果 Unity **没报错**。但我核对时间戳发现 **Unity 压根没重新编译，实验根本没跑**。
> 所以改成"用测试读配置文件做断言"，而且加了一条**阳性对照** ——
> 因为一个不工作的解析器会让"引用为空"永远通过，那也是一种假绿。

# 附：术语速查

| 术语 | 一句白话 |
| --- | --- |
| **对象池** | 用完不删、收起来下次再用，创建次数从"跟使用次数同阶"降到"跟并发峰值同阶" |
| **O(n) / O(1)** | 数据量变大时，耗时是"线性增长"还是"不变" |
| **GC 尖峰** | 垃圾回收集中发生造成的卡顿 |
| **伪 null** | Unity 里被销毁的对象与 `null` 比较返回 true，所以 `!= null` 能测出"已销毁" |
| **快照（snapshot）** | 把内部状态**拷一份只读的**给外面看，而不是把容器本身给出去 |
| **阳性对照** | 一条"必须通过"的断言，用来证明你的检查手段真的在工作 |
| **inconclusive** | 实验没有产生信息量（不是因为结果对或错，而是它压根没跑） |
