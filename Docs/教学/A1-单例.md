# ① 问题是什么

原框架有这么一个东西：

```csharp
public class BaseManager<T> where T : new()
{
    private static T instance;
    public static T GetInstance()
    {
        if (instance == null) instance = new T();
        return instance;
    }
}
```

用法是"每个管理器继承它"，比如 `EventCenter : BaseManager<EventCenter>`。

它想解决的问题是**"全局只有一个"**。但它有三个洞，而且**都不报错**：

| 洞 | 后果 |
| --- | --- |
| **谁都能 `new` 一个** | `new EventCenter()` 合法 → 你拿到第二个实例，监听注册在一个上、触发在另一个上 → **事件永远不触发，却不报错** |
| **`GetInstance()` 可能返回 `null`** | 某个子类的静态状态被清过之后，它可能返回 null → 调用点全都要判空 |
| **没有并发/重入保护** | 两个线程同时第一次访问 → 建出两个实例 |

**第三个洞最阴**：它不是"多线程才会遇到"，而是"**在构造函数里访问自己**"就会遇到（见 §4.3）。

# ② 最小例子

```csharp
// 纯 C# 单例（不依赖 Unity）
public sealed class EventCenter : Singleton<EventCenter>
{
    protected override void OnInit() { /* 第一次创建时做一次 */ }
}

EventCenter.Instance.Trigger(id);   // Instance 永远不是 null

// 需要挂在 GameObject 上的（MonoBehaviour）单例
public sealed class MonoManager : SingletonAutoMono<MonoManager> { }

// 场景里存在就用现成的，不存在就自己建一个
MonoManager.Instance.AddUpdateListener(OnUpdate);
```

三件的分工：

| 类 | 用在什么场合 |
| --- | --- |
| `Singleton<T>` | **纯 C#**，不需要 Unity 生命周期（事件中心、资源管理器） |
| `SingletonMono<T>` | **场景里自己挂**的 MonoBehaviour 单例；没有就返回 null（由你决定怎么办） |
| `SingletonAutoMono<T>` | **不存在就自动建一个**并 `DontDestroyOnLoad`（公共宿主用） |

# ③ 原版错在哪（完整代码）

```csharp
public class BaseManager<T> where T : new()
{
    private static T instance;

    public static T GetInstance()
    {
        if (instance == null)
            instance = new T();
        return instance;
    }
}
```

**逐条**：

**① `where T : new()` 与"禁止外部 new"是天生矛盾的。**

`new()` 约束的意思是"**T 必须有一个 public 无参构造**"。
而你想禁止外部 `new`，就得把构造函数设成 `private`。
**这两个要求不可能同时满足** —— 原框架选了前者，于是 `new` 一直是开放的。

C# 里没有"T 必须有 private 构造"这种约束。所以只能**换路子**：构造是 public 的，但**在构造里检查"这次 new 是不是从单例内部发起的"**。

**② `GetInstance()` 返回 null 的路径**：静态字段被重置（编辑器域重载、或者手工清）之后，如果有别的地方缓存了 `Instance`，就会拿到 null。

**③ 没有锁**：`if (instance == null) instance = new T();` 不是原子的。

# ④ 做法

## 4.1 `Singleton<T>`：用"线程内的创建标记"堵住外部 new

```csharp
public abstract class Singleton<T> where T : Singleton<T>, new()
{
    [ThreadStatic] private static bool t_creatingInsideSingleton;

    private static volatile T s_instance;
    private static readonly object s_lock = new object();

    protected Singleton()
    {
        // ⚠️ 只有"从单例内部发起"的 new 才允许通过
        if (!t_creatingInsideSingleton)
        {
            throw new InvalidOperationException(
                "禁止直接 new 单例。请用 " + typeof(T).Name + ".Instance。");
        }
    }

    public static T Instance
    {
        get
        {
            if (s_instance == null)
            {
                lock (s_lock)
                {
                    if (s_instance == null)
                    {
                        t_creatingInsideSingleton = true;
                        try { s_instance = new T(); }
                        finally { t_creatingInsideSingleton = false; }
                        s_instance.OnInit();
                    }
                }
            }
            return s_instance;
        }
    }
}
```

三个细节值得说：

**`[ThreadStatic]`**：这个标记**每个线程各有一份**。
如果用普通 `static bool`，线程 A 正在创建时线程 B 恰好 `new`，就会**被误判成"内部创建"而放行**。
（`[ThreadStatic]`：让静态字段"每个线程各一份"，而不是全局共享一份。）

**`volatile` + 双重检查锁**：`volatile` 保证"别的线程能看到最新的引用"。
外面那层 `if` 是为了**避免每次都进锁**（绝大多数访问都是"已经有了"）。

**`OnInit()` 钩子**：第一次创建完成后调一次，让子类做初始化，而**不用**去覆写构造函数。

## 4.2 `SingletonMono<T>` / `SingletonAutoMono<T>`：Unity 那一侧

- `SingletonMono<T>`：在场景里 `FindObjectOfType<T>()` 找现成的；找不到返回 `null`（**不擅自建**，因为"该不该建"是你的决定）。
- `SingletonAutoMono<T>`：找不到就 `new GameObject` 建一个并立刻 `DontDestroyOnLoad`。

这里有个细节是 P-13 的修法，A4 会细讲：**`DontDestroyOnLoad` 必须在创建那一刻就调**，
不能等 `Start` —— 否则存在"已经建好了但还没受保护"的一帧窗口。

## 4.3 ⚠️ 当时被我自己推翻的一个设计（补写时要讲清楚的）

第一版我在构造里是这么判的：

```csharp
protected Singleton()
{
    if (s_instance != null) throw new InvalidOperationException("已经有一个了");
}
```

**它挡不住"第一次访问就是 new"**：

```csharp
var a = new EventCenter();   // s_instance 还是 null → 放行！
var b = EventCenter.Instance; // 又建了一个 → 现在有两个了
```

**两个实例，而且不报错** —— 正是我们要防的那个洞。

所以改成"**看这次 new 是谁发起的**"（线程内的创建标记），而不是"看现在有没有实例"。
测试里专门有一条钉住这个隐蔽路径：`NewOutsideSingleton_EvenBeforeAnyAccess_Throws`。

> **教训**：判据要选对。
> "有没有实例"看起来是等价的问题，但在"第一次访问"这个时刻，两者的答案不同。

## 4.4 `SingletonRegistry`：让测试能清理

测试之间必须隔离，否则上一个用例留下的单例会影响下一个。
所以有一个注册表，可以 `ResetAll()` 把所有单例清掉。

⚠️ **这是"给测试用的基础设施"，不是业务能力** —— 它只该在测试和编辑器工具里调。

# ⑤ 一个重要发现：**EditMode 不调用 `Awake`**

这一轮最值钱的产出不是代码，是这个结论。

首轮 15 个用例全放 EditMode，跑了 **11 绿 4 红**。红的全依赖"Unity 调用了 `Awake`"。
于是做了个 **5 对照实验**：五种写法各建一个对象，看 `Awake` 有没有被调 ——

```
A = B = C = D = E = 0
```

**连基线都是 0**，也就是说**在 EditMode 里 `Awake` 根本不会被调用**（编辑模式没有播放循环）。
这不是 bug，是 Unity 的设计。

结果：
- 8 个依赖 MonoBehaviour 生命周期的用例**搬到 PlayMode**
- `AwakeDispatchDiagnostic` 留着当**可复现的证据**
- 定下一条规矩：**EditMode 只测纯逻辑；MonoBehaviour 生命周期 / 协程 / `DontDestroyOnLoad` 一律 PlayMode**

> ⚠️ 记一个方法论教训：**"基线塌了的对照实验没有信息量"**。
> 那次实验里五个对照组全是 0，本来应该先问"这个实验到底跑起来了没有"。
> （这个坑后来在 A11 的 asmdef 实验里又踩了一次。）

**另外还有一个副产品**：那 8 个 PlayMode 用例里有 5 个"在泛型基类丢 `Awake` 时必然变红"，
它们全绿就等价于证明了 **Unity 会正常派发泛型基类里的 `Awake`/`OnDestroy`** ——
那个怀疑（P0 级）被排除，框架无需改动。

> **断言型测试比观察型实验更强**：观察型实验（打印日志看数值）会"看不懂就过去了"，
> 而断言型测试是"要么绿要么红"，**逼你说清楚预期是什么**。

# ⑥ 自测 4 题

**1.** 为什么 `where T : new()` 和"禁止外部 new"天生矛盾？
**2.** 构造里的判据为什么是"这次 new 是谁发起的"，而不是"现在有没有实例"？
**3.** `[ThreadStatic]` 不加会怎样？
**4.** 为什么 8 个用例必须从 EditMode 搬到 PlayMode？

<details>
<summary>点开看答案</summary>

**1.** `new()` 约束要求 `T` 有 **public 无参构造**；禁止外部 `new` 要求构造是 **private**。两个要求不可能同时满足。
   所以只能"构造保持 public，但在构造里检查这次 new 是不是单例内部发起的"。

**2.** 因为**第一次访问就是 `new`** 的时候，`s_instance` 还是 `null` ——
   "看有没有实例"会放行，于是建出第二个实例且不报错。看"谁发起的"才能堵住这条路径。

**3.** 两个线程同时第一次访问时：A 线程设了标记正在创建，B 线程也 `new`，
   **B 会被误判成"内部创建"而放行** → 建出两个实例。
   `[ThreadStatic]` 让标记每线程一份，就不存在这个误判。

**4.** 因为 **EditMode 下连 `Awake` 都不会被调用**（5 对照实验实测，连基线都是 0）。
   放在那里的用例测的是"我以为会发生的事"，结论是假的。
</details>

# ⑦ 一分钟面试版

> 原框架的单例有三个洞：`new()` 约束让外部可以随便 `new` 出第二个实例、
> `GetInstance()` 可能返回 null、没有并发保护。所以我重写了一套三件套：
> 纯 C# 的 `Singleton<T>`、需要挂物体的 `SingletonMono<T>`、以及不存在就自动建的 `SingletonAutoMono<T>`。
>
> 有个设计点值得说：**`where T : new()` 和"禁止外部 new"天生矛盾** ——
> `new()` 要求 public 构造，禁止外部 new 要求 private，两者不可能同时满足。
> 所以我用了"**线程内的创建标记**"：构造保持 public，但在构造里检查这次 `new` 是不是单例内部发起的。
> 这里还有个更细的坑：判据不能是"现在有没有实例" ——
> 因为**第一次访问就是 `new`** 的时候实例还是 null，那样会放行，于是建出两个且不报错。
>
> 另外这一轮有个比代码更值钱的发现：**EditMode 下 Unity 根本不会调用 `Awake`**
> —— 我做了个 5 对照实验，五种写法的计数**全是 0**，连基线都塌了。
> 所以依赖 MonoBehaviour 生命周期的测试**必须放 PlayMode**，
> 我搬了 8 个用例过去，并把那个诊断实验留着当证据。
>
> 顺带一个方法论收获：**断言型测试比观察型实验强** ——
> 打印日志的"实验"看不懂就过去了，而断言只有绿和红，逼你说清预期。

# 附：术语速查

| 术语 | 一句白话 |
| --- | --- |
| **单例** | 全局只有一个实例的类 |
| **`where T : new()`** | C# 泛型约束：要求 T 有一个 public 无参构造 |
| **`[ThreadStatic]`** | 让静态字段"每个线程各一份"，而不是全局共享 |
| **`volatile`** | 告诉编译器/运行时：这个字段可能被别的线程改，别做乐观优化 |
| **双重检查锁** | 先无锁判断一次（快路径），需要创建时才进锁 |
| **编辑器域重载（domain reload）** | Unity 重新编译脚本时会重建整个 C# 运行时状态，静态字段被清空 |
| **EditMode / PlayMode 测试** | 前者在编辑器里跑（没有播放循环），后者进播放模式跑（Unity 回调正常） |
| **对照实验** | 只改一个变量、其余保持相同的实验。**基线塌了就没有信息量** |
