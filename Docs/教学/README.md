## 每篇的标准结构（七段式）

按 `Docs\00` §15.3.1：

1. **① 问题是什么** —— 不用代码，讲清这东西解决什么问题
2. **② 最小例子** —— 错的写法 + 对的写法，一眼看出差别
3. **③ 原版错在哪** —— 配**原代码**，并说清"每条错误会导致什么现象"（新写的模块改成"需求到底要什么"）
4. **④ 改造后的做法** —— 分层 / 关键决定，每条都带"不这么做会怎样"
5. **⑤ 自测若干问** —— 带折叠答案，先自己答
6. **⑥ 30 秒验证** —— 用户自己能跑的验证步骤（含**负向对照**，证明测试真的在测东西）
7. **⑦ 一分钟面试版** —— 可以直接背出口的那段话

## 怎么用这些文档

| 场景 | 建议 |
| --- | --- |
| **复习** | 先只看 ① 和 ⑦，能复述就说明记住了框架；细节翻 ③④ |
| **自检** | 做 ⑤ 的题，**不看答案**。答不上来的那题，对应的 ④ 那段就是你的知识缺口 |
| **面试前** | 直接读 ⑦。要更细就往上翻 ③（"我改掉了什么"是面试官最爱追问的部分） |
| **验证环境还在不在** | 跑 ⑥，应该得到文中写的那个数字 |

## 反复出现的几条"母题"（值得单独记住）

这套文档里有些教训**在不同模块反复出现**，它们比任何单个 API 都值钱：

| 母题 | 出现过的模块 |
| --- | --- |
| **静默失败最危险**：出错但不报错，比崩溃难查十倍 | A3（字符串 key）、A5（`float` 当等待）、A8（兜底字符串）、A9（`Find` 返回 null）、A10（帧号倒退）、D1（两份拷贝漂移） |
| **把不可控环境变成可注入参数** —— 时间 / 设备 / 帧循环 | A5（`Tick(dt)`）、A7（假 `IInputSource`）、A8（探针）、A10（帧号） |
| **"没报错"可能是"实验没跑"** | A1（基线全 0）、A2（asmdef 实验 inconclusive） |
| **验证方法本身要先被验证**（W9） | A2（阳性对照）、A8（产物字符串表）、A10（检查命中全是注释）、A11、**M2-A（第 7 次：阳性对照要覆盖"最可能漏掉的形态"，而不是最容易写的形态）** |
| **给数字，不给容器** | A2（`PoolStats`）、A3（`EventChannelStat`）、A4（监听者计数） |
| **能测量的东西才管得住** | A2（池统计）、A4（监听数上 HUD）、A8（创建过的播放器数） |
| **断言型测试 > 观察型实验** | A1（5 对照实验 vs 8 条断言用例） |
| **每一条新错误都要当新信息读** | B3（三轮排错，前两轮结论都被推翻） |
| **多一个状态，就多一个能不同步的地方** | M2-A（进度**钳位** → "达成只回调一次"不需要标志位）；同源：A3（派发中增删的语义写死成契约） |
| **通用层不许认识业务词**（认识一次，复用就结束了） | M2-A（条件系统不认识"任务/成就"，有机械检查）；同源：C2（项目知识不进 `ConfigKit.Core`）、B2（框架不认识 YooAsset） |
| **"全有或全无"**：要么整个动作生效，要么一点都不生效 | M2-A（`Accept` 先校验全部条件再统一登记；`Submit` 先查奖励再改状态） |
| **断言里的数字必须算出来**（第 4 次了） | E1（看板阈值 ×3）、**M2-B（我算错用例里的伤害：300 血的怪挨两发 120 不会死）** |
| **一个走不到的分支比没有分支更糟** | M2-B（"目标已经死了"的分支永远走不到 → 删掉，把"在场 ⇒ 活着"变成不变量）。判据：**当你写不出某个状态的测试时，先怀疑那个状态是否真的存在** |
| **注释写着 A、代码做的是 B**（比没有注释更危险） | M2-B（`Bind` 注释说"装配时就报错"，实际只查了一半；红的是用例，根因是代码） |
| **规则一处实现、两个调用点** = fail early + fail loud | M2-B（技能归属：装配期早检查 + 结算期兜底，规则只有一份实现） |
| **"读了源码"还不够，要读对代码路径** | M2-C（同一功能两个入口：窗口 UI 一条、运行时反射一条，**输出目录不一样**）。判据：只读一个入口就会得出"看起来有据可查"的错结论 |
| **"手工步骤 + 没有提示" = 某天会以别的 bug 的面目出现** | M2-C（配置资产是快照、模拟清单是快照；"忘了点第二步"**不报任何错**）→ 补了过期检查菜单 + 运行时数据预检 |
| **闸门绿不等于 Unity 绿**（工具能证明什么，要说清楚） | M2-D（编译闸门是**单程序集**，抓不到 **asmdef 级**的程序集边界错误 → CS0012）。同族：C2 的"报告方法不该改数据" |
| **重建式刷新会让所有旧引用失效** | M2-D（UI 行是"销毁并重建"的，刷新后旧引用访问即抛 `MissingReferenceException`） |

## 跨模块的常用词（第一次出现就该解释的，集中放这里）

| 词 | 人话解释 | 用在哪 |
| --- | --- | --- |
| **冒烟测试（smoke test）** | **先跑一遍最粗的主流程，看它冒不冒烟**。名字来自硬件：新板子第一次通电，先看会不会冒烟，不冒烟才谈别的。它只回答"**这东西整体还活着吗**"，不追求覆盖细节。价值在于**失败时报错点离原因最近**（接线没通、地址拼错，第一分钟就暴露）。反面是"接线还没通就写细节测试"——那时测出来的红**全是噪音** | B3（YooAsset 接上后先跑 3 条最小用例走完"初始化→加载→断言内容"） |
| **接缝（seam）** | 留一道可以替换的接口，把"会变的东西"隔离在一处 | A2 / B2 / A9 / E1 / C2 / C4 |
| **依赖倒置** | 上层定义接口，下层去实现它 —— 于是上层不必认识下层 | B2 / E1 / C2 |
| **静默失败** | 出错了但不报错 | 全书 |
| **正 / 负对照** | 故意做对一次、故意做错一次，证明检查真的在工作 | A2 / A9 / A10 / C2 / C4 |
| **闸门（编译闸门）** | 用编译器把"我以为"变成"编译器说" —— 不开 Unity 也能验 C# | A7 / A8 / A9 / C3 |
