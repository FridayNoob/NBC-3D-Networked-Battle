## 每篇的标准结构（七段式）

按 `Docs\00` §15.3.1：

1. **① 问题是什么** —— 不用代码，讲清这东西解决什么问题
2. **② 最小例子** —— 错的写法 + 对的写法，一眼看出差别
3. **③ 原版错在哪** —— 配**原代码**，并说清"每条错误会导致什么现象"（新写的模块改成"需求到底要什么"）
4. **④ 改造后的做法** —— 分层 / 关键决定，每条都带"不这么做会怎样"
5. **⑤ 自测若干问** —— 带折叠答案，先自己答
6. **⑥ 30 秒验证** —— 用户自己能跑的验证步骤（含**负向对照**，证明测试真的在测东西）
7. **⑦ 一分钟面试版** —— 可以直接背出口的那段话

## 怎么用这些文档

| 场景 | 建议 |
| --- | --- |
| **复习** | 先只看 ① 和 ⑦，能复述就说明记住了框架；细节翻 ③④ |
| **自检** | 做 ⑤ 的题，**不看答案**。答不上来的那题，对应的 ④ 那段就是你的知识缺口 |
| **面试前** | 直接读 ⑦。要更细就往上翻 ③（"我改掉了什么"是面试官最爱追问的部分） |
| **验证环境还在不在** | 跑 ⑥，应该得到文中写的那个数字 |

## 反复出现的几条"母题"（值得单独记住）

这套文档里有些教训**在不同模块反复出现**，它们比任何单个 API 都值钱：

| 母题 | 出现过的模块 |
| --- | --- |
| **静默失败最危险**：出错但不报错，比崩溃难查十倍 | A3（字符串 key）、A5（`float` 当等待）、A8（兜底字符串）、A9（`Find` 返回 null）、A10（帧号倒退）、D1（两份拷贝漂移） |
| **把不可控环境变成可注入参数** —— 时间 / 设备 / 帧循环 | A5（`Tick(dt)`）、A7（假 `IInputSource`）、A8（探针）、A10（帧号） |
| **"没报错"可能是"实验没跑"** | A1（基线全 0）、A2（asmdef 实验 inconclusive） |
| **验证方法本身要先被验证**（W9） | A2（阳性对照）、A8（产物字符串表）、A10（检查命中全是注释）、A11 |
| **给数字，不给容器** | A2（`PoolStats`）、A3（`EventChannelStat`）、A4（监听者计数） |
| **能测量的东西才管得住** | A2（池统计）、A4（监听数上 HUD）、A8（创建过的播放器数） |
| **断言型测试 > 观察型实验** | A1（5 对照实验 vs 8 条断言用例） |
| **每一条新错误都要当新信息读** | B3（三轮排错，前两轮结论都被推翻） |
