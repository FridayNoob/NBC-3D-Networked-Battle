### 1.3 D15 的目录骨架：手工建立（教学版）

**为什么这一步要你自己敲，而不是给你一个脚本**

依据规则 15：本项目的目标包括提升你的开发能力。把"建 14 个目录 + 搬 9 个文件"打包成一条命令，
你确实省了 5 分钟，但你会**不知道这 23 个动作分别是什么、为什么要这些目录、怎么确认做对了**。
而这套目录结构接下来要陪你走完 M1~M6，理解它比省 5 分钟值钱。

**你需要的两条命令（PowerShell）**

| 用途 | 命令 | 说明 |
| --- | --- | --- |
| 建目录（含所有父级、已存在不报错） | `New-Item -ItemType Directory -Force -Path <路径>` | `-Force` = "已存在也当成功"，所以可以放心重复执行 |
| 复制文件 | `Copy-Item <源> <目标> -Force` | `-Force` = 覆盖已存在的目标 |

> **怎么验证命令真的生效**：`Test-Path <路径>` 返回 `True`/`False`。
> 这是后面每个步骤的通用验证手法 —— **不要靠"看起来没报错"判断成功**。

**第一步：进入工程根目录并确认 Unity 工程存在**

```powershell
cd "E:\U3D Projects\0_MyFile\3D联网战斗Demo"
Test-Path "Client\Assets"      # 必须是 True（D1 已完成）；False 说明工程还没建
```

**第二步：建立目录骨架**（与需求文档 §2.4 一致）

```powershell
$A = "Client\Assets"
@(
  "_Project\Framework", "_Project\Game\Model", "_Project\Game\View",
  "_Project\Game\Controller", "_Project\Game\Service",
  "_Project\Editor", "_Project\Configs", "_Project\Art",
  "_Project\Tests\Manual", "_Project\Tests\EditMode", "_Project\Tests\PlayMode",
  "LuaScripts", "Scenes", "Art"
) | ForEach-Object { New-Item -ItemType Directory -Force -Path "$A\$_" | Out-Null }
```

**这 14 个目录各自是干什么的**（不然就是照着敲，没有意义）：

| 目录 | 作用 | 为什么必须独立 |
| --- | --- | --- |
| `_Project\Framework` | 框架底座（单例/事件中心/对象池/UI/音效等） | 需求 13 要求可整包导出复用，必须与业务隔离 |
| `_Project\Game\Model` | **纯 C# 逻辑层**（帧同步的战斗逻辑） | **禁引 UnityEngine**，由 asmdef 编译期强制 |
| `_Project\Game\View` | 表现层（UI / 特效 / 动画 / 相机） | MVC 的 V，只做显示 |
| `_Project\Game\Controller` | 调度层（输入 → Model → 通知 View） | MVC 的 C，唯一调度中心 |
| `_Project\Game\Service` | 跨模块服务（网络 / 热更 / 配置） | 与 Controller 职责不同：服务是无状态能力 |
| `_Project\Editor` | 编辑器工具（配置表导出等） | 独立 asmdef + 仅 Editor 平台，否则会被打进包 |
| `_Project\Configs` | Excel 导出的 SO 配置资产 | 配置是"数据"不是"代码"，便于单独打包 |
| `_Project\Art` | 工程自有美术资源 | 与第三方资源（`ThirdParty`）分开，便于清理 |
| `_Project\Tests\Manual` | 手工验证脚本（如 D17 的 AOT 探针） | 与自动化测试分开，避免被当测试程序集处理 |
| `_Project\Tests\EditMode` / `PlayMode` | 自动化测试（NUnit） | 需要独立 asmdef，否则 NUnit 引用会污染正式程序集 |
| `LuaScripts` | Lua 业务脚本 | **热更对象**，要独立于 C# 编译产物 |
| `Scenes` | 场景文件 | Unity 约定 |
| `Art`（Assets 根下） | 第三方/外部来源美术资源 | 与 `_Project\Art` 区分来源，便于整体替换 |

**第三步：搬运 9 个暂存文件**

`ClientStaging\` 里放的是 AI 写好的 9 个文件（因为 D1 之前 `Client\Assets` 还不存在，AI 没地方放）。
逐个复制并**同时理解它是什么**：

```powershell
# ① D17 的 AOT 探针脚本（M0 最关键的验证工具）
Copy-Item "ClientStaging\NBV0_EnvironmentProbe.cs" "$A\_Project\Tests\Manual\" -Force

# ② 编译符号自动注入器（检测 dll 是否存在，自动维护 NBC_HAS_* 符号）
Copy-Item "ClientStaging\Editor\NBV0_DefineInitializer.cs" "$A\_Project\Editor\" -Force

# ③ IL2CPP 裁剪保护清单（放在 Assets 根下，Unity 才会识别）
Copy-Item "ClientStaging\link.xml" "$A\link.xml" -Force

# ④~⑨ 6 个程序集定义（asmdef）
Copy-Item "ClientStaging\AsmDefs\Framework.asmdef"      "$A\_Project\Framework\Framework.asmdef" -Force
Copy-Item "ClientStaging\AsmDefs\Model.asmdef"          "$A\_Project\Game\Model\Model.asmdef" -Force
Copy-Item "ClientStaging\AsmDefs\Game.asmdef"           "$A\_Project\Game\Game.asmdef" -Force
Copy-Item "ClientStaging\AsmDefs\Editor.asmdef"         "$A\_Project\Editor\Editor.asmdef" -Force
Copy-Item "ClientStaging\AsmDefs\Tests_EditMode.asmdef" "$A\_Project\Tests\EditMode\Tests_EditMode.asmdef" -Force
Copy-Item "ClientStaging\AsmDefs\Tests_PlayMode.asmdef" "$A\_Project\Tests\PlayMode\Tests_PlayMode.asmdef" -Force
```

> **为什么 `link.xml` 和 `Framework.asmdef` 都是空壳？**
> `link.xml` 此刻声明的程序集（protobuf-net / xLua）**还没导入**，所以它现在不起作用 —— 这是正常的，
> 它要等 D6/D7 导入插件后才生效。`Framework.asmdef` 也还没有任何 `.cs` 文件，M1 才填内容。
> **"现在就位、稍后生效"是刻意设计**：这样 M1 一开工目录与程序集边界就已正确，不用回头补。

## 二、阶段一：创建 Unity 工程

### D1 · 用 Unity Hub 创建 URP 工程 👤

**前置检查（1 分钟）**

1. 打开 **Unity Hub**
2. 左侧 **Installs** → 确认已有 **2022.3.62f3c1**（版本已于 2026-09-20 从 `2022.3.17f1c1` 升级，原因见需求文档 **R16**）
   - 本机安装位置：新版在 `D:\SOFT\Unity\Hub\Editor\2022.3.62f3c1`（Hub 副安装路径），旧版仍在 `C:\Program Files\Unity\Hub\Editor\2022.3.17f1c1`
3. 点该版本右侧的**齿轮 / 三个点 → Add modules**，确认勾选了：
   - ☑ **Microsoft Visual Studio Community 2022**（或你已装的 VS2022）
   - ☑ **Windows Build Support (IL2CPP)**
   - ☑ **Documentation**（可选）

> ⚠️ **如果没有 "Windows Build Support (IL2CPP)"，现在补装**。IL2CPP 是需求文档 §5.1 冻结的脚本后端，
> 缺了它后面 D17 一定失败。（Mono 后端不需要它，但我们不用 Mono。）
> ✅ 该模块**已确认装好**（两版编辑器的 `PlaybackEngines` 下都有 `windowsstandalonesupport`）。

**创建工程**

4. Unity Hub 左侧 **Projects** → 右上角 **New project**
5. 顶部选中编辑器版本 **2022.3.62f3c1**
6. 模板列表选择 **3D (URP)** —— 这是 Built-in 之外唯一的通用 3D 模板
   - 若模板列表里找不到 "3D (URP)"：先随便建一个 **3D (Built-in)** 工程，后面在 D2 用 Package Manager 装 URP 包并切换（我会在 D2 补充该分支步骤）
7. 右侧填写：
   - **Project name**：`Client`
   - **Location**：`E:\U3D Projects\0_MyFile\3D联网战斗Demo`
   - ☐ **不要勾** "Connect to Unity Cloud"（本机作品集项目，避免引入额外依赖）
8. 点 **Create project**，等待首次导入（约 2~5 分钟）

**预期结果**

- 目录出现：`E:\U3D Projects\0_MyFile\3D联网战斗Demo\Client\`
- `Client\Assets\`、`Client\Packages\`、`Client\ProjectSettings\` 三个目录存在
- 打开后 `Assets\Scenes\SampleScene.unity` 可看到 URP 示例场景，Console 无红色报错

**如果失败看什么**

| 现象 | 排查 |
| --- | --- |
| 创建卡住/进度条不动 | 关闭杀毒软件实时防护后重试；检查 C 盘剩余空间 > 10GB |
| 打开后大量红色报错 | `Window → Package Manager` 检查 URP 包是否装好；或删掉 `Client\Library` 重开 |
| 模板列表是空的 | 断网导致模板拉取失败；检查网络/代理后重启 Hub |

## 四、阶段三：导入依赖与插件

### ⚠️ 导入顺序很重要

按 D5 → D11 的顺序导入。原因：**YooAsset 与 xLua 会改动资源导入流程**，先装它们可以避免后续资源的重复导入。

### D5 · YooAsset（资源/AB 层）👤

YooAsset 通过 **OpenUPM** 发布，需要先加作用域注册表：

1. 菜单：**Edit → Project Settings → Package Manager**
2. 在 **Scoped Registries** 区域点 **+**，填入：

| 字段 | 值 |
| --- | --- |
| **Name** | `package.openupm.com` |
| **URL** | `https://package.openupm.com` |
| **Scope(s)** | `com.tuyoogame.yooasset` |

3. 点 **Apply**
4. 菜单：**Window → Package Manager** → 左上角下拉选 **My Registries**
5. 找到 **YooAsset** → **Install**

**预期结果**：`Packages` 下出现 YooAsset；菜单栏出现 **YooAsset** 顶级菜单。

**验证**：点 **YooAsset → AssetBundle Collector** 能打开窗口（此时还没配置，内容为空是正常的）。

> 参考：[YooAsset 快速开始文档](https://yoo-asset-doc.vercel.app/docs/2.3.x/guide-editor/QuickStart)

### D6 · xLua（Lua 绑定）👤

xLua 不进包管理器，需要手动放源码：

1. 下载 **Tencent/xLua** 最新 Release（或 clone 仓库）：https://github.com/Tencent/xLua
2. 把仓库中的 **`Assets/XLua`** 整个文件夹复制到本工程的 `Client\Assets\ThirdParty\XLua\`
   - 目标结构：`Client\Assets\ThirdParty\XLua\` 下应有 `Src`、`Plugins`、`Examples` 等
3. 回到 Unity，等待编译

**预期结果**
- 菜单栏出现 **XLua** 顶级菜单
- Console 无编译错误

**验证（重要）**：菜单 **XLua → Generate Code**，等待生成完成，Console 无报错。
（这一步是 AOT 的关键：xLua 会生成 `XLua/Gen/` 下的静态绑定代码。）

> ⚠️ `Assets/XLua/Examples` 目录较大且含演示场景，可在确认无误后删除以减少导入时间（可选）。

### D7 · protobuf-net（网络序列化）👤 ⚠️ 本阶段最容易被低估的一步

protobuf-net **不是为 Unity 设计的**，直接扔 NuGet 的 dll 进工程，Editor 能跑、**打包后必崩**。
原因是 Unity IL2CPP 是 AOT 编译，会裁掉 protobuf-net 依赖的反射元数据。

1. 从 NuGet 下载 **`protobuf-net`**（3.2.x）的 `.nupkg`
2. 解压（`.nupkg` 就是 zip），取 `lib\netstandard2.0\protobuf-net.dll`（或 `netstandard2.1`）
3. 复制到 `Client\Assets\ThirdParty\ProtobufNet\`

### D14 · 证明"依赖 Unity 运行时的东西进不了纯 .NET 服务端" ✅（2026-09-20 已完成）

**做法（比原计划更根本）**：原计划是"临时引用 Behavior Designer 的 dll 看编译报错"，但那样测的是

**实测结果（3 / 9 级失败）**：

| 分层 | 能否在纯 .NET 进程工作 | 证据 |
| --- | --- | --- |
| 纯托管数学（`Vector3` / `Mathf`） | ✅ **能，且结果正确** | `magnitude=5`、`Normalize=(0.6,0.8,0)`、`Mathf.Sqrt(16)=4` |

**关键判读**：这是**运行时**异常而不是编译期错误 —— **引用 Unity 程序集能编译通过**，

## 十、附：本机多客户端联机的网络前置（M3 会用到，M0 先规划）

M0 现在不需要联网，但**网络环境要在写代码前就定清楚**，否则 M3 第一次联调时会卡在"连不上"上，
而那种问题排查起来很浪费时间（分不清是防火墙、绑定地址还是协议问题）。

### 需要你决定的三件事

| # | 决定 | 影响 |
| --- | --- | --- |
| **N1** | **联机范围**：① 同一台机器多开（4 个客户端 + 1 个服务端）② 局域网两台机器 ③ 都要 | 决定服务端监听地址与是否放行防火墙 |
| **N2** | **服务端监听地址** | 同机多开用 `127.0.0.1` 即可，**不会触发防火墙提示**；局域网要监听 `0.0.0.0`，**首次会弹防火墙授权** |
| **N3** | 演示时用哪种 | 面试现场通常只能用一台机器 → 建议**优先保证同机多开**，局域网作为加分 |

### 建议方案（推荐，改动最小）

**先用同机多开把联网打通**（`127.0.0.1`），等 M3 联调通过后再处理局域网：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 服务端监听 | 配置文件 `ListenIp`，README/手册统一写 `127.0.0.1` | 同机多开足够；已写在 `Server/NBC.Server.Host/appsettings.json` 的 `Server.ListenIp` |
| 端口 | `9000`（已在配置文件里） | 避免与常用端口冲突；可在配置文件改 |
| 客户端连接目标 | `127.0.0.1:9000` | — |
| 防火墙 | **无需改动** | 环回地址不走防火墙 |

### 若要做局域网联机（M3 之后再处理）

1. 把 `appsettings.json` 的 `Server.ListenIp` 改为 `0.0.0.0`
2. 首次启动服务端时 Windows 会弹出防火墙授权 → 勾选 **专用网络**（不要勾公用网络）
3. 查本机内网 IP：命令行执行 `ipconfig`，找 `IPv4 地址`（形如 `192.168.x.x`）
4. 客户端连接目标改成该 IP
5. **排查顺序**（连不上时按此顺序查，别乱试）：
   - ① 服务端是否真的在监听 → 命令行 `netstat -ano | findstr :9000`
   - ② 本机能连自己吗 → `Test-NetConnection 127.0.0.1 -Port 9000`
   - ③ 对方能 ping 通吗 → `ping 192.168.x.x`
   - ④ 端口在对方机器通吗 → `Test-NetConnection 192.168.x.x -Port 9000`
   - ⑤ 都通但连不上 → 才是代码/协议问题（这时才该来找我）

### 同机多开的注意事项（M3 会用）

| 问题 | 原因 | 应对 |
| --- | --- | --- |
| 多个客户端抢同一个存档/配置目录 | Unity 的 `persistentDataPath` 按**公司名+产品名**生成，多开是同一个目录 | 启动参数传入"实例号"，用它给可写目录加子目录（如 `.../NBC/Instance1`）。**这条要在 M1 设计热更可写目录时就预留** |
| 多开后帧率掉 | 4 个客户端 + 1 个服务端同时跑，机器负载高 | 演示时把客户端画质调到 **Low** 档（需求文档 OPT-13 的三档正好派上用场） |
| 服务端日志混在一起 | 多客户端连到同一个服务端，日志需要区分 session | 日志每行带 `sessionId`（§13.3 SRV-14 已要求） |

> **M0 阶段你不需要做任何网络配置**，只要知道 N1 的答案（联机范围）并告诉我即可，我会在 M3 按它来定实现。

#### ⚠️ 过程中修复的一个真实缺陷（值得记住的排错案例）

首次 `dotnet build` 失败：

```
error NETSDK1005: 资产文件 "Builds\Server\obj\project.assets.json" 没有 "netstandard2.1" 的目标。
```

**根因**：`Server\Directory.Build.props` 早期版本为了"统一输出目录"，覆盖了

```xml
<BaseIntermediateOutputPath>$(RepoRoot)..\Builds\Server\obj\</BaseIntermediateOutputPath>
```

该属性**在项目文件之前求值**（连 `$(MSBuildProjectName)` 都不可用），导致 5 个工程算出**同一个 `obj` 目录**，
它们的 `project.assets.json` 互相覆盖 —— 某个工程读到的是**别人的**资产文件，里面自然没有它需要的目标框架。

**判据（可复用）**：

| 属性 | 能否多工程共享 |
| --- | --- |
| `BaseOutputPath`（`bin`） | ✅ 可以（但要按工程名分子目录：`$(MSBuildProjectName)`） |
| **`BaseIntermediateOutputPath`（`obj`）** | ❌ **绝对不能**（`project.assets.json`、`*.AssemblyInfo.cs` 都是按工程的） |

**修复**：删除这两个路径覆盖，回归 .NET 默认（每工程自己的 `obj`/`bin`）。
**修复后**：5 个工程各有独立 `project.assets.json`，编译通过；`NBC.Shared.dll` 落在
`NBC.Shared\bin\Debug\netstandard2.1\`，其余工程落在 `...\bin\Debug\net8.0\`。

**教训已写入** `Server\Directory.Build.props` 的注释，避免以后重犯。
