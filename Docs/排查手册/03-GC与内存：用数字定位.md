# 03 · GC 与内存：用数字定位，而不是猜

> 现象归类：**第 ③ 层（托管运行时）与第 ⑤ 层（原生/打包）** 都要看这一篇
> 本篇是**方法篇**：先讲清"读哪个数字"，再讲"数字怎么解释"，最后是"常见大户"。
> ⚠️ 凡标 **【本项目实测】** 的是我们真跑过的；其余是通用方法（写清楚，免得把"应该"当"实测"）。

---

## 一、现象（GC/内存问题的四种脸）

| 脸 | 表现 | 常见真因 |
| --- | --- | --- |
| **周期性卡顿** | 每隔几秒顿一下，帧时间曲线是"尖刺 + 平台" | 每帧产生垃圾 → GC 触发（托管堆碎片/回收） |
| **越玩越卡 / 越玩越吃内存** | 内存单调上涨，切场景也不降 | 泄漏：事件没退订、`static` 容器只增不减、资源没 `Release` |
| **打包后突然爆内存** | 编辑器里没事，真机 OOM | 纹理/AudioClip 的压缩与常驻策略、AssetBundle 没卸载 |
| **"读不到数字"** | 看板上某个值是 0，实际有开销 | **读不到 ≠ 是 0**（API 用错/时机不对） |

---

## 二、先确认是哪一层（**读数字之前，先分清"托管"还是"原生"**）

| 你关心的 | 读什么 | 它统计的是 |
| --- | --- | --- |
| **C# 托管堆**（GC 管的那块） | `GC.GetTotalMemory(false)` / `Profiler.GetMonoHeapSizeLong()` | 托管对象；**GC 卡顿直接由它决定** |
| Unity 的**总分配** | `Profiler.GetTotalAllocatedMemoryLong()` | Unity 自己统计的（含原生） |
| Unity 的**总预留** | `Profiler.GetTotalReservedMemoryLong()` | 向系统要了多少（含未用的池） |
| **纹理 / Mesh / AudioClip** | `Profiler.GetAllocatedMemoryForGraphicsDriver()`、Memory Profiler 包 | 原生资产内存（**GC 看不到**） |
| **每帧分配了多少** | Profiler 的 `GC.Alloc` 列 / `ProfilerRecorder("GC.Alloc")` | 每帧托管分配字节数（**定位"谁在每帧分配"的关键数字**） |

> 📌 **规则一**：**托管 ≠ 原生**。`GC.GetTotalMemory` 小但进程内存大 → 问题在纹理/资源，不在 C#。
> 只在托管堆里找"内存泄漏"是最常见的白费功夫。

---

## 三、定位步骤

### A. 先量"有没有 GC 压力"

```csharp
// 每帧分配字节数（编辑器与 Development Build 可用）
using Unity.Profiling;
static readonly ProfilerRecorder GcAlloc =
    ProfilerRecorder.StartNew(ProfilerCategory.Memory, "GC.Alloc");

void Update() => _lastFrameAllocBytes = GcAlloc.LastValue;
```

**判据**：

| 数字 | 结论 |
| --- | --- |
| 大多数帧 **0 B** | 稳态无垃圾（这是目标：本项目 HUD 就要求自己**不分配**） |
| 每帧几百 B ~ 几 KB | 有稳定的小垃圾源（`string` 拼接、闭包、装箱） |
| 每帧 **几十 KB 以上** | 一定有"每帧造对象"的地方，GC 尖刺跑不掉 |

### B. 找"谁在分配"（三级定位）

```
1. Profiler 窗口 → CPU Usage → Hierarchy 视图 → 按 GC Alloc 列排序
   （谁是头号分配者，一眼就看到）
2. 点进去看调用树 → 找到最深的"我们自己写的那个方法"
3. 若看不到深处：开 Deep Profile（慢，但能看到每一层）
```

⚠️ **编辑器里的读数会被编辑器自身污染**：`Debug.Log` 在编辑器里会抓堆栈（**很贵**）、
Profiler 自己也有开销。**最终数字要在 Development Build + Autoconnect Profiler 上取**。

### C. 判断"是泄漏还是抖动"

```csharp
// 每隔 N 秒记一次：托管堆 + 总分配 + 场景对象数
Debug.Log($"mono={Profiler.GetMonoHeapSizeLong()/1024/1024}MB total={Profiler.GetTotalAllocatedMemoryLong()/1024/1024}MB");
```

| 曲线形状 | 结论 |
| --- | --- |
| 锯齿形（涨→GC→落回同一水平） | **抖动**：有垃圾，但在回收 → 找分配源 |
| 阶梯形（每次操作升一级，不回落） | **泄漏**：某处只加不减 → 查事件/静态容器/资源句柄 |
| 稳态不涨、但绝对值很大 | **容量**问题（纹理/常驻资源），不是泄漏 |

### D. 泄漏最有效的抓法：**两次快照做差**

```
1. 做一次"基线快照"（Memory Profiler 包 / 或自己统计关键类型的实例数）
2. 重复可疑操作 100 次（进出场景、开关面板、连断网络）
3. 再做一次快照，按"类型 → 实例数增量"排序
4. 增量最大的那几个类型 = 泄漏对象；再看"谁还引用它"（References 面板）
```

## 四、常见大户（含**为什么**，别只记名字）

| 来源 | 为什么会分配 | 正确做法 |
| --- | --- | --- |
| **字符串拼接 / 内插** | 每次 `+` 都新建 `string` | 热路径用 `StringBuilder` 复用；或先 `IsEnabled` 判断再拼（**本项目日志系统写死了这条规矩**） |
| **闭包捕获** | lambda 捕获外部变量 → 生成一个隐藏类实例 | 热路径避免捕获；把参数提到静态方法 |
| **装箱** | `int`/枚举 → `object`（`string.Format`、`Dictionary<object,...>`） | 用泛型集合；避免把值类型塞进 `object` |
| **`foreach` 老式枚举器** | 某些接口枚举器是**引用类型** → 每次 `foreach` 分配 | 用具体类型（`List<T>` 的 `foreach` 是结构体枚举器，不分配） |
| **`Debug.Log`** | 编辑器里抓堆栈；字符串还要拼接 | 热路径先判 `Debug.isDebugBuild` / 自己的日志开关 |
| **`Object.name` / `tag` 属性** | 每次访问**返回新字符串** | 比较用 `CompareTag("X")`；名字缓存起来 |
| **`new WaitForSeconds(x)`** | 每次 `yield` 都新建 | 缓存成字段（不同时长各一个） |
| **`Camera.main`** | 旧版本内部是 `FindGameObjectsWithTag` | 启动时缓存引用 |
| **LINQ** | 链式操作大量分配（闭包 + 迭代器） | 热路径不用 LINQ |
| **`Resources.Load` 反复调用** | 每次都查表/产生开销；卸载难 | 走 AssetManager 缓存 + 显式 Release |
| **纹理 / AudioClip** | 原生内存，GC 看不到 | 压缩格式、`Read/Write` 关掉、按需 `UnloadUnusedAssets` |

> 📌 **规则二（本项目 E1 的教训）**：**观测工具不能自己制造被观测的问题。**
> 你要显示"每帧 GC 分配"，看板自己就**不能每帧拼字符串** —— 否则你测到的是看板自己的垃圾。
> 这也是为什么 HUD 只读数字、不拼字符串、不每帧 `Instantiate`。

## 五、"读不到 ≠ 是 0"（本项目实测过的一条）

【本项目实测】性能看板早期有个读数恒为 0，被告知"不能当它是 0"——
**先确认 API 在这个平台/这个构建类型下到底有没有值**（有些计数器只在 Development Build 或某些平台可用），
否则你会对着一个"永远 0"的数字下结论。判据：

```csharp
if (!recorder.Valid) { /* 这个计数器不可用 —— 显示"不可用"，不要显示 0 */ }
```

## 六、防复发（项目已落地的）

1. **日志系统**：`IsEnabled(level, channel)` 先判断再拼字符串（不这么写，关掉日志也照样每帧分配）。
2. **性能看板（E1）**：只读计数器、不拼字符串、不每帧建对象；数字读不到就显示"不可用"。
3. **【本项目实测】字体资产的包体代价**：`.ttf` 8.5 MB + SDF 2.1 MB → M5 做字符子集化（`Docs\05` C15 登记）。
4. **网络层刻意不分配**：`FrameCodec.Encode(ReadOnlySpan<byte>)` 重载就是为省掉每条消息一次 `ToArray()`。

## 七、一句话讲清（面试版）

> 我不会凭感觉说"有 GC 问题"，而是先量三个数：**每帧 GC.Alloc 字节数**（稳态应当是 0）、
> **托管堆大小曲线**（锯齿 = 抖动，阶梯 = 泄漏）、**总分配与托管堆的差值**（差值大说明问题在原生资源而不是 C#）。
> 定位分配源用 Profiler 的 Hierarchy 按 GC Alloc 排序；定位泄漏用"两次快照做差 + 看引用链"。
> 两条硬规矩：**观测工具自己不能制造被观测的问题**（看板不许每帧拼字符串），
> 以及**读不到的数字不能当 0**。
