## 一、调研目标与约束

玩家打完副本（怪清光或英雄全灭）后，屏幕上现在**什么都没有**：服务端把这一局记进战绩草稿就结束了，客户端只看到快照不再变化。本步要搞清楚「结束信号从哪来、能不能加协议、面板怎么出、重开怎么走」。

约束五条：

1) **结算必须服务端权威**（`Docs/新项目文档/开放世界方向调研.md` 的结论：伤害/掉落/结算都在服务端），客户端只负责显示，不得自己判胜负。
2) **协议只做纯新增**：新增一条消息与一个 oneof 分支，不删不改既有字段 ⇒ `CONTRACT_VERSION` 仍为 1。
3) 面板先用运行时 UGUI（与 R041 的黑幕同一套），R046 再统一换成预制体 + `UIManager`。
4) 重开不新建协议：复用 `LeaveRoomRequest` + `JoinRoomRequest`，由服务端分配新房间与新战斗世界。
5) R041 的死亡流程与结算流程不能互相抢屏：英雄死亡时若副本还没结束，走死亡倒计时；副本结束时无论生死，都走结算面板。

## 三、最小可运行示例

服务端（在 `RecordIfFinished` 成功之后补一次广播）：

```csharp
var result = new DungeonResult
{
    Outcome = battle.AliveMonsterCount == 0 ? 1 : 2,   // 1 胜 / 2 负
    DurationMs = (int)(battle.Tick * NetContract.TickIntervalMs),
    MonsterKills = battle.MonsterKills,
    HeroDeaths = battle.HeroDeaths,
};
byte[] payload = new ServerMessage { DungeonResult = result }.ToByteArray();
SendToRoom(payload, room);
```

客户端（NetSession 分发 + 事件）：

```csharp
case ServerMessage.PayloadOneofCase.DungeonResult:
    DungeonEnded?.Invoke(message.DungeonResult);
    break;
```

## 四、方案对比

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A 客户端推断 | 快照里怪物列表空了就当赢 | 零协议、最快 | **违反权威原则**；分不清「全灭」与「怪还没刷出来」；输赢只能猜 |
| B 服务端新增 `DungeonResult`（推荐） | 副本结束时服务端判定并广播结果 | 权威、可带用时/击杀、与 PVP 的 `MatchResult` 分语义 | 要改 proto + 重跑 protoc + 重建探针 |
| C 复用 `MatchResult` | 塞进 PVP 的结果消息 | 不改协议 | 字段语义错位（队伍击杀数），以后 PVP 改字段会牵连副本 |

选 **B**；同时把 `room.Phase` 置 `Finished`（复用已有枚举，不改协议）让房间列表也能看出「这局结束了」。

## 五、已知坑与版本兼容

1) **protoc 必须用 3.21.1**：`E:\U3D Projects\TeachNet\Protobuf\protoc.exe`，与运行时 `Google.Protobuf` 配对；离线包里的 `protoc-35.1` 不能用。
2) **不能给 protoc 传中文路径**：`cd` 到仓库根、只给相对路径（本项目路径含中文，这是唯一稳妥做法）。
3) **生成物 `Client/Assets/_Project/Protocol/NbcM3.cs` 要一起提交**（克隆即可编译）。
4) 新增 message 与 oneof 分支属于**兼容变更**，`CONTRACT_VERSION` 不变；但 `Tests/EditMode/Net/ProtocolTests.cs` 会机械比对版本号，改错会红。
5) 改完协议必须重建 `_api-probe` 与 `_net-probe`（W21：探针验的是旧程序集就白验）。
6) 客户端旧版本收到未知 oneof 分支会**静默忽略**（Protobuf 行为），不会崩 —— 但也就看不到结算。
7) 服务端重启后房间与战斗世界都不存在，`DungeonResult` 只在内存里发一次；客户端错过就靠「重新进房」兜底。
8) `RecordIfFinished` 有 `_recorded` 去重，结算广播要放在同一个「只执行一次」的位置，否则每帧都发。

## 六、结论

- 采用 **B**：`DungeonResult`（`outcome` 1 胜 / 2 负、`duration_ms`、`monster_kills`、`hero_deaths`）+ `room.Phase = Finished`。
- 客户端：`NetSession` 新增 `DungeonEnded` 事件 → `RuntimeNetDriver` 转发 → 新增 `DungeonResultPanel`（运行时 UGUI）显示胜负/用时/击杀，两个按钮：**再来一次**（`LeaveRoom` → `JoinRoom(同一 dungeonId)` → 重载 Battle）、**返回世界**（`LeaveRoom` → `SceneFlow.LoadAsync(World)`）。
- 预计代码量：服务端 ~90 行、客户端面板 ~200 行、NetSession/Driver/DeathFlow 改动 ~70 行、测试 ~90 行，合计约 450 行（在 500 行预算内）。
- 需要负责人拍板：结算面板要不要显示「用时 + 击杀数」，还是只显示胜负（默认：显示，数据服务端已经能算）。
