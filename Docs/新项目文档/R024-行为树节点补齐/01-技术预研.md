作者：AI　状态：草稿（待负责人确认）

## 一、调研目标与约束

- 目标：把「怪物 AI 真正需要的节点」**先补进客户端编辑器**（`BTNodeRegistry` + 预览执行器 + 黑板项），
  让客户端成为节点定义的**唯一权威**；服务端随后照抄（R022 系列）。
- 约束：
  1. **只在编辑器**（`NBC.Editor`，不进包）；
  2. 节点名即 JSON 的 `NodeType`，一经发布**不许改名**；
  3. 不引外部插件，沿用 R023 的自研编辑；
  4. 代码量预估 **≈300 行**（见 §七），符合 AGENTS.md §0.1。

## 二、现状（已确认）

| 项 | 事实 |
| --- | --- |

## 三、要补的节点（按 BOSS 需求校准后：11 个新增 + 2 项参数化改造）

> 负责人补充需求（2026-11-08）：**BOSS 会有三个技能 + 多段普攻**。
> 下面按「BOSS 真要能表达出来」重新校准了节点清单 —— 原方案只够普通怪的「追 + 打」，**不够 BOSS**。

### 3.1 条件（6 个）

| # | 节点 | 参数 | 语义 |
| --- | --- | --- | --- |
| 1 | `IsDead` | 无 | 自己死了 → 成功（Selector 最前） |
| 2 | `InAttackRange` | `rangeMm`（int，0 = 用默认射程） | 目标在指定射程内（**参数化**，否则近战/远程/BOSS 技能都得各写一个） |
| 3 | `AttackReady` | `skillId`（int，0 = 普攻） | 指定技能的冷却是否好了（普攻也用同一个节点） |
| 4 | `HPBelow` | `hpThreshold`（int）、`percentOfMax`（bool） | 血量低于阈值；`percentOfMax = true` 时按百分比（**BOSS 分阶段就用它**） |
| 5 | `HasTarget` | 无 | 有目标（已有） |
| 6 | `HomeFar` | 无 | 离家超过回位半径 |

### 3.2 动作（5 个）

| # | 节点 | 参数 | 语义 |
| --- | --- | --- | --- |
| 7 | `Chase` | 无 | 朝目标移动一帧 |
| 8 | `BasicAttack` | `hits`（int，默认 1）、`intervalTicks`（int） | 普攻；`hits > 1` 即**多段普攻**（每段间隔 N 逻辑帧） |
| 9 | `CastSkill` | `skillId`（int）、`cooldownSeconds`（float） | 释放指定技能（**保留，不删** —— 三技能全靠它） |
| 10 | `ReturnHome` | 无 | 朝出生点走 |
| 11 | `Patrol` / `Idle` | 无 | 巡逻 / 站桩 |

> 另有 `Wait(seconds)`：段间隔、技能后摇都用它 → **也保留，不删**。

### 3.3 BOSS 的树可以长成什么样（验证节点够不够）

```
Selector
├─ Sequence [IsDead]                                   → 什么都不做
├─ Sequence [HPBelow(50%, percent)] [AttackReady(技能1)] → CastSkill(技能1)   ← 阶段技能
├─ Sequence [HasTarget] [InAttackRange(6000)] [AttackReady(技能2)] → CastSkill(技能2)  ← 远程技能
├─ Sequence [HasTarget] [InAttackRange(2000)] [AttackReady(技能3)] → CastSkill(技能3)  ← 近身技能
├─ Sequence [HasTarget] [InAttackRange(2000)] [AttackReady(普攻)]  → BasicAttack(hits=3, intervalTicks=5)  ← 多段普攻
├─ Sequence [HasTarget] → Chase
├─ Sequence [HomeFar]   → ReturnHome
└─ Idle
```

**结论：按上表补齐后，三技能 + 多段普攻 + 分阶段都能表达**，不需要为 BOSS 单独发明节点。

## 四、预览执行器怎么落（编辑器内自测用）

预览是简化模拟，不连服务端，所以新节点用**黑板开关**表达：

| 新黑板项 | 类型 | 默认 | 用途 |
| --- | --- | --- | --- |
| `inRange` | bool | false | 给 `InAttackRange` 读：是否在射程内 |
| `homeFar` | bool | false | 给 `HomeFar` 读：是否离家太远 |

| 节点 | 预览行为 |
| --- | --- |
| `IsDead` | `hp <= 0` → 成功；否则失败 |
| `InAttackRange` | 读 `inRange`（参数 `rangeMm` 在预览里只做显示，不参与判定） |
| `AttackReady` | `skillCd <= 0` → 成功 |
| `HomeFar` | 读 `homeFar` |
| `Chase` / `ReturnHome` | 恒「运行中」（模拟持续移动） |
| `BasicAttack` | 成功；`hits > 1` 时在预览日志里标「多段×N」，`skillCd` 置固定 2 秒 |
| `Patrol` / `Idle` | 恒成功 |

> 预览**不求拟真**，只求「条件能变红绿、动作不误判」；真正的行为以服务端为准。

## 五、必须先定的一个取舍：旧的 3 个节点怎么办

客户端现有 `MoveTo` / `CastSkill` / `Wait`，其中：

| 旧节点 | 与新增的关系 | 处理 |
| --- | --- | --- |
| `MoveTo` | 与 `Chase` **重复**（都表示朝目标走） | **删除**（保留 `Chase`，名字更明确） |
| `CastSkill` | **不可替代**（三技能全靠它） | **保留并参数化**（`skillId` + `cooldownSeconds`） |
| `Wait` | **不可替代**（段间隔、技能后摇） | **保留** |

> 负责人 2026-11-08：**已导出的 JSON 暂时不用管**（样例而已），所以可以放心删 `MoveTo`。

节点表最终：**3 组合 + 6 条件 + 5 动作 = 14 个**（`MoveTo` 删除、`CastSkill`/`Wait` 保留）。

## 五之二、服务端能力缺口（不在本需求范围，但必须提前说清）

行为树只能「描述」行为，**真正执行要靠服务端**。BOSS 的三技能与多段普攻在当前服务端**都还没有对应能力**：

| 需要的服务端能力 | 现状 | 归属 |
| --- | --- | --- |
| 释放指定技能（`CastSkill(skillId)`） | 只有普攻 `DungeonBattle.TryBasicAttack`；`SkillCaster` 是老客户端 Demo 的，服务端未接 | **新需求**（技能系统，预估会超 500 行 → 需拆分） |
| 多段普攻（一次攻击 N 段） | 普攻是**单段 + 固定冷却**，没有多段结算 | 可并入上一条，或单独小需求 |
| 按技能独立冷却 | 只有 `AttackCooldownTicksLeft` 一个冷却 | 同上 |

⇒ **建议顺序**：R024（补齐客户端节点、本需求）→ 服务端「技能系统」新需求 → R022-1/2/3 用新节点重建 AI。
如果先做 R022 再做技能，BOSS 的树里会出现「拖了 `CastSkill` 但服务端不会放技能」的假节点。

## 五之三、节点定义数据化（让策划加节点不用改代码）

负责人 2026-11-08 要求：**后续策划想加节点，尽量不要改代码**。

先分清两层，否则会做出「拖出来但不能跑」的假节点：

| 层次 | 例子 | 能否零代码 |
| --- | --- | --- |
| **节点定义**（名字 / 分类 / 参数表 / 参数类型） | 新加一个带 `threshold` 参数的条件 | ✅ **可以**（本需求做） |
| **节点行为**（真正执行时做什么） | 那个条件怎么判断 | ❌ 不行（必须有执行器：服务端 C# + 编辑器预览分支） |

所以本需求把**定义搬到数据文件**：

```
Client/Assets/_Project/Editor/BehaviorTree/Resources/BehaviorTreeNodes.json
  [
    { "TypeName": "Selector", "DisplayName": "Selector（选择）", "Category": "Composite", "MaxChildren": -1, "Params": [] },
    { "TypeName": "HPBelow",  "DisplayName": "HPBelow（血量 < 阈值）", "Category": "Condition", "MaxChildren": 0,
      "Params": [ { "Key": "hpThreshold", "Label": "血量阈值", "Type": "Int", "Default": "30" } ] }
  ]
```

- 编辑器启动时读这个文件 → `BTNodeRegistry` 注册（不再写死在 C# 里）；
- 策划**改参数表 / 加纯数据型定义**：改 JSON 即可，**不用改代码**；
- **边界（必须说清）**：加了定义但没执行器的节点，能拖到画布、能连线、能导出，
  但**预览会返回 Failure、服务端会报「未知类型」** —— 这属于"定义先行、行为后补"，是预期行为；
- **参数化优先于新增节点**：能用现有节点 + 参数表达的（如 `InAttackRange(rangeMm)`、`BasicAttack(hits)`），一律不加新节点。

> 结论：**「改参数/加定义」零代码；「加新行为」仍需服务端补一次执行器**。这条边界写进文档，避免以后误以为能全自动。
> 表达式 DSL（策划写条件）与 Lua 脚本节点**本版不做**（负责人确认：现有节点 + 参数够用）。

## 六、已知坑

1. **改名/删名 = 破坏已导出 JSON**：删 `MoveTo` 后，旧 JSON 导入会报「类型未注册」——这是**预期**，重新导出即可；但要在此需求里明确写出。
2. **预览三态语义**：`Chase` 恒 Running 会让外层 `Sequence` 一直 Running，属预期（它代表"这一帧没结束"）。
3. **黑板新增项要同步 UI**：`inRange` / `homeFar` 必须加进右侧黑板面板，否则策划没法测条件。
4. **服务端随后必须对齐**：本需求只改客户端；R022-1/2/3 要按新名字重写（删别名映射）。
