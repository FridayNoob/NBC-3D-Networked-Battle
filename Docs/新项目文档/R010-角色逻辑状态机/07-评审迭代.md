## 二、优先级

## 三、根因分析

- #1：我把「用属性暴露只读状态」当成了「Inspector 能看到」。**Unity 默认 Inspector 只序列化字段**，属性要显示必须写自定义 Editor 或用第三方 Inspector。
  教训：验收标准里写「能在 Inspector 看到 X」之前，先确认 X 是**字段**。
- #2：凭印象写了 `using NBC.Framework.Event;`（因为 `EventId` 在那儿），但 `StateChangeRecord` 属于 `NBC.Framework.Fsm`。
  教训：加 `using` 前先搜类型定义所在文件，别按「同类概念」猜命名空间。
- #3：状态机换成「闸门」后，`Idle` 禁用了移动组件。这本身是设计意图（站着不该动），但**没有任何地方写过「站着时不能转身」**，属于实现带出的隐含行为。
  教训：任何「禁用组件」的闸门，都要在验收标准里点明它连带停掉了什么。
- #4：每帧 `TryChangeState` 若不判断就打印，会刷屏；框架对同状态切换是空操作，但我们仍在 Brain 里加了 `wanted != Current` 的判断，并只在 `StateChanged` 打日志。

## 八、教训（可复用判据）

1. **想让它出现在 Inspector，就写成 `[SerializeField]` 字段**；属性不会显示，除非写自定义 Editor。
2. **加 `using` 前搜一下类型定义**（`StateChangeRecord` 在 `Fsm` 不在 `Event`），别按概念猜。
3. **禁用组件的闸门要写明连带停掉了什么**（本例：站着时连无输入转身也停）。
4. **日志只在「状态真的变了」时打**，否则 Console 会被刷满、把真问题淹掉。

## 九、遗留（如实）

- 只有 `Idle` / `Move` 两态；`Attack` / `Dead` / `Stun` 未做（等战斗需求）。
- `SendEvent`（事件入口）已具备但**暂无使用者**：以后攻击请求建议走 `fsm.SendEvent(...)`，由状态决定能不能接。
- 逻辑状态暂不驱动表现层（Animator 仍按 `Speed` 自己切）；等有「攻击中不可移动但能播攻击」这类需求时，再让状态注入动画参数。
- FSM 的 `TransitionRejected` 事件没有订阅（拒绝切换目前不可见）；等有 `CanEnterFrom` 拒绝逻辑时再订阅并打日志。
