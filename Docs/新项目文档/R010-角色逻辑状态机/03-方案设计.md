# 03 方案设计

需求：R010-角色逻辑状态机
所属阶段：M4
作者：AI 起草　状态：已确认（2026-10-31）

## 一、整体架构

```
InputManager.Current ──► PlayerBrain.Update
                            │  1) 判断「有没有方向输入」
                            │  2) TryChangeState(Idle/Move)
                            │  3) fsm.Tick(自增帧号)
                            ▼
                     StateMachine<EPlayerState>
                            │  OnEnter / OnUpdate / OnExit
                            ▼
                     Idle / Move 状态
                            │  设置允许移动
                            ▼
                     PlayerMove.enabled  ──► 位移与速度分量
                                                  │
                                                  ▼
                                          PlayerAnimation（零改动）
```

**逻辑状态（FSM）** 与 **表现状态（Animator 的 `S_Idle`/`S_Walk`）** 是两层，互不替代。

## 二、模块划分

| 模块 | 本次改动 | 不负责什么 |
| --- | --- | --- |
| `EPlayerState`（新） | 枚举 `Idle` / `Move` | — |
| `PlayerIdleState`（新） | 进入时禁止移动、打日志 | 不碰动画 |
| `PlayerMoveState`（新） | 进入时允许移动、打日志 | 不碰动画 |
| `PlayerBrain`（新） | 注册状态、`Start(Idle)`、每帧判断与 `Tick` | 不算位移、不写 Animator |
| `PlayerMove`（改） | **只加 `OnDisable` 把三个速度清零** | 算法一行不动 |
| `PlayerAnimation` / `Sword_Controller` | **零改动** | — |

## 三、接口（★ 先定死）

```
EPlayerState
    Idle, Move

PlayerBrain : MonoBehaviour
    公开只读：EPlayerState Current       当前逻辑状态
    公开只读：string CurrentName         状态名（日志用）
    公开只读：bool IsMoving              = Current == Move
    公开只读：int RegisteredCount        已注册状态数（Inspector 看）
    内部：StateMachine<EPlayerState> m_fsm；int m_frame（自增）
    Tick 帧号：自增 1（不用 Time.frameCount，避免编辑器暂停/回放下语义变化）

状态类（都继承 StateBase<EPlayerState>）
    Name / OnEnter(prev) / OnExit(next) / CanEnterFrom(from)
    CanEnterFrom：Idle → Move 允许；Move → Idle 允许（两态都放行）
```

## 四、数据结构

- `EPlayerState`：两值枚举。
- 状态切换判据：**输入是否有方向**（`|MoveX| > 0 || |MoveY| > 0`），不用速度阈值 —— 避免「按着键但被挡住」时状态乱跳。

## 五、时序与流程

1. `Awake`：取 `PlayerMove`，`Register(Idle/Move)`，`Start(Idle)`。
2. `Update`：
   1. 读 `InputManager.Instance.Current`（或 `!input.IsEnabled` 视为无输入）；
   2. `shouldMove = 有方向输入`；
   3. `shouldMove != IsMoving` 时 `TryChangeState(...)`；
   4. `m_fsm.Tick(++m_frame)`；Tick 内部会调状态的 `OnUpdate`。
3. 状态 `OnEnter`：`m_move.enabled = 允许`；并 `Debug.Log("[PlayerBrain] A → B")`。
4. `PlayerMove.OnDisable`：三个速度字段清零（否则动画会一直读到旧的 `CurrentSpeed`）。

## 六、技术选型与理由

| 选择 | 选定 | 理由 | 被否的方案 |
| --- | --- | --- | --- |
| FSM 类型 | `StateMachine<EPlayerState>`（非分层） | 两态用分层是过度设计 | `HierarchicalStateMachine` |
| 帧号来源 | **自增计数器** | 语义稳定，不受编辑器暂停/时间缩放影响 | `Time.frameCount` |
| 切换判据 | 输入有无方向 | 与「被挡住」解耦，不会来回抖 | `CurrentSpeed > 阈值`（被挡住时会反复切） |
| 闸门实现 | `PlayerMove.enabled` | 一处开关，禁用后 `PlayerAnimation` 自然读到 0 | 在 `PlayerMove` 里加 if（要改算法） |

## 六之二、为什么位移**不**放进 PlayerMoveState.OnUpdate（2026-10-31 负责人问过，定稿保留现状）

两种做法都成立，本项目选「状态管闸门、PlayerMove 管怎么动」，四条理由：

1. **`StateTick` 没有 deltaTime**（只有 `Frame` / `DeltaFrames`）。位移必须乘真实时间：
   在状态里读 `Time.deltaTime` 会把状态绑死 UnityEngine（脱离引擎无法测）；
   用 `DeltaFrames` 反推时间则「帧率一变速度就变」—— 帧同步项目最忌讳这条。
2. **执行顺序会变隐式**：现在 `PlayerAnimation` 用 `LateUpdate` 显式保证「读完位移再喂动画」。
   位移若挪进 `OnUpdate`，它就发生在 `PlayerBrain.Update` 内部，`PlayerAnimation` 与位移的先后变成依赖组件挂载顺序 —— 顺序反了会喂上一帧的速度（动画慢半拍）。
3. **状态机该表达意图，不是物理**：加 Attack 时，位移在状态里就要把位移代码复制到另一个状态，或提到基类；
   闸门方案下 Attack 只写一条「不允许移动」，位移代码永远只有一份。维护成本随状态数是常数而非线性。
4. **可复用与可测**：`PlayerMove` 不依赖 FSM 也能动（`PlayerAnimation` 用 `[RequireComponent]` 直接绑它，以后怪物/NPC 可复用）；
   位移只在状态里的话，任何没有 `PlayerBrain` 的物体都不会动。

**代价（承认）**：「移动」这件事被两处知道 —— Brain 判「该不该 Move」、PlayerMove 做「怎么动」。
将来的正解不是把位移搬进状态，而是**状态给 PlayerMove 设参数**（`SpeedScale` / `CanTurn` / `CanMove`），
把「蹲走慢」「攻击中小幅移动」「受击不能动」都变成参数注入。等真有这类需求时按 C 方案演进。
## 七、风险与对策

- **每帧反复切换** ⇒ 只在「状态该变」时调 `TryChangeState`，且 `TryChangeState` 对同状态是空操作（框架已保证）。
- **禁用 `PlayerMove` 后速度残留** ⇒ 已在 `OnDisable` 清零（04 里落实并验证）。
- **状态未注册就 `Start`** ⇒ 框架会抛异常（这是好事，能立刻发现装配错）。
- **FSM 与 Animator 混淆** ⇒ 文档与注释都写明：FSM 管逻辑，Animator 管表现。
- **帧号倒退** ⇒ 自增计数器不会倒退；编辑器重编译后字段重置为 0 也没问题（FSM 允许从 0 起）。
