# 02 需求：配置以 SO 为编辑真值、导出 CSV 给服务端（试点 Dungeon）
## 一、业务目标（一句话）

让负责人在客户端 Inspector/编辑器窗口里改 `DungeonConfig.asset`，点一次「导出」就把数据写回 `Configs/Design/Dungeon.csv`，服务端重启后按新数据生成副本；反方向也能把 CSV 导回 SO。
## 二、用户与场景

- 用户：负责人（唯一开发者，兼任策划）。
- 场景 A：想给「狼巢」加一只狼 → 在窗口里把 `monsters` 从 3 个改成 4 个 → 导出 → 重启服务端 → 进副本看到 4 只。
- 场景 B：手改过 CSV（比如批量改 spawnRadiusMm）→ 想让客户端 SO 跟上 → 点「从 CSV 导入」→ SO 被覆盖。
- 场景 C：改完 SO 忘了导出 → 重新打开窗口时看到红字「SO 有未导出改动」，避免服务端跑旧数据。
## 三、功能列表
**P0（本次必须）**
1. 菜单 `Tools/NBC/配置表/副本表（SO ↔ CSV）` 打开编辑器窗口，列出 `DungeonConfig.rows` 全部行。
2. 窗口内可增行、删行、复制行；字段：`id`、`name`、`maxPlayers`、`spawnRadiusMm`、`monsters`（列表）、`bossId`。
3. 校验：主键唯一、`maxPlayers` 2~4、`spawnRadiusMm` 500~20000、`monsters`/`bossId` 在 `Monster` 表存在、`name` 非空且 ≤16 字。
4. 「导出到 CSV」：校验通过才写；只重写数据行，前 4 行表头原样保留；UTF-8 无 BOM、LF；写前留 `.bak`。
5. 「从 CSV 导入」：解析 → 校验 → 弹确认框 → 覆盖 SO 的 `rows` 并保存资产；失败不动资产。
6. 「未导出改动」红字提示：用当前 SO 重拼 CSV 文本与磁盘逐字比较。
**P1（本次尽量）**
7. 导出成功后自动跑一次 `ConfigKit.Cli`（生成 `.cs/.tsv/.json`），失败回滚 CSV。
8. 导出/导入结果写进 Console，带行数与文件路径。
**P2（以后）**
9. 推广到其余 9 张表；一张表一个窗口或一个通用窗口按表名切换。
## 四、边界（不做什么）

- 不做「改 SO 自动导出」（避免误写磁盘）。
- 不做运行时（Play 模式）编辑；只在编辑器里用。
- 不改 ConfigKit 生成器、不改服务端读表方式、不改 `Generated/**` 手写内容。
- 不处理 CSV 的列顺序变更（按表头字段名匹配，列序变了也能读）。
- 不负责重启服务端（只提示）。
## 五、优先级

P0 全部做完才可用；P1 是便利性；P2 是推广，另开子需求。
## 六、验收标准（当…时，应…）

1. 当打开窗口时，应看到 `Dungeon.csv` 的 2 行数据（1001 狼巢、1002 蛛网洞穴）与 SO 一致。
2. 当把 1001 的 `monsters` 改成 4 个并点导出时，应写回 CSV 且第 5 行数据为 4 个怪物号，前 4 行表头逐字不变。
3. 当把 `maxPlayers` 改成 1 并点导出时，应被拦截并提示范围 2~4，且磁盘文件不变。
4. 当把 `id` 改成与另一行重复并点导出时，应提示主键重复，磁盘不变。
5. 当 `monsters` 填了 `Monster` 表里没有的编号时，应提示引用不存在，磁盘不变。
6. 当导出成功后，应生成 `.bak` 且窗口红字提示消失。
7. 当手改 SO 未导出时，应显示「SO 有未导出改动」。
8. 当点「从 CSV 导入」时，应先弹确认框，确认后 SO 的 `rows` 与 CSV 完全一致。
9. 当 CSV 有语法错误（引号不配对）时，导入应失败并提示行号，SO 不变。
10. 当导出且 P1 生效时，应自动跑 ConfigKit 并提示「已生成，请重启服务端」。
11. 当导出后重启服务端并进副本时，怪物数量应与新 CSV 一致。
12. 当只用本工具、不手改 CSV 时，重复「导出→导入→导出」应得到逐字节相同的文件（幂等）。
