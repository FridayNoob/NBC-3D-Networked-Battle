## 三、根因分析

- #1：我用 `InRoom` 当「能不能发输入」的判据，而 `NetSession.InRoom` 只看房间字段，**`Fail` 不清房间**。
  教训：**判「能不能发」永远看连接状态，不要看业务状态**（房间、局号这些在断线后都是残留）。
- #2：我把「未在线」当成「连接失败」，没区分 `Connecting` / `Handshaking` 这两个**进行中**状态。
  教训：**任何「重试」逻辑都必须区分「进行中」与「已失败」**，否则就是对进行中的操作再发一次。
- #3：TCP 连一个不通的地址可能长时间无响应；没有超时，策略永远等不到状态变化。
  教训：**重试必须配超时**，而且超时后的动作要包含「把旧连接断掉」（否则下一次 `Connect` 会被状态闸挡住）。
- #4：我把 `Reset` 后的阶段置成 `Waiting`，于是下一帧走「正在等退避」分支，`m_waitSeconds` 已是 0 ⇒ 立刻 `Connect`。
  教训：**阶段枚举的语义要唯一**：「本次尝试未结算」和「正在等待」是两种状态，不能合并。
- #5：我原来用 `!InRoom` 清「在房」标记 —— 又一次踩了 `InRoom` 不断线变 false 的坑（与 #1 同源）。

## 八、教训（可复用判据）

1. **判「能不能发」看连接状态，不看业务状态**（`InRoom` 这类字段断线后是残留）。
2. **重试必须区分「进行中」与「已失败」**，否则会对进行中的操作重复发起（`Connect` 会直接抛）。
3. **重试必须配超时**，且超时后要能把旧连接断掉，否则状态闸会一直挡住下一次尝试。
4. **阶段枚举语义要唯一**：合并两个语义就一定会出现「该等的时候不等」。
5. **能给纯逻辑建独立验算工程，就别指望人工点**：本需求 4 个 bug 里有 2 个先被自动化断言抓到（`Connecting 中只 Wait`、`超时 ⇒ Reset`），真机只是把它们复现出来。

## 九、遗留（如实）

- **锁步局重连回来不参与本局**（服务端 `StartRoom` 只开一次）：要恢复需协议加 `LockstepResume`（tick + hash + 实体），另开需求。
- 没有专门的「锁步局已开局，无法恢复本局」文案：目前走的是「回房成功」的通用日志，玩家能回房但看不到本局状态。**这条要在接战斗时补**。
- HUD 还没显示重连阶段（本版只有 Console）；要显示得给 prefab 加控件。
- `m_attemptElapsed` 用的是每帧 `deltaTime` 累加，编辑器暂停时会停住（符合预期，不修）。
