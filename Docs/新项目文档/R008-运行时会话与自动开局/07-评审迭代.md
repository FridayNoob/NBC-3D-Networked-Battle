## 三、根因分析

- #1：`TcpTransport` 在 `NBC.Framework.Net.Adapter`，我按 `NBC.Framework.Net` 猜了命名空间。
  **教训**：跨程序集用类型前，先 `grep 'namespace' 该文件`，别按名字推。
- #2：我当时只看了 `NetSession.Pump` 里没有 `Step` 调用，就断言「没人步进」；
  实际上步进发生在 `HandleLockstepFrame → LockstepClient.ApplyFrame → WorldStep.Step`。
  **教训**：判断「某能力有没有」不能只搜一个方法名，要**追调用链到终点**。
- #3：会话是非静态的，谁建谁持有；两个入口（窗口 / 运行时）各自能建一份。
  **对策**：文档写死「验收前断开窗口」，不给它加互斥逻辑（避免为一个调试便利引入全局状态）。
- #4：`m_mode` 是序列化字段，驱动只在每帧读值、不监听变更；Inspector 改动只在下次 `Start` 生效。

## 八、教训（可复用判据）

1. **判断「某能力有没有」要追调用链到终点**：`Pump` 里没有 `Step`，不代表没人步进 —— 它在「收到帧」的回调链里。
2. **跨程序集用类型前先 grep 它的 `namespace`**，别按程序集名推。
3. **非静态会话 = 谁建谁持有**：多入口（窗口 / 运行时）就会有多份，靠文档约束比加强制互斥更划算。
4. **序列化字段改动只在 `Start` 生效**：Inspector 改完要重进 Play，这条要写在使用说明里。
