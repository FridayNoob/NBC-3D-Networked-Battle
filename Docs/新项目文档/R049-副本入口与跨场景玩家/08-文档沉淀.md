## 一、文档范围

本篇沉淀四个可复用单元的用法与坑：`DungeonEntrance`（副本入口与跨场景交接）、`PlayerPersist`（跨场景保留玩家 + 相机接线）、`RuntimeNetDriver` 的两个开关（`AutoJoin` / `BindPresentation`）、`HpBarDemoBehaviour` 的驱动复用；以及「单场景加载会杀掉挂在该场景物体上的协程」这条通用结论。

## 二、模块文档

### 2.1 DungeonEntrance

- 简介：站在门口按 E，先连服进房，成功后再切 Battle，并把玩家与相机一起交过去。挂在 World 的 `[DungeonEntrance]` 上，同一物体下挂 `ModuleA` 预制体当门面。
- 接口：Inspector 字段 `m_triggerRadius`（米，默认 3.5）、`m_enterKey`（默认 E）、`m_host`/`m_port`/`m_dungeonId`、`m_connectTimeoutSeconds`（默认 8）、`m_battleSpawn`（副本出生点，默认原点）、`m_logDiagnostics`；对外只读 `IsConnecting`。
- 示例：走到 z≈431 的门楼 3.5 米内，屏幕出现「按 E 进入副本」，按 E 后 Console 出现 `开始进入副本，先握手`。
- 原理：`EnterRoutine` 协程负责「找/建 `[DungeonSession]` → 配置会话 → 等 `IsOnline` → 标记玩家常驻 → 调 `SceneFlow.LoadAsync`」。**收尾必须在 `LoadAsync` 的回调里做**，因为切场景会销毁本组件、协程随之终止。
- 坑：见 2.5 第 1 条。
- 维护：改出生点只动 Inspector 或 `m_battleSpawn` 默认值；改成「多个副本」时把 `m_dungeonId` 提成参数，别复制脚本。

### 2.2 PlayerPersist

- 简介：把玩家根物体标成「跨场景保留」，并在切场景后把相机接回去。
- 接口：`static bool MarkPersistent(GameObject playerRoot)`（父物体为空才 `DontDestroyOnLoad`，同时关掉 `WorldPlayerSetup` 的贴地逻辑，返回是否成功）；`static void BindCamera(GameObject playerRoot)`（没有 `WorldFollowCamera` 就挂一个，`SetTarget`，并关掉旧 `FollowCamera`）。
- 示例：`PlayerPersist.MarkPersistent(m_player.gameObject);` → 切场景 → `PlayerPersist.BindCamera(m_player.gameObject);`
- 原理：`DontDestroyOnLoad` 只对根物体生效；`WorldFollowCamera` 是「只跟位置、鼠标控朝向」的版本，副本里比旧的 `FollowCamera` 更合适。
- 坑：见 2.5 第 2、3 条。
- 维护：新增跨场景状态（如副本内 HUD）时，优先挂在玩家根下的子物体上，跟着一起走。

### 2.3 RuntimeNetDriver 的两个开关

- 简介：`AutoJoin` 控制「连上就自动进房」，`BindPresentation` 控制「是否把快照渲染成场景物体」，`ConfigureSession(host, port, dungeonId)` 用来在连接前改写目标。
- 接口：`bool AutoJoin { get; set; }`（默认 true）、`bool BindPresentation { get; set; }`（默认 true）、`void ConfigureSession(string host, int port, int dungeonId)`、只读 `IsOnline`/`IsJoined`/`HeroAlive`/`HeroEntityCount`/`FailureReason`/`LastError`、`void LeaveRoom()`。
- 示例：入口先 `ConfigureSession` + 两个开关置 false，等握手成功、切完场景再置回 true，避免「在 World 里就进房、快照把人渲染到副本坐标」。
- 原理：进房判断是 `if (m_autoJoin && m_session.IsOnline && !m_joinRequested)`；渲染入口 `RefreshPresentation` 首行是 `if (!m_bindPresentation) return;`。
- 坑：两个开关默认 true，Battle 单场景运行时（不经过入口）行为不变。
- 维护：新增「延迟到某个时机才生效」的能力，优先加开关，不要在 `Update` 里堆条件。

### 2.4 HpBarDemoBehaviour

- 简介：Battle 的临时 HUD/驱动宿主，原来在 `Start` 里无条件 `AddComponent<RuntimeNetDriver>()`；现在先找已有驱动并复用。
- 接口：无对外接口；行为变化只在 `Start`。
- 示例：从 World 带着驱动进 Battle 时，日志出现「沿用已有的 RuntimeNetDriver」。
- 原理：`FindObjectOfType<RuntimeNetDriver>()` 在 `DontDestroyOnLoad` 物体上也能找到，所以跨场景后仍能复用。
- 坑：见 2.5 第 4 条。
- 维护：R046 做正式 HUD 时，把这段临时逻辑整体换掉。

### 2.5 踩坑清单

1) **协程随组件、组件随场景。** 单场景切换会销毁源场景物体，`yield` 之后的代码不会执行，而且不报错。凡是「切完场景再做的事」，都要放进 `LoadAsync` 的回调（回调由常驻的 `SceneFlow` 执行）。
2) **`DontDestroyOnLoad` 只认根物体。** 子物体调用会警告并无效；本项目玩家是 `[Player_Hero]` 根，正好满足。
3) **删物体前先看谁引用它。** 删掉 Battle 里的遗留玩家后，`FollowCamera.m_target` 变成空引用，必须同时置空或改接新目标。
4) **预制体实例会被误认成「脚本挂错」。** 场景里旧实例自带一组脚本，和运行时带过来的玩家并存时，Inspector 看起来像挂错；先看层级里是不是有两个同名物体。
5) **端口要有单一真源。** 服务端 appsettings 与客户端 Inspector 各写一份，任何一边改都会静默失配，表现为「服务器开着却超时」。
6) **调试账号是开关不是默认。** `--dev-accounts` 不开时查数据库；客户端默认账号只在调试表里存在。
7) **测试前退出 Play。** `This cannot be used during play mode.` 来自测试框架保存场景的步骤，不是测试本身失败。
