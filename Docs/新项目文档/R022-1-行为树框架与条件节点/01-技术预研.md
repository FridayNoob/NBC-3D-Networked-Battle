# 01 技术预研

需求：R022-1-行为树框架与条件节点
所属阶段：M4
作者：AI　状态：草稿（待负责人确认）

## 一、调研目标与约束

- 目标：做一套**纯 C# 的最小行为树内核**（三态、组合节点、条件叶子、执行上下文），作为后续「动作节点 / 怪物大脑 / 编辑器 JSON」三块的地基。
- 约束：
  1. **必须在服务端跑**：纯 .NET、无 `UnityEngine`（服务端权威 AI）；
  2. **确定性**：只用整数与逻辑帧，不用 `float` 运算、不读真实时间、不用 `Random`；
  3. **本需求不做**：动作节点（移动/攻击）、怪物大脑接线、JSON 加载 —— 那是 R022-2 / R022-3；
  4. 代码量预估 **≈477 行**（见 §七），符合 AGENTS.md §0.1 的 500 行上限；
  5. **架构约定（负责人 2026-11-08 明确）**：**怪物（含 BOSS）一律用行为树，玩家用状态机**，两者不混用。
     玩家侧已经是状态机（`PlayerBrain` + `PlayerStates`：`PlayerIdleState` / `PlayerMoveState`，`StateBase<EPlayerState>`），
     **本需求不改玩家侧任何代码**；行为树只服务于怪物。
  6. **数据流约定（负责人 2026-11-08 明确）**：**策划在客户端行为树编辑器（R023）里编写各怪物的树 → 导出 JSON → 服务端解析 JSON 并构建行为树**。
     由此对本需求（内核）提出三条硬约束：
     - **节点名就是协议**：`Name`（将来即 JSON 的 `NodeType`）一经发布**不可改名**，改名等于破坏已导出的树；
     - **参数只能来自 JSON 的 `Params`**（如 `hpThreshold`），节点内部不得写死「哪种怪走哪个分支」；
     - **解析与文件读取不属于本需求**：本需求只保证内核「可被 JSON 工厂组装」；读文件、解析、注册表在 **R022-3**。
  7. **节点以客户端为准（负责人 2026-11-08 明确）**：**行为树节点的定义与命名以客户端编辑器（`BTNodeRegistry`）为唯一权威**。
     服务端**不得自创节点名、不得用别名映射**，只能实现客户端注册表里已有的类型。
     若服务端需要某种能力（例如「在射程内」「冷却好了」），必须**先在客户端注册该节点**，服务端再跟进实现。

## 三、方案（只做框架 + 条件）

```
BtStatus           三态：Success / Failure / Running
BtNode             抽象基类：Name + Tick(BtContext)
BtComposites       Selector（第一个非 Failure 就赢）/ Sequence（遇 Failure 短路）/ Parallel
BtContext          世界 / 自己 / 出生点 / 目标 / 帧号 / AI 参数 / Chasing / LastAction
BtOps              世界操作薄封装（查最近敌人、算距离、算离家距离）
BtLeaves(条件)     IsDead / HasTarget / InAttackRange / AttackReady / HPBelow / HomeFar
```

**条件节点全部无副作用**（只读上下文与世界），这是硬约束：条件若动状态，Selector/Sequence 的短路语义会被破坏。

## 四、关键技术判断

| 判断 | 理由 |
| --- | --- |
| 自己写内核，不用 FSM 框架 | 行为树要「组合 + 短路 + 后续可视化编辑」，FSM 表达不了复用 |
| 三态而不是 bool | 动作需要「本帧未结束」（Running），否则等待/位移只能靠外部计时器 |
| 上下文用可变对象而非参数透传 | 节点间要共享「目标、帧号、是否追击」；每帧复用同一个实例，避免每帧分配 |
| 距离/移动全部调既有世界函数 | 规则只有一份（射程、冷却、钳位都在 `DungeonBattle`），行为树不重复实现 |

### 分工约定：怪物 = 行为树，玩家 = 状态机（本次定稿）

| 对象 | 用什么 | 理由 | 本次是否改 |
| --- | --- | --- | --- |
| **怪物 / BOSS** | **行为树**（本需求的内核 + 条件，后续接动作与 JSON） | 怪种多、行为差异大，靠「通用节点 + 各自组树」扩展；配置化程度高 | 是（只做内核与条件） |
| **玩家** | **状态机**（`PlayerBrain` + `PlayerStates`） | 玩家状态少而固定（Idle / Move）、与输入强耦合，状态机更直白 | **否，一行不动** |

> 这条约定的作用：以后不要问「要不要把玩家也改成行为树」。答案是**不要**。
> 行为树只解决「怪多、行为各异」的问题；玩家的状态机已经够用，改了只有成本没有收益。

### 数据流：策划搭树 → JSON → 服务端构建（本次定稿）

```
策划（客户端 R023 编辑器）
  拖节点 / 连线 / 填参数
        │  导出
        ▼
  BehaviorTrees/<aiKind>.json      ← TreeId / RootNodeId / Nodes{NodeType, Pos, Params, Children}
        │  启动时读取（一次，不每帧读盘）
        ▼
服务端（R022-3）
  BtJsonLoader：按 NodeType 字符串查工厂 → 建节点 → 挂 Children → 得到一棵 BtNode 树
        │
        ▼
  MonsterBrain 每逻辑帧 Tick（30Hz，确定性）
```

三条由此产生的硬约束（本需求就要遵守）：

| # | 约束 | 为什么 |
| --- | --- | --- |
| 1 | `Name` = `NodeType`，**发布后不许改名** | 改名会让已导出的 JSON 在服务端「找不到节点」 |
| 2 | 节点参数**只从 JSON `Params` 来** | 否则「策划改数值」这件事就失效了 |
| 3 | 未知 `NodeType` **必须报错**，不许静默跳过 | 静默跳过 = AI 少一半行为，且极难排查 |

> 分工：**R022-1** 只保证内核可被组装（节点可组合、参数进构造函数）；
> **R022-3** 负责读 JSON、按类型建节点、缺类型时报错。中间的动作节点与接线在 **R022-2**。

### 节点清单以客户端为准 —— 现状差距（必须先解决）

客户端 `BTNodeRegistry` 当前只有 8 种：`Selector` / `Sequence` / `Parallel` / `HPBelow` / `HasTarget` / `MoveTo` / `CastSkill` / `Wait`。

按「以客户端为准」，服务端**只能**实现这 8 种。但决定怪物行为的几件事在客户端**还没有节点**：

| 缺的节点 | 为什么需要 | 现在服务端是怎么凑的（**必须改掉**） |
| --- | --- | --- |
| `IsDead` | 死亡后停止一切行为 | 服务端自创 |
| `InAttackRange` | 够得着才打（否则攻击节点空转） | 服务端自创 |
| `AttackReady` | 冷却没好就别打 | 服务端自创 |
| `HomeFar` | 离家太远回位（leash） | 服务端自创 |
| `Chase` / `BasicAttack` / `ReturnHome` / `Patrol` / `Idle` | 五个动作 | 用 `MoveTo` / `CastSkill` / `Wait` **别名映射** |

⇒ **结论：R022-1 目前只能覆盖 `HPBelow` 与 `HasTarget` 两个条件**（加上 3 个组合节点）。
要让怪物真正「会追会打会巡逻」，得**先在客户端补齐节点**（新需求），再回来做 R022-1 的条件与 R022-2 的动作。

> 这条差距不是「实现细节」，是**顺序问题**：客户端是权威，那就先把权威那一侧补齐。

## 五、已知坑

1. **Selector 短路陷阱**（真踩过）：任何「返回 Success 的动作」放在 Selector 里都会**吃掉整帧**，导致后面的分支永不执行。
   → 条件节点一律无副作用；「刷新目标」这种前置动作必须放在大脑里做，不能做成树节点（R022-2 会落实）。
2. **每帧分配**：`BtContext` 必须复用（一只怪一个），否则 30Hz × N 只会持续产生垃圾。
3. **浮点**：距离比较一律用整数毫米（`DistanceMm`），不要为了「好看」引入 `float`。
4. **条件顺序**：`HasTarget` 必须在 `InAttackRange` 之前（后者依赖 `ctx.Target` 非空），否则空引用。
5. **命名即契约**：`Name` 字符串将来要作为 JSON 的 `NodeType`，一旦定下不要改。
