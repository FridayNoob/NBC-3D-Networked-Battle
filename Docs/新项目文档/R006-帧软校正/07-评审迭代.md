## 二、优先级

1 是主目标；2、3 是同一改动的边界，必须一起处理；4 只影响验证手段。

## 三、根因分析

- #1：`SnapshotSceneBinder.LateUpdate` 直接把快照位置赋给 `localPosition`，而快照率 30Hz、渲染 60fps ⇒ 一半的帧显示的是同一个旧位置。
- #2：一旦改成「朝目标移动」，就必须回答「目标在 500 米外时怎么办」。不设阈值就会出现 60 米/秒的横穿。
- #3：槽位是池化复用的，新建时在原点；若第一帧就走「追」的逻辑，实体会从地图中心飞过来。
- #4：`unity_execute_code` 的执行上下文不跨帧存活，`EditorApplication.update +=` 注册的委托跑不到下一帧；而 MCP 单次往返 2~4 秒，外部轮询也分辨不了 33ms 的帧间距。
  结论：**帧级观感只能靠眼睛 + 二值判定实验**（例如「扔到 500 米外用多久回来」）。

## 八、教训（可复用判据）

1. **任何「朝目标移动」的逻辑都要回答两个问题**：目标太远怎么办（瞬移阈值）、第一次出现怎么办（首帧归位）。
2. **平滑的代价是位置不再精确等于权威值**：这是方案定义的一部分，要写进文档，别让后来人以为「位置不对 = bug」。
3. **速度取「距离 / 快照间隔」而不是固定值**：固定值在远近距离下都错。
4. **验证 30Hz vs 60fps 这类帧级现象，别指望远程轮询**：用「时长 → 距离」的宏观实验做二值判定（500 米 2 秒内回来 ⇒ 不是匀速追）。

## 九、遗留（如实）

- 位置从「精确等于快照」变成「在路上」：若以后要做严格的回放/对账（R005 `.replay`），**回放用的应是数据层快照，不是表现层位置**。
- 未做旋转/朝向插值（当前表现层不写朝向）。
- 未做外推（预测未来位置），所以网络延迟大时仍会「慢半拍」。
- 实体数很多时可以在静止槽位上跳过计算（当前每帧都算，问题不大）。
- 胶囊仍是占位代理：换成模型是另一个需求（已确定由负责人自己找模型，后续开 R015）。
