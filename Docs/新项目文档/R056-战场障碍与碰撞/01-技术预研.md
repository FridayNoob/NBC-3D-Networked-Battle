## 调研目标与约束

**目标**：让服务端能判定「这个地方过不去」，判定依据是客户端可视化编辑、写回 CSV 的障碍数据；怪物与玩家的移动被障碍挡住，并且能贴着障碍滑动而不是卡死。

**约束**：

1. 服务端权威，逻辑只有一份（`DungeonBattle`/`BattleEntity`），不在客户端复制战斗判定。
2. 不用 Unity 物理（PhysX 是浮点 + 多线程，帧同步与回放不可复现），碰撞用整数毫米坐标判。
3. 数据入口在客户端（§0.4）：场景里摆障碍 → 菜单写回 `Configs/Design/BattleObstacle.csv` → ConfigKit 生成 → 服务端重启后生效。
4. 不新增第三方依赖；新增 + 修改 `.cs` 不超过 500 行。
5. 不改协议：障碍只影响服务端位移结果，客户端从快照看到位置变化。

## 最小可运行示例

判定一个圆障碍是否挡住某点（整数、无浮点）：

```csharp
long dx = x - circle.Xmm;
long dz = z - circle.Zmm;
long r  = circle.RadiusMm;
bool blocked = dx * dx + dz * dz <= r * r;
```

分轴滑动（先试 X 再试 Z，任一轴被挡就只走另一轴）：

```csharp
int nextX = PosXmm + dx;
if (!field.IsBlocked(nextX, PosZmm)) { PosXmm = nextX; }
int nextZ = PosZmm + dz;
if (!field.IsBlocked(PosXmm, nextZ)) { PosZmm = nextZ; }
```

## 方案对比

| 方案 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| A 格子位图 | 场地切成 500mm 格子，导出 0/1 位图 | 判定 O(1)，天然支持复杂形状 | 编辑要在格子工具里画；斜边锯齿；数据体积大 | 复杂地形、寻路一体 |
| **B 圆 + 矩形列表（采用）** | 每行一个障碍：圆（圆心+半径）或矩形（中心+半宽半高） | 数据小、编辑器里摆空物体就能出数据、判定便宜 | 只能表达凸形；凹形要拆几块 | 本项目的房间式副本地形 |
| C 烘焙 NavMesh/碰撞体 | 用 Unity 烘网格给服务端 | 精度最高 | 服务端读不了 Unity 资产；确定性无法保证 | 单机或纯客户端判定 |

## 已知坑与版本兼容

1. **浮点禁令**：全部用 `long`（毫米），平方距离比较，避免 `float` 参与判定导致两端不一致。
2. **斜向穿角**：只判终点会「从两个障碍的缝里穿过去」；本项目按分轴推进，等价于 AABB 近似，够用但要写清。
3. **CSV 中文表头**：字段行必须是英文（ConfigKit 按字段名取列），第二行中文给人看；Excel 保存会变 GBK，服务端已按 BOM→UTF-8→GBK 回退读。
4. **生成时机**：新增 CSV 后必须跑一次 ConfigKit，否则客户端 `BattleObstacleConfig` 不存在，Gizmos 报空。
5. **服务端重启才生效**：`ServerTables.TryLoad` 在启动时读一次，改表不重启无效（与 Monster 表一致）。
6. **Gizmos 只在编辑器绘制**：运行时不可见，验收要在 Scene 视图看。

## 结论

采用方案 B：新表 `BattleObstacle.csv`（圆/矩形两种），服务端新增 `BattleField` 负责「读表 + 阻挡判定 + 分轴滑动」，客户端用场景空物体授权 + Gizmos 显示 + 菜单写回。预估 460 行（服务端 150、客户端 230、测试 80）。
