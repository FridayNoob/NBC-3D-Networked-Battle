# 02 需求

需求编号：R053
所属阶段：M4
作者：AI（DeepSeek）
状态：开发中

## 一、业务目标（一句话）

让「房号」不再是易变的开房计数，而是跟着副本走的稳定编号；「第几局」由独立对局号表达。

## 二、用户与场景

- 玩家 A 单人去打副本 1001：进房看到 `d1001 · 第 1 局`。
- 打完点「再来一次」：仍在 `d1001`，变成`第 2 局`，怪满血。
- 点「返回世界」再进来：还是 `d1001`，`第 3 局`（上一局的世界已被回收）。
- 四人都满时，第五个人进不来（直接拒绝，不开溢出房）。

## 三、功能列表

| 优先级 | 功能 |
| --- | --- |
| P0 | 房号 = `"d" + 副本号`；同一副本重复进房复用同一间 |
| P0 | 空房保留（`Phase` 回 `Waiting`），不再删除 |
| P0 | `Room.MatchId` 每开一局 +1，并在 `RoomState` 下发 |
| P0 | 房间没人时回收战斗世界，下一局重新开 |
| P0 | 满员直接拒绝（沿用现有 `RoomFull`） |
| P1 | 客户端日志显示「副本 1001，第 N 局」 |
| P2 | 编辑器网络调试窗口显示对局号 |

## 四、边界（不做什么）

- 不做「同副本多队」与溢出房（C 方案）。
- 不做房间超时回收（本项目副本数量个位数，可忽略）。
- 不改副本内容、掉落、数值。
- 不改 `JoinRoom` 的「指定房号」语义（仍要求房间已存在）。

## 五、优先级

P0 全做，P1 顺手做（一行日志），P2 留给需要时。

## 六、验收标准（当…时，应…）

1. 当玩家留空房号进副本 1001 时，房号应为 `d1001`。
2. 当第二个玩家留空房号进同一个副本时，应进入同一间 `d1001`。
3. 当最后一个人离开时，房间应保留、席位为 0、`Phase` 为 `Waiting`。
4. 当玩家再次进房时，应复用 `d1001` 且 `MatchId` 比上一局大 1。
5. 当点「再来一次」时，房号不变、`MatchId` +1、怪满血。
6. 当房间没人时，战斗世界应被回收且 `_recorded` 被清（下一局重新广播结算）。
7. 当房间满员时，再进入应被拒绝（`RoomFull`），不得偷偷开新房。
8. 当客户端收到 `RoomState` 时，日志里应出现「第 N 局」。
9. 当协议重生成后，旧字段编号不变、`CONTRACT_VERSION` 不变。
10. 当同一副本的两名玩家看到席位表时，`room_id` 与 `match_id` 应一致。
