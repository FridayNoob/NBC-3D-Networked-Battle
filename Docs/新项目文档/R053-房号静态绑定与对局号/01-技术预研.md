# 01 技术预研

需求编号：R053
所属阶段：M4
作者：AI（DeepSeek）
状态：开发中

## 一、调研目标与约束

目标：房号不再随开房次数变化——**房号静态绑定副本**（`d1001`），同一间房里的「第几局」用独立的**对局号**表达。

约束：

1. 只改房间与协议的编号语义，不改副本内容与战斗规则。
2. 协议属兼容变更：`RoomState` 只**新增**字段，旧编号不动。
3. 空房常驻：房间对象保留，战斗世界必须回收（否则内存里留着没人看的世界）。
4. 同一副本同时只允许一组人；满员直接拒绝（不做溢出房）。

## 二、核心 API 清单

| 位置 | 现有 | 要变成 |
| --- | --- | --- |
| `RoomRegistry.Create` | `"r" + _nextRoomNumber` 自增 | `"d" + dungeonId`，已存在就返回 |
| `RoomRegistry.Leave` | 空房 `_rooms.Remove` | 空房**保留**，`Phase = Waiting` |
| `Room` | 无对局号 | 新增 `MatchId`（int，从 0 起，开打 +1） |
| `Room.ToState()` | 无对局号 | 带 `MatchId` |
| `RoomBattleService.EnsureBattle` | 建世界 | 建世界并 `room.MatchId++` |
| `RoomBattleService.DropBattlesOfDeadRooms` | 房间不存在才回收 | 房间不存在**或没人**都回收世界 |
| `RoomState`（proto） | 1~5 号字段 | 新增 `int32 match_id = 6` |

## 三、最小可运行示例

```csharp
Room room = registry.Join(a, a.PlayerName, string.Empty, 1001).Room!;   // 建房：d1001
battle = battles.EnsureBattle(room);                                   // 第 1 局
battles.ResetBattle(room);                                             // 丢掉旧世界
battle = battles.EnsureBattle(room);                                   // 第 2 局（房号仍是 d1001）
```

## 四、方案对比

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A 只加对局号 | 保留 `rN` | 改动最小 | 房号仍会变，配置与房间两套号 |
| **B 静态房号 + 对局号** | 房号 `d1001` 常驻，`MatchId` 每局 +1 | 房号稳定、语义清晰、可直接按副本号进房 | 同副本同时只一组人 |
| C 固定房 + 溢出错 | 满了再开 `rN` | 支持多队 | 两套规则并存，最复杂 |

负责人 2026-11-17 选 **B**，明确「同副本同时只一组人，满员直接拒绝」。

## 五、已知坑与版本兼容

1. 空房不删后，「留空房号自动找房」会找到空房——这正是想要的行为。
2. 房间保留但战斗世界要回收，否则下一局会拿回一地尸体；同时要清 `_recorded`，否则第二局不再广播结算。
3. `RoomState` 新增字段属兼容变更：客户端旧版本忽略它即可，`CONTRACT_VERSION` 不变。
4. 房号变了（`r1` → `d1001`），任何写死 `r1` 的测试/日志都要改。
5. 机器人占位（`--fill-seats`）不改变 `IsEmpty` 的定义（只看真人席位），空房回收世界时会连机器人一起清掉。

## 六、结论

采用 B：`RoomRegistry.Create` 用静态房号、空房保留、`Room.MatchId` 每局 +1、`RoomState.match_id` 下发、战斗世界在「没人」时回收。**预估改动约 120 行**（不含测试与文档）。
