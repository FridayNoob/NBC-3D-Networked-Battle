# 03 方案设计

需求编号：R053
所属阶段：M4
作者：AI（DeepSeek）
状态：开发中

## 一、整体架构

```
客户端进房（留空房号）
   ↓ JoinRoomRequest(dungeon_id=1001)
RoomRegistry.Join → FindJoinableRoom(dungeonId) → 没有就 Create(dungeonId)
   ↓ 房号 = "d" + 1001
RoomBattleService.EnsureBattle(room) → room.MatchId++ → 建战斗世界
   ↓ BroadcastSnapshot / BroadcastState（RoomState.match_id）
客户端 NetSession.HandleRoomState → 日志「房间 d1001（副本 1001，第 2 局）」
```

## 二、模块划分

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `RoomRegistry` | 房号生成、空房保留、席位 | 战斗世界、协议编解码 |
| `Room` | 存 `MatchId`、`ToState` 带对局号 | 递增时机 |
| `RoomBattleService` | 开打/重开时 `MatchId++`、没人时回收世界 | 房号规则 |
| `NetSession`（客户端） | 把对局号显示出来 | 判定对局号 |

## 三、接口

| 方法/字段 | 入参 | 出参 | 约定 |
| --- | --- | --- | --- |
| `RoomRegistry.Create(int dungeonId)` | 副本号 | `Room` | 房号 `"d"+dungeonId`；已存在则返回同一个 |
| `RoomRegistry.Leave(ClientSession)` | 会话 | `Room?` | 空房保留，`Phase=Waiting`；重复离开返回 null（幂等） |
| `Room.MatchId` | — | `int` | 从 0 起；每建一局 +1；只读给客户端 |
| `RoomBattleService.EnsureBattle(Room)` | 房间 | `DungeonBattle?` | 建世界成功后 `room.MatchId++` |
| `RoomBattleService.DropBattlesOfDeadRooms()` | — | — | 房间不存在**或 `IsEmpty`** 都回收世界并清 `_recorded` |
| `RoomState.match_id`（proto 6 号） | — | `int32` | 兼容新增 |

## 四、数据结构

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `Room.RoomId` | `string` | `d` + 副本号，静态 |
| `Room.MatchId` | `int` | 这一间房的第几局（0 表示还没开打） |
| `Room.Phase` | `RoomPhase` | `Waiting/Running/Finished` |
| `RoomState.match_id` | `int32` | 下发给客户端的对局号 |

## 五、时序与流程

1. 玩家留空房号进副本 → `Join` → `FindJoinableRoom` 找到 `d1001` 就加入，否则 `Create`。
2. 房间人满/开打 → `EnsureBattle` 建世界前 `MatchId++`。
3. 结算 → `RecordIfFinished` 广播结果、`Phase=Finished`。
4. 「再来一次」→ `ResetBattle` 丢世界 → 下一次 Tick `EnsureBattle` 再 `MatchId++`。
5. 所有人离开 → `Leave` 保房、`Phase=Waiting`；Tick 里 `DropBattlesOfDeadRooms` 回收世界并清 `_recorded`。
6. 再进房 → 复用 `d1001`，`MatchId` 继续 +1。

## 六、选型与理由

- **静态房号**：房号可直接由副本号推导，客户端/日志/排查都不再依赖「第几次开房」。
- **对局号放在 `Room` 而不是世界**：世界会被重建（tick 归零），对局号必须跨世界存活。
- **空房保留、世界回收**：两者解耦——房间是「副本的常驻实例」，世界是「一局的临时数据」。
- **满员拒绝**：不做溢出房，规则只有一条，避免 C 方案的复杂度。

| 风险 | 对策 |
