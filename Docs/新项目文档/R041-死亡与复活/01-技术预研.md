# R041 死亡与复活 —— 01 技术预研

需求编号：R041
所属阶段：M4
作者：AI 辅助
状态：开发中

## 1. 调研目标与约束

目标：玩家在副本里被打死后，**5 秒后在出生点满血复活**，客户端有倒计时与黑屏，复活后能继续打；这一局不会因为一个人死掉就结束。

现状（实读代码）：

| 位置 | 现状 |
| --- | --- |
| `Server/NBC.Server.Game/DungeonBattle.cs:509` | `IsFinished => AliveMonsterCount == 0 \|\| AliveHeroCount == 0` —— **英雄一死这局就判结束** |
| `Server/NBC.Server.Game/RoomBattleService.cs:852` | `RecordIfFinished` 一旦 `IsFinished` 就交战绩草稿，`IsWin = AliveMonsterCount == 0` |
| `DungeonBattle.Step()`（:831） | 只推进实体与行为树，没有任何"死亡计时 / 复活"逻辑 |
| `DungeonBattle.HeroSpawnPoint(int)`（:803） | 四个席位的出生点是确定性的：`(-500,0) / (500,0) / (0,-500) / (0,500)` |
| `Client/.../Bootstrap/RuntimeNetDriver.cs:857` | 英雄掉血只做 `PlayHit` + 飘字；**血量归零不会播死亡动画** |
| `Client/.../Player/PlayerBrain.cs` | 死亡状态只能由调试键 `L` 触发（`NotifyDead`），没有接服务端 `Alive` |
| 客户端 UI | 没有死亡遮罩/倒计时面板 |

约束：

1. **服务端权威**：谁死了、几秒后活、活在哪，全在 `DungeonBattle` 里算；客户端只负责显示与等。
2. 规则只写在 `DungeonBattle`（`RoomBattleService` 只负责广播与记账）。
3. **不新增协议字段**：`EntitySnapshot.Alive` 已经是布尔，复活就是它从 `false` 翻回 `true`；倒计时用两端同一份配置算。
4. 复活时长按 AGENTS.md §0.4 进 `Configs/Design/Dungeon.csv`（新列 `reviveSeconds`，默认 5）。
5. 不改生成代码（`NBC.Protocol`、`Config/Generated` 只由工具生成）。

## 3. 最小可运行示例

服务端（伪代码，落在 `DungeonBattle.Step` 里）：

```csharp
// 每帧：先把"死了多久"加一，到点就满血搬回出生点
for (int i = 0; i < _entities.Count; i++)
{
    BattleEntity e = _entities[i];

    if (e.Kind != 0 || e.Alive)
    {
        continue;
    }

    e.DeadTicks++;

    if (e.DeadTicks >= ReviveTicks)
    {
        (int x, int z) = HeroSpawnPoint(e.SpawnIndex);
        e.Respawn(x, z);      // Hp = MaxHp、Alive = true、DeadTicks = 0、清冷却
    }
}
```

客户端（伪代码）：

```csharp
// 快照里自己的英雄 Alive=false ⇒ 开黑屏 + 倒计时；翻回 true ⇒ 淡出、放开输入
if (!hero.Alive && !m_deathShown) { m_deathShown = true; m_deathPanel.Show(reviveSeconds); }
else if (hero.Alive && m_deathShown) { m_deathShown = false; m_deathPanel.Hide(); }
```

## 4. 方案对比

| 决策点 | 方案 | 优缺点 | 适用 |
| --- | --- | --- | --- |
| 复活位置 | **A 出生点** | 简单、不会卡在怪堆里；要挪位置 | 推荐（demo） |
| | B 原地满血 | 不挪位置；可能一睁眼又被围殴 | 硬核玩法 |
| 复活次数 | **A 无限** | demo 不会卡死；没有失败压力 | 推荐 |
| | B 每局 3 次 | 有压力；要加计数与"没次数→结束"判定 | 正式关卡 |
| | C 每局 1 次 | 压力最大；失败得快 | 高难 |
| 全灭判定 | **A 只有清怪才结束** | 与"无限复活"配套；不会中途结算 | 推荐 |
| | B 无次数且全灭 → 判负 | 需要次数系统一起做 | 后续 |
| 表现 | **A 黑屏 + 5 秒倒计时 + 「已复活」提示** | 最直观；要一个面板 prefab | 推荐 |
| | B 灰屏 + 数字 | 轻量；观感弱 | 省美术 |
| | C 只 HUD 提示 | 最省；容易不知道自己在等什么 | 不推荐 |

## 5. 已知坑与版本兼容

1. **`IsFinished` 的语义要先改**：不改的话英雄一死，`RoomBattleService` 立刻交战绩并结束这一局，复活逻辑永远走不到。
2. **`AliveHeroCount` 还被别处用**：`DungeonBattle.cs:468` 与 `RoomBattleService.cs:897` 的 `IsWin` 都读它，改判定时要逐个看（W15：改取值范围前 grep 所有比较点）。
3. **客户端血量归零不播死亡**：`RuntimeNetDriver` 只在掉血时 `PlayHit`，要新增"快照 Alive=false → `NotifyDead()`"。
4. **死亡期间输入要挡住**：服务端 `ApplyMove` 已经 `if (!Alive) return;`（`DungeonBattle.cs:204`），客户端还要在表现层停掉移动/攻击，否则会"原地跑"。
5. **复活位置要与客户端贴合**：`RuntimeNetDriver.ReconcileHeroPosition` 已有"漂移 > 2 米直接吸附"的逻辑，复活搬回出生点距离通常 > 2 米，会被自动吸附——要在复活那一帧确认它确实吸过去了。
6. **倒计时两端要同一份配置**：客户端也读 `Dungeon.csv` 的 `reviveSeconds`（走 `Config/Generated`），否则两端差 1~2 秒会出现"面板还没消失人已经活了"。
7. **AOI 不影响**：`ToSnapshot` 不过滤死亡单位，死掉的英雄仍在快照里（只是 `Alive=false`），客户端能收到复活。
8. **快照 `Alive` 翻转是布尔**：不需要新协议字段，也不用改 `NBC.Protocol` 生成代码。

## 6. 结论（已按负责人 2026-11-15 的决策修订）

死亡后的去向**按场景分三种**，倒计时统一 5 秒（黑屏 + 「已复活 / 即将退出副本」提示）：

| 场景 | 死亡后 | 结算/掉落 |
| --- | --- | --- |
| `World`（主世界） | 黑屏 5 秒 → 回到出生点满血复活 | 不结算、不掉落 |
| `Battle` 单人副本 | 黑屏 5 秒 → 退出副本回 `World`，副本重置 | 不结算、不掉落 |
| `Battle` 多人副本 | 黑屏 5 秒 → **留房旁观**（角色隐藏、输入禁用、可手动退出） | 房间继续，其他人照打 |

- 复活次数：`World` 里无限；副本里不复活（单人退出 / 多人旁观）。
- 复活位置：`World` 的出生点（村口，当前是 `(280.799, 1.450, 425.014)`）；副本没有复活点。
- 副本"重置"= 客户端退出房间后由服务端回收战斗世界（`RoomBattleService.DropBattlesOfDeadRooms` 已有），下次进房是新的世界。
- 结论偏向**客户端驱动流程 + 服务端只提供权威 Alive 状态**：服务端不需要新协议、不需要"复活计时"；`IsFinished` 维持"英雄全灭即结束"即可（单人副本死亡本来就该结束）。
- 预估 320 行（客户端流程与 UI ~260 / 服务端小改 ~20 / 测试 ~40）。
