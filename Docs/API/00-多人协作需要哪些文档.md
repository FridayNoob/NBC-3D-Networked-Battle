# 00 · 多人协作的游戏项目，需要哪些文档？

> 回答一个问题：**"一个几个人一起做的联网游戏，该有哪些文档？"**
> 每一类都给：**它防的是什么事故** / **本项目现状**。
> ⚠️ 判断标准不是"看起来专业"，而是 —— **没有它，会出什么事？**
> 答不出事故的文档，就是**没人会看**的文档。

---

## 一、先立一条总判据

> 📌 **文档按"它防止哪一类返工"分类，不按"它长什么样"分类。**

同一个项目里，一份"接口说明"可能同时是 A 类的产物和 B 类的输入 ——
分类的意义是让你知道**什么时候必须写、写完谁看**。

本项目的取舍很明确（也是这份文档的立场）：

| 值得写 | 不值得写 |
| --- | --- |
| **别人会照着做决定**的东西（契约、不变量、坑） | **能从源码一次读出来**的东西（成员列表、字段清单） |
| **机械检查覆盖不到**的东西（为什么这么选、踩过什么） | **机械检查已经覆盖的**东西（程序集依赖、表字段合法性） |
| **会改变行为**的约定 | **仪式性**的汇报 |

> ⚠️ 反例（本项目真实踩过）：`Docs\教学` 里手抄过一张"模块依赖图"，
> 而 asmdef 一改它就错了 —— 后来改成 **`Tools\Check-AsmdefBoundaries.ps1` 从真源读**。
> **能被机械检查的东西，不要用手写文档表达。**

## 二、十类文档（按"防什么事故"排）

| # | 类型 | 它防的事故 | 本项目现状 |
| --- | --- | --- | --- |
| 1 | **需求 / 范围** | 做完了才发现**不是要的**；边界没人定，越做越大 | ✅ `Docs\01-项目需求文档.md`（含 SRV-01~21、DB-01~10、DET-01~08 等**可验收编号**） |
| 2 | **架构 / 模块边界** | 两个人**同时改同一处**；依赖绕成环；"这个该放哪"每次都要吵 | ✅ `Docs\02-架构设计文档.md` + `Docs\图\03-程序集与模块依赖`（**从 asmdef 真源生成**） |

## 三、⚠️ 联网游戏**额外**需要哪些（单机项目没有的）

这是这类项目最容易漏的一类：**"两端必须一致"的东西**。

| 类型 | 为什么联网项目**必须**单独写 | 本项目现状 |
| --- | --- | --- |
| **双端共享层契约** | 同一份逻辑要在 **Unity（Mono/IL2CPP）** 和 **.NET 8** 上算出**同一个结果** —— 任何"看起来无所谓"的差别（浮点、字典顺序、随机数）都会造成**两端不同步且不报错** | ✅ `Shared\`（唯一源码）+ `Docs\教学\D1-双端共享层.md` + `D2-定点数学.md` |
| **权威归属表** | 谁说了算？（移动算状态、动作算事件）写不清就会做出"客户端自己扣血"这种**可作弊**的设计 | ✅ `Docs\教学\M3-B` + `Server\NBC.Server.Game\` |
| **Tick / 帧率 / 时序契约** | 30Hz 逻辑帧、快照 20Hz、输入保鲜 6 帧 —— 这些数字**必须两端同一个来源** | ✅ `Shared\Net\NetContract.cs`（`Version` / `TickRate` / `MaxRoomMembers` / `MaxFrameBytes`） |
| **协议版本与兼容策略** | 老客户端连新服务端怎么办？加字段要不要升版本？ | ✅ `NetContract.Version` + 握手校验（SRV-19） |
| **状态同步 vs 帧同步的边界** | 这个项目**混合**用（大世界状态同步 / PVP 帧同步）—— 边界不写清，两个人会做出互相矛盾的两套 | ✅ `Docs\01` 的 Q2 决策 + `Docs\20` |
| **确定性清单** | 帧同步要求"同输入 ⇒ 同结果"，哪些 API **禁止**用（`float`、`System.Random`、字典遍历序）要列清楚 | ✅ `Docs\教学\D2` + `Shared\Battle\BattleRandom`（自研 xorshift32） |
| **回滚 / 重连语义** | 掉线 60 秒回来会发生什么？ | 🔨 部分（`ReconnectGraceSeconds` 已配，语义待补文档） |
| **反作弊声明** | 哪些是服务端算的、客户端能改什么 | ✅ `Docs\教学\M3-B`（"客户端没有自己那份血条"） |

## 四、本项目**故意不写**的文档（以及为什么）

| 不写 | 为什么 |
| --- | --- |
| **全量成员 API 表**（每个类的方法清单） | 一定会过期，而且**过期后看起来还是对的** —— 比没有更危险。用 IDE 看源码，那是唯一真源。⇒ 本目录只写"源码里看不出来的"（不变量/时序/坑） |
| **手画的模块依赖图** | 已经有 `Tools\Check-AsmdefBoundaries.ps1` **从 asmdef 真源**生成并**机械校验**；手画的必然漂 |
| **测试用例清单** | `dotnet build` + 跑测试就有；抄一份进文档只会对不上 |
| **每日/每周进度汇报** | 对"防返工"没有贡献。项目的**变更记录**（`Docs\00` v1.9.x）已经是"决策 + 实测 + 踩坑"的最小充分形式 |

## 五、一份文档"该不该写"的三问（可以直接拿去用）

1. **没有它，会出什么事故？** —— 答不出 ⇒ 不写。
2. **这个信息能不能被机械检查代替？** —— 能 ⇒ **写检查**（脚本/测试），不写文档。
3. **它会不会过期？谁来保证它对？** —— 会过期又没人维护 ⇒ **只写"不容易过期的那部分"**
   （原理、坑、判据），或者**让它自动生成**。

> 📌 第 3 问是本项目最贵的一条教训：
> **一份过期但看起来权威的文档，比没有文档更害人。**
