## 三、这套文档怎么组织的（与程序集一一对应）

```
Client\Assets\_Project\
├── Shared\        → 01  （双端共享：Unity 与 .NET 8 编**同一份源码**）
├── Framework\     → 02
├── Framework.UI\  → 02
├── Framework.Net\ → 02
├── Framework.YooAsset\ → 02
├── Model\         → 02
└── Game\          → 03
Server\
├── NBC.Server.Core\ → 04
├── NBC.Server.Game\ → 04
└── NBC.Server.Data\ → 04
Protocol\          → 05
Configs\Design\    → 06
```

**为什么按程序集分而不是按功能分**：程序集的**引用方向是机械保证的**
（`asmdef` / `csproj` 写死了谁能看见谁），而"功能"是可以随便跨的。
按程序集分，读者能一眼看出**"我改的这个，谁会被影响"**。

## 四、⚠️ 文档会过期 —— 所以它必须能被"检查"，而不只是靠自觉

| 机制 | 位置 | 防的是什么 |
| --- | --- | --- |
| **文档链接检查** | `Tools\Check-DocLinks.ps1` | 文档里指向的**文件/路径**不存在（改名、搬目录之后最容易坏） |
| **脚本编码检查** | `Tools\Check-ScriptEncoding.ps1` | 中文 `.ps1` 少 BOM ⇒ PowerShell 5.1 按 GBK 读 ⇒ 乱码报错 |
| **asmdef 边界检查** | `Tools\Check-AsmdefBoundaries.ps1` | "文档里写的程序集依赖"与**真实 asmdef** 不符（人写的依赖图一定会漂） |
| **跨表检查** | `Tools\ConfigKit`（CFG0020~0023） | 配置表之间"单看都对、合起来玩不成" |
| **⚠️ 本文档的成员列表** | **没有机械检查** | ⇒ 所以本套文档**刻意不写全量成员表**（那种表一定会过期，而且过期后**看起来还是对的**） |

> 📌 判据：**"没有机械检查的文档内容，就不要写那些容易过期的部分。"**
> 结论落成上面那条约定 —— 这不只是"少写点"，是**故意的取舍**。
