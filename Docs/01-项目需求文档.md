## 1. 文档定位与阅读指南

### 1.1 本文档解决的问题

原始需求大纲是 13 条**技术点清单**，它回答的是"要用到什么技术"，但没有回答：

- 这些技术点如何组装成一个**完整的、能玩的游戏**？
- 各项需求的**优先级**如何？（3~4 个月做不完全部理想化方案）
- 每一项做到什么程度算**达标**？（避免无限打磨）
- 各项技术之间是否有**冲突**？（例如帧同步的确定性与 URP 渲染并无冲突，但与 `float` 物理、`Time.deltaTime` 驱动的逻辑严重冲突）

本文档的核心工作就是把这些技术点**收敛成一个自洽的、单个开发者能在 3~4 个月内完成并讲清楚的系统**。

### 1.2 阅读方法

| 角色 | 必读章节 |
| --- | --- |
| 本人（开发者） | 全部；开发时以 §18 里程碑作为排期表 |
| 面试官（技术评审） | §3 玩法、§4 架构图、§6 同步方案、§9 AI、§12 性能，其余按兴趣深挖 |
| 未来复用本项目的自己 | §5 技术栈、§14 模块化、§21 附录的目录规范 |

### 1.3 需求分层约定

本文档对每条需求标注**优先级**，含义是"在 3~4 个月周期内必须做到什么程度"：

| 标记 | 含义 | 处理原则 |
| --- | --- | --- |
| **P0** | 必须完成，缺失则项目不成立 | 排进里程碑，不可裁剪 |
| **P1** | 应该完成，是核心加分项 | 排进里程碑，工期紧张时可降级为"可演示的最简实现" |
| **P2** | 加分项，锦上添花 | 只在 P0/P1 全部达标后启动，可随时砍掉 |

以及**验收等级**：

| 等级 | 含义 |
| --- | --- |
| **A** | 有可运行代码 + 可在 Demo 中现场演示 |
| **B** | 有可运行代码 + 有自动化测试或数据对比结果 |
| **C** | 有完整设计文档 + 关键代码骨架（不强制可运行） |

> **原则**：宁可 8 个技术点全部达到 A 级，也不要 13 个技术点全是 C 级"糊上去"。
> 面试中"我实现了 X 并知道它的边界在哪"远胜于"我听说并用了 X"。

## 2. 项目总览

### 2.1 一句话定义

> 一个使用**自研轻量框架底座**、具备**服务端权威同步**与**确定性帧同步**双模式、支持**Lua + AB 包热更新**、包含**行为树敌人 AI 与多种寻路算法**、并用**MVC 分层 + ScriptableObject 数据驱动**组织起来的 3D 第三人称 ARPG 联网战斗技术演示项目。

### 2.2 项目目标（按重要性排序）

| # | 目标 | 说明 |
| --- | --- | --- |
| G1 | **证明网络同步能力** | 状态同步、帧同步、状态帧同步三种模型都有真实可跑的实现；有客户端预测与回滚 |
| G2 | **证明架构能力** | MVC 分层清晰、模块可插拔复用、设计模式用得恰当而非堆砌 |
| G3 | **证明工程能力** | 有构建工具、配置表工具、资源打包（YooAsset）、性能看板，不是"手搓一堆脚本" |
| G4 | **证明性能意识** | 有 DC/SetPass/GC Alloc 的可量化优化过程与前后对比数据 |
| G5 | **证明能落地** | 有一个真正能玩、能打包、能演示的完整闭环，而不是散落的示例场景 |

**明确非目标（Out of Scope）**：

- ❌ 不追求商业级美术品质、不追求完整剧情与关卡设计
- ❌ 不追求运营级服务端（无分布式、无跨服、无网关集群、无压测到万级并发）
- ❌ 不做移动端发布与真正的线上热更 CDN（本机模拟本地文件服务器）
- ❌ 不做账号体系的安全加固（密码明文/哈希即可，不做防 DDoS、防作弊）

### 2.3 成功判据（Definition of Done）

项目完成时必须能当场演示以下**一条连续流程**：

```
启动服务端 → 启动客户端A → 登录 → 进入大厅 → 创建房间
→ 启动客户端B（或另一台机器/第二个进程）→ 加入房间 → 双方准备
→ 进入战斗场景（异步加载 + AB 加载 + 进度条）
→ 双端同步移动/攻击/技能（带预测与插值，无明显卡顿）
→ 敌人 AI 使用行为树决策 + 寻路追击玩家
→ 战斗结算 → 回到大厅（数据落库 MySQL）
→ 现场修改一个 Lua 技能数值文件 → 重启客户端 → 无需重新打包即生效
→ 打开性能 HUD，展示 FPS / DrawCall / SetPass / GC Alloc
→ 切换同步模式为帧同步，重开一局，展示帧号推进与确定性校验
```

| 胜利条件 | PVE：清空波次；PVP：击杀数达标或限时结束 |

### 3.2 核心玩法循环

```
大厅（登录/选角色）
   ↓
房间（创建/加入/准备）  ← 服务端分配座位号
   ↓

   ↓

```

### 4.2 分层依赖规则（强约束）

| 规则 | 说明 | 违反后果 |
| --- | --- | --- |
| R1 | **Model 层不得引用 `UnityEngine`**（战斗核心逻辑、帧数据、数学库） | 破坏帧同步确定性，且无法被服务端复用 |
| R2 | Controller 不得直接操作 UI 控件，只能通过事件或 View 接口 | MVC 退化为"三个文件夹" |
| R3 | View 不得直接修改 Model 数据，必须经 Controller | 数据流混乱，联机状态回滚失效 |
| R4 | 框架底座不得引用 Game 业务命名空间 | 无法整包导出复用（§14） |
| R5 | 客户端与服务端共享的代码只能放在 `NBC.Shared` | 双端逻辑漂移，帧同步不同步 |

> 这 5 条规则会用**程序集定义（asmdef）+ 单元测试**机械校验，见 §14.3。

### 4.3 数据流：一次技能释放的完整链路

这是理解整个架构的主线，建议开发时反复对照：

```
[Client-A] 玩家按 1（技能）
  → InputController 采集输入，生成 InputCommand{ tick, skillId, dir }
  → ① 立即本地预测：调用 NBC.Shared 技能逻辑 → 播放动画/特效（表现层）
  → ② 上行发送 InputCommand 到服务端（带 clientTick 与冗余历史帧）

[Server] 收到 InputCommand
  → 放入该玩家对应的输入缓冲队列
  → 定长帧循环（30Hz）推进：取出本帧所有玩家的输入
  → 调用 NBC.Shared 同一份技能逻辑 → 权威结果（位移、伤害、Buff）
  → 生成快照（或帧数据）广播给房间内所有客户端
  → 若本次伤害导致击杀 → 写战斗事件、更新统计

[Client-A] 收到权威结果
  → 对比预测状态与实际状态 → 误差在阈值内则忽略（预测成功）
  → 误差超阈值 → 回滚到权威状态并重放未确认输入（Rollback & Replay）
  → 通知 View 层修正表现（平滑修正，不瞬移）

[Client-B] 收到他人状态
  → 存入快照缓冲（Jitter Buffer，保留约 200ms）
  → 按服务器时间戳对两个快照做插值（Interpolation）
  → 渲染到屏幕
```

#### 5.4.5 ⚠️ 已购插件的架构约束与应对（v1.2 定稿，必读）

本项目采用 **Behavior Designer 经典版**（行为树）与 **A\* Pathfinding Project Pro**（寻路）。
这是效率上的正确决策，但两个插件各带一条**硬约束**，必须在架构层面正面处理 —— 而不是绕过去。

**事实 1：Behavior Designer 的运行时建立在引擎对象之上，因此在纯 .NET 服务端进程里"能引用、不能运行"。**

> ✅ **2026-09-20 实测修正**：本节原先把这一条写成"**引用不了它**"，**实测证明这个表述过头了**。
> 完整实验见 §5.4.6；结论收窄为下面这个更准确、也更有支撑力的版本。

实测得到的分界（用 `Server\_unity-ref-probe` 在 .NET 8.0.21 上跑出）：

| 级别 | 被测内容 | 结果 |
| --- | --- | --- |
| 引用 `UnityEngine.CoreModule` 并编译 | — | ✅ **编译通过，0 错误** |
| `Vector3` / `Mathf` 的运算与静态方法 | 纯托管实现 | ✅ **正常运行**（`magnitude=5`、`Normalize`、`Mathf.Sqrt(16)=4`） |
| 反射获取 `GameObject` / `Component` / `MonoBehaviour` / `ScriptableObject` **类型** | 仅类型元数据 | ✅ 可见（`MonoBehaviour` 的基类链 `Behaviour → Component` 可读出） |
| `new GameObject()`、访问 `go.name` | 需要引擎创建对象 | ❌ `SecurityException: ECall methods must be packaged into a system module.` |
| `Time.deltaTime` | 需要引擎主循环 | ❌ 同上 `ECall` 异常 |

**因此准确的表述是**：

> Unity 的托管程序集**可以被纯 .NET 进程引用，甚至纯托管部分（`Vector3`/`Mathf`）能正常运行**；
> 但**凡是需要 Unity 原生引擎参与的操作 —— 创建/访问引擎对象、时间系统、`MonoBehaviour` 生命周期、资源加载等 —— 都会在运行时抛 `ECall` 异常**。
> 而 Behavior Designer 的运行时**正是建立在 `MonoBehaviour` / `GameObject` / 时间系统之上**（其 `Task` 基类继承自 `MonoBehaviour`），
> 因此它**无法在本项目的纯 .NET 8 服务端进程里工作**。§4.2 R5 要求双端共享 `NBC.Shared`，行为树因此进不了共享逻辑层。

**这条修正没有削弱架构裁决，反而让它更站得住**：原来只是"我说编译不过"，
现在是"**我实测过它编译能过、纯托管部分能跑，但一碰引擎对象就炸**" —— 这解释了**为什么**它不能进服务端，而不只是断言。

**事实 2：Opsive 官方网络方案是"行为树跑在权威端"—— 而这恰恰需要它能跑在服务端。**

[Behavior Designer 官方 Networking 文档](https://opsive.com/support/documentation/behavior-designer-pro/networking/) 建议：
行为树应在**服务端/权威端**运行，由权威端做所有决策，只把 transform/animation 结果同步给客户端，行为树本身不需要在网络间同步。
这条建议本身正确，但它要求**行为树能运行在服务端** —— 而事实 1 说明本项目的服务端进程做不到。
在**帧同步**下这条建议更无法照做：帧同步要求**每个客户端独立算出相同结果**，而不是"只有权威端跑 AI"。

**事实 3：A\* Pathfinding Project 是浮点 + 异步多线程寻路，不能进入帧同步逻辑层。**

Pro 版提供多线程寻路与[异步图更新](https://arongranberg.com/2012/05/more-threads-multithreaded-pathfinding/)，路径代价使用 `float`。
**关键认知：即使一个插件都不用，只要在帧同步逻辑层调用 Unity NavMesh，照样会破坏确定性（违反 DET-01）。**
所以这条约束是**帧同步本身的要求**，与是否使用插件无关 —— 唯一的解法是自己写一份**定点寻路**。

#### 5.4.6 D14 实测：纯 .NET 进程使用 Unity 程序集的失败边界（2026-09-20，已完成）

> **这一节是 §5.4.5「事实 1」的证据来源**，也是架构裁决 A1/A2/A3 的**事实基础**。
> 之所以要花时间做这个实验，是因为 §5.4.5 原来只有"文档推断"：**"文档说插件不能"远不如"我实测过它不能"**。

**① 为什么不直接引用 `BehaviorDesigner.Runtime.dll`**

`Docs\12-D14实验操作单.md` 最初的方案是"在服务端工程里临时引用 Behavior Designer 的运行时 dll，看编译报什么错"。
实际执行时改了做法，原因有两条：

| 原因 | 说明 |
| --- | --- |
| D8（导入 Behavior Designer）尚未完成 | 插件还没进工程，没有 dll 可引用 |
| **更重要的是：原来的方案不够根本** | 它测的是"**这个插件**能不能被引用"，结论会被插件版本影响；而真正决定架构的是"**Unity 程序集**能不能在纯 .NET 进程里用"。后者与插件无关，结论更硬、更持久 |

于是改成**向下挖一层**：不引用插件，**直接引用 Unity 自己的程序集**，测出"托管代码 / 引擎原生"的精确分界。
这个实验**在任何一台装了 Unity 的机器上都能重跑**，且结论不会因为换插件版本而失效。

**② 实验工程与运行方式**

| 项 | 内容 |
| --- | --- |
| 位置 | `Server\_unity-ref-probe\`（`probe.csproj` + `Program.cs`） |
| 目标框架 | `net8.0` |
| 引用 | `UnityEngine.CoreModule` + `UnityEngine.SharedInternalsModule`（绝对路径指向本机 Unity 安装目录，`<Private>true</Private>`） |
| 运行 | 工作目录切到 `Server\_unity-ref-probe` 后执行 `dotnet run` |
| 是否进解决方案 | **否**（不在 `NBC.sln` 里，`dotnet build` 不会连带编译它） |
| 是否进 Git | **否**（`Server\.gitignore` 忽略 `_unity-ref-probe/`；HintPath 是本机绝对路径，换机器即失效） |

> **⚠️ 一个关键的实验设计细节：`<Private>true</Private>` 不能省。**
> 如果只是 `<Reference>` 而不复制 dll 到输出目录，运行时只会得到
> `FileNotFoundException: 找不到 UnityEngine.CoreModule` —— 那只能证明"**我没把 dll 放过去**"，
> 证明不了任何关于 Unity 的事实。**要让实验有意义，必须先让运行时真的能加载到它。**

> **另一个细节：9 个探针级别都是独立方法，且用反射调用。**
> 因为失败可能发生在 JIT / 类型加载阶段 —— 直接顺序调用的话，一次异常会中断后面所有级别，
> 就分不清"是这一级失败"还是"因为上一级失败而没能跑到"。反射调用把每一级隔离开，
> 异常被包在 `TargetInvocationException` 里，可以逐个定位。

**③ 阶段 1 结果：9 级探针，3 级失败**

| L2 | 反射获取 `GameObject` **类型** | ✅ 成功 |
| **L3** | **`new GameObject("probe")`** | ❌ 失败 |
| **L4** | **`go.name`（访问引擎对象属性）** | ❌ 失败 |

**④ 怎么读这个结果（这才是实验的价值所在）**

结论**不是**"Unity 程序集在 .NET 里用不了"（那太粗），而是**一条精确的分界线**：

| 分层 | 能否在纯 .NET 进程里工作 | 证据 |
| --- | --- | --- |
| **纯托管数学**（`Vector3` / `Quaternion` / `Mathf` / `Rect`…） | ✅ **能，且结果完全正确** | L1：`magnitude=5`、`Normalize=(0.6,0.8,0)`、`Mathf.Sqrt(16)=4` |
| **类型元数据**（反射拿 `Type`、看基类链） | ✅ **能** | L2/L5/L6/L7：`MonoBehaviour` 的基类链 `Behaviour → Component` 能完整读出 |
| **引擎对象与原生调用**（创建/访问对象、时间系统、生命周期、资源加载） | ❌ **不能** | L3/L4/L8：`SecurityException` |

**`ECall` 是什么**：Unity 的托管程序集里，凡是要落到 C++ 引擎里的方法都标了
`[MethodImpl(MethodImplOptions.InternalCall)]`（简称 **ECall**，即"由运行时内部实现的方法"）。
在 Unity 自己的运行时里，这些调用会被转到原生引擎；而在**独立 .NET 进程**里，
CLR 找不到对应的内部实现，于是在**调用那一刻**（不是加载时）抛
`System.Security.SecurityException: ECall methods must be packaged into a system module.`

> **这条错误信息的价值**：它是**运行时**错误而不是**编译期**错误。
> 也就是说 —— **引用 Unity 程序集能编译通过，问题在运行时才炸，且只在真正调用引擎时炸。**
> 这正好解释了为什么"编译成功"不能用来证明"服务端能跑行为树"（见 §5.4.5 事实 1 的修正）。

**⑤ 阶段 2：引用一个 Unity 模块会拖进一串模块**

用 `System.Reflection.Metadata` 读取 Unity 模块的 `AssemblyRef` 表并求传递闭包（Unity 安装目录下共 **87 个** Unity 模块 dll，合计 19.1 MB）：

| 起点模块 | Unity 侧传递闭包 | 数量 |
| --- | --- | --- |
| `UnityEngine.CoreModule` | CoreModule、SharedInternalsModule | **2** |
| `UnityEngine.IMGUIModule` | IMGUIModule、SharedInternalsModule、CoreModule、InputLegacyModule、TextRenderingModule、TextCoreTextEngineModule、TextCoreFontEngineModule | **7** |
| `UnityEngine.AIModule` | AIModule、SharedInternalsModule、CoreModule | **3** |

`IMGUIModule` 的依赖边（实测）：

```text
UnityEngine.IMGUIModule -> UnityEngine.CoreModule
UnityEngine.IMGUIModule -> UnityEngine.SharedInternalsModule
UnityEngine.IMGUIModule -> UnityEngine.InputLegacyModule
UnityEngine.IMGUIModule -> UnityEngine.TextRenderingModule
UnityEngine.IMGUIModule -> UnityEngine.TextCoreTextEngineModule
UnityEngine.TextCoreTextEngineModule -> UnityEngine.TextCoreFontEngineModule
UnityEngine.TextCoreTextEngineModule -> UnityEngine.TextRenderingModule
UnityEngine.TextCoreFontEngineModule -> UnityEngine.TextRenderingModule
UnityEngine.InputLegacyModule -> UnityEngine.CoreModule
UnityEngine.TextRenderingModule -> UnityEngine.CoreModule
（其余为各模块对 CoreModule / SharedInternalsModule 的公共依赖，已省略）
```

**工程含义**：在服务端引用任何一个 Unity 模块，`<Reference>` 都要把整个闭包补全，否则会得到
`CS0012`（"类型在未引用的程序集中定义"）。**这不是"多加一行 HintPath"的小事，而是"要拖进多少引擎代码"的成本** ——
也再次说明：**服务端不应该有任何 Unity 依赖**，这正是本项目让 `NBC.Shared` 保持 `netstandard2.1`、且 `NBC.Model` 设 `noEngineReferences: true` 的原因。

**Q：为什么 protobuf-net 而不是 Google.Protobuf？**

| 维度 | protobuf-net | Google.Protobuf |
| --- | --- | --- |
| 使用方式 | C# 特性标注（`[ProtoContract]`），无双端代码生成步骤 | 需 `.proto` + `protoc` 生成，双端各生成一次 |
| 与 Unity 集成 | 需注意 IL2CPP 下的 AOT 泛型问题（本项目用**预生成序列化器**规避） | 官方生成代码，AOT 友好 |
| 性能 | 相近，protobuf-net 略占优（可预编译） | 稳定可靠 |
| 维护状态 | 活跃 | 官方，最活跃 |

**决策**：选 protobuf-net，理由是**双端共享同一份协议类**（配合 §4.2 R5），零代码生成步骤，减少协议漂移风险。
风险点是 IL2CPP AOT，缓解措施是开启 `protobuf-net` 的预生成（`precompiled serializer`）并纳入打包流程强制检查。

**Q：为什么不用 KCP / 不用现成网络库（如 LiteNetLib、Mirror、ET）？**

- 需求大纲第 11 条要求使用自研框架；第 1 条"尽量使用成熟方案"与第 11 条存在张力，
  **本项目的裁决原则是：框架底座用自研（体现能力），底层库与第三方插件用成熟方案（不重复造轮子）**。
- TCP 足够满足本 Demo 的 2~4 人、本机/局域网环境；KCP（可靠 UDP）列为 **P2**，作为"我知道 TCP 队头阻塞问题"的加分回答。
- 明确**不使用** Mirror / Photon / ET / GameFramework 这类**完整游戏/网络框架**（会直接违背需求 11 的用意）。
- 明确**使用**已购的功能型插件：**Behavior Designer 经典版**（行为树）、**A\* Pathfinding Project Pro**（寻路）、DOTween、Cinemachine 等。
  选择原则：**功能型插件 = 成熟方案（需求 1）；完整游戏框架 = 会架空自研框架（违背需求 11）**。

**Q3 最终确认（v1.2）**：行为树用 **Behavior Designer 经典版**，寻路用 **A\* Pathfinding Project Pro**，**两者都投入使用**。
但这两个插件各带一条**必须正面处理的架构约束**（前者依赖 Unity 运行时、后者是浮点异步寻路），
本项目用 **A1/A2/A3 三条架构裁决**隔离 —— 完整分析与裁决见 **§5.4.5** 与 **§9.6**。
框架层（定点数学、帧同步、预测回滚、自研热更管理）**仍然自研**，这部分才是本项目的技术核心。

> **评审过程记录**：Q3 在 v1.0→v1.2 之间经历了"自研 → 用插件 → 自研 → 用插件"的反复。
> 这个反复是有价值的：**它逼出了一个明确的结论 —— 插件可以加速表现层与工具链，但"确定性"与"服务端权威"这两件事
> 插件给不了，必须自研。** 因此本项目的技术含量并不因使用插件而降低，只是把它集中到了更硬的地方。

## 6. 联网与同步系统（需求 2）

> **本章是全项目技术含量最高、也是最需要提前定死的一章。**
> 需求 2 要求同时体现"状态同步 / 帧同步 / 状态帧同步"三种技术 + 预测算法。
> 本项目的解决方案是 **一套传输层 + 三个可插拔的同步策略（策略模式）**，运行时在房间配置中切换。
> 这样三套方案共享网络层、协议层、战斗逻辑层，工作量约为"做三套 Demo"的 40%，且架构上更能体现设计能力。

### 6.1 三种同步模式的定义与取舍（先对齐认知）

| 维度 | 状态同步（State Sync） | 帧同步（Lockstep） | 状态帧同步（State-Frame Hybrid） |
| --- | --- | --- | --- |
| 权威方 | 服务端 | 客户端（逻辑上） | 服务端（逻辑上） |
| 传输内容 | 世界快照（位置/血量/状态） | 玩家输入指令 | **输入 + 关键状态校验/修正帧** |
| 带宽 | 高（与实体数量成正比） | 极低（只传输入） | 中 |
| 逻辑耗时 | 服务端一份 | **N 份**（所有客户端 + 服务端校验） | 服务端 + 客户端各自一份 |
| 确定性要求 | 无 | **极严**（浮点/容器顺序/随机数都要控） | 中（允许有校正） |
| 表现平滑难度 | 中（插值） | 低（逻辑帧与表现帧分离） | 中 |
| 抗作弊 | 强 | 弱（需回放校验） | 强 |
| 断线重连 | 简单（发全量快照） | 困难（需重放全部历史帧或存快照） | 中（发快照 + 追帧） |
| 不适合的场景 | 大量实体（如 RTS 千单位） | 含物理/浮点的强实时动作 | — |

**本项目的定位**：三种都实现，但**用途不同、优先级不同**。

| 模式 | 用途 | 优先级 | 说明 |
| --- | --- | --- | --- |
| 状态同步 | **PVE 清怪 / PVP 主模式**：新手引导、AI 战斗、演示平滑手感 | **P0** | 最稳、最容易做出"能玩"的效果 |
| 帧同步 | **PVP 对战模式**：展示确定性与输入同步 | **P0** | 面试硬指标，必须有真实可跑的实现 |
| 状态帧同步 | **PVP 对战模式的可选开关**：帧同步 + 服务端周期性全量校验 | **P1** | 在帧同步基础上加"每 30 帧一个权威关键帧"，用于断线重连与漂移校正 |
| 客户端预测 + 回滚 | 状态同步下的本地玩家移动/技能、帧同步下的输入预表现 | **P0** | 见 §6.6 |

### 6.2 网络传输层需求（双模式共用）

| 编号 | 需求 | 优先级 | 验收 |
| --- | --- | --- | --- |
| NET-01 | 基于 TCP 长连接，自定义**长度前缀**协议（4 字节大端长度 + 消息体） | P0 | A：能承受分片/粘包测试（发送 1KB / 64KB / 连续 1000 条小包均正确解析） |
| NET-02 | 消息分发采用**消息号（MsgId）+ 处理器注册**（不用反射，用显式注册表，避免 IL2CPP AOT 问题） | P0 | A：新增协议只需注册一行 |
| NET-03 | 心跳机制：客户端每 2s 发心跳，服务端 10s 未收到判定超时 | P0 | A：抓包可见心跳；拔网线 10s 后服务端清理会话 |
| NET-04 | **断线重连**：会话保留 60s，重连后恢复房间座位与战斗状态 | P1 | A：杀进程重启客户端后自动回到原房间 |
| NET-05 | 接收缓冲区**环形缓冲 + 零拷贝**解析，避免每包一次 `byte[]` 分配 | P1 | B：性能 HUD 显示网络层 GC Alloc 为 0 B/frame |
| NET-06 | 消息压缩：大于 512B 的消息启用 LZ4/Deflate，并带 1 字节压缩标记 | P2 | B：带宽统计对比数据 |
| NET-07 | **网络模拟器**（Network Simulator）：可注入人工延迟 0~300ms、抖动、丢包率 | **P0** | A：能现场演示"高延迟下预测与插值的效果"——**这是面试演示的关键道具** |
| NET-08 | 网络统计面板：上下行流量、RTT、丢包/重传统计、服务器 Tick 耗时 | P1 | A：HUD 中可见 |

> **NET-07 是强烈建议优先做的一项**。没有它，你无法向面试官证明预测算法真的在工作。
> 有了它，"我把延迟调到 200ms，你看角色依然跟手，因为本地预测+回滚；其他玩家有插值所以不抽搐"—— 这句话就是一次完整的技术答辩。

### 6.3 模式一：状态同步（P0）

#### 6.3.1 运行机制

```
服务端 Tick 率：30 Hz（固定，与帧同步统一，便于共用代码）
客户端渲染帧率：60~120 FPS（不固定）
快照下发率：20 Hz（每 1.5 个 Tick 发一次，可配）
```

**服务端权威内容（快照字段）**：

| 字段组 | 字段 | 说明 |
| --- | --- | --- |
| 头部 | `serverTick`、`serverTimeMs`、`snapshotSeq` | 客户端据此做时间轴对齐 |
| 实体（Entity） | `netId`、`entityType`、`position(x,y,z)`、`rotation(y)`、`velocity` | 位置用**量化压缩**（见 6.3.3） |
| 属性（Attr） | `hp`、`maxHp`、`mp`、`moveSpeed`、`stateEnum` | 变化时才发（脏标记） |
| 技能/动作 | `actionId`、`actionStartTick`、`actionPhase` | 用于客户端还原动作时间轴 |
| 事件（Events） | `damage`、`heal`、`death`、`buffAdd/Remove`、`hit` | 事件一次性下发，不放进快照循环 |

**下行策略**：
- **全量快照**：进入战斗、断线重连、首次同步时下发（`snapshotType = FULL`）
- **增量快照**：常规下发（`snapshotType = DELTA`），只含与上次快照的差异实体
- 关键点：**对每个客户端单独计算"可见集"**（简化版视野裁剪：`距离 > 50m` 的实体不下发），并在客户端做实体创建/销毁的 `enterView`/`leaveView` 管理

#### 6.3.2 客户端处理流水线

```
收包 → 快照缓冲（按 serverTick 排序，Jitter Buffer 保留 200ms）
     → 渲染时刻确定：renderTick = 最新收到的serverTick - 插值延迟(100ms)
     → 对相邻两个快照做插值（位置用 Lerp，朝向用 Slerp/角度插值）
     → 本地玩家例外：走预测+校正分支（§6.6）
     → 写入 Model 层的"表现状态" → View 层读取并驱动动画/位置
```

**插值实现要求**：
- 位置使用 **Hermite 插值**（利用快照里的 velocity 提高平滑度，减少"拐弯切角"感）
- 渲染时刻落后服务器最新快照约 **100ms**（2 个快照间隔），这是"平滑 vs 延迟"的权衡点，必须在文档中记录为可调参数
- 极端情况（快照丢失/迟到）要有降级：快照不足时退化为**外推（Extrapolation）**，最多外推 200ms，之后冻结并显示"网络不稳定"

#### 6.3.3 快照压缩（性能加分项）

| 手段 | 效果 | 说明 |
| --- | --- | --- |
| 位置量化 | float(4B) → int16(2B) | 以 0.01m 精度量化，范围 ±327m，足够 |
| 朝向量化 | float → int8/uint16 | 360°/256 ≈ 1.4° 精度 |
| 血量量化 | int32 → uint16 | — |
| 实体索引 | 用**房间内短 ID**（1~2 字节）代替全局 netId | 房间内实体数 < 255 |
| 脏标记 | 未变化字段不发 | 静止实体开销趋近于 0 |

> 目标：**单实体单快照 ≤ 16 字节**，4 人 + 20 怪、20Hz 下下行带宽 ≈ **7.7 KB/s**。
> 这个数字要能在面试现场算出来并给出实测值。

### 6.4 模式二：帧同步（P0）

#### 6.4.1 确定性——帧同步的生死线

帧同步要求**所有客户端对同一帧输入算出完全相同的结果**。为了做到这一点，本项目必须遵守以下**确定性约束清单**（违反任意一条都会导致"不同步"，且极难排查）：

| 编号 | 约束 | 正确做法 | 错误做法 |
| --- | --- | --- | --- |
| DET-01 | **禁止 `float`/`double` 参与逻辑计算** | 使用自研 `Fix64`（Q32.32，基于 `long`） | 直接用 `Vector3`（内部是 float） |
| DET-02 | **禁止逻辑层引用 `UnityEngine`** | 逻辑层用自研 `FixVector3`、`FixMath` | 用 `Mathf`、`Physics.Raycast` |
| DET-03 | **禁止 `Time.deltaTime` 驱动逻辑** | 逻辑帧固定步长（1/30s 的 Fix64 常量） | `transform.position += v * Time.deltaTime` |
| DET-04 | **随机数必须用可复现的确定性随机** | 自研 `DeterministicRandom`（线性同余/PCG，种子确定） | `UnityEngine.Random`、`System.Random`（无固定算法保证） |
| DET-05 | **容器遍历顺序必须确定** | 用**数组/列表 + 显式排序**，实体按 `netId` 升序处理 | `Dictionary`/`HashSet` 遍历（顺序不保证） |
| DET-06 | **禁止逻辑层依赖帧率、平台、时间** | 逻辑只依赖 `tick` 与输入 | 依赖 `DateTime.Now`、`Application.platform` |
| DET-07 | **三角函数/开方等必须用定点实现** | `FixMath.Sqrt/Sin/Cos/Atan2` 查表或定点迭代 | `Mathf.Sqrt`（不同平台可能不同） |
| DET-08 | **服务端与客户端必须是同一份逻辑** | `NBC.Shared` 被双端引用，同版本 | 双端各写一遍逻辑 |
| DET-09 | **逻辑层不得开多线程/协程** | 单线程顺序执行一帧 | `Task`/`async` 修改战斗状态 |

> **DET-01 与 DET-07 是本项目最大的技术挑战**，请看 §19 风险 R1。
> 好在**本 Demo 的物理很简单**（角色是圆柱体/胶囊体，移动是"位置 + 速度积分 + 简单圆形/胶囊碰撞检测"），
> 不需要完整物理引擎，因此定点实现的量是**可控的**：只需要 `Fix64`、`FixVector3`、`FixMath.Sqrt/Atan2/Sin/Cos`、圆-圆与圆-矩形碰撞。

**确定性验证机制（必须有）**：

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| DET-V1 | 每帧计算一个 **状态哈希**（`hash = FNV1a(所有实体位置/血量/状态)`） | B：单元测试 |
| DET-V2 | 客户端每 30 帧上报自己的哈希，服务端比对并记录 | A：控制台能看到"Frame 300 hash match" |
| DET-V3 | 出现哈希不一致时，日志输出**首个分歧帧**与分歧实体，并保存该帧前的输入序列用于复现 | A：能人为注入一个分歧（如改一个技能数值）并看到日志定位到帧 |
| DET-V4 | **回放系统**：记录整局所有输入帧，可用同一份逻辑重放并比对哈希 | P1，B：录制一个 `.replay` 文件并能重放一致 |

> DET-V3 + DET-V4 是"我做过帧同步"和"我看过帧同步教程"的分水岭。**强烈建议做**。

#### 6.4.2 帧同步运行机制

```
逻辑帧率：30 Hz（固定步长）
帧推进：服务端收集所有人本帧输入 → 打包为 FrameData{tick, [playerId, inputCmd...]}
       → 广播给房间所有人（含自己）
客户端：收到 FrameData 后放入帧队列 → 按 tick 顺序逐帧执行逻辑
       队列为空时**等待**（不自我推进）→ 这就是"锁步"
      队列积压过多（> 10 帧）时加速追帧（一渲染帧跑多逻辑帧）
```

| 编号 | 需求 | 优先级 | 验收 |
| --- | --- | --- | --- |
| LOCK-01 | 服务端定长 30Hz 帧循环，收集输入并广播 `FrameData` | P0 | A |
| LOCK-02 | 客户端帧队列 + 锁步等待 + 追帧加速 | P0 | A：能人为制造卡顿并看到追帧 |
| LOCK-03 | 输入**冗余发送**（每次发送最近 3 帧的输入，服务端去重），抵抗丢包 | P0 | A：丢包 10% 下仍能开局 |
| LOCK-04 | 玩家输入缺失时的填充策略：**预测输入**（沿用上一帧输入）或**空输入**，服务端决定并广播 | P0 | A |
| LOCK-05 | 战斗开始前**服务器等待所有客户端加载完成**（加载进度上报 + 就绪确认），避免开局不同步 | P0 | A |
| LOCK-06 | 逻辑帧与表现帧分离：表现层用插值渲染 `prevState → curState` 之间的位置 | P0 | A：30 逻辑帧下画面依然流畅 |
| LOCK-07 | 帧数据压缩：输入指令位压缩（按键用 bitmask、方向量化到 uint16 角度） | P1 | B：单帧数据 ≤ 6 B/玩家 |
| LOCK-08 | **战斗回放**（`.replay` 文件：随机种子 + 全部帧输入 + 结果哈希） | P1 | A：可从文件重放一局 |
| LOCK-09 | **断线重连（帧同步模式）**：重连时下发**最新全量快照 + 当前 tick**，客户端直接"跳"到该状态继续 | P1 | A |
| LOCK-10 | 加速/倍速与暂停（单机模式下演示确定性用） | P2 | C |

> LOCK-06"逻辑帧与表现帧分离"是个非常值得讲的点：
> **逻辑 30 帧，渲染 120 帧，玩家看到的依然丝滑 —— 因为表现层在逻辑状态之间做插值。**
> 实现方式：逻辑层保留 `prevPosition` 与 `curPosition`，表现层按 `alpha` 插值，`alpha` 由累积的未消费时间决定。

### 6.5 模式三：状态帧同步（P1）

**定义（本项目的实现口径）**：以帧同步为主，服务端**周期性插入权威状态帧**用于校正与重连。

| 编号 | 需求 | 优先级 | 验收 |
| --- | --- | --- | --- |
| HYB-01 | 服务端每 **30 帧（1 秒）** 下发一个 `StateFrame{tick, 全量实体状态, 状态哈希}` | P1 | A |
| HYB-02 | 客户端收到 `StateFrame` 后与本地计算状态比对，哈希一致则不动作（只在日志记录） | P1 | A |
| HYB-03 | 哈希不一致时：客户端**回滚到该状态帧并重放后续输入**（软校正），日志报警 | P1 | A：人为制造漂移可见校正过程 |
| HYB-04 | 新玩家中途加入 / 断线重连：直接用最新 `StateFrame` 作为起点，无需重放全部历史 | P1 | A |
| HYB-05 | 带宽对比报表：状态同步 vs 帧同步 vs 状态帧同步（同样 4 人对局 5 分钟） | P1 | B：一张对比表 + 图表 |

> **HYB-05 这张表是本项目最有说服力的交付物之一**。面试时直接展示："同一局，状态同步下行 1.8MB，帧同步 42KB，状态帧同步 78KB —— 所以我在这里选了帧同步+周期校正。"
> 请在开发 M4 阶段就把统计数据埋点做好，不要最后补。

### 6.6 客户端预测与回滚（P0，需求 2 明确要求"预测算法"）

本项目要实现的预测相关算法，按深度递进：

| 编号 | 算法 | 优先级 | 说明 | 验收 |
| --- | --- | --- | --- | --- |
| PRED-01 | **输入缓冲（Input Buffer）+ 序号确认** | P0 | 本地输入带 `seq`，服务端在快照中回带 `lastProcessedInputSeq`，客户端据此丢弃已确认的预测 | A |
| PRED-02 | **本地玩家移动预测** | P0 | 按下方向键立即本地模拟移动，不等服务端 | A：200ms 延迟下操作依然跟手 |
| PRED-03 | **服务端和解（Reconciliation）与状态回滚重放** | P0 | 收到权威状态 → 比对预测 → 超阈值则回滚到权威状态并重放 `lastProcessedSeq` 之后的所有输入 | A：人为调高误差可看到校正 |
| PRED-04 | **平滑误差修正（Error Smoothing）** | P0 | 校正时不瞬移：把位置误差分摊到后续 N 帧内插值消化，或按误差大小决定"软修正/硬回滚" | A：视觉上无跳变 |
| PRED-05 | **技能/动作预测（含失败回滚）** | P1 | 立刻播放技能前摇，若服务端拒绝（CD 中/蓝不够）则回滚并播放"打断"表现 | A |
| PRED-06 | **命中判定的客户端预测 + 服务端裁决** | P1 | 客户端本地预判命中并播特效；服务端权威判定；不一致时回滚伤害数字 | A |
| PRED-07 | **其他实体插值（Interpolation）而非预测** | P0 | 他人只做插值不做预测，避免"预测错了更难受" | A |

## 7. 客户端框架底座与 MVC 分层（需求 7、11）

### 7.1 框架来源与改造策略

需求 11 指定使用唐老师框架笔记中的那套框架。该框架在笔记中包含 9 个模块：

| 笔记中的模块 | 本项目处理 | 改造要点 |
| --- | --- | --- |
| `BaseManager<T>`（纯 C# 单例） | **保留并加固** | 笔记作者已指出"子类可通过构造函数创建新对象"的问题 |
| `SingletonMono<T>` / `SingletonAutoMono<T>` | **保留并加固** | 统一改用 `FindFirstObjectByType`（笔记中已给出改进版）；加线程安全与场景重载处理 |
| 缓存池 `PoolMgr` | **保留 + 重写核心** | 笔记版用 `List.RemoveAt(0)` 是 O(n)；且 `Resources` 依赖需替换 |
| 事件中心 `EventCenter` | **保留 + 加类型安全** | 字符串 key 易写错，需加常量类与调试工具 |
| 公共 Mono `MonoMgr` | **保留** | 增加 `LateUpdate`/`FixedUpdate`/定时器/延迟调用 |
| 场景切换 `ScenesMgr` | **保留 + 扩展** | 增加 AB 场景加载、加载进度事件、加载遮罩 |
| 资源加载 `ResMgr` | **⚠️ 重写为 `AssetMgr`** | 原版基于 `Resources`，**必须替换为 AssetBundle**（需求 5 的 AB 包要求） |
| 输入控制 `InputMgr` | **保留 + 重构** | 原版硬编码 WASD，需扩展为按键映射表 + 输入命令生成（服务同步用） |
| 音效 `MusicMgr` | **保留** | 增加音效池、3D 音效、音量分组 |
| UI 模块 `UIManager` + `BasePanel` | **保留 + 强化** | 加 UI 生命周期、异步加载、栈式管理、MVC 绑定 |

> **改造记录要求**：对每个模块的改造都要在 `Docs/06-框架改造记录.md` 中记录"原版问题 → 改造方案 → 为什么"。
> 这是面试时的加分材料：**能指出自己框架的缺陷并说明改进了什么，远胜于"我用了这个框架"。**

#### 7.1.1 框架底座的已知缺陷与必须修复项（P0）

| 编号 | 问题（来自笔记代码） | 影响 | 修复方案 |
| --- | --- | --- | --- |
| FW-01 | `BaseManager<T>` 无 `private` 构造保护，子类可被 `new` 出多个实例 | 单例失效、状态不一致 | `protected` 构造 + 静态 `GetInstance`，并在基类加断言防重入 |
| FW-02 | `SingletonMono<T>` 的 `GetInstance` 直接返回可能为 `null` 的 `instance` | 空引用崩溃 | 采用笔记中的改进版 `FindFirstObjectByType` + 自动创建 + `DontDestroyOnLoad` |
| FW-03 | `SingletonAutoMono<T>` 未做**重复创建保护**（多线程/多次调用可能建多个） | 出现多个实例 | 加锁 + 二次检查 + `FindFirstObjectByType` 兜底 |
| FW-04 | `PoolMgr.GetObj` 用 `List.RemoveAt(0)` | 池子大时 O(n)，性能隐患 | 改为 `Stack<T>`/索引尾取，O(1) |
| FW-05 | 缓存池无上限、无自动回收 | 内存持续增长 | 加最大容量、按时间清理、池统计面板 |
| FW-06 | `EventCenter` 用 `string` 作 key | 拼写错误编译期无法发现 | 定义 `EventId` 静态常量类 + 编辑器校验 + 未注册事件警告 |
| FW-07 | `EventCenter` 的 `EventInfo<T>` 若同一 key 被不同类型监听会强转异常 | 运行时崩溃 | 存入时校验类型一致性并抛明确异常 |
| FW-08 | `ResMgr` 基于 `Resources`，无法热更、无法按需卸载 | **直接违反需求 5** | 完整替换为 `AssetMgr`（AB 加载 + 引用计数 + 依赖管理） |
| FW-09 | `MusicMgr.Update` 用 `GameObject.Destroy` 销毁对象 | 与缓存池冲突 | 改为回池 |
| FW-10 | `UIManager` 用 `Canvas.Find("Bot")` 硬编码路径 | 改名即崩 | 改为序列化引用/配置表 |
| FW-11 | `ScenesMgr` 用 `yield return ao.progress` 作为等待 | 逻辑错误（progress 是 float，语义不对） | 改为 `yield return null` |
| FW-12 | 框架职责与业务耦合风险（笔记框架是给单机小游戏用的） | 无法复用 | 强制 §4.2 R4：框架层不得引用业务命名空间 |

### 7.2 MVC 分层架构（需求 7）

#### 7.2.1 分层定义

| 层 | 目录 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| **Model** | `Game/Model/` | 数据 + 业务规则 + 状态计算。包含：战斗实体数据、属性、Buff、背包（若做）、配置读取、帧数据 | 禁止引用 `UnityEngine`（除 SO 配置类）、禁止持有 View 引用、禁止操作 UI |
| **View** | `Game/View/` | 纯表现：UI 面板、场景实体显示、动画、特效、相机、飘字 | 禁止直接改 Model 数据、禁止发网络包、禁止含业务判断 |
| **Controller** | `Game/Controller/` | 接收输入/网络消息 → 调用 Model → 通知 View。是唯一的"调度中心" | 禁止直接引用 UI 控件类型、禁止写业务算法 |
| **Service/Manager** | `Game/Service/` | 跨模块服务：网络服务、热更服务、配置服务、战斗服务 | — |

#### 7.2.2 MVC 数据绑定方式

本项目**不使用**响应式框架（不引 UniRx），改用显式的事件通知 + 手动刷新，以便面试时能清楚讲出数据流：

```
[Model 变更] → Model 抛出变更事件（EventCenter）
            → Controller 监听到变更 → 调用 View.Refresh(data)
            → View 只做显示
```

**强制要求**：
- 每个 `Panel` 都必须是 `BasePanel` 子类，且**不得直接访问 Model**（只能通过对应 Controller）
- 每个 `Panel` 的 `ShowMe/HideMe` 必须成对处理事件注册/注销（框架的 `BasePanel` 已提供钩子，需补全注销）
- 提供**代码审查清单**（§7.3）用于自检

| `skillId` | int | 唯一 ID |
| `name` / `desc` / `icon` | string/Sprite | 显示 |
| `castType` | enum | 瞬发 / 蓄力 / 引导 |
| `castTimeFrames` | int | 前摇逻辑帧数 |
| `recoverFrames` | int | 后摇逻辑帧数 |
| `cancelFrame` | int | 从第几帧起可取消 |
| `cooldownMs` | int | 冷却 |
| `costMp` | int | 消耗 |
| `range` | Fix64 | 施法距离 |
| `hitShape` | enum | 圆形 / 扇形 / 矩形 / 胶囊 |
| `hitParam1/2` | Fix64 | 形状参数（半径/角度/长宽） |
| `hitFrame` | int | 第几帧结算判定 |
| `damageRatio` | Fix64 | 伤害倍率 |
| `damageType` | enum | 物理 / 魔法 / 真实 |

> `logicScript` 字段是**技能逻辑热更**的入口：普通技能走 C# 数据驱动，特殊技能走 Lua。

#### 8.2.1 技能逻辑的两条路径（Q6 确认后的强制规则）

| 路径 | 适用 | 判定条件 | 帧同步可用 |
| --- | --- | --- | --- |
| **C# 数据驱动**（主路径） | **绝大多数技能**：伤害、位移、Buff、击退、范围判定 —— 全部由 `Skill` 配置表字段 + 通用 C# 逻辑实现 | `logicScript` 为空 | ✅ 可用（定点数学保证确定性） |
| **Lua 脚本**（特殊技能） | **特殊机制技能**：召唤物、弹射/连锁、条件分支复杂的一次性逻辑、活动期间临时技能 | `logicScript` 非空 | ⚠️ 仅单机 / 状态同步模式；**帧同步模式下强制回退到 C# 路径**（技能需提供 C# 兜底实现，或该技能在帧同步模式禁用） |

**Lua 技能的确定性约束（若要在帧同步模式启用）**：

| 约束 | 说明 |
| --- | --- |
| 禁止 `math.random` | 必须使用 C# 侧传入的 `DeterministicRandom` 实例 |
| 禁止 `os.time` / `os.clock` | 必须使用传入的**逻辑帧号** |
| 禁止依赖浮点累积 | 伤害/位置计算使用 C# 侧提供的定点 API（如 `FixMath.Mul`），不直接在 Lua 里做浮点累加 |
| 禁止遍历无序表 | Lua 的 `pairs` 遍历顺序不确定，必须用 `ipairs` 或显式排序 |
| 禁止 I/O 与协程挂起 | 逻辑帧内必须同步执行完毕 |

> **设计意图**：这条规则让"热更演示"与"帧同步确定性"两个需求同时成立且互不拖累 ——
> 演示热更时用单机/状态同步模式改 Lua 数值（立刻生效，效果好）；
> 演示帧同步时走 C# 路径（确定性有保障）。**面试时这是一个很好的"我知道边界在哪"的回答。**

#### 9.2.4 三种敌人的行为树设计（初版）

> 使用 Behavior Designer 编辑器绘制，下列结构可直接对照实现。
> 三棵树共用大量子树（死亡/受击/追击），正好使用插件的 **Subtrees** 能力。

**① 近战追击型（MeleeChaser）**

```
Selector（Root）
├─ Sequence [死亡检查]：IsDead? → PlayDeath → Wait(∞)
├─ Sequence [受击]：IsHit? → PlayHit → Wait(hitFrames)
├─ Sequence [攻击]：InAttackRange? AND AttackReady?
│    → FaceTarget → PlayAttackAnim → Wait(前摇) → DealDamage → Wait(后摇) → SetCooldown
├─ Sequence [追击]：HasTarget?
│    → MoveToTarget(寻路) → Running...（超时 3s 失败）
└─ Action [巡逻]：Patrol（路点循环）
```

**② 远程投射型（RangedCaster）**

```
Selector（Root）
├─ Sequence [死亡/受击]：（同上）
├─ Sequence [拉开距离]：Distance < keepDistance?
│    → MoveAwayFromTarget（流场反向） → Running
├─ Sequence [施法]：InCastRange? AND HasLineOfSight? AND SkillReady?
│    → FaceTarget → Wait(蓄力) → SpawnProjectile → Wait(后摇)
├─ Sequence [寻找射击位]：InRange? AND !HasLineOfSight?
│    → FindCoverPoint → MoveTo → Running
└─ Action [待机/巡逻]
```

**③ 精英怪（EliteBrute）**

```
Selector（Root）
├─ Sequence [死亡/受击]
├─ Sequence [阶段切换]：HpPercent < 0.3 AND !Enraged? → Roar(霸体) → SetEnraged(加攻速移速)
├─ Sequence [范围技]：InAoeRange? AND AoeReady?
│    → Telegraph预警(地面圈) → Wait → DealAoeDamage
├─ Sequence [冲锋]：Distance in [8,15]? AND ChargeReady?
│    → Charge（直线冲刺，碰墙自晕）→ Wait(自晕)
├─ Sequence [普攻]：InMeleeRange? → PlayAttack → DealDamage
├─ Sequence [追击]：（同上）
└─ Action [巡逻]
```

> 三棵树共用大量子树（死亡/受击/追击），这正好展示 BT-06 的**子树复用**能力。

### 9.4 三种寻路算法（需求 3）

#### 9.4.1 算法一：A\* Pathfinding Project Pro（插件，P0，客户端主用）

| 项 | 内容 |
| --- | --- |
| 适用 | **客户端表现层与单机/状态同步模式的主寻路方案**：怪物追击、绕障、巡逻、多单位路径分配 |
| 可用能力（Pro 版） | **Grid Graph / Point Graph / Navmesh Graph / Layer Grid Graph**；多线程异步寻路（`PathProcessor`）；**RVO 局部避障**；动态障碍图更新；路径平滑与简化；`AIPath` / `AIDestinationSetter` / `Seeker` |
| 集成 | ① 与 Behavior Designer **官方支持集成**（用 `Seek` / `Patrol` 等任务节点）② 但**不直接用 `AIPath` 驱动移动**，改为手动驱动（`seeker.StartPath` + 自研移动积分），以便接入同步与回滚 |
| 性能 | 多线程异步寻路 + 降低重寻路频率 + 用 `NNConstraint` 限制搜索范围 |
| ⚠️ 限制 | **不得进入帧同步逻辑层**（浮点代价 + 异步多线程，不确定）→ 见 A3 |
| 交付 | `Scene_Test_Pathfinding` 中可视化：图、路径、单次寻路耗时、同时寻路单位数 |

#### 9.4.2 算法二：Unity NavMesh（P0，对照与特定场景）

| 项 | 内容 |
| --- | --- |
| 适用 | 单机模式 / 状态同步模式下的 AI 移动；**主要用于与 A\* Pathfinding Project 做对比** |
| 实现 | `NavMesh.SamplePosition` + `NavMesh.CalculatePath` 手动驱动（关闭 `NavMeshAgent` 自动移动，用自研速度积分） |
| 优势场景 | 大范围连续地形、需要**自然贴地**与 Off-Mesh Link（跳跃/爬梯）时优于网格图 |
| ⚠️ 限制 | ① **不得在帧同步模式使用**（烘焙数据 + 浮点运算）② 动态障碍（`NavMeshObstacle`）开销较高 |
| 交付 | 与 A\* 的对比：路径长度、平滑度、寻路耗时、内存、动态障碍支持度 |

#### 9.4.3 算法三：流场（Flow Field）+ 群体避障（P1，大量单位）

| 项 | 内容 |
| --- | --- |
| 适用 | **大量敌人**场景（如 50+ 只怪追同一目标），性能优势明显；也是需求 3"两三种算法"的第三种 |
| 实现 | ① 用 Dijkstra/BFS 从目标点反向生成**积分场（Integration Field）** ② 由积分场生成**方向场（Flow Field）** ③ 每个 AI 只查表得到方向（O(1)） |
| 图数据 | **可以复用 A\* Pathfinding Project 的 Grid Graph 数据**作为网格输入（省去自己写地图解析） |
| 群体 | 叠加 **Boids 分离力 / RVO 简化版**：邻居排斥 + 与玩家保持间距，避免叠成一坨 |
| 确定性 | 用定点数学实现时可作为帧同步下大量单位的寻路方案（与自研定点 A\* 互补） |
| 交付 | 压测场景：插件 A\* 逐个体寻路 vs 流场，50~100 个 AI 的单帧耗时对比与 FPS 对比 |

#### 9.4.4 算法四：自研确定性 A\*（P0，**帧同步必需的兜底**）

| 项 | 内容 |
| --- | --- |
| 适用 | **帧同步模式下的唯一权威寻路**（含 PVE 帧同步、状态帧同步） |
| 实现 | 定点数学（`Fix64`）+ 网格（可复用插件的 Grid Graph 烘焙数据导出为静态数据）+ 二叉堆开放列表 |
| 确定性要求 | ① 代价全程定点 ② 开放列表用 `(f, h, index)` **三元组全序比较**，避免同 f 值时取点顺序不一致 ③ 禁止 `Dictionary`/`HashSet` 遍历 ④ 邻居访问顺序固定（固定方向数组） |
| 性能 | 分帧寻路（限制每帧展开节点数）+ 路径缓存 + 共用同一目标的流场 |
| 交付 | 与插件 A\* 的**路径一致性对比**（理想情况下拓扑一致，允许平滑差异）+ 确定性单测 |

> **9.4 的四个算法共同构成需求 3 的完整回答。** 面试时这样讲最有说服力：
> "我用了 A\* Pathfinding Project 作为主力寻路，但帧同步要求确定性，插件的浮点与多线程异步不满足，
> 所以我另外用定点数学实现了确定性 A\*，并复用插件的图数据。此外我还做了流场来支撑大量单位。"
> —— 这句话同时证明了**会用插件**、**懂插件的边界**、**能自己兜底**。

> **本项目使用 Behavior Designer 经典版**（标准 C# 运行时、IMGUI 编辑器，**无 DOTS/Entities 依赖**）。

> ② 不需要在工程里引入 Entities/Burst 包，减少与 xLua、protobuf-net 的版本冲突面。
> 代价是缺少 Pro 版的部分新特性（如 Save/Load、Event Branches、Entity Task），对本 Demo 规模无影响。
>
> ⚠️ **经典版与 Pro 版的序列化结构和 API 不同，不能中途切换**（切换等于重建所有树）。本项目已定死经典版。

#### 9.6.2 各模式下的 AI 运行位置（落地口径表）

| 运行模式 | AI 实现 | AI 运行在哪 | 服务端角色 | 说明 |
| --- | --- | --- | --- | --- |
| **单机模式** | Behavior Designer | 客户端（Host 实例） | 无独立进程（LocalTransport） | 演示效果最好，零网络开销 |
| **状态同步（PVE）** | Behavior Designer | **客户端 Host 的权威实例** | 广播快照（不跑 AI） | 本 Demo 服务端与客户端同机；纯服务端进程不含 Unity，不能跑 AI（见下方诚实说明） |
| **状态同步（PVP）** | 不需要（全是玩家） | — | 权威战斗判定 | — |
| **帧同步（PVE）** | `DeterministicBrain` | **每个客户端各自算** | 只收集输入 + 广播帧 | 确定性保证所有端结果一致 |
| **帧同步（PVP）** | 不需要（全是玩家） | — | 只收集输入 + 广播帧 | 纯输入同步，无 AI 问题 |
| **状态帧同步** | 同帧同步模式对应的选择 | 同左 | 加发权威关键帧校正 | — |

#### 9.6.3 ⚠️ 需要你知晓的一个诚实限制

**"服务端权威 AI"在本项目的技术栈下有一个前置条件。**

真实的商业项目里，服务端通常是**不带渲染的 Unity Dedicated Server 构建**（Headless Build），
那样 Behavior Designer 是可以跑的（它运行在 Unity 运行时里，只是没有画面）。
本项目的服务端按需求 12 是**独立 .NET 控制台进程**，因此**不能**跑 Behavior Designer。

本项目采取的处置方式（三种，按推荐顺序）：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **方案 1（本项目采用）** | 服务端保持纯 .NET；**AI 由客户端 Host 实例运行**；服务端负责输入收集、快照广播、权威战斗判定与落库 | 改动最小，符合需求 12 的"独立进程"表述 | 严格来说 AI 决策不在服务端进程内，需在文档与面试中**诚实说明** |
| 方案 2（P2 加分项） | 额外打一个 **Unity Headless Server 构建**作为"权威 AI 进程"，与 .NET 服务端并存（.NET 负责登录/房间/DB，Unity 进程负责战斗模拟） | 最接近商业架构，技术含量最高 | 约 +1~2 周，增加部署复杂度 |
| 方案 3（降级） | 把服务端也做成 Unity Headless 构建，放弃独立 .NET 进程 | AI 天然在服务端 | **违背需求 12 的表述**，且丢失"双端共享纯 C# 逻辑"的亮点 |

> **建议**：M3~M4 采用方案 1 把联网与同步做扎实；若 M5 结束时进度富余，方案 2 作为**最强的加分项**补上
> （届时你可以说："我做了两套服务端形态，.NET 处理逻辑与数据，Unity Headless 处理 AI 模拟，两者通过内部协议通信"）。
>
> **面试话术（方案 1 下）**：
> "AI 我用了 Behavior Designer，它依赖 Unity 运行时，所以我把它放在客户端侧的权威实例里跑；
> 帧同步模式下我另外做了一套纯 C# 的确定性决策模块，因为帧同步要求每个端独立算出一致结果。
> 如果要做到真正的服务端权威 AI，我会额外打一个 Unity Headless 构建作为模拟进程 —— 这也是我下一步的计划。"

## 10. 数据配置系统：Excel → ScriptableObject（需求 8）

### 10.1 需求解读

需求 8：**"对于角色数据等要使用 ScriptableObject 进行配置，可以写个工具将 Excel 表数据转成 SO 数据，方便策划填写"**

### 10.7 SO 与 Excel 的职责边界（写清楚很重要）

| 数据 | 存储位置 | 理由 |
| --- | --- | --- |
| 数值、ID、引用名（字符串） | **Excel → SO** | 策划可改，频繁变化 |

| 运行时可变状态（当前血量等） | **纯 C# Model 对象** | 绝不写回 SO（**SO 是只读配置，运行时修改 SO 在 Editor 下会污染资产**） |
| 玩家存档、账号、战绩 | **MySQL（服务端）** | 见 §13 |

> **"SO 只读"这条要写进代码规范**：任何对 SO 字段的运行时写入都是 Bug，
> 可以在 Editor 下加 `OnValidate` 保护，或用只读包装类（`Config_Hero` 提供只读属性）。

## 11. 热更新系统：Lua + AssetBundle（需求 5）

> 需求 5 明确："热更新部分使用 Lua 脚本语言、AB 包，**这部分不用框架**"。
> **本项目对该条的解读（已在 §5.4 说明，Q1 已确认）**：
> - **不使用**完整的游戏框架（如 ET、GameFramework、XLuaFramework 这类"整套游戏架构"）
> - **使用** xLua 及其配套的成熟封装（Lua 绑定层 + 现成的热更加载器），因为它们是**库/工具**，不是游戏架构
> - 本项目的**业务侧热更管理（版本、清单、下载、校验、加载策略）自研**，以便讲清细节
>
> **v1.1 变更**：按 Q1 的确认，放宽为"**可以用 xLua 相关框架简化开发**"。
> 因此 `CustomLoader`、Lua 加载器、常见问题规避（GC、AOT 生成、绑定裁剪）可直接采用社区成熟方案，
> 不必从零手写。但仍需满足 LUA-03~LUA-12 的要求（尤其是"Lua 代码走 AB 热更"与"热重载"）。

### 11.2 职责分层：YooAsset 负责什么，自研负责什么（v1.3 定稿）

#### 11.2.2 需求 5「AB 包」用词的说明（已确认的解读）

需求 5 原文为「热更新部分使用 Lua 脚本语言、**AB 包**，这部分不用框架」。
**YooAsset 底层构建与加载的仍然是 AssetBundle**，它只是把"构建 / 依赖 / 版本 / 下载 / 校验"这些基础能力封装好了。
因此本项目对该条的解读是：

| 需求 5 的要素 | 本项目如何满足 | 是否用框架 |
| --- | --- | --- |
| 使用 **AB 包** | ✅ 底层就是 AssetBundle（YooAsset 构建产物即 AB） | 构建工具用 YooAsset（规则 12） |
| 使用 **Lua** | ✅ xLua + 自研热更加载流程 | 绑定库用 xLua |
| "这部分**不用框架**" | ✅ **业务侧热更管理全部自研**（更新流程/UI/强制更新/原子性切换/回滚/日志），见 §11.3 | 不用游戏框架 |

> **此解读已与项目负责人确认**（§17.0 Q15）。若后续要求"自己写 AB 打包器"，则需在 §5.4.0 例外清单追加第 6 项并重估工期（约 +1 周）。

## 12. 性能优化与 DC 治理（需求 10）

### 12.1 需求解读

需求 10：**"要有性能优化，降低 DC 数"**

### 13.4 数据库设计（MySQL 8.0）

**库名**：`nbc_db`　**字符集**：`utf8mb4`　**引擎**：InnoDB

```sql
-- ① 账号表
CREATE TABLE `account` (
  `account_id`   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `username`     VARCHAR(32)  NOT NULL COMMENT '登录名',
  `password_hash` CHAR(64)    NOT NULL COMMENT 'SHA256(salt+password)',
  `salt`         CHAR(16)     NOT NULL,
  `created_at`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `last_login_at` DATETIME    NULL,
  PRIMARY KEY (`account_id`),
  UNIQUE KEY `uk_username` (`username`)

-- ② 玩家档案表（与账号 1:1）
CREATE TABLE `player_profile` (
  `player_id`    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `account_id`   BIGINT UNSIGNED NOT NULL,
  `nickname`     VARCHAR(32)  NOT NULL,
  `level`        INT          NOT NULL DEFAULT 1,
  `exp`          BIGINT       NOT NULL DEFAULT 0,
  `gold`         BIGINT       NOT NULL DEFAULT 0,
  `total_kill`   INT          NOT NULL DEFAULT 0,
  `total_death`  INT          NOT NULL DEFAULT 0,
  `total_win`    INT          NOT NULL DEFAULT 0,
  `total_lose`   INT          NOT NULL DEFAULT 0,
  `selected_hero` INT         NOT NULL DEFAULT 1001,
  `updated_at`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`player_id`),
  UNIQUE KEY `uk_account` (`account_id`),
  KEY `idx_gold` (`gold`) COMMENT '排行榜用',
  CONSTRAINT `fk_profile_account` FOREIGN KEY (`account_id`) REFERENCES `account`(`account_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='玩家档案表';

-- ③ 战斗记录表（一局一条，含每个玩家的 JSON 明细）
CREATE TABLE `battle_record` (
  `record_id`    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `room_id`      BIGINT UNSIGNED NOT NULL,
  `game_mode`    TINYINT      NOT NULL COMMENT '1=PVE 2=PVP',

  `duration_ms`  INT          NOT NULL,
  `result_json`  JSON         NOT NULL COMMENT '各玩家击杀/死亡/伤害/治疗',
  `created_at`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`record_id`),
  KEY `idx_created` (`created_at`),
  KEY `idx_room` (`room_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='战斗记录表';

-- ④ 战斗明细表（一人一行，便于统计与排行查询）
CREATE TABLE `battle_player_detail` (
  `detail_id`    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `record_id`    BIGINT UNSIGNED NOT NULL,
  `player_id`    BIGINT UNSIGNED NOT NULL,
  `hero_id`      INT          NOT NULL,
  `team`         TINYINT      NOT NULL DEFAULT 0,
  `kill`         INT          NOT NULL DEFAULT 0,
  `death`        INT          NOT NULL DEFAULT 0,
  `assist`       INT          NOT NULL DEFAULT 0,
  `damage_dealt` BIGINT       NOT NULL DEFAULT 0,
  `damage_taken` BIGINT       NOT NULL DEFAULT 0,
  `heal`         BIGINT       NOT NULL DEFAULT 0,
  `is_win`       TINYINT      NOT NULL DEFAULT 0,
  `is_ai`        TINYINT      NOT NULL DEFAULT 0,
  PRIMARY KEY (`detail_id`),
  KEY `idx_player` (`player_id`, `detail_id`),
  KEY `idx_record` (`record_id`),
  CONSTRAINT `fk_detail_record` FOREIGN KEY (`record_id`) REFERENCES `battle_record`(`record_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='战斗玩家明细';
```

**用于面试展示的 3 个 SQL 查询**：

```sql
-- ① 玩家胜率排行（Top 20）：展示聚合 + 索引
SELECT p.nickname, p.total_win, p.total_lose,
       ROUND(p.total_win / GREATEST(p.total_win + p.total_lose, 1) * 100, 1) AS win_rate
FROM player_profile p
WHERE p.total_win + p.total_lose >= 3
ORDER BY win_rate DESC, p.total_win DESC
LIMIT 20;

-- ② 某玩家最近 10 局的场均数据：展示 JOIN + 分组
SELECT b.record_id, b.game_mode, b.duration_ms, d.hero_id,
       d.kill, d.death, d.damage_dealt, d.damage_taken, d.is_win
FROM battle_player_detail d
JOIN battle_record b ON b.record_id = d.record_id
WHERE d.player_id = ?
ORDER BY d.detail_id DESC
LIMIT 10;

-- ③ 各英雄出场率与胜率：展示双表关联统计
SELECT d.hero_id,
       COUNT(*) AS games,
       SUM(d.is_win) AS wins,
       ROUND(AVG(d.damage_dealt)) AS avg_damage
FROM battle_player_detail d
WHERE d.is_ai = 0
GROUP BY d.hero_id
ORDER BY games DESC;
```

## 15. 设计模式清单（需求 4）

> 需求 4：**"要遵循常见的设计模式"**
> 本项目采取的原则是：**模式是为解决问题而引入的，每个模式都要能说清楚"不用它会怎样"**。
> 下面列出本项目实际使用的模式、使用位置、以及它解决的具体问题。

### 15.1 实际使用的设计模式

| # | 模式 | 使用位置 | 解决的具体问题 |
| --- | --- | --- | --- |
| 1 | **单例（Singleton）** | 各 Manager（`EventCenter`、`AssetManager`、`ConfigMgr`、`NetClient` 等） | 全局唯一访问点；注意避免滥用（见 15.2） |
| 2 | **观察者（Observer）** | `EventCenter`、`BattleEvent` 分发、Model→View 通知 | 模块解耦，Model 不需要知道谁在关心数据变化 |
| 3 | **策略（Strategy）** | ① 三种同步模式 `ISyncStrategy` ② `INetTransport`（TCP/本地）③ 伤害计算 `IDamageCalculator` ④ AI 寻路 `IPathfinder` | 同一抽象下可替换实现，是本项目"模块化"的核心手段 |
| 4 | **状态（State）** | 玩家/敌人/战斗流程的有限状态机；`BattleStateMachine`（加载/战斗/结算） | 状态与转移显式化，避免大量 `if/switch` |
| 5 | **分层状态机（HFSM）** | 玩家控制（Locomotion/Action/Special + 下层子状态） | 状态爆炸问题；需求 9 明确要求 |
| 6 | **组合（Composite）** | 行为树节点（组合节点含子节点，叶节点为原子操作）、UI 层级 | 树形结构的统一接口 |
| 7 | **工厂（Factory）** | ① `EntityFactory`（按 ID 创建实体）② `SkillFactory`（按配置构造技能）③ `PoolFactory` | 创建逻辑集中，避免 `new` 散落 |
| 8 | **对象池（Object Pool）** | `ObjectPool`（怪物/特效/飘字/子弹/消息对象） | 减少 GC 与实例化开销（OPT-20/21） |
| 9 | **命令（Command）** | 玩家输入封装为 `InputCommand`；网络消息处理封装为 `ICommand` | 输入可缓冲、可回放、可重放（帧同步/回滚的前提） |
| 10 | **备忘录（Memento）** | 状态快照 `Snapshot`、回滚用的 `StateBuffer` | 预测回滚（PRED-03）的实现基础 |
| 11 | **中介者（Mediator）** | `BattleController` 作为战斗内各系统的中介；`RoomMgr` 作为服务端房间的中介 | 减少多对多依赖 |
| 12 | **外观（Facade）** | `GameFacade` / 各 Manager 对外提供简化接口，隐藏内部子系统 | 降低调用方复杂度 |
| 13 | **适配器（Adapter）** | `INetTransport` 适配 TCP 与本地；AB 加载适配 Editor `AssetDatabase` 与运行时 AB | 环境差异隔离（单机模式的关键） |
| 14 | **代理（Proxy）** | AB 加载的 `AssetProxy`（延迟加载/引用计数）；远程玩家的 `RemotePlayerProxy` | 延迟开销与访问控制 |
| 15 | **模板方法（Template Method）** | `BasePanel` 定义 UI 生命周期；`StateBase` 定义状态回调骨架 | 复用骨架，子类填细节 |
| 16 | **迭代器（Iterator）** | 帧队列、输入序列、快照缓冲的遍历 | 统一遍历接口 |
| 17 | **职责链（Chain of Responsibility）** | 伤害计算链（闪避判定 → 暴击 → 护甲减免 → Buff 修正 → 最终伤害）；网络消息拦截器（日志/校验） | 可插拔的处理流程 |
| 18 | **享元（Flyweight）** | SO 配置数据被大量实体共享；`Sprite` 图集共享 | 内存复用 |
| 19 | **建造者（Builder）** | 行为树构建器（链式 API 构建树）、YooAsset 分组配置构建 | 复杂对象的分步构建 |
| 20 | **桥接（Bridge）** | 逻辑层（定点数学）与表现层（Unity 浮点）分离 | 逻辑与表现独立演化（DET-02 的实现手段） |
| 21 | **原型（Prototype）** | 怪物/技能配置的模板复用（SO 克隆生成变体） | 配置复用 |
| 22 | **访问者（Visitor）** | 协议消息分发（MsgId → Handler）、战斗事件遍历消费 | 在不改数据结构的前提下增加操作 |
| 23 | **MVVM/MVC** | 三层架构（需求 7） | 表现与逻辑解耦 |
| 24 | **服务定位器（Service Locator）** | `ServiceLocator` 管理跨模块服务（可选，避免单例泛滥） | 替代部分单例 |
| 25 | **脏标记（Dirty Flag）** | 快照增量、UI 局部刷新、属性重算 | 避免无谓计算（性能） |
| 26 | **双缓冲（Double Buffer）** | 逻辑状态的双缓冲（`prevState`/`curState`）供表现层插值；快照缓冲 | 插值渲染（LOCK-06） |

### 15.2 单例滥用的约束（主动展示工程判断力）

单例是本项目最主要的反模式风险。约束如下：

| 规则 | 说明 |
| --- | --- |
| 只有"全局唯一且无状态耦合"的管理器才做单例 | 如 `AssetManager`、`ConfigMgr`、`EventCenter` |
| 有状态、有生命周期的对象**禁止单例** | 如 `PlayerController`、`Room`、`Battle` 实例 |
| 逻辑层（`NBC.Shared`）**禁止单例** | 否则帧同步下多实例/测试无法隔离 |
| 依赖应通过**构造函数注入**（逻辑层）或**服务定位器**（表现层） | 便于单测 |
| 单例数量设上限并登记在文档中 | 可量化、可评审 |

### 19.1 R1 降级预案详述（最重要的预案）

如果帧同步确定性在 M4 阶段无法达成，按以下顺序降级，**每一步都保留可演示的成果**：

| 级别 | 方案 | 仍能演示的需求 2 内容 | 诚实表述 |
| --- | --- | --- | --- |
| 完整（目标） | 全定点 + 完整战斗帧同步 + 确定性校验 + 回放 | 状态同步 / 帧同步 / 状态帧同步 / 预测回滚 | — |
| 降级 1 | 帧同步仅覆盖"移动 + 普攻 + 1 技能"，其余走状态同步混合 | 帧同步（简化）+ 状态帧同步 | "我把帧同步范围限制在确定性可控的部分，复杂技能用状态同步下发结果，这是工程上的取舍" |
| 降级 2 | 帧同步只在局域网/0 丢包下演示，外加明确文档说明边界 | 帧同步（限制条件）+ 全部确定性测试 | "帧同步我实现了也测通了，受限于浮点与 Unity 依赖，我把它用在可控场景" |
| 降级 3 | 状态帧同步为主（服务端权威 + 帧驱动），帧同步保留**完整设计与单测** | 状态帧同步 / 预测回滚 / 确定性工具链 | "我实现了状态帧同步与完整的定点数学与确定性测试，帧同步的完整实现在文档与测试中" |

> **诚实说明边界永远不会致命，假装做到了才会。** 面试官最反感的是"号称做了帧同步但说不出确定性怎么保证"。

### 21.6 术语表

## 22. 结语

这份文档把 13 条技术清单收敛成了 **一个能跑、能讲、能量化、能复用的 3D 联网 ARPG 战斗作品**。

1. **每个里程碑都必须有可演示成果。** 不做"两个月的隐形工作"，任何时刻中断都能拿出东西。
