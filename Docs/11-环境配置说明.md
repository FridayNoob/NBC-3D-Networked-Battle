## 一、数据库连接：密码怎么传（重要）

### 现状

`Server/NBC.Server.Host/appsettings.json` 里的 `Database.Password` **是空字符串**，这是**有意的**：

```json
"Database": {
    "Provider": "MySql",
    "Host": "127.0.0.1",
    "Port": 3306,
    "Database": "nbc_db",
    "User": "root",
    "Password": "",          // ← 故意留空
    "ConnectionTimeoutSeconds": 5
}
```

原因：**`appsettings.json` 要提交进 Git**（它是配置模板，团队/未来的你都需要它），
而**密码绝不能进 Git**。

### 三种注入方式（按推荐顺序）

| 方式 | 怎么做 | 适用场景 | 是否入库 |
| --- | --- | --- | --- |
| **① 环境变量（推荐）** | 设置 `NBC_DB_PASSWORD=你的密码` | 日常开发、CI | ❌ 不入库 |
| ② 本地覆盖文件 | 新建 `appsettings.Local.json`（只写要覆盖的字段） | 想跟其他本地配置放一起 | ❌ 已被 `.gitignore` 忽略 |
| ③ 直接改 `appsettings.json` | 填进去 | ⚠️ **不推荐** | ✅ 会入库 → **有泄漏风险** |

**方式 ① 的具体做法**

临时（仅当前命令行窗口有效）：

```powershell
$env:NBC_DB_PASSWORD = "你的root密码"
dotnet run --project NBC.Server.Host
```

永久（写入用户级环境变量，重开命令行后仍有效）：

```powershell
[Environment]::SetEnvironmentVariable("NBC_DB_PASSWORD", "你的root密码", "User")
```

> ⚠️ **这也是规则 13 的一部分**：需要凭据时**直接由你设置**，AI 不接触、不猜测、不写入任何密码。

### 服务端读取配置的优先级（M3 实现时遵守）

```
环境变量 NBC_DB_PASSWORD   ← 最高
    ↓ 未设置则
appsettings.Local.json
    ↓ 不存在则
appsettings.json           ← 最低（模板）
```

### 如果本机 MySQL 的 root 没有密码

本机 MySQL 是默认安装，**root 密码取决于你安装时的设置**，两种情况都要能跑：

| 情况 | 连接串 | 处理 |
| --- | --- | --- |
| root 无密码 | `Password=`（空） | 什么都不用做，默认即可 |
| root 有密码 | 需注入 | 按上面方式 ① 设置环境变量 |

> **M3 实现要求**：连接失败时要给出**明确的错误提示**（"数据库连接失败：请检查 appsettings.json 的 Database 配置与环境变量 NBC_DB_PASSWORD"），
> 而不是抛一个看不懂的异常。同时按需求文档 **DB-10** 降级：**数据库不可用时服务端仍能启动**，只让存档功能报错。

## 二、端口占用

| 用途 | 端口 | 在哪配 | 备注 |
| --- | --- | --- | --- |
| MySQL | 3306 | MySQL 安装时确定 | 本机 MySQL80 服务已占用 |
| **NBC 服务端 TCP** | **9000** | `appsettings.json` → `Server.ListenPort` | 本机已确认 3306 在用；9000 需在 M3 首次启动前确认未被占用 |

**启动服务端前查端口是否被占用**：

```powershell
netstat -ano | findstr :9000
# 若无输出 = 未被占用，可以启动
# 若有输出，最后一列是占用进程的 PID，可用 Get-Process -Id <PID> 查看是谁
```

| 被占用了怎么办 | 做法 |
| --- | --- |
| 偶发占用 | 改 `appsettings.json` 的 `Server.ListenPort` 为其他值（如 9100），客户端同步改 |
| 被自己的残留进程占用 | 结束该进程；M0/M3 阶段服务端没做优雅退出时常见 |

## 三、可写目录（为多开与热更预留）

Unity 的 `Application.persistentDataPath` 由 **Company Name + Product Name** 决定：

| 项 | 值 | 在哪设 |
| --- | --- | --- |
| Company Name | `NBC` | Project Settings → Player |
| Product Name | `NBC` | Project Settings → Player |

因此默认路径是：

```
Windows: %USERPROFILE%\AppData\LocalLow\NBC\NBC\
```

### ⚠️ 多开冲突（M3 会踩）

同时开 4 个客户端演示联机时，**它们共用同一个可写目录** → 热更清单、缓存、日志互相覆盖。

**约定（M1 实现热更可写目录时必须预留）**：

```
可写根目录 = <persistentDataPath>/<InstanceId>/
InstanceId 取值：
  · 未传启动参数 → "Default"
  · 传了 -instance 2 → "Instance2"
```

启动参数示例（M3 演示多开时用）：

```
NBC.exe -instance 1
NBC.exe -instance 2
NBC.exe -instance 3
```

> **现在只需知道有这回事**，M1 写热更/存档可写目录时按上面的约定实现，M3 多开就不用返工。

## 四之二、⚠️ AI（DSH 沙箱）里跑 `dotnet build` 必须加 `-m:1`（2026-09-20 实测）

**这一条只影响"AI 代跑构建"，不影响你自己在终端里构建。**

| 现象 | `dotnet build NBC.sln` 在 DSH 沙箱里会**静默失败**：`生成失败。0 个警告 0 个错误`，退出码 1，**没有任何错误信息** |
| --- | --- |
| 影响范围 | **仅限多节点并行构建**。任何含 ≥2 个 `ProjectReference` 的工程都会触发（`NBC.Server.Game` / `Host` / `Tests` 都中招） |
| 解决方案 | **`dotnet build NBC.sln -m:1`** —— 单节点构建，一切正常（0 警告 0 错误） |
| 根因 | MSBuild 在 `-m`（并行）下会启动**进程外的工作节点**，节点间靠 **命名管道（named pipe）** 通信；DSH 的受限沙箱不允许打开命名管道，子节点起不来 → 任务返回失败但不记录任何错误 |
| 为什么确定与本项目无关 | 用**最小对照工程**（TEMP 里新建 A/B/C 三个工程，C 引用 A+B，共 20 行代码）复现了完全相同的现象：`-m:1` 成功、`-m:2`/`-m` 静默失败。**D13 记录的 `dotnet build` 成功也仍然有效** |

**给 AI 的固定做法**：在沙箱内构建/还原一律加 `-m:1`。

```powershell
cd "E:\U3D Projects\0_MyFile\3D联网战斗Demo\Server"
dotnet build NBC.sln -m:1          # ✅ AI 代跑时用这条
dotnet build NBC.sln               # ✅ 你在自己的终端里用这条（正常环境不受限）
```

> **判断这类"无错误信息的失败"的通用手法**：① 换 `-m:1` 试；② 用**最小可复现工程**验证是不是环境问题
> （本次就是靠"20 行的三工程对照"把嫌疑从项目上摘掉的）；③ 看退出码而不是看输出 ——
> **"0 个错误"不代表成功**。
