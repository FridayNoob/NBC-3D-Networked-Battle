## 一、数据库连接：密码怎么传（重要）

### 现状

`Server/NBC.Server.Host/appsettings.json` 里的 `Database.Password` **是空字符串**，这是**有意的**：

```json
"Database": {
    "Provider": "MySql",
    "Host": "127.0.0.1",
    "Port": 3306,
    "Database": "nbc_db",
    "User": "root",
    "Password": "",          // ← 故意留空
    "ConnectionTimeoutSeconds": 5
}
```

原因：**`appsettings.json` 要提交进 Git**（它是配置模板，团队/未来的你都需要它），
而**密码绝不能进 Git**。

### 三种注入方式（按推荐顺序）

| 方式 | 怎么做 | 适用场景 | 是否入库 |
| --- | --- | --- | --- |
| **① 环境变量（推荐）** | 设置 `NBC_DB_PASSWORD=你的密码` | 日常开发、CI | ❌ 不入库 |
| ② 本地覆盖文件 | 新建 `appsettings.Local.json`（只写要覆盖的字段） | 想跟其他本地配置放一起 | ❌ 已被 `.gitignore` 忽略 |
| ③ 直接改 `appsettings.json` | 填进去 | ⚠️ **不推荐** | ✅ 会入库 → **有泄漏风险** |

**方式 ① 的具体做法**

临时（仅当前命令行窗口有效）：

```powershell
$env:NBC_DB_PASSWORD = "你的root密码"
dotnet run --project NBC.Server.Host
```

永久（写入用户级环境变量，重开命令行后仍有效）：

```powershell
[Environment]::SetEnvironmentVariable("NBC_DB_PASSWORD", "你的root密码", "User")
```

> ⚠️ **这也是规则 13 的一部分**：需要凭据时**直接由你设置**，AI 不接触、不猜测、不写入任何密码。

### 服务端读取配置的优先级（M3 实现时遵守）

```
环境变量 NBC_DB_PASSWORD   ← 最高
    ↓ 未设置则
appsettings.Local.json
    ↓ 不存在则
appsettings.json           ← 最低（模板）
```

### 如果本机 MySQL 的 root 没有密码

本机 MySQL 是默认安装，**root 密码取决于你安装时的设置**，两种情况都要能跑：

| 情况 | 连接串 | 处理 |
| --- | --- | --- |
| root 无密码 | `Password=`（空） | 什么都不用做，默认即可 |
| root 有密码 | 需注入 | 按上面方式 ① 设置环境变量 |

> **M3 实现要求**：连接失败时要给出**明确的错误提示**（"数据库连接失败：请检查 appsettings.json 的 Database 配置与环境变量 NBC_DB_PASSWORD"），
> 而不是抛一个看不懂的异常。同时按需求文档 **DB-10** 降级：**数据库不可用时服务端仍能启动**，只让存档功能报错。

## 二、端口占用

| 用途 | 端口 | 在哪配 | 备注 |
| --- | --- | --- | --- |
| MySQL | 3306 | MySQL 安装时确定 | 本机 MySQL80 服务已占用 |
| **NBC 服务端 TCP** | **9000** | `appsettings.json` → `Server.ListenPort` | 本机已确认 3306 在用；9000 需在 M3 首次启动前确认未被占用 |

**启动服务端前查端口是否被占用**：

```powershell
netstat -ano | findstr :9000
# 若无输出 = 未被占用，可以启动
# 若有输出，最后一列是占用进程的 PID，可用 Get-Process -Id <PID> 查看是谁
```

| 被占用了怎么办 | 做法 |
| --- | --- |
| 偶发占用 | 改 `appsettings.json` 的 `Server.ListenPort` 为其他值（如 9100），客户端同步改 |
| 被自己的残留进程占用 | 结束该进程；M0/M3 阶段服务端没做优雅退出时常见 |

## 三、可写目录（为多开与热更预留）

Unity 的 `Application.persistentDataPath` 由 **Company Name + Product Name** 决定：

| 项 | 值 | 在哪设 |
| --- | --- | --- |
| Company Name | `NBC` | Project Settings → Player |
| Product Name | `NBC` | Project Settings → Player |

因此默认路径是：

```
Windows: %USERPROFILE%\AppData\LocalLow\NBC\NBC\
```

### ⚠️ 多开冲突（M3 会踩）

同时开 4 个客户端演示联机时，**它们共用同一个可写目录** → 热更清单、缓存、日志互相覆盖。

**约定（M1 实现热更可写目录时必须预留）**：

```
可写根目录 = <persistentDataPath>/<InstanceId>/
InstanceId 取值：
  · 未传启动参数 → "Default"
  · 传了 -instance 2 → "Instance2"
```

启动参数示例（M3 演示多开时用）：

```
NBC.exe -instance 1
NBC.exe -instance 2
NBC.exe -instance 3
```

> **现在只需知道有这回事**，M1 写热更/存档可写目录时按上面的约定实现，M3 多开就不用返工。

### 四之一、⚠️ `git push` 到 GitHub：**git 不读 Windows 系统代理**（2026-09-20 实测）

**症状**：浏览器能正常打开 GitHub，但 `git push` 报

```
fatal: unable to access 'https://github.com/...': Failed to connect to github.com:443 after 21118 ms: Could not connect to server
```

**根因**：Clash 的系统代理只被 **Windows / 浏览器**使用，**git 不读它**，得单独配。

**实测数据（同一台机器、同一时刻）**：

| 走法 | 结果 |
| --- | --- |
| 直连 `github.com:443` | ❌ 不可达（DNS 正常，解析到 `20.205.243.166`，TCP 被拦） |
| `github.com:22`（SSH） | ✅ 可达 |
| 代理 **`127.0.0.1:7897`** | ✅ **可用**（`git ls-remote` 退出码 0） |
| 代理 `127.0.0.1:7890` | ❌ `CONNECT tunnel failed, response 400` |
| `ssh -T git@github.com` | ✅ `Hi FridayNoob! You've successfully authenticated`（本机 `~/.ssh/id_rsa` 已注册） |

> ⚠️ **别用 PowerShell 的 `Invoke-WebRequest -Proxy` 去判断代理能不能用**：
> 实测它对 7897 报"基础连接已经关闭"、对 7890 报 400，**两个结论都是错的**（PS 的 HTTPS 代理处理与 git 的 CONNECT 不是一回事）。
> **要判断就直接用 git 自己测**。

**可用的两条路（选一条）**：

```powershell
# 路线 A：HTTPS + 代理（推荐；已实测端到端可用）
#   注意：--local 只作用于本仓库，不影响其它项目
git config --local  http.proxy  http://127.0.0.1:7897
git config --local  https.proxy http://127.0.0.1:7897
git push -u origin main
#   想对所有仓库生效：把 --local 换成 --global
#   ⚠️ 代价：Clash 没开时 push 会失败（这是预期的，不是配置错了）

# 路线 B：改用 SSH（不需要代理，走 22 端口；本机密钥已验证可用）
git remote set-url origin git@github.com:FridayNoob/NBC-3D-Networked-Battle.git
git push -u origin main
```

**凭据**：GitHub **早已不接受账号密码**。HTTPS 路线第一次 push 会弹 Git Credential Manager 的浏览器授权；
若它退化成在终端里问密码，要贴 **Personal Access Token**（Settings → Developer settings → Personal access tokens）。

> 📌 **本仓库当前状态（2026-09-20）**：远端 `origin` = `https://github.com/FridayNoob/NBC-3D-Networked-Battle.git`，
> 已配好**仓库级**代理 7897，`main` 分支 15 笔提交待推。

## 四之二、⚠️ AI（DSH 沙箱）里跑 `dotnet build` 必须加 `-m:1`（2026-09-20 实测）

**这一条只影响"AI 代跑构建"，不影响你自己在终端里构建。**

| 现象 | `dotnet build NBC.sln` 在 DSH 沙箱里会**静默失败**：`生成失败。0 个警告 0 个错误`，退出码 1，**没有任何错误信息** |
| --- | --- |
| 影响范围 | **仅限多节点并行构建**。任何含 ≥2 个 `ProjectReference` 的工程都会触发（`NBC.Server.Game` / `Host` / `Tests` 都中招） |
| 解决方案 | **`dotnet build NBC.sln -m:1`** —— 单节点构建，一切正常（0 警告 0 错误） |
| 根因 | MSBuild 在 `-m`（并行）下会启动**进程外的工作节点**，节点间靠 **命名管道（named pipe）** 通信；DSH 的受限沙箱不允许打开命名管道，子节点起不来 → 任务返回失败但不记录任何错误 |
| 为什么确定与本项目无关 | 用**最小对照工程**（TEMP 里新建 A/B/C 三个工程，C 引用 A+B，共 20 行代码）复现了完全相同的现象：`-m:1` 成功、`-m:2`/`-m` 静默失败。**D13 记录的 `dotnet build` 成功也仍然有效** |

**给 AI 的固定做法**：在沙箱内构建/还原一律加 `-m:1`。

```powershell
cd "E:\U3D Projects\0_MyFile\3D联网战斗Demo\Server"
dotnet build NBC.sln -m:1          # ✅ AI 代跑时用这条
dotnet build NBC.sln               # ✅ 你在自己的终端里用这条（正常环境不受限）
```

> **判断这类"无错误信息的失败"的通用手法**：① 换 `-m:1` 试；② 用**最小可复现工程**验证是不是环境问题
> （本次就是靠"20 行的三工程对照"把嫌疑从项目上摘掉的）；③ 看退出码而不是看输出 ——
> **"0 个错误"不代表成功**。

## 四之三、⚠️ AI 沙箱里的另外两条硬约束（2026-09-22 实测）

### ① `dotnet run` 必须配 `--no-build`

| | |
| --- | --- |
| **现象** | `dotnet run --project X`（**带隐式构建**）失败，报 `生成失败。请修复生成错误并重新运行。` —— 而**构建其实是好的** |
| **根因** | 与 §四之二 同一个：`dotnet run` 要去**捕获构建过程的 stdio**，受限沙箱不允许打开命名管道 → 报一个误导性的错 |
| **解决** | **先 `dotnet build ... -m:1`，再 `dotnet run ... --no-build`**；或者**直接跑生成的 exe** |

⚠️ 顺带记一个白跑两轮的坑：产物 exe 的名字是 **`AssemblyName`**（如 `NBC.ConfigKit.Cli.exe`），
**不是工程名**（`ConfigKit.Cli`）。

### ② **NuGet 还原在这个沙箱里做不到**（最要紧的一条）

```
error NU1301: 无法加载源 https://api.nuget.org/v3/index.json ...
              The SSL connection could not be established / Authentication failed
```

| | |
| --- | --- |
| **影响** | **任何需要新 NuGet 包的活，AI 都做不了**（NPOI、xUnit…）。已经还原进缓存的包照常可用 |
| **应对（AI 侧）** | 把"需要第三方的部分"隔离成**叶子工程**，其余**零依赖**照常推进 —— `Tools\ConfigKit` 就是这么做的（Xlsx 适配器是唯一带包的工程，它构建不了不影响其他任何东西） |
| **应对（你侧）** | 在能联网的机器上 `dotnet restore <sln>`，之后 AI 就能编译那一部分 |
| **判据** | **"要不要引入 NuGet 包"是一条分水岭：它决定 AI 能不能自己验证。** 能不引就不引；非引不可，就把它关进一个叶子里 |

## 四之三、编译闸门：不开 Unity 也能核对 Unity API（2026-09-20 建立）

**它解决什么问题**：AI（以及你）在写 `Client\Assets` 下的 C# 时，最大的风险是"**这个 API 到底存不存在 / 这个签名对不对**"。
M0 已经踩过两次同类坑（一次 `ToByteArray` 少 `using`，一次 `link.xml` 条目永远匹配不到）。
Unity 自己编译一次要几十秒到几分钟，反馈太慢；而**编译器其实可以提前说话**。

**做法**：建一个纯 .NET 工程，引用**本机 Unity 程序集**，把框架源码与测试源码一起编译一遍。

| 项 | 值 |
| --- | --- |
| 工程 | `Server\_api-probe\ApiProbe.csproj`（**不进 Git**，见 `Server\.gitignore`） |
| 引用 | `D:\SOFT\Unity\Hub\Editor\2022.3.62f3c1\Editor\Data\Managed\UnityEngine\UnityEngine.CoreModule.dll` + `UnityEngine.SharedInternalsModule.dll` |
| 测试用引用 | `Client\Library\PackageCache\com.unity.ext.nunit@1.0.6\net35\unity-custom\nunit.framework.dll`、`Client\Library\ScriptAssemblies\UnityEngine.TestRunner.dll` |
| 编译的源码 | `Client\Assets\_Project\Framework\**\*.cs` + `Client\Assets\_Project\Tests\EditMode\**\*.cs` |
| 命令 | `dotnet build Server\_api-probe\ApiProbe.csproj -m:1`（`-m:1` 的理由见 §四之二） |

**两条让它"可信"的关键设置**（少一条就会变成"永远绿灯的摆设"）：

1. **`<LangVersion>9.0</LangVersion>` + `<ImplicitUsings>disable</ImplicitUsings>`**
   —— 与 Unity 2022.3 对齐。不这么设，`net8.0` 默认是 C# 12，
   于是"探针通过、Unity 编译失败"这种**假绿**就出现了。
2. **负向对照**：临时塞一个调用不存在 API 的文件，确认它**真的会报错**（实测报 `error CS0117`），再删掉。
   这就是工作规则 **W9**："验证脚本本身也要被验证"。

**它做不到什么**（不要把它的绿灯当万能）：

| 做不到 | 原因 | 该用什么 |
| --- | --- | --- |
| 验证**运行时**行为（单例是不是真的唯一、池是不是真的 O(1)） | 它只编译，不运行 —— 纯 .NET 进程加载 Unity 程序集后无法实例化引擎对象（D14 已实测，见 `Docs\12`） | Unity Test Runner（EditMode/PlayMode） |
| 验证 Editor-only 代码 | 没引 `UnityEditor.dll` | 需要时按同样办法加一个 Editor 版闸门 |
| 验证 `.meta` / 资源导入 / 序列化 | 与 C# 编译无关 | Unity Editor |

## 五之二、protoc 生成协议代码（`.proto` → C#）

> 适用场景：**改了 `.proto` 之后重新生成协议代码**。日常 clone / 编译**不需要**这个 —— 生成产物已经入库。

### 5.2.1 工具位置与版本配对（⚠️ 必须配对）

| 项 | 值 |
| --- | --- |
| **在用的 protoc** | `E:\U3D Projects\TeachNet\Protobuf\protoc.exe`（实测 `libprotoc 3.21.1`） |
| 配套运行时 | **Google.Protobuf 3.21.1**（`Client\Assets\ThirdParty\GoogleProtobuf\Google.Protobuf.dll`） |
| **未采用的另一份** | 离线包目录里的 `protoc-35.1-win64`（`libprotoc 35.1`）—— 它要配 **Google.Protobuf 3.35.1**，本项目**不用它** |
| `.proto` 源文件 | 仓库顶层 `Protocol/`（唯一来源） |
| 生成的 C# | `Client\Assets\_Project\Protocol\`（命名空间 `NBC.Protocol`，**入库**） |

> ⚠️ **protoc 与运行时版本必须配对**：混用不同版本会得到"生成代码编译不过"或"运行期报错"，
> 而且报错信息通常**不会**提示是版本问题，很难查。

### 5.2.2 生成命令（在仓库根目录、用相对 ASCII 路径）

```bat
cd /d "E:\U3D Projects\0_MyFile\3D联网战斗Demo"
"E:\U3D Projects\TeachNet\Protobuf\protoc.exe" --proto_path=Protocol --csharp_out=Client/Assets/_Project/Protocol Protocol/nbc_probe.proto
```

生成后应看到 `Client\Assets\_Project\Protocol\NbcProbe.cs` 被更新（文件头是 `// <auto-generated>`）。

### 5.2.3 ⚠️ 坑：**绝不要给 protoc 传含中文的路径**

**现象**：如果把路径写成绝对路径（本项目根目录含中文 `3D联网战斗Demo`），protoc 会报：

```
Could not make proto path relative : <路径> : No such file or directory
```

**原因**：protoc 的**命令行参数（`argv`）在 Windows 上要经过 ANSI 代码页转换**，
而**中文路径无法在 ANSI 下无损表示** → protoc 拿到的是一个坏掉的路径。
注意：**这不是"文件不存在"，文件其实好好的**。

**绕法（两条同时用）**：

| 做法 | 说明 |
| --- | --- |
| ① **让工作目录是根目录**（`cd /d <仓库根>`） | 工作目录走的是 Unicode API，**中文没问题** |
| ② **参数里只给相对路径**（`Protocol/...`、`Client/Assets/...`） | 相对路径是纯 ASCII → 不经过中文转换 |

> 📌 **这与 `mysql.exe` 打不开中文路径是同一类问题**（都是"命令行工具 + 非 ASCII 路径 + ANSI 转换"）。
> `mysql` 那边的完整诊断（`error: 42` = `EILSEQ`）见 `Docs\10-M0手动操作手册.md` 的 **D12**
> 与 `DeepSeekOutput\2026-09-20-知识点总结.md` 第五节。
> **差别**：protoc 可以用"工作目录 + 相对路径"绕过，而 `mysql` 的 `source` 命令绕不过去（只能改用输入重定向）。

### 5.2.4 生成之后要做什么

1. **把 `.proto` 与生成的 `.cs` 一起提交**（两个都是协议的来源，缺一不可复现）
2. 运行 `powershell -NoProfile -ExecutionPolicy Bypass -File Tools\Verify-PluginDlls.ps1` 复核（它会盘点 `_Project\Protocol`）
3. 若新增了**消息类型**，确认 `Client\Assets\ThirdParty\GoogleProtobuf\` 仍是 **2 个 DLL**（换库后不需要再加）

## 六、Unity 版本升级：2022.3.17f1c1 → 2022.3.x（≥2022.3.21）

### 6.1 为什么要升（结论先说）

| 项 | 内容 |
| --- | --- |
| 触发者 | **A\* Pathfinding Project 5.4.7**，在编辑器加载时 `Debug.LogError`：<br>*"This version of Unity has a bug which causes components in the A\* Pathfinding Project to randomly stop working. Please update to unity 2022.3.21 or later."* |
| 触发位置 | `Packages/com.arongranberg.astar/PackageTools/Editor/DependencyCheck.cs:61` —— 条件就是 `major==2022 && minor==3 && patch < 21` |
| 同一门槛还写在 | `Editor/NavmeshCutEditor.cs:100`、`Runtime/.../TileHandler.cs:101`，原文：*"The **NavmeshCut** component requires Unity 2022.3 or newer to work, due to Unity bugs in earlier versions. Please update Unity to 2022.3.21 or later, if you want to use navmesh cutting."* |
| 决定 | ✅ **升级 Unity 到 2022.3.x（≥2022.3.21）**，登记为需求文档 **风险 R16**。**旧版 2022.3.17 保留不卸载**（`RPG_Git` 继续用它） |

**为什么在 M0 就升**：此刻工程里只有脚手架、**一行业务代码都没有**，且 **D17（IL2CPP 出包）还没做** ——
升级后只需验证一遍；拖到 M2/M4 再升，就是"验过的东西全部重验"。

### 6.2 为什么**否决**了"降级 A\*"（重要，避免以后重走）

| 论点 | 说明 |
| --- | --- |
| 告警的主体是 **Unity**，不是 A\* | 原文是 *"**This version of Unity** has a bug…"*。降级 A\* **不会改变 Unity 版本** → bug 还在，只是没人提醒了 |
| 降级会**放大**风险 | 旧版 A\* **没有**这条检查 → 同样的问题从"红色告警"变成"**静默失效**"；4.2.x 连 NavmeshCut 的版本守卫都没有 → **悄悄坏** |
| 代价还不小 | 5.0（2024-03）是**大重写**：Grid/Recast 扫描改为 **Burst + Job System**（快约 3 倍）。降级等于放弃它 + 3 年 bug 修复 |
| 获取渠道受限 | Pro 旧版在官网下载页的 "Older versions" 折叠区，**需先输入发票号/序列号**；Asset Store 只给最新版 |

> **一句话**：降级 = 把报信的人赶走，不是治病。
>
> **可行性附记（查过，为省你以后再查）**：旧版门槛确实低 ——
> CHANGELOG 4.2.10（2019）写 *"supported in Unity 2017.4 LTS and later"*，5.0.3（2024-03）修的是 *"compilation errors in Unity 2022.1"*；
> 而 *"NavmeshCut requires Unity 2022.3 or newer"* 是 **5.2.0（2024-10）首次出现**。
> 但那条 `patch < 21` 的**具体**告警是哪个版本引入的，CHANGELOG 里查不到（只在源码里）—— 即"5.1.6 到底有没有这条告警"**无法从现有资料确认**。

### 6.4 升级步骤（👤 你执行；AI 不碰编辑器）

1. **先做一次 git 检查点**（这样升级改了什么都由 git 精确告诉我）：
   ```powershell
   cd "E:\U3D Projects\0_MyFile\3D联网战斗Demo"
   git add --dry-run .        # 确认无 Library/、无付费插件
   git add .gitignore Docs/ DeepSeekOutput/ Client/
   git commit -m "chore(m0): Unity 升级前检查点（2022.3.17f1c1 + A* 5.4.7）"
   ```
2. Unity Hub（`D:\SOFT\Unity Hub\Unity Hub.exe`）→ **Installs → Install Editor → Archive**
   → 选 **2022.3 系列 ≥ 2022.3.21**（建议直接取 2022.3 最后一个版本，含 Unity 2025-09 那批安全修复）
   → **务必勾选 `Windows Build Support (IL2CPP)`**
3. **关闭**当前工程 → 用新编辑器打开 `E:\U3D Projects\0_MyFile\3D联网战斗Demo\Client`
4. 首次打开会做资源升级，**等它跑完**（可能几分钟，期间别点）
5. 把 Console 内容与 `git status` 发我

> **磁盘**：升级前 C 剩 31.6 GB / D 剩 65.1 GB / E 剩 51.7 GB。编辑器 + IL2CPP 模块约需 8~11 GB。
> 本机实际做法：Hub 里设了**副安装路径** `D:\SOFT\Unity\Hub\Editor`（配置在 `%APPDATA%\UnityHub\secondaryInstallPath.json`），
> 所以新旧两个编辑器**分处两地**：新版在 `D:\SOFT\Unity\Hub\Editor\2022.3.62f3c1`，旧版仍在 `C:\Program Files\Unity\Hub\Editor\2022.3.17f1c1`。
