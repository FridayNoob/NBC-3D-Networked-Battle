## 二、分组策略（`YOO-02` 的落地）

需求原文的三条：**① 按模块（`ui`/`hero`/`monster`/`scene_battle`）② 按逻辑单元（同角色模型+材质+动画同包）③ 公共依赖单独成包（`shared`）**。

### 2.1 组清单（目标形态）

| 组名 | 收集路径 | 打包规则 | 地址规则 | 为什么这么分 |
| --- | --- | --- | --- | --- |
| `shared` | `Assets/_Project/SharedAssets` | `PackDirectory` | **`AddressByFileName`** | **公共依赖单独成包**（需求③）。被多个包引用的资源（通用材质/Shader/字体）放这里，避免被复制进每个包 |
| `config` | `Assets/_Project/Configs` | `PackDirectory` | **`AddressByFileName`** | 配置 SO（C 组产物）。**小、启动必读、且会热更** —— 单独成包最划算 |
| `ui` | `Assets/_Project/Art/UI` | `PackDirectory` | `AddressByFileName` | 按模块（需求①） |
| `hero` | `Assets/_Project/Art/Hero` | **`PackDirectory`**（每个角色一个子目录） | `AddressByFileName` | **按逻辑单元**（需求②）：一个角色的 模型+材质+动画 放同一目录 → 同一个包，切换角色时只加载一个包 |
| `monster` | `Assets/_Project/Art/Monster` | 同上 | `AddressByFileName` | 同上 |
| `scene_battle` | `Assets/_Project/Scenes/Battle` | `PackDirectory` | `AddressByFileName` | **场景也走 YooAsset**（`YOO-08`），保证被热更覆盖 |
| `scene_dev` | `Assets/_Project/Scenes/Dev` | `PackDirectory` | `AddressByFileName` | 调试场景（如 `PerfHudDebug`）。**单独一组**，免得把调试场景打进正式内容包 |

> 📌 **`hero` / `monster` 的"按逻辑单元"靠目录约定实现**：`Art/Hero/<角色名>/…`。
> 于是"加一个角色 = 加一个目录"，规则不用改。**目录约定就是分组规则**。

### 2.2 ⚠️ "无重复资源"（`YOO-02` 的验收）到底靠什么

**这一条必须讲清楚，否则验收会变成碰运气。**

AssetBundle 时代的经典坑是"同一个资源被两个包引用 → 被打进两个包 → 包体翻倍"。
YooAsset 的处理方式是：**资源归属由"哪个收集器收它"决定**，而不是"谁引用了它"。
由此推出两条可操作的规则：

| # | 规则 | 不遵守的后果 |
| --- | --- | --- |
| 1 | **收集路径必须互不重叠**（一个资源只能被一个收集器命中） | 归属不确定：改一次收集器顺序，资源就可能换包 → **同一资源出现在两个包里** |
| 2 | **被多处引用的资源要主动收进 `shared`**，且**不要在别的组里再收一次** | 依赖被打进每个引用它的包 → 包体随引用数线性增长 |

⚠️ **诚实标注**：上面两条里，"路径不重叠"是**可以直接检查的事实**（看收集器列表）；
而"YooAsset 遇到重叠收集时到底怎么归属"我**没有在本机验证过**（没打过包）。
所以操作单里把这件事排成**第一次打包必须核对的一项**（见 §7 第 6 步），
而不是当成已知结论写死。

**验收方法（可执行）**：打包报告里检查"**同一个资源路径只出现在一个 Bundle 里**"（§六）。

## 三、打包参数（`YOO-04`）

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 压缩方式 | **`LZ4`** | 需求点名。LZ4 解压快、包体略大；对"要频繁加载的小包"比 LZMA 更合适 |
| **TypeTree** | **关闭**（`DisableWriteTypeTree`） | 包体显著变小。⚠️ **代价**：失去跨 Unity 版本兼容 —— 换引擎版本必须重打全部包。本机 Unity 版本已冻结（`2022.3.62f3c1`），可以接受 |
| `AppendHash` | **开启** | 文件名带哈希 → 内容变则文件名变 → **CDN 缓存不会拿到旧包**（这是热更最容易出错的地方） |
| 构建模式 | 首次 **`ForceRebuild`**；之后 **`IncrementalBuild`**（`YOO-06`） | 需求要求对比"全量 vs 增量"耗时 |

> ⚠️ **一个必须先想清的取舍**：关 TypeTree 之后，**同一个包不能被不同 Unity 版本加载**。
> 这对"客户端版本与热更包必须匹配"是**好事**（不匹配就加载失败，而不是静默出错），
> 但要求发版流程把"引擎版本"也当成版本号的一部分。记在 §8。

## 五之二、⚠️ "运行模式"怎么切（2026-09-22 读源码更正）

**它不是 Editor 窗口里的开关** —— 这一点我第一版写错了（写成"在 Builder 窗口里选 OfflinePlayMode"）。
3.0.5 的真实情况是：**运行模式是初始化时传进去的参数**。

| 模式 | 代码 | 现状 |
| --- | --- | --- |
| `EditorSimulate`（日常开发） | `await AssetManager.Instance.InitializeAsync(AssetRuntimeMode.EditorSimulate)` | ✅ 已实现 |
| **`Offline`（读内置包）** | `…InitializeAsync(AssetRuntimeMode.Offline)` | ✅ 已实现（`OfflinePlayModeOptions` + `CreateDefaultBuiltinFileSystemParameters()`） |
| `Host`（热更） | `…InitializeAsync(AssetRuntimeMode.Host)` | ⚠️ **明确抛异常**，M5 才实现 |

⚠️ **实测缺口**：全工程搜 `InitializeAsync(` —— **只有测试在调**（`YooAssetAdapterSmokeTests` 与各 EditMode 测试）。
**游戏里没有启动流程**，所以"想切 Offline 跑一次"当时没有入口。

**补的入口**：`Assets\_Project\Editor\AssetRuntimeBootstrapMenu.cs`

```
Tools → NBC → 资源 → ① EditorSimulate 模式（日常开发）
Tools → NBC → 资源 → ② Offline 模式（读内置包）
```

用法：**先进播放模式** → 点菜单。它会打印：用的哪个模式、初始化是否成功、
**试加载 `HeroConfig` 的结果** —— 于是"Offline 通没通"当场就有答案。

> 📌 这也顺带暴露一个 **M3 要补的东西**：真正的**游戏启动流程**（谁负责初始化资源、加载 Canvas、进首个场景）。
> 现在这一步是"靠菜单手动点"，M3 要把它做成一条正式的启动链。

## 六、打包报告（`YOO-07` / B5）

**报告必须入库**（它才是"M5 优化的基线"），建议落在 `Docs\资源打包报告.md`（每次打包追加一节）。

### 6.1 必含的数字（缺一不可）

| # | 指标 | 为什么要它 |
| --- | --- | --- |
| 1 | **总包数 / 总大小** | 基线 |
| 2 | **最大包（名字 + 大小）** | 一个巨大的包通常意味着"该拆的没拆" |
| 3 | **每个组 → 包数 / 大小** | 一眼看出哪个模块最重 |
| 4 | **重复资源检查结果**（同一资源是否只在一个包里） | `YOO-02` 的验收 |
| 5 | **全量 vs 增量耗时**（第二次打包） | `YOO-06` 的验收 |
| 6 | **版本号 + 打包时间 + 引擎版本** | 否则数字没法对比（换版本后包体本来就变） |
| 7 | 参考基线：**`IL2CPP` 出包 76.5 MB**（`Docs\09` §三） | 内容包体积要和"整个包体"放在一起看 |

### 9.2 ⚠️ 我的操作单**漏了关键一步**：`BundledCopyOption`

**现象**（你贴的报错）：

**根因（读源码确认）**：

| 证据 | 位置 |

| 选项 | 含义 | 建议 |
| --- | --- | --- |
| **`ClearAndCopyAll`** | **清空后**复制全部 | ✅ **首次/干净验证选它** |

| `ClearAndCopyByTags` / `OnlyCopyByTags` | 按 Tag 复制（配合 Tag 输入框） | 首包资源分级时才用 |

### 9.4 ⚠️ 怎么排除它（读完收集器源码后的三个办法。**注意：内置规则做不到**）

YooAsset 3.0.5 的收集器结构（源码 `BundleCollector.cs` / `BundleCollectorPackage.cs`）：

| 层级 | 字段 | 说明 |
| --- | --- | --- |
| 包（Package） | **`IgnoreRuleName`** | **包级**忽略规则，默认 `NormalIgnoreRule`（按**扩展名**忽略） |
| 组（Group） | 若干 Collector | —— |
| 收集器（Collector） | `CollectPath` / `CollectorType` / **`FilterRuleName`** / `PackRuleName` / `AddressRuleName` | **按目录递归收集** |

内置的过滤规则只有这些（`DefaultAssetFilterRule.cs`）：
`CollectAll` / `CollectScene` / `CollectPrefab` / `CollectSprite` / `CollectShader` / `CollectShaderVariants`。
内置的忽略规则只有：`NormalIgnoreRule` / `RawFileIgnoreRule`（都按扩展名）。

> 📌 **所以结论是：内置规则里没有"排除某个子目录"这一条。**
> 而收集器是**按目录递归**的 —— 父目录被收，子目录就跑不掉。
> 这就是为什么内置 UI 里**找不到"排除 Design"的开关**。

三个可行办法：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A（推荐）把 Design 挪出 `Assets`** | CSV 属于**策划的输入**、不是 Unity 资源。挪到仓库根 `Configs/Design/`，Cli 的 `--source` 指过去 | ✅ **已落地（2026-09-22）**：CSV 已 `git mv` 到 `Configs/Design/`（`.meta` 随行，历史保留为 rename），旧文件夹的 meta 已清；**实测从新位置跑生成 = 3 张表 / 12 个文件 / 退出码 0**。零 YooAsset 代码 |
| **B 自定义 `IAssetIgnoreRule`** | 在 `NBC.Editor`（它本来就是 Editor 程序集）里写一个实现 `IAssetIgnoreRule` 的类，排除 `Design/*.csv`；YooAsset 会**自动发现**它并出现在包的"忽略规则"下拉里 | ✅ 不用挪文件；<br>⚠️ 它是**包级**的（会作用于整个 `DefaultPackage`）—— 排除 `.csv` 本身是安全的（CSV 不该进任何包）；<br>代价：多一个 YooAsset 扩展类 |
| C 给 Design 单独加 collector 过滤 | 需要一个"什么都不收"的过滤器 —— 内置没有，还是要写自定义 `IAssetFilterRule` | ❌ **等价于方案 B 但更绕**，不选 |

**我的建议：A**。理由是分层的：**策划的表格本来就不该住在 `Assets/` 里**
（`Assets/` 是"运行时资源"的地盘；现在它被收进包，正是这个错位的症状）。
B 只是把症状压住。

> ⚠️ 顺带说明：`Docs\17` §九 当初把 `Design\` 放在 `Assets` 内，图的是"Cli 与导入器就近读写"。
> 现在实测发现它会**被收集器收进包** —— 所以那条目录约定要改，属于"按实测回改规范"。

### 9.5 ⚠️ "增量打包怎么设置" —— **不用设置，3.0.5 默认就是增量**

**先说结论**：**3.0.5 的 Builder 里没有"增量 / 全量"这个下拉框**。我上一版操作单第 8 步写"选 `IncrementalBuild`"是**错的**（这是本会话第 4 次"凭印象写操作"）。

**源码证据**：

| 证据 | 位置 | 说明 |
| --- | --- | --- |
| `buildParams.UseCache = true;` | `ScriptableBuildParameters.cs:109` | **SBP 的构建缓存始终开启** → 增量是默认 |
| "除非设置 `ForceRebuildAssetBundle` 标记，否则会进行增量打包" | `LegacyBuildParameters.cs:45`（源码注释） | 旧管线的同样语义 |
| `EBuildMode` / `BuildMode` / `ForceRebuild` 在 Builder 里**搜不到** | 整个 `Editor/BundleBuilder` grep | 只有注释里出现，**没有这个枚举/选项** |
| **`ClearBuildCacheFiles`（默认 `false`）** ← **这个才是相关开关** | `BuildParameters.cs:58` | `TaskPrepare_SBP.cs:22` 里 `if (ClearBuildCacheFiles) { 清缓存 }` |

所以：

| 你想干什么 | 怎么做 |
| --- | --- |
| **增量打包** | **什么都不用做**（默认就是）。报告 `Summary` 里的 `ClearBuildCacheFiles` 会是 `False` |
| **强制全量重建** | 勾上 **`ClearBuildCacheFiles`**（窗口里那个 toggle），或删掉输出目录，或换版本号 |

**那么"增量到底生效了没有"怎么验？**

⚠️ **诚实说一句**：我们当前只有 **4 个包 / 126 KB** —— 全量与增量的耗时**可能都是几秒**，
**耗时对比在这个体量下很可能测不出差异**。所以 `YOO-06` 的验收我建议改成两条：

| 判据 | 怎么看 |
| --- | --- |
| ① **耗时**（`YOO-06` 原文要求） | 对比两次 `.report` 的 `BuildSeconds`（`Summary` 里就有） |
| ② **缓存是否命中**（更可信） | 看 `OutputCache\buildInfo.log` 的时间戳与内容是否变化；以及第二次构建时 `.bundle` 文件的**修改时间没变**（说明没重新生成） |

> 📌 **如果 ① 没差异、② 显示命中** —— 那结论就该写成"**增量生效，但本量级下耗时不可测**"，
> **而不是**"增量没生效"。**判据选错会得出相反的结论**（W9 的老教训）。
