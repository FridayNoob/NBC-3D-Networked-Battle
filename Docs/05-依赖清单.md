### 2.1 为什么 protobuf-net 选 3.2.30 而不是更新的 3.4.x

| 版本 | `netstandard2.1` 目标 | 说明 |
| --- | --- | --- |
| **3.2.30（选用）** | ✅ 有，且**该目标不依赖 `System.Reflection.Emit`** | 对 IL2CPP 最友好（`Reflection.Emit` 在 AOT 下不可用） |
| 3.4.x（最新） | 未核实 | 新版可能改动依赖与 API；本项目**不需要新特性**，"能打包运行"比"用最新版"重要 |

> 这属于需求文档 §5.3 的"版本冻结原则"：**M0 阶段锁定一个已验证可用的版本，比追新更有价值。**

### 2.2 ⚠️ Unity 侧不是装 NuGet，而是放 DLL —— 且必须放齐依赖

> ✅ **本表已于 2026-09-20 实测校正**：实际需要 **4 个 DLL**（此前误写为 3 个）。
> 判据不是猜包名，而是**读 DLL 自己的程序集引用元数据**
> （`Assembly.ReflectionOnlyLoadFrom` + `GetReferencedAssemblies`）。真实引用链：

```
protobuf-net.dll              引用 → protobuf-net.Core, System.Collections.Immutable
protobuf-net.Core.dll         引用 → System.Collections.Immutable
System.Collections.Immutable  引用 → System.Memory, System.Runtime.CompilerServices.Unsafe
```

| DLL | 来自 | 必需? | 说明 |
| --- | --- | --- | --- |
| `protobuf-net.dll` | protobuf-net 3.2.30（`lib/netstandard2.1`） | ✅ 必需 | 主程序集（程序集名 `protobuf-net` v3.0.0.0） |
| `protobuf-net.Core.dll` | protobuf-net.Core 3.2.30（`lib/netstandard2.1`） | ✅ 必需 | 3.x 拆出的核心程序集（v3.0.0.0） |

| `System.Runtime.CompilerServices.Unsafe.dll` | System.Runtime.CompilerServices.Unsafe **6.0.0**（`lib/netstandard2.0`） | ✅ 必需 | **Unity 不提供**它；它是 `Immutable` 的依赖（v6.0.0.0） |

**判断某个依赖要不要放的方法**（可复用）：

```powershell
# Unity 的 shim 目录：这里已有的程序集，Unity 会提供，不要重复放
$shim = "C:\Program Files\Unity\Hub\Editor\<版本>\Editor\Data\NetStandard\compat\2.1.0\shims\netstandard"
Get-ChildItem $shim -File | Where-Object { $_.Name -match 'Immutable|Memory|Buffers|Vectors|Unsafe' }
# 实测（2022.3.17f1c1）：有 Memory/Buffers/Numerics.Vectors，【没有】Immutable、没有 Unsafe
# 复核（2026-09-20，升级到 2022.3.62f3c1 后重跑）：文件数依旧 103，结论【完全一致】
#   → 4 个 DLL 的设置（C7~C7c）在新引擎下依然必要，不需要改动
```

**踩坑记录（实际发生过的报错）**：只放 3 个 DLL 时，Unity Console 报三段**层层上冒**的错误：

```
System.Collections.Immutable.dll ... Unable to resolve reference 'System.Runtime.CompilerServices.Unsafe'   ← 根因
protobuf-net.Core.dll ... Reference has errors 'System.Collections.Immutable'                              ← 被拖累
protobuf-net.dll ... Reference has errors 'protobuf-net.Core'                                              ← 被拖累
```

> **判据：从"最底层那条报错"开始修**，而不是从第一条。补上 `Unsafe` 后三段一起消失。

> **`link.xml` 必须同时声明 `protobuf-net`、`protobuf-net.Core`、`System.Collections.Immutable`**
> —— 已写入 `ClientStaging/link.xml`（程序集名均经元数据实测确认）。

**取 DLL 的快捷方式**：

```powershell
# 在项目内建临时目录做还原（放项目里便于复核，也便于 AI 读取）
$work = "E:\U3D Projects\0_MyFile\3D联网战斗Demo\Server\_nupkg-verify"
Remove-Item $work -Recurse -Force -EA SilentlyContinue
New-Item -ItemType Directory -Force -Path $work | Out-Null
Set-Content "$work\probe.csproj" @'
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup><TargetFramework>netstandard2.1</TargetFramework></PropertyGroup>
  <ItemGroup>
    <PackageReference Include="protobuf-net" Version="3.2.30" />
  </ItemGroup>
</Project>
'@
dotnet restore "$work\probe.csproj" --packages "$work\packages"

# 取出 4 个 DLL（注意：后两个在 netstandard2.0 目录里！）
$dst = "E:\U3D Projects\0_MyFile\3D联网战斗Demo\Client\Assets\ThirdParty\ProtobufNet"
New-Item -ItemType Directory -Force -Path $dst | Out-Null
Copy-Item "$work\packages\protobuf-net\3.2.30\lib\netstandard2.1\protobuf-net.dll" $dst -Force
Copy-Item "$work\packages\protobuf-net.core\3.2.30\lib\netstandard2.1\protobuf-net.Core.dll" $dst -Force
Copy-Item "$work\packages\system.collections.immutable\7.0.0\lib\netstandard2.0\System.Collections.Immutable.dll" $dst -Force
Copy-Item "$work\packages\system.runtime.compilerservices.unsafe\6.0.0\lib\netstandard2.0\System.Runtime.CompilerServices.Unsafe.dll" $dst -Force
```

> ⚠️ **注意目标框架不统一**：主包两个取 `netstandard2.1`，后两个只能取 `netstandard2.0`
> （因为 `System.Collections.Immutable 7.0.0` **没有 2.1 目标**）。这是正常且正确的组合。

把筛选出的 `protobuf-net.dll` / `protobuf-net.Core.dll` / `System.Collections.Immutable.dll`
复制到 `Client/Assets/ThirdParty/ProtobufNet/` 即可。

## 三·补 ⚠️ NuGet 还原在本机被阻塞（2026-09-16 实测发现）

**这是 M1 起会阻塞依赖引入的真实环境问题，必须在 M0 收关前解决。**

### 实测现象

在本机用 `netstandard2.1` 探针工程还原 `protobuf-net 3.2.30`，两次都失败：

```
error NU1301: 无法加载源 https://api.nuget.org/v3/index.json 的服务索引。
error NU1301:   The SSL connection could not be established, see inner exception.
error NU1301:   Authentication failed, see inner exception.
error NU1301:   安全包中没有可用的凭证
```

换成国内镜像源 `https://nuget.azure.cn/v3/index.json` **同样失败**（同一 SSL/凭证错误）。

### 分层诊断结果（用 `Tools\Test-Network.ps1` 实测）

"SSL 失败"这个报错不足以定位原因，因此做了分层探测：

| 层 | 结果 |
| --- | --- |
| DNS 解析 | ✅ 正常（baidu / nuget.org / nuget.azure.cn 三个目标都解析出 IP） |
| TCP 443 | ✅ 可达 |
| **TLS 握手 / HTTP** | ❌ **三个目标全部失败**，内层错误「安全包中没有可用的凭证」 |
| 本地代理监听 | ❌ **无任何端口在监听** |
| 代理进程 | ⚠️ `clash-verge-service`(6284)、`verge-mihomo`(39980) **在运行**，但代理未启用（`~/.config/clash/config.yaml` 里 `mixed-port: 7890`，而 7890 无监听） |
| 系统代理开关 | `ProxyEnable = 0`（关闭）；`ProxyServer = 127.0.0.1:7897`（配置但未启用）；WinHTTP 为"直接访问" |
| 全局 NuGet 缓存 `~\.nuget\packages` | 存在，但**只有 9 个 SDK 运行时包**，无任何业务依赖 |
| 已配置的第二个源 "Microsoft Visual Studio Offline Packages" | 本地离线目录里同样没有这些包 |

### 两个可能原因（需在沙箱外验证才能区分）

| # | 原因 | 判据 |
| --- | --- | --- |
| 1 | **AI 运行环境的网络沙箱**：从子进程发出的所有直连 HTTPS 都失败（实测连 `https://www.baidu.com` 都失败） | 若你在**普通 PowerShell** 里跑 `Tools\Test-Network.ps1` 能成功，则此原因成立 |
| 2 | **系统代理未开启**：Clash Verge 在跑但代理功能关闭 | 若沙箱外也失败，但打开系统代理后成功 |

> **必须在沙箱外的普通 PowerShell 里跑一次 `Tools\Test-Network.ps1`** —— 那才是 M1 的真实条件。

### 为什么这很重要

1. **服务端骨架目前能编译**（M0 阶段刻意没引任何 NuGet 包）—— 但到 M1 一打开 `PackageReference` 就会失败
2. **`dotnet build` 现在能过，不代表依赖问题不存在** —— 它是一个被推迟的阻塞点
3. 用户在 M15 手册 D17 需要 IL2CPP 出包，Unity 侧的 DLL 也需要先能拿到

### 解决方向（按推荐顺序，需要你选择）

| # | 方案 | 说明 | 成本 |
| --- | --- | --- | --- |
| **1** | **打开 Clash Verge 的系统代理**，然后在**普通 PowerShell**里跑 `Tools\Test-Network.ps1` 复验 | 最直接。脚本会自动检测端口并做"直连 vs 代理"对比 | 极低 |
| **2** | **为本次会话设置代理环境变量后重试还原** | `$env:HTTPS_PROXY="http://127.0.0.1:7890"`（或 `dotnet restore -p:HttpsProxy=...`） | 低 |
| **3** | **用 Visual Studio 的 NuGet 包管理器图形界面还原** | VS 用自己的 TLS 栈与 Windows 代理设置，可能不受此限 | 低 |
| **4** | **手动下载 `.nupkg` 并解压取 DLL** | `.nupkg` 就是 zip，改后缀解压取 `lib/netstandard2.1/*.dll`。**服务端也用同样办法手工放置** | 中（要逐个包做） |
| **5** | 配置可用的私有/离线源 | 公司源或本地目录源 | 中 |

### M0 阶段的影响与结论

| 结论 | 说明 |
| --- | --- |
| ✅ **不阻塞 M0 收关** | M0 的服务端骨架不含任何 NuGet 包；Unity 侧 DLL 是手工放置，不依赖 dotnet restore |
| ⚠️ **必须在 M1 开工前解决** | M1 要引入 Dapper / MySqlConnector / protobuf-net / xUnit / NPOI |
| 📌 **已记入 M0 验收清单** | 见 `Docs\10-M0手动操作手册.md` §11 的附加检查项 **N-1** |

> **需要你做的**：在**沙箱外的普通 PowerShell** 里执行
> `powershell -NoProfile -ExecutionPolicy Bypass -File Tools\Test-Network.ps1`，
> 把输出贴给我。有了它就能确定是沙箱限制还是代理未开，再选上面哪个方案。
> 如果最终只能走方案 4（手动 `.nupkg`），我会给你一份"需要哪些包、从哪取哪个 DLL"的精确清单 ——
> 好在 **Unity 侧本来就必须手工放 DLL**，所以这条路对客户端影响不大，主要是服务端会麻烦一些。
