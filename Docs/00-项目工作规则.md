### 代码书写附加条款（2026-09-16 新增，源于一次真实缺陷）

| # | 条款 | 原因 |
| --- | --- | --- |
| **W1** | **`.csproj` / `.props` / `.xml` 等 XML 文件的注释内禁止出现连续两个连字符 `--`** | XML 规范硬性规定。用 `------` 画分隔线会导致 **工程文件直接无法解析**（`MSB4025` / `not well-formed`）。分隔线请改用 `=======` 或 `~~~~~~~` |
| **W2** | 生成文件后**必须做一次只读合法性校验**再交付 | 本项目 M0 就靠这一步抓出了上面那个缺陷。校验方式：`[xml]` 解析、`json.load`、括号配平、编码/BOM 检查 |
| **W3** | **不要用 PowerShell 的 `Get-Content -Raw` 校验 UTF-8 中文文件** | 本机 PowerShell 默认按 GBK 解码，会把正常 UTF-8 文件读成乱码，造成"JSON 校验失败"之类的**误报**。校验中文文件请用 Python 显式 `encoding="utf-8"`，或 PowerShell 显式 `-Encoding UTF8` |
| **W3a** | ⚠️ **同一根因的第二个症状：`Get-Content` 连"行数"都是错的，`Select-String` 报的"行号"也不可信**（2026-09-22 实测）。<br>**实测数据**：`Docs\16-M1开工清单.md` 真实 **1488** 行（`[System.IO.File]::ReadAllLines` 与 ripgrep **一致**），而 `Get-Content` 报 **1094** 行 —— **静默吞掉 394 个换行**（内容同时还是乱码）。`Select-String` 同源，行号随之偏移。<br>**后果（W9 的又一次现形）**：我拿 `Select-String` 给的行号去**切一段文本**做"Markdown 表格完整性检查"，切到的是**完全不相干的段落**（`## 十一` 而不是 `§10.2.19`），于是那次校验**一个表格都没检查**，却报"0 问题" —— **假绿**。<br>**本环境下的正确读法**：`[System.IO.File]::ReadAllText/ReadAllLines($path, [System.Text.Encoding]::UTF8)`，或直接用编辑器的 `read` / `grep` 工具。**凡是要行号、要计数、要按行切段落，一律不用 `Get-Content` / `Select-String`**；后者只允许用于"看一眼大概内容"，且必须显式 `-Encoding UTF8` | 这是**静默**错误：不像 W3 那样一眼就是乱码，而是"看着像正常文本、数字却是错的"。**用错的行号去切片，校验会转向一个不相干的对象，而结果永远是"通过"** —— 比不校验更危险 |
| **W4** | 写文件一律 **UTF-8 无 BOM + LF** | 与规则 8 的编码安全一致；已有 GBK/带 BOM 文件按原编码回写 |
| **W5** | **`.gitignore` 写法的三条要点**（2026-09-20 用真实 git 仓库实测校正）：<br>① **`#` 只在行首是注释 —— `.gitignore` 不支持行尾注释**。写 `!**/Packages/   # 说明` 会让**整行**（含说明文字）变成一个永远匹配不到的取反模式，**静默失效、不报错**<br>② **需要忽略目录时，写「目录名 + 斜杠」**，例如 `Client/Library/`、`bin/`、`obj/`<br>③ **不要靠取反去救回被误伤的同名目录，正解是收窄作用域**：Windows 上 `core.ignoreCase = true`，`**/packages/` 会连 Unity 的 `Packages/` 一起忽略；把该规则放进 `Server\.gitignore`（该目录下没有 Unity 工程）即可，不需要 `!` | ① 是**静默失效**，最危险 —— 直到某天发现 Unity 的 `Packages/` 被忽略、工程拉下来跑不起来。③ 是"用作用域代替取反"，语义更清晰、不易出错 |
| **W5a** | ⚠️ **更正**：本条原写"`[Ll]ibrary/` 只匹配目录本身、目录内文件会被误提交"、"`**/bin/` 不如裸 `bin/` 可靠"—— **这两条结论都是错的**，2026-09-20 已用 `git check-ignore -v` 实测推翻。真实语义是：**已被忽略的目录，git 不会向下遍历**，所以目录内文件自动一并忽略；`[Ll]ibrary/` 与 `Library/`、`**/bin/` 与 `bin/` **都有效**。本项目仍统一用精确大小写的写法（`Client/Library/`、裸 `bin/`），理由是**可读性**，不是因为另一种写法有缺陷 | 错误结论会让人做无谓的"改写规则"工作，并误导后续排查。**规格说明要经得起实测检验** |
| **W6** | 改完 `.gitignore` 必须用**地面真值**验证，判据是「**这些文件最终会不会进仓库**」，而不是某条规则"看起来有没有写对"：<br>① 在临时目录 `git init` 一个最小仓库，摆出真实的目录骨架；<br>② **地面真值命令**：`git add --dry-run .`（列出"将被加入仓库"的文件）或 `git status --porcelain -uall`；<br>③ 逐个核对：该保留的**必须出现**，该忽略的**必须不出现**。<br>⚠️ **不要只依赖 `git check-ignore -v`**：它会**把"被取反规则命中"的路径也打印出来且退出码为 0**，容易被误读成"已忽略" | 2026-09-20 一天之内**两次**验证翻车：先是用"自己写的模拟脚本"得出两条与真实 git 相反的结论（见 W5a）；改用 `git check-ignore -v` 后，又把 `.gitignore` 末尾 `!Server/**/*.csproj` 这类**取反保命规则**误判成"被忽略"。换成 `git add --dry-run` 后，22 项保留 + 17 项忽略全部符合预期。**判据选错，比不验证更危险** |
| **W7** | **`.ps1` 脚本的编码分两种情况**（见下）：**① 正文全 ASCII** → 无 BOM；**② 必须含非 ASCII**（如中文文件名/路径）→ **必须 UTF-8 with BOM** | 本机是 **Windows PowerShell 5.1**，它**按 ANSI(GBK) 读取无 BOM 的脚本源码**；含中文的无 BOM `.ps1` 会因字符串字面量被破坏而报一堆 `Unexpected token`，而文件本身是合法 UTF-8（普通编辑器看完全正常），**排查成本极高**。详见 `Tools/README.md` |
| **W7a** | **`.csproj` / `.props` / `.xml` 等由 MSBuild 读取的文件不受此限** | MSBuild 按 UTF-8 读，无 BOM 即可 |
| **W7b** | ⚠️ **本项目所有 `.ps1` 都不能含非 ASCII —— 除非该路径是运行所必需的** | 2026-09-16 实测：`Check-DocLinks.ps1` 需要真实中文路径 `Docs\01-项目需求文档.md`，此时**必须带 BOM**。写完后用下面命令自检 |

| **W8** | 若某个脚本/文件**必须**含非 ASCII（如中文注释的 `.cs`），需确认其**消费方**用什么编码读取 | 例如 `.cs` 由 Roslyn/Unity 按 UTF-8 读，所以无 BOM 也没问题；但 `.ps1` 由 PowerShell 引擎按 ANSI 读，就必须带 BOM。**判据是"谁来读"，不是"我写了什么"** |
| **W9** | **自研校验器/模拟器必须先被校验**：① 能用官方工具时**优先用官方工具**（真实的 git / `dotnet build` / 编译器）；② 确实必须自己写时，先用**一个已知答案的用例**校准它，通过了再去判定别的文件；③ 校验器给出"异常结论"时，**先怀疑校验器**，别急着改被检查的文件；④ **选对判据**比"有没有验证"更重要 —— 要验证的应该是**最终效果**（文件会不会进仓库），而不是中间产物"看起来对不对" | 2026-09-20 真实事故：一个自己写的路径模拟脚本给出两条与真实 git 相反的结论，被当成事实写进了 `.gitignore` 注释；随后 `git check-ignore -v` 又把取反保命规则误判为"已忽略"。**"验证工具"本身是代码，也会有 bug；把它的输出当真理是最容易犯的错** |

### PowerShell 脚本编码自检（W7 系列，建议每次改完脚本就跑）

```powershell
# 对每个 .ps1 检查：非 ASCII 字节数 与 BOM 状态
Get-ChildItem Tools\*.ps1 | ForEach-Object {
    $b = [System.IO.File]::ReadAllBytes($_.FullName)
    $na = ($b | Where-Object { $_ -gt 127 }).Count
    $bom = ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)
    $verdict = if ($na -eq 0 -and -not $bom) { 'OK  (pure ASCII, no BOM)' }
               elseif ($na -gt 0 -and $bom)  { 'OK  (has non-ASCII, BOM present)' }
               else                          { 'BAD (would be mis-decoded by PowerShell)' }
    "{0,-24} 非ASCII={1,-4} BOM={2,-6} {3}" -f $_.Name, $na, $bom, $verdict
}

# 再检查语法（0 个错误才算通过）
Get-ChildItem Tools\*.ps1 | ForEach-Object {
    $e = $null
    $null = [System.Management.Automation.Language.Parser]::ParseFile($_.FullName, [ref]$null, [ref]$e)
    "{0,-24} 语法错误数 = {1}" -f $_.Name, $(if ($e -and $e.Count) { $e.Count } else { 0 })
}
```

**判据（两条必须同时成立）**：

| 非 ASCII 字节数 | BOM | 结论 |
| --- | --- | --- |
| 0 | 无 | ✅ 正确（回归无 BOM 的统一约定） |
| \> 0 | **有** | ✅ 正确（PS 5.1 能正确解码） |
| 0 | 有 | ➖ 可接受（但不统一） |
| **\> 0** | **无** | ❌ **脚本会崩**，必须补 BOM |

补 BOM 的一行命令：

```powershell
$p = "Tools\Check-DocLinks.ps1"
$t = [System.Text.Encoding]::UTF8.GetString([System.IO.File]::ReadAllBytes($p))
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))
```

### 代码改动边界（**W10**，2026-09-21 由项目负责人明确）

> 原文：**"后续要尽量避免修改框架代码或者插件源码"**。

| 对象 | 要求 | 理由 |
| --- | --- | --- |
| **第三方插件 / 包源码**（YooAsset、xLua、Google.Protobuf…） | 🚫 **一律不改** | 改了就没法升级；别人 clone 下来行为和包不一致；出问题时分不清是自己写错还是包被改过 |
| **已收关框架模块的既有代码**（测试全绿 + 已留档） | ⚠️ **尽量避免改**。优先"**新增**"（新文件 / 新模块 / 新程序集），而不是"**改动**" | 每改一次都要重跑全部测试；已验收的东西被动过，就得**重新证明一遍** |
| **框架的公共接口**（ADR 里冻结过的） | ⚠️ 改之前**必须先问** | 见 §五「已冻结的关键技术决策」 |

**「新增」不算「修改」**：加新文件、新模块、新程序集都属于新增，**不受本条限制**。

**确实非改不可时，四件事一件都不能少**：

1. 先说清**为什么非改不可**（不能是"这样写更顺手"）

## 二之二、规则 15 的落地：以培养用户能力为目标（2026-09-16 新增）

### 规则原文

> 本项目的目的也包括教会用户相关操作和知识以及技能，提升用户开发能力，**尽量避免使用一键脚本，即使它能够提高工作效率**。

### 15.1 目标定位（写在最前面，因为它裁决一切冲突）

| 目标 | 相对优先级 |
| --- | --- |
| **提升用户的开发能力（操作 / 知识 / 技能）** | **高** |
| 项目交付速度与自动化程度 | 低（为前者让路） |

**冲突裁决**：当"某个做法能提高效率"与"该做法会让用户少学到东西"冲突时，**选择前者（教学优先）**。
这与规则 14（边做边教）方向一致，但更强硬：规则 14 管"讲不讲原理"，规则 15 直接管"**要不要替用户做**"。

### 15.2 「一键脚本」的判据（什么禁止、什么允许）

判据不是"是不是脚本"，也不是"用没用 PowerShell"，而是：

> **这个工具是在"替用户完成流程"，还是在"帮用户观察与判断"？**
> 把**多个步骤打包成一次执行**、使中间动作与中间结果不再出现在用户眼前 → **属于禁止的一键脚本**。
> 只是**输出信息供用户判断**、不代替用户做任何修改动作 → **不属于**，可以保留。

| 类别 | 例子 | 判定 |
| --- | --- | --- |
| ❌ **一键式流程自动化** | 建目录 + 搬文件 + 初始化 Git + 建库"一次跑完" | **禁止**。用户看不到中间动作，也不知道每步在做什么 |
| ❌ 把多步配置合成一个"Setup"脚本 | 装包 + 改设置 + 生成配置一把梭 | **禁止** |
| ⚠️ 便捷别名/包装（把一条命令包成短命令） | 如 `mk` 代替 git 三步 | **不鼓励**。要写就得讲清它展开了什么，且优先直接给原命令 |
| ✅ **只读诊断工具** | 分层探测网络（DNS/TCP/TLS/代理）并打印结果 | **允许**。用户必须自己读结果、自己判断、自己动手修 |
| ✅ **只读验证工具** | 读 DLL 元数据核对程序集名、比对配置条目 | **允许**。它只是把"结论"呈现给用户，不改任何东西 |
| ✅ **生成对照物** | 打印一份应放的 DLL 清单供手工放置 | **允许**。放置动作仍由用户完成 |

> **一句话**：**观察与判断可以自动化，动手与理解不可以。**

### 15.3 今后每一步对话的教学要求

每涉及一个需要用户动手的步骤，必须同时给出：

| # | 要给的东西 | 说明 |
| --- | --- | --- |
| 1 | **逐步操作** | 精确到菜单路径 / 按钮名 / 命令原文（规则 4 已要求） |
| 2 | **每步在干什么** | 一句白话，说明这一步改变了什么 |
| 3 | **验证方式** | 怎么知道成功了（看什么信号、什么数值） |
| 4 | **失败时先看什么** | 常见现象 → 可能原因 → 判据（不只给结论） |
| 5 | **为什么这样做** | 设计权衡与替代方案，不堆术语 |
| 6 | **让用户决策** | 列**选项 + 判据 + 后果**，由用户拍板，并记录其选择与理由 |

**禁止的做法**：说"我已经帮你搞定了"就结束；或在用户没看懂的情况下继续往下推进。

#### 15.3.1.1 ⚠️「说人话」硬约束（**2026-09-21 由项目负责人第二次指出**）

> 原文：**"教我的时候尽量说人话，太多专业术语混在一起我看不懂了"**。
>
> ⚠️ **这是同一个问题的第二次**。第一次是 2026-09-20 的"我看不懂了"，
> 当时立的 §15.3.1 只写了"不许甩术语"，**没给可执行的判据** ——
> 于是我又用"术语堆叠 + 破折号套破折号 + 跨模块类比"讲了一遍 A8，负责人**再次没看懂**。
>
> **教训：光说"要讲清楚"没有用。必须给能当场自查、能当场判违规的硬规则。**

| # | 硬规则 | 我自己犯过的反例 |
| --- | --- | --- |
| 1 | **先讲具体场景，再讲道理。** 每节开头必须是"玩家做了什么 / 屏幕上发生什么" | A8 第①节我上来就讲"音效是高频、同构、可复用的东西" —— 这是**结论**，不是**场景** |
| 2 | **专业词可以随便用，但每个词第一次出现必须当场解释。** 解释要落在"它解决什么问题"或"打个比方"，不是背定义 | ⚠️ 我第一版**走偏了**：把"术语太多"理解成"禁用术语"，定了"一次最多 2 个新词"，结果讲得干巴巴、反而更难懂。**负责人 2026-09-21 纠正："说明的时候可以有专业词，但是要对专业词进行解释"** |
| 3 | **代码示例尽量给、越详细越好。** 宁可多贴几段真实代码，也不要一句抽象概括带过。每段代码旁边配一句话说它在干嘛 | ⚠️ 同上，我第一版给单个代码块定了"不超过 10 行"的上限 —— **纯属自缚手脚**。**负责人 2026-09-21 纠正："代码可以放，而且示例越详细越好"** |
| 4 | **一句话别塞三件事。** 破折号 / 括号里再套一个从句，读的人就断了 | "音效是高频、同构、可复用的东西 —— 恰好是对象池最典型的场景" |
| 5 | **跨模块类比可以用，但不能默认对方记得那个模块。** 要先一句话把被类比的东西说清 | A8 里我插了"顺手对照 A7：`InputActionId` 的 0 是合法索引…" —— 对方当时根本没在想 A7 |
| 6 | **多说"看得见的东西"**：屏幕上的数字、Console 里的字、能点的按钮、玩家的体感 | 我讲了半天"ABA 问题"，却没说"玩家会听到两首歌同时停" |
| 7 | **语言自然点**，像平常说话。别写成电报体，也别写成说明书。**"你""我""咱们"都能用** | ⚠️ 我第一版把句子砍得太短，读起来一句一顿像在下命令。**负责人 2026-09-21 纠正："语言不要太生硬"** |

**篇幅**：**不设硬上限**。考核指标不是"讲了多少行"，而是"讲完对方能不能复述"。
（我第一版定过"80 行以内"，结果为了压行数把话说得像电报 —— **已被负责人纠正**。）
但**每一段都要有用**：不要为了显得全面而堆砌，**也不要把该展开的细节压掉**。

**讲完的自查（必做，不许跳）**：让负责人回答两个问题 ——
**① 这东西是干嘛的？ ② 不修会怎样？** 答不上来 → **重讲，不许进下一个模块**。
（这比"你听懂了吗"有效：那个问题对方出于礼貌会说懂了。）

> **违反本节的判定方式**：把讲课里出现的**每一个专业词**圈出来，
> 逐个问一句"它**第一次**出现的地方，有没有当场解释？"
> —— 有没解释的，就是违规，回去补。

> **为什么写进规则**：2026-09-20 之前，我连续几个模块只交代码 + 甩文档，负责人直接说
> **"我看不懂了"**。规则 15 的原始条文其实已经覆盖这件事（"在用户没看懂的情况下继续往下推进"是被禁止的），
> 但**没有把"讲"绑定到"下一轮开工之前"这个时间点上**，于是就被效率压过去了。
> 现在把它变成**前置门**：讲完才开工。
