## 一、结论速览（TL;DR）

分界线**不是**"Unity 程序集用不了"（太粗），而是**精确的三层**：

| 分层 | 纯 .NET 进程里能否工作 | 实测证据 |
| --- | --- | --- |
| **纯托管数学**（`Vector3` / `Quaternion` / `Mathf`） | ✅ **能，结果完全正确** | `magnitude=5`、`Normalize=(0.6,0.8,0)`、`Mathf.Sqrt(16)=4` |
| **类型元数据**（反射拿 `Type`、看基类链） | ✅ **能** | `MonoBehaviour` 的基类链 `Behaviour → Component` 可完整读出 |
| **引擎对象与原生调用**（创建/访问对象、时间、生命周期、资源加载） | ❌ **不能** | `new GameObject()` / `go.name` / `Time.deltaTime` 全部抛异常 |

失败异常原文（**记住它**）：

```text
System.Security.SecurityException: ECall methods must be packaged into a system module.
```

> ⚠️ **它是运行时错误，不是编译错误**。引用 Unity 程序集**能编译通过**，
> 问题只在真正调用引擎的那一刻才炸 —— 所以"编译成功"不能用来证明"服务端能跑行为树"。

## 二、实验设计：为什么不直接引用 `BehaviorDesigner.Runtime.dll`

最初的方案（本文件的历史版本）是"在服务端工程里临时引用 Behavior Designer 的运行时 dll，看编译报什么错"。
实际执行时**改了做法**：

| 原因 | 说明 |
| --- | --- |
| M0 的 D8（导入 Behavior Designer）尚未完成 | 插件还没进工程，没有 dll 可引用 |
| **更重要：原方案不够根本** | 它测的是"**这个插件**能不能被引用"，结论会被插件版本影响；真正决定架构的是"**Unity 程序集**能不能在纯 .NET 进程里用"。后者与插件无关，结论更硬、更持久 |

于是**向下挖一层**：直接引用 Unity 自己的程序集，测出"托管代码 / 引擎原生"的精确分界。
这个实验**在任何装了 Unity 的机器上都能重跑**，且换插件版本也不失效。

> **收益**：结论从"某个插件不行"升级为"**一整类东西都不行，原因是 CLR 里没有 ECall 的内部实现**"。
> 这比原方案的面试价值更高。

## 三、可复现操作步骤

### 3.1 阶段 1：托管 / 原生分界（9 级探针）

工程已在 `Server\_unity-ref-probe\`（`probe.csproj` + `Program.cs`）。运行：

```powershell
cd "E:\U3D Projects\0_MyFile\3D联网战斗Demo\Server\_unity-ref-probe"
dotnet run
```

**预期**：退出码 `1`（这是**设计如此** —— 程序把"失败级别数 > 0"当作返回 1），
输出最后一行是 `失败级别数: 3 / 9`。

### 3.2 阶段 2：模块依赖闭包（引用一个模块会拖进几个）

阶段 1 的 `CoreModule` 只拖进 1 个模块，看不出成本。换 `IMGUIModule` 就能看到连锁。

最可靠的做法是**直接读程序集元数据**（而不是靠编译器报错去猜）：

```powershell
# 用 System.Reflection.Metadata 读 AssemblyRef 表并求传递闭包
# （完整脚本见 §五；一次写成小工程跑，比在 PowerShell 里反射加载可靠 —— 见 §六 坑 3）
```

实测结果：

| 起点模块 | Unity 侧传递闭包 | 数量 |
| --- | --- | --- |
| `UnityEngine.CoreModule` | CoreModule、SharedInternalsModule | **2** |
| `UnityEngine.IMGUIModule` | + InputLegacyModule、TextRenderingModule、TextCoreTextEngineModule、TextCoreFontEngineModule | **7** |
| `UnityEngine.AIModule` | AIModule、SharedInternalsModule、CoreModule | **3** |

**工程含义**：服务端引用任何一个 Unity 模块，`<Reference>` 都要把**整个闭包**补全，否则得到
`CS0012`（"类型在未引用的程序集中定义"）。
**这不是"多加一行 HintPath"的小事，而是"要拖进多少引擎代码"的成本。**

### 3.3 关于"还原"

**本次实验不需要还原任何东西** —— 因为做法改了：**没有**去改 `NBC.Server.Core.csproj`。
探针是**独立工程**，不在 `NBC.sln` 里，`dotnet build` 不会连带编译它。
（历史版本的"实验后必须删除 ItemGroup"一节因此作废。）

## 四、实测结果

### 4.1 阶段 1：9 级探针

| 级别 | 被测内容 | 结果 |
| --- | --- | --- |
| L0 | 纯 C# 基线（`1+1`） | ✅ 成功 |
| L1 | `Vector3` 运算、`Vector3.Normalize`、`Mathf.Sqrt` | ✅ 成功 |
| L2 | 反射获取 `GameObject` **类型** | ✅ 成功 |
| **L3** | **`new GameObject("probe")`** | ❌ 失败 |
| **L4** | **`go.name`（访问引擎对象属性）** | ❌ 失败 |
| L5 | `Component` 类型、`Object.IsAssignableFrom` | ✅ 成功 |
| L6 | `MonoBehaviour` 类型、基类链 | ✅ 成功 |
| L7 | `ScriptableObject` 类型 | ✅ 成功 |
| **L8** | **`Time.deltaTime`** | ❌ 失败 |

逐字输出：见 `Docs\01-项目需求文档.md` §5.4.6 ③。

### 4.2 为什么 9 级探针要用**反射**调用，而不是顺序调用

因为失败可能发生在 **JIT / 类型加载阶段**。顺序调用时，一次异常会中断后面所有级别，
就分不清"**是这一级失败**"还是"**因为上一级失败而没能跑到**"。
反射调用把每一级隔离开，异常被包在 `TargetInvocationException` 里，可以逐个定位。

### 4.3 为什么 `<Private>true</Private>` 不能省

```xml
<Reference Include="UnityEngine.CoreModule">
  <HintPath>C:\Program Files\Unity\Hub\Editor\2022.3.17f1c1\Editor\Data\Managed\UnityEngine\UnityEngine.CoreModule.dll</HintPath>
  <Private>true</Private>   <!-- ← 必须：把 dll 复制到输出目录 -->
</Reference>
```

如果只写 `<Reference>` 不带 `<Private>`，运行时只会得到
`FileNotFoundException: 找不到 UnityEngine.CoreModule`。
**那只能证明"我没把 dll 放过去"，证明不了任何关于 Unity 的事实。**
要让实验有意义，必须先让运行时真的能加载到它。

## 五、阶段 2 的完整测量脚本（可复制）

把下面内容存成临时 .NET 工程跑一次即可（**别用 PowerShell 的 `Assembly.LoadFrom`，原因见 §六 坑 3**）：

```csharp
using System.Reflection.Metadata;
using System.Reflection.PortableExecutable;

var dir = @"C:\Program Files\Unity\Hub\Editor\2022.3.17f1c1\Editor\Data\Managed\UnityEngine";
var index = Directory.GetFiles(dir, "UnityEngine.*.dll")
                     .ToDictionary(f => Path.GetFileNameWithoutExtension(f), f => f);

List<string> Closure(string root)
{
    var seen = new List<string> { root };
    var q = new Queue<string>(); q.Enqueue(root);
    while (q.Count > 0)
    {
        var cur = q.Dequeue();
        if (!index.ContainsKey(cur)) continue;
        using var fs = File.OpenRead(index[cur]);
        using var pe = new PEReader(fs);
        if (!pe.HasMetadata) continue;
        var md = pe.GetMetadataReader();
        foreach (var h in md.AssemblyReferences)
        {
            var r = md.GetString(md.GetAssemblyReference(h).Name);
            if (index.ContainsKey(r) && !seen.Contains(r)) { seen.Add(r); q.Enqueue(r); }
        }
    }
    return seen;
}

Console.WriteLine("CoreModule : " + string.Join(", ", Closure("UnityEngine.CoreModule")));
Console.WriteLine("IMGUIModule: " + string.Join(", ", Closure("UnityEngine.IMGUIModule")));
Console.WriteLine("AIModule   : " + string.Join(", ", Closure("UnityEngine.AIModule")));
```

> 同一套脚本还能回答"**某个类型到底在哪个模块**"（遍历 `TypeDefinitions` 比全名即可）——
> 这是排查 `CS0012` / `CS0234` 最快的办法，比凭记忆猜模块归属可靠得多。

## 六、这次实验踩到的坑（都值得记住）

| # | 坑 | 真相 |
| --- | --- | --- |
| 1 | 以为 `UnityEngine.Debug` 在 `IMGUIModule` | **错，它在 `CoreModule`**。`IMGUIModule` 里是 `GUI` / `GUILayout` / `GUIStyle` / `Event` |
| 2 | 以为 `NavMesh` 的命名空间是 `UnityEngine` | **错，是 `UnityEngine.AI`**（`UnityEngine.AI.NavMesh` / `NavMeshAgent` / `NavMeshPath`），在 `UnityEngine.AIModule` 里 |
| 3 | 想在 PowerShell 里 `Assembly.LoadFrom(...).GetExportedTypes()` 扫类型 | **不行**：pwsh 的加载上下文解析不了 `netstandard 2.1`，抛 `FileNotFoundException`。**要读元数据就用 `System.Reflection.Metadata`** |
| 4 | 在 `.csproj` 的 XML 注释里写了 `dotnet run --project` | **`MSB4025 未能加载项目文件`** —— **XML 注释里不能出现 `--`**。这个坑本项目已经踩过一次，务必记住 |
| 5 | 只写 `<Reference>` 不写 `<Private>true</Private>` | 会得到 `FileNotFoundException`，**实验直接失去意义**（见 §4.3） |

> **共同教训**：这五个坑全是"**凭印象/凭感觉**"造成的。
> 凡是"某个东西在哪、能不能用"的问题，**都要用工具问出答案，而不是从记忆里取答案**。

## 七、这次实验对架构的实际影响

| 裁决 | 本实验提供的支撑 |
| --- | --- |
| **A1**（AI 分两套实现，`IAgentBrain`） | `MonoBehaviour` 是 Behavior Designer `Task` 的基类（L6 实测其类型与基类链可见），而"创建/访问 `MonoBehaviour` 实例"必然触发 `ECall`（L3/L4 实测）→ 插件版无法进共享逻辑层 |
| **A2**（帧同步不由服务端跑 AI） | 服务端进程**根本没有引擎对象系统**（连 `new GameObject()` 都不行），自然无从运行依赖引擎的 AI |
| **A3**（寻路分两套，`IPathfinder`） | `NavMesh` 系列位于 `AIModule`（实测），与引擎强绑定，且实现是浮点 → 帧同步逻辑层必须自研定点实现 |

**诚实边界（没证明什么）**：

| 未覆盖 | 何时补 |
| --- | --- |
| 没有**直接**在服务端工程里引用 `BehaviorDesigner.Runtime.dll` | D8 导入插件后可补做一次"端到端对照"；但**它不会改变结论** |
| 没有测 IL2CPP / AOT 侧行为 | 那是 D17 的范围（`Docs\09-IL2CPP验证清单.md`），与本实验问题不同 |

## 八、面试讲法（可直接背）

> "我用 Behavior Designer 做怪物 AI，它官方文档建议行为树跑在权威端。
> 但我的服务端是独立 .NET 进程，所以我写了个探针工程，直接引用 Unity 的 `CoreModule`，分 9 级测下去：
> **托管部分能用** —— `Vector3`、`Mathf` 算得完全正确，反射还能读出 `MonoBehaviour` 的基类链；
> **但一碰引擎对象就炸** —— `new GameObject()`、`go.name`、`Time.deltaTime` 全部抛
> `SecurityException: ECall methods must be packaged into a system module`。
> 这让我看清一件事：**引用 Unity 程序集能编译通过，失败在运行时的原生调用上**。
> 所以架构上我用 `IAgentBrain` 把 AI 抽象成两套：插件版跑客户端，自研定点版跑帧同步。
> 顺带我量了模块依赖 —— 引用 `IMGUIModule` 一个会拖进 7 个模块，
> 这也是我坚持让共享逻辑层保持 `netstandard2.1`、并用 `noEngineReferences` 从编译期堵死引擎依赖的原因。"
