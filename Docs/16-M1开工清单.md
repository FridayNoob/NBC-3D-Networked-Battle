**FW-04 的 O(1) 证据（实测原文）**：

```
[POOL-BENCH] N=20000  List.RemoveAt(0) 基线=1116023 ticks  Stack 池=52886 ticks  快了 21.1 倍
```

> ⚠️ **一处更正**：本文档 v1.4 在这里写过"实测差距在三个数量级"。那是**推测，不是测量**。
> 实测是 **21.1 倍**。原因是池路径除了 Pop/Push 还要做 `HashSet` 增删、钩子判空、计数维护，
> 并非"纯 Pop/Push 对纯 RemoveAt"。
> FW-04 的真正结论是**渐进复杂度不同**（O(N²) vs O(N)）—— 差距会**随 N 增大而拉大**，
> 而不是"固定快多少倍"。测试断言只要求 5 倍以上，留余量就是为了不变成偶发红灯。

> 第一版 `UIManager` 内部用的是**第一版 `async/await`**。写完之后我意识到一个隐患：
> **C# 的 `await` 恢复执行时，会把后续代码投递回它捕获的 `SynchronizationContext`**
> （Unity 编辑器里装了 `UnitySynchronizationContext`），而那个队列**要靠帧循环去跑**。
> **EditMode 测试没有帧循环** → 续体被投递了就永远没人跑 → 测试会**挂死**。
>
> 于是**重写成回调驱动**（`AssetHandle.OnComplete`）——
> 回调是**在完成那一刻被直接调用**的，不经过任何上下文投递，所以在 EditMode 里确定性可跑。
> `ShowPanelAsync` 只作为外面的一层便利（`TaskCompletionSource`），
> 因为它在回调触发时就 `SetResult` 了，外面 `await` 到的是**已经完成的任务**，同样不会卡。
>
> **这也顺便解释了本框架为什么一直是"回调 + 句柄"风格，而不是 `async/await` 风格**
> —— 不是为了复古，是因为**回调在编辑器里可以被确定性地测**。
>

> 而不是"红"，那就是我判断错了，请把现象告诉我。

| `MaskPrefabWithWrongPanelType_LogsActionableError` | 预制体挂错脚本时**报一句能看懂的错**，而不是静默什么都不发生 |

> 📌 **加载遮罩为什么拆成两个类**（`LoadingMaskPanel` + `LoadingMaskController`）：
> 「面板长什么样」是美术的事，「什么时候出现」是逻辑的事。分开之后换皮肤不用改逻辑，
> 而且逻辑**可以脱离任何预制体单独测**（那 12 条用例一个 UI 预制体都不需要真资源）。
>
> 📌 **控制器是普通类，不是单例** —— **由游戏层决定什么时候装上去**。
> 框架不该擅自决定"这个项目一定要有加载遮罩"。
> 装配示例（M1-D 写业务时用）：
> ```csharp
> var mask = new LoadingMaskController(UIManager.Instance);
> mask.Attach();
> // 游戏退出 / 切模式时：mask.Dispose();
> ```

"机械保证"= 即使有人手滑也**编译不过**，不依赖自觉。这四个字必须**实测过**才敢写进文档。

**但我进一步测量后发现：这次实验根本没跑起来。** 证据是三条时间戳/日志：

| 证据 | 值 | 说明 |

**已落地**：`Client\Assets\_Project\Tests\EditMode\Framework\FrameworkLayeringTests.cs`（**4 条用例**）：

| 用例 | 作用 |
| --- | --- |

### 10.4 B3 操作单：YooAsset 包配置 + 编辑器模拟模式（**你执行**）

> 前置：B2 的代码已完成（`AssetManager` + `YooAssetProvider`）。

#### 10.4.1 先说结论：`packageRoot` 是什么、从哪来

`YooAssetProvider` 在编辑器模拟模式下需要一个 `editorSimulatePackageRoot`。它**不是随便填的**，源码链条如下（全部实测读到，带位置）：

| 环节 | 事实 | 位置 |
| --- | --- | --- |
| **读取方** | `EditorFileSystem` 用 `PathUtility.Combine(_packageRoot, 文件名)` 找清单 | `Runtime\FileSystem\Services\EditorFileSystem\EditorFileSystem.cs:293-314` |
| 三个文件名 | `{包名}.version` / `{包名}_{版本}.hash` / `{包名}_{版本}.bytes` | `Runtime\Settings\YooAssetConfiguration.cs:132 / 115 / 95` |
| **写入方** | 模拟构建把这三个文件写进 `GetPackageOutputDirectory()` | `Editor\BundleBuilder\BuildTasks\TaskCreateManifest.cs:41,92,101,109` |
| 输出目录公式 | `{BuildOutputRoot}/{BuildTarget}/{PackageName}/{PackageVersion}` | `Editor\BundleBuilder\BuildParameters.cs:226-229` |
| `BuildOutputRoot` 默认 | `{Unity工程根}/Bundles` —— 对我们就是 **`Client/Bundles`** | `Editor\BundleBuilder\BundleBuilderHelper.cs:18-22` |
| 默认文件夹名 | `YooFolderName = "yoo"`、`PackageFilePrefix = ""` | `Runtime\Settings\YooAssetSettings.cs:15,21` |
| 菜单入口 | `YooAsset/Bundle Collector`、`YooAsset/Bundle Builder` | `Editor\BundleCollectorWindow.cs:20`、`Editor\BundleBuilderWindow.cs:16` |

**所以 `packageRoot` 的形态是**：

```
Client/Bundles/<构建目标>/<包名>/<版本>/
```

> ⚠️ **但请以构建日志为准，不要照上面手算** —— 模拟构建跑完时，YooAsset 会自己打印三行：
> ```
> Create package manifest file: '<路径>/<包名>_<版本>.bytes'
> Create package manifest hash file: '<路径>/<包名>_<版本>.hash'
> Create package version file: '<路径>/<包名>.version'
> ```
> **那个 `<路径>` 就是 `editorSimulatePackageRoot` 要填的值。**
> 这比按公式推更可靠：公式里 `BuildTarget` / `PackageVersion` 的取值由窗口里的选择决定，日志是**结果本身**。

#### 10.4.2 步骤（在 Unity 里）

| # | 操作 | 预期 |
| --- | --- | --- |
| 1 | 菜单 **`YooAsset/Bundle Collector`** | 打开资源收集窗口 |
| 2 | 建一个 **Package**（包名，例如 `NBCMain`） | 树里出现一个包 |
| 3 | **在 Package 下建 `Group`（分组）** | 包下面出现分组 |
| 4 | **在 Group 下建 `Collector`（收集器）**，把 `CollectPath` 指到**一个真实资源目录** | 收集器出现在分组下面 |
| 5 | 点 **`Save`** | 配置落到磁盘 |
| 6 | 菜单 **`YooAsset/Bundle Builder`** | 打开构建窗口 |
| 7 | 选 **构建管线 = `EditorSimulateBuildPipeline`**、**包名 = 刚才那个**，点 **`Build`** | 构建成功，Console 出现 `Create package version file: '...'` 三行 |
| 8 | **把第 7 步日志里的路径记下来** | 那就是 `editorSimulatePackageRoot` |

> ⚠️ **2026-09-20 更正**：本节 v1.5 早先写的是"Package → **Collector** → **Group**"，**层级顺序写反了**。
> 依据（读源码）：`BundleCollectorSetting.Packages` → `BundleCollectorPackage.Groups`
> → `BundleCollectorGroup.Collectors` → `BundleCollector.CollectPath`
> （`BundleCollectorPackage.cs:60`、`BundleCollectorGroup.cs:39`、`BundleCollector.cs:19`）。
> **Collector 是最里层那个带路径的**。

#### 10.4.2.1 ⚠️ 报 `[ErrorCode202] Pack asset list is empty` 怎么解（2026-09-20 实际踩到）

**报错原文**：

```
System.InvalidOperationException: [ErrorCode202] Pack asset list is empty.
  at YooAsset.Editor.TaskGetBuildMap.CreateBuildMap (...)
       TaskGetBuildMap.cs:145
```

**含义**：构建走到最后一步，**参与打包的资源列表是空的**。源码里有三道筛子（`TaskGetBuildMap.cs`）：

| 位置 | 规则 |
| --- | --- |
| `:100` | `CollectorType == None` 的资源**直接跳过** |
| `:139-142` | 拿不到"资源包名（BundleName）"的资源被**移除** |
| `:144-147` | 筛完还是 0 个 → 抛 `ErrorCode202` |

**所以只有三种可能**（按概率排序）：

| # | 原因 | 怎么确认 / 怎么修 |
| --- | --- | --- |
| 1 | **Collector 的 `CollectPath` 是空的**，或者根本没有 Collector | 看最里层那个收集器的路径栏是不是空。层级必须是 **Package → Group → Collector** |
| 2 | **收的是 `.cs` 目录**（例如 `Assets\_Project\Protocol`）—— **脚本不是可打包资源** | 换成**真实资源**：新建 `Assets\_Project\TestAssets\hello.txt`（Unity 导入成 `TextAsset`，可打包，而且测试里好断言内容） |
| 3 | `CollectPath` 指向的路径**无效**（拼错 / 已被删） | 这时 `BundleCollector.cs:87-89` 会抛 `Collect path is invalid`。若 Console 里是这句，就是路径本身的问题 |

**每个 Collector 在源码里的字段**（`BundleCollector.cs`）——**对照窗口显示自查**：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `CollectPath` | **空** | 收集路径。**空的就什么都收不到** |
| `PackRuleName` | `PackDirectory` | 打包规则（决定 BundleName 从哪来）—— 保持默认 |
| `FilterRuleName` | `CollectAll` | 过滤规则 —— 保持默认即全收 |
| `CollectorType` | `MainAssetCollector` | **必须是 Main / Static；`None` 会被跳过** |

## 十一、工具说明：Test Runner / EditMode / PlayMode 到底是什么

> **这一节是补课。** 前面几轮我直接说"去 Test Runner 跑一下"，默认你已经知道它是什么 ——
> 这违反了**规则 15**（本项目的目的包括教会你）。补在这里，以后不必再问。
>
> 顺带一句：这一节里的**日志去哪了**（§11.5）正好解释了你这次"找不到 `[POOL-BENCH]`"的原因。

### 11.1 一句话

**Unity Test Runner 是 Unity 自带的一个测试窗口。** 它把工程里带 `[Test]` / `[UnityTest]` 标记的方法
自动找出来、逐个执行、告诉你哪个过哪个不过。菜单：`Window → General → Test Runner`。

它**不是**"点 Play 跑游戏"——它跑的是代码里的小段检查，不进游戏逻辑。

### 11.2 为什么要用它

| 理由 | 具体到本项目 |
| --- | --- |
| **"我觉得对"不是证据** | 我说"单例只会有一个"，你说"我试了没问题" —— 都可以是错的。**跑一遍才有绿/红** |
| **能回归** | 以后改框架（A3~A11）时，跑一遍就知道有没有弄坏以前的功能。这就是 M1 验收 **V13** 的意义 |
| **能写清"验证过什么"** | 文档/面试里"EditMode 27/27 全绿"比"我自己试了没问题"硬得多。**这是作品集里能拿出来的东西** |

### 11.3 界面与术语

| 位置 | 含义 |
| --- | --- |
| 顶部 **PlayMode / EditMode** 两个标签页 | 决定**在哪个环境里跑**（不是"跑哪一类测试"）。EditMode = 编辑模式，无玩家循环；PlayMode = 真进播放模式 |
| 左侧树 | `命名空间 → 测试类 → 测试方法`。例如 `NBC.Tests.EditMode → ObjectPoolTests → Get_WhenPoolEmpty_CreatesViaFactory` |
| **Run All** | 跑当前标签页里的全部测试 |
| **Run Selected** | 只跑你选中的那几个（调试单个用例时用它，快很多） |
| 绿 / 红 / 灰 | 通过 / 失败 / 未运行 |

**点一下失败的用例**，右侧（或下方）会显示失败原因和堆栈；双击通常能跳到出错的代码行。

### 11.4 "一次 Test Run"是什么

就是你**点一次 Run All 产生的那一批结果**。它不是一个工程文件，是一次执行记录。
顶部会显示类似 `共 27 个，通过 27`。我们在文档里写的"27/27 全绿"指的就是它。

> 所以"TestRun"不是一个需要你去创建或配置的东西 —— **按一下按钮就是一次 run**。

### 11.5 日志去哪了（**你这次 `[POOL-BENCH]` 找不到，就是这个问题**）

**关键区别**：测试结果显示在 **Test Runner 窗口**；而测试里 `Debug.Log` 打的日志进的是
**Console 窗口**（两个不同的窗口）。`[POOL-BENCH]` 是日志，所以要去 Console 找。

找不到通常就两个原因：

| 原因 | 怎么确认 / 怎么解决 |
| --- | --- |
| ① Console 右上角的 **三个开关**（Error / Warning / **Log**）里，`Log` 被关掉了 | 把 `Log` 点亮。普通日志属于 Log 档 |
| ② Unity 的 Console 开了 **Clear on Play** —— 你跑完 EditMode 接着跑 PlayMode，**进播放模式时把 Console 清空了** | 或者单独重跑那一个用例：选中它 → **Run Selected** → 立刻看 Console |

**这次我是怎么拿到那个数字的**：我没在你的 Console 里找，而是**直接读了 Unity 的日志文件**
`%LOCALAPPDATA%\Unity\Editor\Editor.log` —— 它是 Unity 的完整日志，**Console 的输出也在里面，
且不受 Console 的过滤/清空影响**。所以实测原文是：

```
[POOL-BENCH] N=20000  List.RemoveAt(0) 基线=1116023 ticks  Stack 池=52886 ticks  快了 21.1 倍
```

> 这招你也可以用：**当 UI 里看不到时，去读日志文件**。它的价值在于
> "不受界面过滤影响" —— 这正是本项目的规矩"能实测的绝不靠印象"的一个具体用法。

### 11.6 术语小词典（我前几轮默认你懂的词）

| 术语 | 是什么 |
| --- | --- |
| **Console** | Unity 的日志窗口，分 Error / Warning / Log 三档 |
| **Hierarchy / Scene** | 当前场景的对象树 / 场景视图 |
| **Project** | 工程的资源目录，对应磁盘上的 `Client\Assets\` |
| **Inspector** | 选中对象后的属性面板（asmdef 的 references 就是在这里改的） |
| **`.meta`** | Unity 给**每个**资源生成的伴随文件，里面存 **GUID**。资源改名/移动时靠它保持引用不断 —— **所以不要手动删 `.meta`** |
| **asmdef** | 汇编定义文件（其实就是个 JSON），决定"哪些脚本编进哪个 DLL、这个 DLL 能引用谁" |
| **程序集 / assembly / DLL** | 编译产物。`asmdef` 是配方，`DLL` 是成品，存放在 `Client\Library\ScriptAssemblies\` |
| **GUID** | Unity 内部标识一个资源的 32 位十六进制串。在 Inspector 里选引用时，asmdef 里会存成 `GUID:xxxx` 而不是名字 |
| **Editor.log** | Unity 的完整日志文件，Console 的输出也在里面（见 §11.5） |
| **编译闸门** | 本项目自建的东西：用 `dotnet build Server\_api-probe` 在**不开 Unity** 的情况下先编译一遍框架与测试代码（见 `Docs\11` §四之三） |
