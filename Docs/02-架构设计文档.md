## 1. 分层与依赖方向（M1 视角）

```
┌──────────────────────────────────────────────────────────────────┐
│  Game 层（NBC.Game / NBC.Model）—— 业务与表现                      │
│    Model(纯 C#，noEngineReferences) / View / Controller / Service  │
└───────────────┬──────────────────────────────────────────────────┘
                │ 只能向下依赖
┌───────────────▼──────────────────────────────────────────────────┐
│  Framework 层（NBC.Framework）—— 自研框架底座（例外 E1）            │
│  Base(单例)  Pool  Event  Mono/Coroutine  Scene  Asset  Input      │
│  Audio  UI  Log  PerfHUD  Timer  StateMachine                      │
│  ★ 唯一允许接触 YooAsset / xLua 等第三方类型的地方（Adapter 在此层）│
└───────────────┬──────────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────────┐
│  第三方与引擎：UnityEngine / URP / YooAsset / Google.Protobuf / xLua│
└──────────────────────────────────────────────────────────────────┘
```

### 1.1 依赖方向靠 asmdef **机械强制**，不靠自觉

| 规则 | 强制手段 | 违反时会发生什么 |
| --- | --- | --- |
| `Game` 可引用 `Framework`；`Framework` **不可**引用 `Game` | 各自 asmdef 的 `references` 里**只列被允许的** | 反向引用时 **Unity 编译报错**（不是靠 code review） |
| `NBC.Model` 不得引用 `UnityEngine` | `noEngineReferences: true`（M0 已建） | 写 `using UnityEngine` **直接编译失败** |
| **业务层不得出现 YooAsset 类型**（YOO-09） | `NBC.Game.asmdef` 的 `references` 里**不列 YooAsset 的程序集** | 编译失败；另有 `rg` 机械校验兜底 |
| 同上，xLua 类型只在 `Framework` 的 Hotfix 模块出现 | 同上 | 同上 |

> **为什么用 asmdef 而不是"约定"**：M0 的经验 —— **靠自觉的约定一定会漂移**。
> 编译期失败是零成本、零歧义的；code review 不是。

## ADR-001 · `AssetManager` 资源加载接口设计

### ① 背景 / 问题

框架原有的资源加载是 `ResMgr`（`FrameTang\Assets\Scripts\ProjectBase\Res\ResMgr.cs`，47 行），公开 API 只有两个：

```csharp
public class ResMgr : BaseManager<ResMgr>
{
    public T Load<T>(string name) where T : Object;                  // 同步
    public void LoadAsync<T>(string name, UnityAction<T> callback);  // 异步回调
}
```

它有三个**根本性**问题（其中第一个是需求 5 的硬冲突）：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 基于 `Resources.Load`（**FW-08**） | **无法热更、无法按需卸载**，直接违反需求 5 |
| 2 | **完全没有卸载 API**，也没有引用计数 | 资源只增不减；换场景即泄漏 |
| 3 | 异步只有"回调 + 不给句柄" | 调用方无法查询进度/状态、无法取消、无法释放 |

因此需要设计一个新的 `AssetManager`，并用 `YooAssetAdapter` 把 YooAsset 隔离在框架层内（**FW-M05 / FW-M17 / YOO-09**）。

### ② 决策

**决策 1：接口用泛型 `LoadAsset<T>`，句柄类型为 `AssetHandle<T> : IDisposable`。**
**决策 2：`AssetHandle<T>` 同时提供"回调 / 轮询 / `await`"三种消费方式**（同一个对象，不是三套 API）。
**决策 3：`AssetManager` 只出现在 `NBC.Framework`；业务层只依赖 `AssetManager`，绝不出现 YooAsset 类型。**
**决策 4：⚠️ 有意偏离 `FW-M05` 的措辞 —— 不做 `Resources` 兜底。✅ 已获负责人批准（2026-09-20）。**
**决策 5：同步加载保留但受限**（仅编辑器与极小的资源；Player 里调用会打警告）。
**决策 6：适配层独立成一个程序集 `NBC.Framework.YooAsset`**（2026-09-20 确认）——
只有它引用 `YooAsset`；`NBC.Framework` 保持**零依赖**，换资源方案时只需删掉这一个程序集。

**决策 7：UI 模块独立成一个程序集 `NBC.Framework.UI`**（2026-09-21 确认，A9）——
只有它引用 `UnityEngine.UI`（UGUI）；`NBC.Framework` 继续保持**零依赖**。

> **为什么必须做这个决定（事实，不是偏好）**：Unity 官方手册
> [Referencing assemblies](https://docs.unity3d.com/6/Documentation/Manual/assembly-definitions-referencing.html) 写明：
> 用 asmdef 建的**自定义程序集会自动引用"预编译程序集（插件 dll）"**，
> 引用关系图里**没有**"自定义程序集 → 另一个自定义程序集"这条线；
> "To use code from another assembly, **you must add a reference** to the other assembly."
> 而 **UGUI（`Button` / `Toggle` / `UIBehaviour`）是包程序集**，不是预编译 dll。
> ⇒ 要用 `Button`，`NBC.Framework` **必须**把 `UnityEngine.UI` 写进 `references`。
>
> **这与决策 6 之后加强的那条守卫直接冲突**（守卫断言 `references` **必须为空**）。
> 两条路：① 把 UGUI 加进底座、把守卫改成白名单；② **UI 单独成程序集**。
> **负责人 2026-09-21 选 ②** —— 理由：底座的空引用列表一个字不动，
> 守卫继续有效，和 `NBC.Framework.YooAsset` 是同一个套路；
> "底座零依赖、可整包导出复用"这句话也继续成立。
>
**决策 8：双端共享逻辑的「唯一源码」放在 Unity 侧，服务端 `<Compile Include>` 引用它**（2026-09-21 确认，D1）——
共享源码位置 `Client\Assets\_Project\Shared\`；Unity 由 `NBC.Shared.asmdef`（`noEngineReferences: true`）编译；
服务端 `Server\NBC.Shared\NBC.Shared.csproj` **不存放任何 .cs**，用 `<Compile Include>` 引用同一批文件。

> **为什么不做两份拷贝**：帧同步最怕的就是"**两端逻辑不一致**" —— 算出来不一样就废了，而且极难发现。
> 两份拷贝一定会漂移。**宁可多一个服务端→客户端目录的路径耦合，也不要逻辑漂移。**
>
> **⭐ 顺带抓出一个真隐患并当场消掉**：改之前服务端用 SDK 默认 `LangVersion`，
> **允许 C# 10 语法**，而 **Unity 2022.3 只到 C# 9**。
> 也就是说服务端**可以**写出"服务端编得过、Unity 编不过"的共享代码，**没有任何东西拦得住**。
> （改动前 `SharedInfo.cs` 恰好用了 C# 10 的**文件作用域命名空间**，就是一处真实隐患。）
>
> 处理：把服务端 `LangVersion` **钉成 9.0**，并关掉 `ImplicitUsings`
> （钉完才暴露：SDK 自动生成的 `global using` 文件也是 C# 10 特性；
> 而 **Unity 根本没有隐式 using**，共享代码本来就必须写全）。
>
> 效果：**"服务端编得过"这件事本身就代表"Unity 也能编过"** ——
> 与编译闸门 `ApiProbe.csproj` 的 `<LangVersion>9.0</LangVersion>` 同一个理由。
>
> **机械保证**：`SharedLayerTests` 8 条，把上面每条约定都钉住了 ——
> 包括"服务端目录里不许再出现 .cs"（编译器不会报的漂移，测试会报）。
> ⚠️ **不许为了让自己代码过而改守卫** —— 这次是**先问、得到批准**才动的结构，
> 而且动的是"往哪放代码"，**不是守卫本身**。

> ⚠️ **决策 6 顺带暴露了 A11 那条分层测试的一个弱点**：它当时只断言"`NBC.Framework` 不引用 **`NBC.*`**"，
> 而 `YooAsset` 不是 `NBC.*` —— 也就是说**把 YooAsset 塞进 Framework，那条测试照样是绿的**。
> 已改为更强的断言：**`NBC.Framework` 的 `references` 必须为空**（底座不依赖任何东西，含第三方），
> 外加"`NBC.Game` 不得引用 `YooAsset`"。**比 `rg` 文本搜索更可靠**（不受注释/字符串影响）。

> 📌 **实现这个 Adapter 之前，必读 `Docs\05-依赖清单.md` 的「一·补」**：
> 装的 YooAsset **3.0.5 是重构过的 v3 API**，v2.3 那套写法（`InitializeAsync` / `EditorSimulateModeParameters` / `RawFileHandle`）
> **默认不参与编译、写了编译不过**。对照表在那边。

### ③ 接口草案（提交评审用）

```csharp
namespace NBC.Framework.Asset
{
    /// 运行模式（对应 YOO-03）
    public enum AssetRuntimeMode
    {
        EditorSimulate,   // 编辑器：免打包迭代
        Offline,          // 单机：只用随包内容
        Host,             // 联机：可从资源服务器更新（热更）
    }

    public enum AssetStatus { None, Loading, Succeeded, Failed }

    /// 非泛型句柄：便于统一收集、统计、批量释放（不关心具体资源类型）
    public interface IAssetHandle : System.IDisposable
    {
        string       Location { get; }
        AssetStatus  Status   { get; }
        bool         IsDone   { get; }
        float        Progress { get; }        // 0..1
        string       Error    { get; }
        UnityEngine.Object AssetObject { get; }   // 类型擦除视图，供统计/兜底
        void WaitForAsyncComplete();              // 阻塞直到完成（仅工具/编辑器）
    }

    /// 泛型句柄：业务层拿这个
    public sealed class AssetHandle<T> : IAssetHandle where T : UnityEngine.Object
    {
        public T      Asset    { get; }     // 成功后非 null；失败/未完成时为 null
        public bool   IsValid  { get; }     // Status==Succeeded && Asset != null
        // ... IAssetHandle 的实现 ...
        public void Dispose();               // ★ 释放一次引用计数；重复 Dispose 安全
    }

    public sealed class AssetManager
    {
        // —— 初始化（YOO-03）——
        System.Threading.Tasks.Task InitializeAsync(AssetRuntimeMode mode);

        // —— 加载 ——
        AssetHandle<T> LoadAsset<T>(string location)            where T : UnityEngine.Object;  // 受限，见决策 5
        AssetHandle<T> LoadAssetAsync<T>(string location)       where T : UnityEngine.Object;

        // —— 场景（YOO-08：场景也走 YooAsset）——
        ISceneHandle LoadSceneAsync(string location, UnityEngine.SceneManagement.LoadSceneMode mode);

        // —— 释放与观测 ——
        void ReleaseUnused();                       // 释放引用计数为 0 的缓存（不强制 GC）
        void UnloadUnusedAssets();                  // 触发引擎级卸载
        AssetDebugInfo GetDebugInfo();              // 句柄数 / 引用计数 / 加载中 / 失败数（泄漏排查用）
    }
}
```

**业务层的典型用法**（两种都支持，二选一）：

```csharp
// 用法 A：回调
var h = AssetManager.Instance.LoadAssetAsync<GameObject>("ui_login");
h.OnComplete += handle => { if (handle.IsValid) Instantiate(handle.Asset); };
// 用完：h.Dispose();

// 用法 B：await（同一个句柄，零 Task 分配的自定义 awaitable）
var h = AssetManager.Instance.LoadAssetAsync<GameObject>("ui_login");
await h;
if (h.IsValid) Instantiate(h.Asset);
h.Dispose();
```

### ④ 理由（逐条对应需求/实测）

| 决策 | 理由 | 依据 |
| --- | --- | --- |
| 泛型 `LoadAsset<T>` | 与旧 `ResMgr` 的调用风格一致（迁移成本低）；只有一条代码路径；`T` 只用于强转，不参与多态 | 旧 API 实测签名 |
| 句柄而非"直接返回对象" | **必须有引用计数与释放入口**，否则换场景就泄漏（旧 API 的致命缺陷 #2） | FW-M05「引用计数、句柄管理」 |
| **同时提供回调与 `await`** | `await` 让业务代码不必层层回调（M2 的战斗流程会大量异步）；自定义 awaitable 不产生 `Task` 分配，IL2CPP 下也没有线程池开销 | 本项目 IL2CPP 已验证；`Task` 在 IL2CPP 可用但有分配 |
| `IAssetHandle` 非泛型基接口 | 统计面板、批量释放、泄漏排查都需要"不关心类型的句柄集合" | FW-M12（PerfHUD）会用到 |
| YooAsset 只出现在 Framework | 需求 **YOO-09** 明确要求；且换资源库时业务层零改动 | YOO-09、FW-M17 |
| **不做 `Resources` 兜底** | ① `Resources` 正是 FW-08 的病根；② 编辑器已有 `EditorSimulateMode`，**不需要**兜底；③ 兜底会**掩盖"资源没进包"**的真实缺陷（M0 的教训：静默降级最危险） | ⚠️ **有意偏离 FW-M05 措辞** —— **已获负责人批准（2026-09-20）**，见 §ADR-001 决策 4；需求文档 FW-M05 行已同步标注 |
| 同步加载受限 | YooAsset 的同步接口在 Player 里会阻塞主线程；大资源上同步加载是卡顿来源 | 见决策 5 的约束与验证 |

### ⑤ 否决的备选方案

| 备选 | 为什么不选 |
| --- | --- |
| **按类型分 API**（`LoadPrefab` / `LoadSprite` / `LoadAudioClip`…） | 每加一种资源类型就要改接口与 Adapter；泛型一条路就够 |
| **只做 `await`（内部用 `Task`）** | `Task` 带来分配与线程池交互，且 WebGL 上不可用；自定义 awaitable 更轻 |
| **只做回调（沿用旧风格）** | 战斗流程会出现多层嵌套回调（回调地狱），可读性与异常传播都差 |
| **保留 `Resources` 兜底** | 见决策 4 —— 会掩盖缺陷，且编辑器已有模拟模式 |
| **让业务层直接用 YooAsset** | 直接违反 YOO-09；且 M5 若调整资源层（如加 CDN/加密）业务层要全改 |
| **自己做一套 AB 加载** | 违反规则 12（资源加载是明确点名的"必须用现成方案"） |

### ⑥ 由此产生的约束（写进开发约束，违反即返工）

| # | 约束 | 怎么机械验证 |
| --- | --- | --- |
| C1 | `NBC.Game` 的 asmdef **不得**引用 YooAsset 程序集 | Unity 编译失败 |
| C2 | `Client\Assets\_Project\Game\` 下不得出现 `YooAsset` 字样 | `rg -n "YooAsset" Client\Assets\_Project\Game` → 0 结果 |
| C3 | 每个 `LoadAssetAsync` 的返回值**必须**有配对的 `Dispose()`（或明确移交给长期持有者） | 定期的 `GetDebugInfo()` 泄漏检查 + code review |
| C4 | 同步 `LoadAsset<T>` 不得出现在**每帧路径**与**玩家侧大资源**上 | Player 里调用会打警告日志（带 location） |
| C5 | 场景也必须经 `AssetManager`（不得直接 `SceneManager.LoadScene`） | C2 同类检查：`rg "SceneManager.LoadScene" Client\Assets\_Project\Game` → 只应出现在 Framework 的 Scene 模块里 |
| C6 | 句柄的 `Dispose()` **必须幂等**（重复调用安全） | EditMode 测试 |

### ⑦ 怎么验证（M1 的 V3/V4 验收挂钩）

| 验证项 | 方法 |
| --- | --- |
| 编辑器模拟模式可用 | `EditorSimulateMode` 下加载一个测试资源成功 |
| 打包后内容包模式可用 | IL2CPP 出包后同一测试资源加载成功（**这条会覆盖 M0 的 D17 经验**） |

## ADR-002 · 事件中心的 key 与派发安全（A3）

| | |
| --- | --- |
| **背景** | 原版用 `string` 作 key（`FW-06`）：拼错=静默不触发；同一 key 用不同类型监听/触发 → `NRE`（`FW-07`）；派发中增删监听者行为未定义 |
| **决策** | ① key 用 **`readonly struct EventId`**（编译期常量，**不提供 string 重载**）② 派发**同步**进行 ③ 派发前拍**快照**（copy-on-write） |
| **理由** | `string` 拼错只能运行时发现，而 `EventId` 拼错**编译不过**；快照让"派发中订阅/退订"的语义**确定**（不是"看运气"） |
| **否决** | ❌ 保留 string 重载（"方便"）—— 那就等于把 `FW-06` 的静默失败留在系统里<br>❌ 异步派发 —— 会把"事件到达顺序"变成不确定，帧同步下不可接受 |
| **约束** | 热路径上避免装箱；派发**不吞异常**（与 A4 的逐回调容错刻意不同，理由见 `Docs\06` §12.6） |
| **验证** | `EventCenterTests` **26** 条；`EventChannelStat`（给数字不给容器） |

## ADR-004 · 混合同步模型的边界（2026-09-22 负责人拍板）

| | |
| --- | --- |
| **背景** | 项目要做"开放世界 + 副本 + PVP"，而同步模型决定服务器与客户端整套架构。原计划（`Docs\01` §6）已定"状态同步 PVE/PVP 主模式 + 帧同步 PVP 对战"，但**开放世界**这个新范围让问题重新摆上桌 |
| **决策** | **混合**：<br>· **大世界 / 社交 / 任务** → **状态同步（服务器权威）**<br>· **PVP 小房间** → 可切 **帧同步**（复用 D2 的定点数学与确定性）<br>· **规模目标 2~4 人**（房间制） |
| **理由** | ① 状态同步"最容易做出能玩的效果"，且**天然抗外挂**（权威在服务器）② 帧同步是 `Docs\01` §808 点名的**面试硬指标**，D2 已经为此铺好路 ③ **2~4 人**这一条直接**砍掉 AOI 与分线/分服**——这是本轮最大的成本节约 |
| **否决** | ❌ **全帧同步**做开放世界 —— 玩家数一多，输入广播与确定性开销会爆；且"任何人都能算出全图"在开放世界里没有意义<br>❌ **全状态同步** —— 那 D2 的确定性成果（帧同步的基础）就白做了，而它是面试硬指标 |
| **约束** | 两套同步模式**不得并行开发**：先把状态同步做完（M3），再做帧同步（M4）；用 `ROOM-02`（房间可配同步模式）隔离 |
| **验证** | M3：2 个客户端状态同步副本通过；M4：帧同步 PVP 一局**位级一致**（不同客户端的战斗结果哈希相同） |

## ADR-006 · 配置中间产物：TSV（导入器）+ JSON（对外）

| | |
| --- | --- |
| **背景** | 导入器需要一种"工具 → Unity"的中间格式。行业默认是 JSON，所以"为什么不用 JSON"是个必然会被问的问题 |
| **决策** | **两份都出**：**TSV 给导入器**、**JSON 给外部工具/人**（`--emitter all` 默认三种产物） |
| **理由** | **Unity 序列化不支持可空值类型**（`int?` 静默不序列化 = 丢数据），且 **`JsonUtility` 里 enum 按整数走**（而枚举成员值工具并不知道）。**这两条我在本机无法实测**（没有 Unity，工程里也没有 Newtonsoft）→ **不赌自己验不了的行为**。TSV 只需要 `string.Split`，零解析库，且**文本我能逐字断言** |
| **否决** | ❌ 只做 JSON —— 上面两个坑任何一个踩到都是**静默丢数据**<br>❌ 只做 TSV —— 它是**扁平**格式，将来嵌套结构（`Vector3`/子表）装不下，且外部工具要额外学习 |
| **约束** | 三份产物（C# / TSV / JSON）对"空的可空 ref"必须给**同一个答案**（`int` + `0`）；表格里**调换列顺序不能错位**（TSV 表头与 JSON 都按**字段名**） |
| **验证** | 自测里"三份产物答案一致"那条 + **用 `System.Text.Json` 反过来解析手写的 JSON** |

## ADR-007 · 可空值类型收窄（`CFG0019`）

| | |
| --- | --- |
| **背景** | `Docs\17` §六 原写"任意类型加 `?` 表示可空"。但**生成的类型必须能被 Unity 序列化** |
| **决策** | 可空**只允许** `ref:` / `ref:[]` / `string`；可空 `int?`/`float?`/`bool?`/`long?` **一律报错** |
| **理由** | 两条路都不可接受：生成 `int?` → Unity **静默不序列化**（丢数据）；退化成 `int` → 空值与显式 `0` **分不开**。安全的只有 `ref`（**主键永远 ≥ 1，所以 `0` 不可能是合法引用**）与 `string`（`null` 就是 `null`） |
| **否决** | ❌ 生成 `int?` 交给 Unity 处理 —— 静默丢数据<br>❌ 用 `bool hasXxx` 配对字段 —— 能用但把每个可空字段变成两个，代价高于收益（M1 只有 3 张表） |
| **约束** | 这是对 `Docs\17` §六 的**收窄**，按 §十二 的约定"回改规范并记一笔"处理 |
| **验证** | 自测 `可空值类型 int? → CFG0019` + `可空 ref / string → 允许` |

## ADR-008 · 生成代码的注释密度（W11）

| | |
| --- | --- |
| **背景** | 生成物要给人看。第一版字段注释用前置 `/// <summary>` 块 + 字段间空行，读起来很散；随后又一度要求"每个变量都加注释" |
| **决策** | **最终版（负责人当日第二次修正）**：① 文件开头 ② **成员变量**（行尾）③ 类名/方法名前 **必定有注释**；**其他变量看实际情况加**；其余非必要不加 |
| **理由** | 实测"每个变量都加"会产出**照抄代码本身**的废话（`string[] lines = ... // 按行拆开`），信息量为零还让 diff 变脏。**判据：注释要加在"读的人会卡住"的地方，而不是"有变量的地方"** |
| **否决** | ❌ 只在字段加、局部变量一律不加 —— 那样 `for (int i = 1; ...)` 为什么要从 1 开始就没人知道（这个信息值得留）<br>❌ 每个变量都加 —— 见上 |
| **约束** | 由自测 `CodeGen_CommentDensityRule` 机械检查（**只强制成员变量**），并带正对照 |
| **验证** | 自测那条 + **守卫自己被抓两次**的记录（特性行没跳、字段以注释结尾导致判据永假） |
