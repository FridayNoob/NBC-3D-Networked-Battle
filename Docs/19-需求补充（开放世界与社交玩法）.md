## 三、影响面（对**已完成**与**已规划**的模块）

### 3.1 对已完成的 M1 模块

| 模块 | 影响 | 结论 |
| --- | --- | --- |
| A 组（框架底座） | 单例/池/事件/宿主/UI/输入/音频/状态机/日志/性能 | **不受影响**，都能继续用 |
| B 组（资源） | ⚠️ **受影响**：开放世界要**按地形块/区域分块加载** | `Docs\18` 的分组策略要**加一层"按区域分块"**（现在只按模块分）；M1 的最小打包集合不受影响 |
| C 组（配置表） | 基本不受影响；N4/N5/N6/N7 **都要新表**（掉落、任务、成就、副本、好友无关） | `ConfigKit` 直接能加表 —— **这正是 C 组做成通用工具的回报** |
| D 组（共享层/定点数学） | ⚠️ **取决于同步模型**（§四 Q2）：若坚持帧同步房间，D2 是硬需求；若整体转状态同步，D2 只在小房间用 | 已有成果**不会浪费** |
| E 组（日志/性能） | 不受影响 | ✅ |

### 3.2 对 M2~M5 的影响

| 里程碑 | 原计划 | 需要加的东西 |
| --- | --- | --- |
| **M2** | 单机 PVE 一局可玩（3 波怪 + AI + 寻路对比） | 基本不变；**可顺带接"任务系统"的最小版本**（任务在单机就能做完整闭环，不依赖网络） |
| **M3** | 网络框架 + 房间 + 状态同步 | 加：**组队与副本实例**、AOI（若做开放世界） |
| **M4** | 帧同步 + 定点战斗 | 加：**PVP 规模**、**任务/成就持久化** |
| **M5** | 热更 + 优化 + 出包 | 加：**好友/聊天（社交服 + 持久化）**、开放世界分块流式加载优化 |

> ⚠️ **一句实话**：你描述的这些**加起来是一个商业级 MMORPG 的骨架**。
> 以现有节奏，**M1 用了很长一段时间才把框架底座 + 资源 + 配置 + 日志/性能做完**，
> 而社交、副本、PVP、任务成就、开放世界**每一个都比 M1 里任何一个模块大**。
> 所以我必须先问清楚 §四 Q1 —— **是"作品集 Demo"还是"真的要上线"**，两者差一个数量级。

## 四、需要你决定的 5 件事（**都会改架构，所以必须你拍板**）

### Q1. 目标定位：作品集 Demo 还是上线产品？（**最关键**）

| 选项 | 含义 | 代价 |
| --- | --- | --- |
| **A（推荐）作品集 Demo** | **体现设计能力**：每个系统做出"能跑通的最小闭环 + 讲得清的设计"（例如副本只做 1 个 BOSS、聊天只做私聊+世界频道） | 几个月；与现有 M1~M5 排期一致 |
| B 上线产品 | 真要做成能运营的游戏 | **数年 + 团队**（服务器集群、反外挂、运维、内容生产）；个人做不完 |

**我的建议是 A** —— 而且 A 并不"缩水"：**面试里"我把好友+聊天+副本+任务都做出了最小闭环，并说清取舍"比"我做了一个大而空的开放世界"值钱得多**。

### Q2. 同步模型：大世界 + 房间，怎么分工？

| 选项 | 说明 |
| --- | --- |
| **A（推荐）混合** | **大世界/社交/任务走状态同步（服务器权威）**；**PVP 小房间可切帧同步**（复用 D2 的确定性基础）。这也是国内 ARPG 的常见做法 |
| B 全状态同步 | 更简单，但**帧同步那套确定性成果（D2）就没用上** —— 而它是面试硬指标（`Docs\01` §808） |
| C 全帧同步 | 开放世界用帧同步**不现实**（玩家数一多，输入广播与确定性开销爆掉） |

### Q3. 规模目标（要可测，不能写"很多玩家"）

建议先定一个**能测的小目标**，例如：

| 指标 | 建议值（M3 目标） | 为什么 |
| --- | --- | --- |
| 同屏可见玩家 | **10** | 决定 AOI 与同步频率 |
| 单服在线 | **50** | 决定要不要分线/分服 |
| 副本队伍 | **4** | 决定副本实例管理复杂度 |
| PVP 人数 | **2v2 ~ 4v4** | 与 `Docs\01` 的"2~4 人小局"衔接，不推翻 |

### Q4. 优先级 / 排到哪个里程碑？

我的建议顺序（按"**能独立跑通 + 依赖少**"排）：

1. **任务系统**（M2，单机即可完整闭环，**不依赖网络**）
2. **BOSS 副本 + 组队**（M3，依赖网络与房间）
3. **PVP**（M3/M4，依赖同步模型）
4. **成就系统**（M4，依赖"事件总线 + 持久化"，可与任务共用一套条件系统）
5. **好友 + 聊天**（M4/M5，**需要独立社交服 + 持久化 + 敏感词**，工作量常被低估）

### Q5. "开放世界"到什么程度？

| 选项 | 说明 | 建议 |
| --- | --- | --- |
| A（推荐）**分区加载的大地图** | 一块区域一张场景，走传送/过场；实现上就是"多场景 + 分块资源" | 对 Demo 完全够，成本低一个数量级 |
| B 真·无缝开放世界 | 地形流式加载、无缝边界、LOD、动态分块 | 光是"无缝地形"就是数月的专项 |

## 四之一、✅ 负责人的决定（2026-09-22）

| # | 问题 | 决定 | 直接后果 |
| --- | --- | --- | --- |
| **Q1** | 目标定位 | **作品集 Demo** | 每个系统做**最小可信闭环**；"讲得清取舍"与"跑得通"同等重要 |
| **Q2** | 同步模型 | **混合** | 大世界/社交/任务 = **状态同步（服务器权威）**；**PVP 小房间可切帧同步**（复用 D2 的确定性成果） |
| **Q3** | 规模 | **2~4 人**（房间制） | ✅ **顺带砍掉一批最贵的东西**：**不需要 AOI（可见性裁剪）、不需要分线/分服**。开放世界按"**分区加载的大地图 + 每区最多 2~4 人可见**"来做 —— 这是本轮**最大的成本节约** |
| **Q4** | 优先级 | 按推荐 | 任务(M2) → 副本+组队(M3) → PVP(M3/M4) → 成就(M4) → 好友+聊天(M4/M5) |
| **Q5** | 开放世界程度 | **分区加载的大地图** | 一块区域一张场景 + 传送/过场；**B 组分组策略要加"按区域分块"这一维** |

> 📌 **Q3 值得单独说一句**：我原本按"商业级 MMORPG"的直觉把 AOI/分线列成了影响项，
> 而"**2~4 人**"这个答案把它们**整条砍掉**了。
> 这说明"先定规模再定架构"是对的 —— **规模没定时，讨论 AOI 是纯浪费**。
