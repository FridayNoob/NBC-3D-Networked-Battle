## 一、M3 要达成什么

**一句话**：**两个客户端**组队进副本，**打死 1 个 BOSS**，**掉落一致**。

### 1.1 验收标准（源自 `Docs\20` §三 M3 行）

| # | 完成标准 | 验证方式 |
| --- | --- | --- |
| V1 | 自研传输层跑通（`Google.Protobuf` 载荷，**两端同一份协议代码**） | 一个 echo/心跳协议端到端 |
| V2 | 房间与席位：2 人能进同一个房间，各自收到**同样的世界状态** | 两个客户端各自的画面/日志一致 |
| V3 | **状态同步（服务器权威）**：服务端 30 Hz 跑战斗、下发快照 | 服务端日志与客户端表现对得上 |
| V4 | 副本实例 + BOSS（复用 A10 状态机） | 打死 BOSS |
| V5 | **掉落一致**：服务端权威掉落，两边看到一样的东西 | 两边收到同一份掉落 |

### 1.2 明确不做（写清楚，免得以后以为漏了）

| 不做 | 什么时候做 |
| --- | --- |
| **匹配队列** | **维持不做**（`Docs\01` §260–261 的非目标） |
| `HostPlayMode`（热更） | M5 |
| 多阶段 / 多 BOSS / 难度分级 / 随机词缀 | 作品集 Demo 不做（`Docs\20` §二） |
| 观战 / 回放 | 不做 |
| **客户端预测 + 回滚** | **M4**（PVP 帧同步时才需要；M3 先正确、后手感） |
| AOI / 分线 / 分服 | ✅ **已按 Q3（2~4 人）砍掉** |

### 2.1 环境约束（实测，会直接影响写法）

| 约束 | 应对 |
| --- | --- |
| **沙箱里 NuGet restore 不可用**（`NU1301`） | 服务端**只允许 BCL**；第三方（protobuf）走仓库里的 DLL |
| `dotnet build` 必须 **`-m:1`** | 所有构建命令都带 |
| `dotnet run` 必须 **`--no-build`**（否则沙箱下构建 stdio 被挡） | 先 build 再 run |
| **AI 不能开 Unity、不能点菜单**（规则 13） | 客户端的场景/预制体由负责人操作 |

## 三、关键决策（**请负责人过目**；推荐已标注）

| # | 决策 | 推荐 | 理由 | 别的选项 |
| --- | --- | --- | --- | --- |
| D1 | **传输层** | **TCP + 4 字节长度前缀 + protobuf 载荷** | M3 是**状态同步**，"可靠 + 有序"最重要；自研（需求 12 的例外 E2）；**不引第三方**；几十行就能跑通 | 直接上 UDP+KCP 式重传：M3 用不上，且调试成本高 |
| D2 | **服务端 tick** | **30 Hz**（需求 §6.1 已定） | 客户端 60 fps、服务端 30 Hz 下发，2~4 人完全够 | —— |
| D3 | **权威边界** | **服务端算伤害/位置/掉落**；客户端只发**意图**（输入命令） | 这是"服务器权威"的定义；也让 M4 的 PVP 能直接复用 | 客户端自算 + 服务端校验（更复杂，M3 不需要） |
| D4 | **要不要客户端预测** | **M3 不做**（**有意**的取舍） | 先正确、后手感；预测+回滚属 M4 的帧同步 | 现在做 → M3 会变成"手感 + 网络"两件事一起调 |
| D5 | **同步内容与粒度** | 每 tick **全量实体快照** + 事件（伤害/死亡/掉落） | 2~4 人、实体数少 → 全量最省心；**差分/压缩留 M5** | 增量同步：现在做会先优化后正确 |
| D6 | **房间与副本** | **一个房间 = 一个副本实例**；进程内 `RoomRegistry`，每房 2~4 席位 | 最简单又能演示组队；也天然支持"打完退出" | 独立副本服：M5+ |
| D7 | **共享什么** | 协议（`.proto`）+ **M2 已有的伤害结算/条件系统**；**位置移动的确定性逻辑暂不共享** | M3 不是帧同步，位置由服务端权威下发即可；共享层已经在，白拿 | 现在就把移动也做成确定性的：M4 帧同步时再做 |
| D8 | **两个客户端怎么跑** | **一个 Editor + 一个打包版**（需要打一次包） | Unity 里同时 Play 两个实例做不到；这是最省事又真实的方式 | ParrelSync 之类第三方工具：多一个依赖，且是编辑器插件 |

## 四、切片顺序（每片自成闭环）

| 片 | 内容 | 产出 | 验收 |
| --- | --- | --- | --- |
| **S1** | **协议定义**：`Protocol/nbc_m3.proto`（握手/进房/席位/输入/快照/伤害事件/死亡/掉落）+ protoc 生成两端 C# | `.proto` + 生成物入库 | 两端都能编过（客户端走编译闸门，服务端走 `dotnet build -m:1`） |
| **S2** | **传输接缝 + 实现**：框架侧只定义 `ITransport`（**不认识 TCP**）；新增适配程序集装 TCP 实现（BCL `System.Net.Sockets`，不算第三方） | 接缝 + 实现 + EditMode 用例（假传输） | 假传输上跑通"发送→分帧→回调" |
| **S3** | **端到端回环**：服务端监听 + 客户端连接 + 心跳/echo | 服务端 `NBC.Server.Host` 能起、客户端能连 | **本机两个进程互通**（这是"网络真的通了"的第一证据） |
| **S4** | **房间与席位**：`RoomRegistry` + 加入/离开 + 席位广播 | 房间模块 + 用例 | 2 个连接进同一房间、各自收到席位表 |
| **S5** | **状态同步**：服务端跑战斗（**复用共享层伤害结算**）+ 30 Hz 快照下发 + 客户端按快照更新 | 同步模块 + 用例 | 客户端表现与服务端日志一致 |
| **S6** | **副本 + BOSS**：`Dungeon`/`DropTable` 配置表 + 怪物 AI（复用 A10 状态机）+ BOSS 技能 | 配置表 + AI + 用例 | 打死 BOSS |
| **S7** | **掉落一致**：服务端权威掷掉落并广播 | 掉落模块 | 两边收到**同一份**掉落 |
| **S8** | **网络模拟器**（`NET-07`，⚠️ **面试关键道具**）：可注入延迟/丢包/抖动 | 模拟器 + 用例 | 注入 200ms 延迟后仍能打完 |
| **S9** | **端到端验收 + 收关**：两个客户端进副本打死 BOSS、掉落一致 | `Docs\26-M3收关报告.md` + 教学留档 | 负责人亲手跑通 |

> 📌 顺序的理由：**先把"能通"证明掉（S2/S3），再谈同步逻辑**。
> 反过来做的话，一旦不通，你分不清是"同步写错了"还是"根本没连上"。

## 六、风险（如实记）

| # | 风险 | 应对 |
| --- | --- | --- |
| 1 | **两客户端联调麻烦**（要打包一次） | S8/S9 才需要；前面所有片都能"单进程 + 假传输"验证 |
| 2 | 沙箱 NuGet 不可用 | 服务端只用 BCL；protobuf 用仓库里的 DLL |
| 3 | **状态同步的手感**（没有预测 → 操作有延迟） | **有意**的取舍（D4）；M4 做预测+回滚时再解决，而且那时正是"帧同步"上场 |
| 4 | 协议一经下发就难改 | 协议里**留 version 字段**（握手时校验），两端不一致直接拒绝并说清 |
| 5 | 服务端与客户端的**装配重复** | 共用 `BattleSession` 的**形状**（构造参数一致），但服务端不依赖 UnityEngine → 装配代码分两处，**共享的是它下面那层**（伤害结算/条件系统） |
