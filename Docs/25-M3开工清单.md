## 一、M3 要达成什么

**一句话**：**两个客户端**组队进副本，**打死 1 个 BOSS**，**掉落一致**。

### 1.1 验收标准（源自 `Docs\20` §三 M3 行）

| # | 完成标准 | 验证方式 |
| --- | --- | --- |
| V1 | 自研传输层跑通（`Google.Protobuf` 载荷，**两端同一份协议代码**） | 一个 echo/心跳协议端到端 |
| V2 | 房间与席位：2 人能进同一个房间，各自收到**同样的世界状态** | 两个客户端各自的画面/日志一致 |

## 三、关键决策（**请负责人过目**；推荐已标注）

| # | 决策 | 推荐 | 理由 | 别的选项 |
| --- | --- | --- | --- | --- |
| D1 | **传输层** | **TCP + 4 字节长度前缀 + protobuf 载荷** | M3 是**状态同步**，"可靠 + 有序"最重要；自研（需求 12 的例外 E2）；**不引第三方**；几十行就能跑通 | 直接上 UDP+KCP 式重传：M3 用不上，且调试成本高 |
| D2 | **服务端 tick** | **30 Hz**（需求 §6.1 已定） | 客户端 60 fps、服务端 30 Hz 下发，2~4 人完全够 | —— |
| D3 | **权威边界** | **服务端算伤害/位置/掉落**；客户端只发**意图**（输入命令） | 这是"服务器权威"的定义；也让 M4 的 PVP 能直接复用 | 客户端自算 + 服务端校验（更复杂，M3 不需要） |
| D4 | **要不要客户端预测** | **M3 不做**（**有意**的取舍） | 先正确、后手感；预测+回滚属 M4 的帧同步 | 现在做 → M3 会变成"手感 + 网络"两件事一起调 |
| D5 | **同步内容与粒度** | 每 tick **全量实体快照** + 事件（伤害/死亡/掉落） | 2~4 人、实体数少 → 全量最省心；**差分/压缩留 M5** | 增量同步：现在做会先优化后正确 |
| D6 | **房间与副本** | **一个房间 = 一个副本实例**；进程内 `RoomRegistry`，每房 2~4 席位 | 最简单又能演示组队；也天然支持"打完退出" | 独立副本服：M5+ |
| D7 | **共享什么** | 协议（`.proto`）+ **M2 已有的伤害结算/条件系统**；**位置移动的确定性逻辑暂不共享** | M3 不是帧同步，位置由服务端权威下发即可；共享层已经在，白拿 | 现在就把移动也做成确定性的：M4 帧同步时再做 |
| D8 | **两个客户端怎么跑** | **一个 Editor + 一个打包版**（需要打一次包） | Unity 里同时 Play 两个实例做不到；这是最省事又真实的方式 | ParrelSync 之类第三方工具：多一个依赖，且是编辑器插件 |

### 7.1 S2b 里三个值得记的决定

| # | 决定 | 为什么（**实测出来的，不是审美**） |
| --- | --- | --- |
| 1 | **接缝 `ITransport` 和 TCP 实现住同一个程序集** `NBC.Framework.Net`（`noEngineReferences: true` + 只引 `NBC.Shared`），**不放** `NBC.Framework` | 放 `NBC.Framework` 的话，网络层就挂上了 UnityEngine 依赖 → 我在沙箱里**一行都跑不了**（只能等负责人开 Unity）。挪出来之后，`Server\_condition-probe`（.NET 8）能把这批源码直接编进去**真开端口跑**：回环、粘包、拆包、对端关闭、超限帧当天就有证据。代价：网络层用不了框架的日志/事件中心（报错走 `Closed` 的人话原因，够用） |
| 2 | **`NoDelay = true`（关 Nagle）** | Nagle 会攒小包，最多压到 ~200ms 才发 → 对 30Hz 动作战斗就是"操作忽然一顿一顿的"。我们包本来就小、频率也低，值得 |
| 3 | **收到 0 字节 = 对端关了，必须当断开** | `Poll(SelectRead)` 为真但 `Available == 0` 就是 FIN。漏掉它的表现是"对方早退了，本端一直以为自己还连着" —— 又一个只在联机里才看得见的静默失败（已写成用例 `Receive_PeerCloses_ReportsClosed`） |

### 7.2 探针这一版**实测**到的两条（写下来，免得以后当成"应该是那样"）

| 场景 | 本机实测原因（探针原样打印） |
| --- | --- |
| 连一个没人监听的端口 | `连接 127.0.0.1:10027 失败：对端没有在监听（连接被拒绝）` |
| 连不可达地址 `10.255.255.1:9`（超时设 300ms） | `连接 10.255.255.1:9 超时（300ms）`，耗时 **309ms** → **走的是超时分支**（不是"网络不可达"），所以那条 Unity 用例确实覆盖到了超时这条代码路径 |

### 7.3 顺带修掉/补上的一处（诚实记）

`Tests\EditMode\Framework\AsmdefReferenceGuardTests.cs` 的映射表原来只有 11 行，且是**按命名空间全名精确匹配**的 —— 于是：

* `using NBC.Framework.Net.Adapter;`（用了实现、却只引了接缝程序集）**从表里漏过去**

### 8.5 S5 的待决问题 —— ✅ **已定案（2026-09-23，S5 开工第一件事）**

**原问题**：`SharedInfo.SnapshotSendRate = 20`（共享层写着"快照 20Hz"）与 D5 的"**每 tick 全量快照**"（= 30Hz）矛盾。

**定案：M3 的快照 = 每 tick 一张（30Hz），并删掉 `SnapshotSendRate`。**理由三条：

| # | 理由 |
| --- | --- |
| 1 | M3 **不做插值、也不做预测**（D4）→ 发得越勤画面越顺。20Hz 只会让动作更顿，没有任何好处 |
| 2 | 代价可以忽略：2~4 人、十几个单位，一张快照几百字节 → 每秒十几 KB |
| 3 | 那个 `SnapshotSendRate` **一行代码都没用到** —— 它唯一的作用是让启动日志显示一个**错数字**（这就是"两份数据一定会漂移"的最好例子） |

**顺带把根挖了**（同一类隐患一次清掉，不止这一处）：

| 改前 | 改后 | 为什么 |
| --- | --- | --- |
| `ContractVersion = 1`、`LogicTickRate = 30`、`SnapshotSendRate = 20` **各写一个数** | `ContractVersion = NetContract.Version`、`LogicTickRate = NetContract.TickRate`（**派生**），`SnapshotSendRate` 删除 | 从"两处要对齐"变成"**只有一处**" —— 漂移在编译期就不可能发生 |
| `SharedInfo.Describe()` 里印着 `Snapshot=20Hz` | 只印 `LogicTick=30Hz` | 日志里不该出现第二个、还没被兑现的速率 |
| 测试 `TickRate_MatchesSharedLayerLogicRate`（断言两个常量相等） | **删掉**，换成 `SharedInfoDescribe_MentionsOnlyOneRate` | 派生之后原断言**恒真** = 死检查（"走不到的分支比没有分支更糟"的测试版）；新测试防的是"有人再加一个速率" |
| `SkeletonSelfCheck` 断言字面量 `30 / 20` | 断言 `SharedInfo.LogicTickRate == NetContract.TickRate` | 断言真正的不变量，而不是两个魔数 |
