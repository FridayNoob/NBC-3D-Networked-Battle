## 三、FW-01 ~ FW-12 逐条记录

### FW-01 · `BaseManager<T>` 允许被 `new` 出第二个实例

| 项 | 内容 |
| --- | --- |
| 原版位置 | `Base/BaseManager.cs:7-16` |
| 原版代码 | `public class BaseManager<T> where T:new()` → `if (instance == null) instance = new T();` |
| **现象** | 任何代码都能写 `new PoolMgr()`。它与 `PoolMgr.GetInstance()` **不是同一个对象**，两份状态各改各的；不报错、不警告 |
| **根因** | ① 基类没有对**子类构造可见性**做任何限制；② 更关键：`where T : new()` 这个约束**反过来要求** `T` 具有 **public** 无参构造 —— 也就是说"给子类加 `private` 构造"与"在基类用 `new T()`"在 C# 里**互相排斥**（见下方改法的技术抉择） |
| 审计补充 | 框架**内部** 8 处调用全部走 `GetInstance()`（grep `new \w+Mgr\s*\(` 全工程无结果）。所以"单例失效"目前是**潜伏缺陷**，不是已发生事故。**更现实的入口是 `public` 字段**：`Pool/PoolMgr.cs:66 poolDic`、`AStar/AStarMgr.cs:15 nodes`、`UI/UIManager.cs:25 panelDic` / `:33 canvas` —— 外部可直接改状态，绕开所有方法 |
| **改法（A1）** | 不移植 `BaseManager<T>`，改为 `Singleton<T>`（CRTP：`where T : Singleton<T>, new()`）+ 三条防线：<br>① **锁 + 二次检查**（线程安全）；<br>② **构造期防重入断言**：基类构造里若"已创建过实例"则 `throw InvalidOperationException` 并在消息里点名"请用 `Xxx.Instance`" → 让 `new` 在**调用点**爆掉，而不是静默产生第二份状态；<br>③ **`[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` 静态重置**（应对"关闭 Domain Reload"的 Enter Play Mode Options，即 FW-M01 的"场景重载安全"）；<br>④ 内部状态字段一律 `private`，只暴露只读视图（治"public 字段"这个更现实的入口）；<br>⑤ `GetInstance()` 保留为 `Instance` 的别名 —— **兼容原调用点**（见 §六） |
| **技术抉择（为什么不用 private 构造）** | 想用编译期禁止 `new`，只能 `private` 构造，而 `private` 构造就不能 `new T()`，只剩 **`Activator.CreateInstance(typeof(T), nonPublic: true)`** 这条路 —— 那是**反射**。M0 的 D17 已经用血证明：**本项目 IL2CPP 路径上的反射要付额外代价**（protobuf-net 就是死在反射式建模上）。所以这里**主动选择**"运行时断言 + 文档约束"，**换掉**"编译期保证 + 反射"。这个权衡要能讲出来 |
| **验证** | EditMode 测试（`NBC.Tests.EditMode`）：<br>① `GetInstance_CalledManyTimes_ReturnsSameInstance`；<br>② `NewOutsideSingleton_Throws`（断言异常消息含类型名）；<br>③ `Instance_AfterDomainReloadReset_IsRecreated`（手动调 `ResetForTests()` 模拟） |
| 状态 | 🟢 **已修复并验证**（2026-09-20）：编译闸门 0 错 + EditMode 7/7 + PlayMode 8/8 —— 见 §9.4 / §9.7.6 |

### FW-02 · `SingletonMono<T>.GetInstance()` 可能返回 `null`

| 项 | 内容 |
| --- | --- |
| 原版位置 | `Base/SingletonMono.cs:12-18` |
| 原版代码 | `public static T GetInstance() { return instance; }`（注释还写着"U3D 内部帮助我们实例化它"） |
| **现象** | 只要 `Awake` 没执行过（对象未激活 / 未挂载 / 已被销毁），`GetInstance()` 就返回 `null`，调用方在最远处 NRE |
| **根因** | 静态字段**只由 `Awake` 赋值**，没有任何兜底查找，也没有生命周期校验。单例的"存在性"被绑死在"某个场景对象恰好被激活"这个脆弱前提上 |
| 审计补充 | `SingletonMono<T>` 在 `FrameTang` 工程内 **零子类、零引用**（grep `class \w+ : (SingletonMono\|SingletonAutoMono)` 无结果）→ 缺陷**未触发**，属潜伏 |
| **改法（A1）** | 三条兜底：<br>① `Instance` 里若字段为空 → `Object.FindFirstObjectByType<T>()` 主动找（覆盖"场景里手动摆了对象但还没 Awake"）；<br>② 找到后校验并回填字段；<br>③ `OnDestroy` 中**仅当 `instance == this`** 时清空（避免"旧对象销毁把新对象注册的单例清掉"这一经典 Bug） |
| **API 前提核对** | `FindFirstObjectByType<T>()` 是 Unity **2022.2+** 新增（`FindObjectOfType` 在 2022.3 已标过时）。本项目是 2022.3.62f3c1 → **落笔前用 DLL 元数据核对一次该 API 确实存在**（M0 建立的方法：读 `UnityEngine.CoreModule.dll` 的导出符号，不靠记忆） |
| **验证** | EditMode/PlayMode 测试：<br>① `GetInstance_WhenNoneInScene_ReturnsNull_OrThrows`（明确语义，二选一写死）；<br>② `GetInstance_WhenInSceneButAwakeNotRun_FindsIt`；<br>③ `AfterDestroy_GetInstance_DoesNotReturnDestroyedObject` |
| 状态 | 🟢 **已修复并验证**（2026-09-20）：编译闸门 0 错 + EditMode 7/7 + PlayMode 8/8 —— 见 §9.4 / §9.7.6 |

### FW-03 · `SingletonAutoMono<T>` 缺**并发 / 重入**保护

| 项 | 内容 |
| --- | --- |
| 原版位置 | `Base/SingletonAutoMono.cs:13-24` |
| **⚠️ 措辞修正** | 需求文档原文写"未做**重复创建保护**"—— **与代码不符**。代码**有**判空：`if ( instance == null ){ ... }`。真正缺的是 **`lock` 与二次检查**（check-then-act 非原子） |
| **现象（诚实地缩小）** | 单线程、单次调用路径下**看不出问题**。要触发"建两个"需要两个线程同时进入 `if`。但 Unity 的 `new GameObject()` / `AddComponent` **只能在主线程调用**，多线程走到这里会直接抛异常 → **"多线程建多个实例"在本工程内不可复现**。<br>所以这一条修的是**模式正确性**（FW-M01 明确要求"线程安全"），不是"已复现的 bug" |

### FW-04 · 缓存池取对象是 O(n)

| 项 | 内容 |
| --- | --- |
| 原版位置 | **`Pool/PoolMgr.cs:47-48`（`PoolData.GetObj`）** —— ⚠️ 需求文档写的是 `PoolMgr.GetObj`，**位置不准**：`PoolMgr.GetObj`（`:75-95`）只是转发，`RemoveAt` 在 `PoolData` 里 |
| 原版代码 | `obj = poolList[0]; poolList.RemoveAt(0);` |
| **现象** | 池内 N 个对象时，每次取出要把后面 N-1 个元素整体前移 → 取出 N 次共 O(N²)。子弹/飘字这类"每帧取几十个"的池会直接吃满 CPU |
| **根因** | 用 `List<T>` 实现了**队列语义**（FIFO：先回收的先取出），而 `List` 的头删是 O(n)。这是"数据结构选错"，不是"代码写得丑" |
| **改法（A2）** | 换 `Stack<GameObject>`（LIFO，`Pop/Push` 均摊 O(1)）。**顺带一个副作用要讲清楚**：LIFO 会优先复用"刚刚回收的对象"，对 CPU cache 更友好；但会改变"复用顺序"，如果某模块依赖 FIFO 顺序（本项目没有），需要显式用 `Queue` 或环形缓冲 |
| 附带发现 | `PoolMgr.GetObj` **只从已有抽屉里取**（`:75-95`），抽屉空时才 `ResMgr` 新建；而**没有任何代码会自动 `PushObj`** → 池内元素只增不减。这让 O(n) 的头删随运行时间越来越痛（与 FW-05 是一条因果链） |
| **验证** | 纯 C# 层即可测（不需要 Unity）：`List.RemoveAt(0)` 基线 vs `Stack.Pop`，N=1万/10万 的 `Stopwatch` 对比，数字写进本文档；再加 EditMode 测"取出 1万次后池统计正确" |
| 状态 | 🟢 **已修复并验证**（2026-09-20）：编译闸门 0 错 + EditMode **31/31** + PlayMode **19/19** 全绿 —— 见 §十 |

### FW-05 · 缓存池无上限、无自动回收

| 项 | 内容 |
| --- | --- |
| 原版位置 | `Pool/PoolMgr.cs:100-115`（`PushObj` 无上限判断）、`:29-37`（`PoolData.PushObj` 只 `Add`）、`:122-126`（唯一清理入口 `Clear()`，手动） |
| **现象** | 一场战斗里被回收的对象永远留在池里；没有任何"按容量/按时间"的回收策略 → 内存单调增长。全工程**没有任何**时间戳/计数上限/自动回收的代码 |
| **根因** | 池只实现了"复用"，没实现"治理"。池的收益（省 Instantiate）与代价（常驻内存）需要一个**上限**来平衡，原版只有收益侧 |
| **改法（A2）** | 每池 `maxSize`（超出即 `Destroy`，不进池）+ 可选**空闲超时回收**（对象记 `lastUsedTime`，定时扫描清理长期不用的，应对"波次战斗之间内存不释放"）+ **统计**（取出次数 / 新建次数 / 回收次数 / 当前容量 / 峰值 / **复用率**）。统计直接服务 **V8** |
| 附带发现（P-04） | `Clear()` 只做 `poolDic.Clear(); poolObj = null;` —— **既不 `Destroy(poolObj)`，也不销毁抽屉父对象与池内对象**。注释写"主要用在 场景切换时"，而实现**根本没起到清理作用**，池内对象变成**场景孤儿**（还有一部分在外使用的对象连清点都做不到）。这是"注释与实现不符"的实例 |
| **验证** | 压测脚本（纯 C# 或 EditMode）：新建 1000 个、回收 1000 个、上限设 100 → 断言池容量 == 100 且统计里"销毁数"== 900；`Clear()` 后断言 `Object.FindObjectsOfType` 找不到残留 |
| 状态 | 🟢 **已修复并验证**（2026-09-20）：编译闸门 0 错 + EditMode **31/31** + PlayMode **19/19** 全绿 —— 见 §十 |

## 五、对本次审计自身的修正（规则 W9 的执行）

W9 说"**验证脚本本身也要被验证**"。这一节记录：本次审计在哪些地方**先入为主**，以及**怎么发现并纠正的** —— 这比结论本身更有教学价值。

### 5.1 修正一：FW-03 的措辞（审计结论正确，需求文档错）

- 需求文档："`SingletonAutoMono<T>` 未做**重复创建保护**"。

### 5.2 修正二：FW-09 的措辞（审计报告本身也错了一处）

发现过程值得完整记下来：

1. 需求文档说"`Destroy` 与缓存池冲突"。
2. 审计报告核对了代码，正确地指出"**缓存池没参与音频路径**"，但**为了给这条缺陷找个更严重的解释**，额外加了一句："`:31` 传 `AudioSource` 给 `GameObject.Destroy` 重载，语义合规（**等价于销毁其 gameObject**）"。
3. 这句话**是凭记忆下的判断**。我去查了 [Object.Destroy 官方文档](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Object.Destroy.html)：

   > *"If `obj` is a `Component`, this method removes the component from the `GameObject` and destroys it. If `obj` is a `GameObject`, it destroys the `GameObject`, all its components and all transform children."*

   → 销毁 `AudioSource` 组件**不会**销毁 `soundObj`。审计的补充解释**是错的**。
4. 纠正后的 FW-09 真实问题重新定位为 3 条（不复用、宿主未 `DontDestroyOnLoad`、`Update` 无防御），见 §三 FW-09。

> **教训**：审计者（无论人还是 AI）在"想论证一个结论"时，最容易在**细节机制**上凭记忆补故事。
> 这就是为什么本项目把"能实测的绝不靠记忆"写成规矩 —— 它对**审查者**同样适用。

## 六、重写兼容边界（**A 组的硬约束**）

> 这一节回答一个问题：**哪些签名不能随意改？**
> 答案来自"实测调用点"，不是"看起来该保留什么"。

### 6.1 被实际调用的 5 组签名（约 20 处调用）

| 组 | 签名 | 调用点 |
| --- | --- | --- |
| 基类 | `T GetInstance()`（**静态、无参**） | 8 个管理器的所有业务调用点 |
| 事件 | `AddEventListener<T>` / `AddEventListener` / `RemoveEventListener<T>` / `RemoveEventListener` / `EventTrigger<T>` / `EventTrigger` / `Clear` | `ScenesMgr.cs:51`；`InputMgr.cs:38,41`（框架内）；业务侧 |
| Mono | `AddUpdateListener(UnityAction)` / `RemoveUpdateListener(UnityAction)` / `StartCoroutine(IEnumerator)` | `ResMgr.cs:31`、`ScenesMgr.cs:35`、`MusicMgr.cs:22`、`InputMgr.cs:19` |
| 池 | `GetObj(string, UnityAction<GameObject>)` / `PushObj(string, GameObject)` / `Clear()` | 框架内无调用者（业务侧） |
| 资源 | `T Load<T>(string)` / `void LoadAsync<T>(string, UnityAction<T>)` | 6 处（见 6.2） |

**结论**：`Singleton<T>.GetInstance()`、`MonoMgr` 的三个方法、`EventCenter` 的 7 个方法、`PoolMgr` 的三个方法 —— **重写时可以改内部实现，但要保留这些形状**（至少保留一层兼容 API），否则所有业务调用点编译失败。

### 6.2 `ResMgr` 的**隐式契约**（`AssetManager` 必须分流）

`ResMgr` 只有 2 个公开方法，但 6 个调用点**依赖了 3 条没写在签名里的约定**：

| # | 隐式契约 | 证据（调用点） |
| --- | --- | --- |
| 1 | 泛型参数 `T : Object`，路径是 **`Resources` 相对路径、无扩展名**（`"UI/Canvas"`、`"Music/BK/Black"`） | 全部 6 处 |
| 2 | **`GameObject` 自动 `Instantiate`，其他类型返回共享 asset** | `ResMgr.cs:20-21,40-43`；`PoolMgr.cs:85`（回调里直接改 `o.name`）、`UIManager.cs:93`（直接 `SetParent` + `GetComponent<T>`）、`MusicMgr.cs:50,103`（直接用 `clip`） |
| 3 | `LoadAsync` 是**回调式**（`UnityAction<T>`），不是 `await`/`Task`/句柄式；内部用 `MonoMgr.StartCoroutine` 驱动 | `ResMgr.cs:31` → **AssetManager 的异步路径仍需要 `MonoMgr` 先可用** |

**第 2 条是最容易踩的**：`YooAsset` 的句柄给我们的是**原始 asset**，`Instantiate` 要自己做。适配层若不做分流，6 个调用点会**全部行为错乱**（比如把 prefab 的共享资源直接 `SetParent`，污染所有实例）。

**另**：路径前缀 `"UI/"`、`"Music/BK/"`、`"Music/Sound/"` 是硬编码在框架里的**目录约定** → 迁移到 YooAsset 的 Address/Location 体系时要一并设计（建议统一为 Address 常量表，顺带解决 FW-06 同类的魔法字符串问题）。

> ⚠️ **2026-09-20 更正（B2 实施时推翻了本节的一条结论）**：
> 上面第 2 条说"适配层必须复刻『GameObject 自动实例化』这条隐式契约，否则 6 个调用点行为全错"。
> **这个前提不成立** —— 那 6 个调用点**全在原框架自己**的 `PoolMgr` / `UIManager` / `MusicMgr` 里，
> 而这些模块我们**正在重写**（A2 已完成，A8/A9 待做），所以**没有兼容包袱**。
>
> 于是 B2 **有意改变**了这个行为：**`LoadAssetAsync<GameObject>` 返回原始 prefab，不自动实例化**。
> 三条理由：① "加载资源"和"创建实例"本来就是两件事，原版混在一起正是麻烦来源；
> ② **能和 A2 的池自然组合**（池本来就通过工厂拿对象：`new GameObjectPool(name, () => Instantiate(prefab), ...)`）；
> ③ 避免"资源引用计数"与"实例生命周期"两套东西纠缠（实例谁销毁？原版根本没回答）。
>
> **A8/A9 写调用方时必须按新语义来。** 判定依据与完整理由见 §十四 的 14.2。

**现有资源实际只有 4 个**（实测列举）：`Assets/Resources/UI/Canvas.prefab`、`Assets/Resources/UI/EventSystem.prefab`、`Assets/Resources/Music/BK/Black.mp3`、`Assets/Resources/Music/Sound/Black.mp3` → **迁移工作量很小**，这是好消息。

### 6.3 依赖方向与**替代顺序**

实测的引用关系（`→` = 编译期引用）：

```
MonoMgr        ← 无依赖（最底层）
EventCenter    ← 无依赖（只依赖 System.Collections.Generic + UnityEngine.Events）
BaseManager    ← 无依赖（被除 BasePanel / MonoController / AStarNode 外所有管理器继承）
ResMgr         → MonoMgr
PoolMgr        → ResMgr
ScenesMgr      → MonoMgr, EventCenter
MusicMgr       → MonoMgr, ResMgr
InputMgr       → MonoMgr, EventCenter
UIManager      → ResMgr
BasePanel      ← 无框架依赖
AStarMgr       ← 无框架依赖（纯算法）
```

- **没有编译期循环依赖** ✅
- **但存在运行期反向依赖** ⚠️：`MonoMgr → MonoController → Update → MusicMgr.Update / InputMgr.MyUpdate`。
  即 `MonoMgr` 在**运行期反向驱动**上层模块的每帧逻辑 —— **控制反转只发生在运行期**。这是重写时最容易踩的耦合点（A4 必须处理）。
- **单例访问是全局静态**：全部走 `Xxx.GetInstance()`，**没有 DI / 服务定位器接口** → 编译期依赖图**无法约束**实际耦合（这条是 FW-12 的深层原因，也是 A11 要面对的真问题）。

**替代顺序**（为什么这么排）：

```
① MonoMgr + EventCenter      ← 两个真正的底层（无依赖）
② AssetManager（替代 ResMgr） ← 被 Pool / UI / Music 依赖，自己又依赖 MonoMgr
③ Pool / UI / Music / Input / Scenes
```

### 9.2 三个关键实现决策（面试可以直接讲）

| # | 决策 | 为什么 |
| --- | --- | --- |
| 1 | **不用反射**换编译期保证 | 想"编译期禁止 `new`"必须 `private` 构造，而 `private` 构造与 `where T : new()` 互斥，只剩 `Activator.CreateInstance(..., nonPublic: true)`。本项目在 IL2CPP 上已实测过反射的代价（D17 / protobuf-net），所以主动选择"运行期断言 + 明确错误消息"，而不是"编译期保证 + 反射" |
| 2 | **`[ThreadStatic]` 的"内部创建中"标记** | 构造函数据此区分"单例自己创建"与"外部误写 new"。用 `ThreadStatic` 而非普通静态 bool：否则 A 线程创建期间，B 线程的 new 会被误放行 |
| 3 | **`OnInit()` 跑完才发布 `s_instance`** | 别的线程不会拿到"初始化了一半"的单例。代价是多一个 `s_pending` 字段来处理"`OnInit` 里重入访问 `Instance`"的情况（否则会死等自己持有的锁） |

### 9.3 A1 过程中被自己推翻的两个设计（W9 自检）

写在文档里，是因为**这两次都是"写下去之后才发现有问题"，而不是一开始就想清楚的**：

| # | 第一版写法 | 漏洞 | 为什么会漏 |
| --- | --- | --- | --- |
| 1 | 构造函数用 `s_created` 标志："已经创建过一次就不许再 new" | **如果第一次访问就是外部 `new`，那次 new 会被放行**，随后 `Instance` 仍会创建自己的那一个 → 又出现两个实例，而且是**静默的**。这与 FW-01 要修的病是同一个病 | 只想着"挡住第二次 new"，没想"第一次 new 发生在 Instance 之前"这条路径 |
| 2 | 用**静态** `s_awakeCalled` 判断"基类 Awake 是否执行过" | 静态状态被重置后（关闭 Domain Reload 每次进 Play 都会重置），场景里**确实 Awake 过**的对象会被连累成 false → **误报**"子类隐藏了 Awake" | 把"某个对象的事实"挂在了"类型"身上。改成**实例字段 `m_registered`** 后与任何重置无关 |

> 这两条都是**自查**发现的（第一版还没编译就跑出问题）。规则 W9 说的"验证者也要被验证"，
> 在写代码时同样成立：**写完不等于对，要主动找反例**。

**关键推理 —— 为什么"全绿"本身就回答了泛型基类那个问题，而且比诊断实验更有说服力：**

第 9.7.4 节本来打算用 5 对照实验去问"泛型基类会不会丢 `Awake`"。
但 **8 个 PlayMode 用例的通过，把同一个问题回答得更硬** —— 因为它们是**断言**，不是**观察**：

| 用例 | 若泛型基类丢 `Awake`（`C = 0`）会怎样 |
| --- | --- |
| `SingletonMono_WhenInScene_ReturnsTheComponent` | 断言 `AwakeCount == 1` → 必红 |
| `SingletonMono_FindFallback_..._AfterStaticReset` | `Awake` 没跑 → `m_registered == false` → 命中"基类 Awake 从未执行过"的 **LogError** → 未预期日志 → 必红 |
| `SingletonMono_AfterDestroy_...` | 断言 `HasInstance` 为真 **且** `DestroyCount == 1` → 必红 |
| `SingletonMono_DuplicateInScene_...` | 那条"场景中存在多个"的日志由 `Awake` 打出 → `LogAssert.Expect` 落空 → 必红 |
| `SingletonAutoMono_WhenNotInScene_CreatesOne` | 断言 `AwakeCount == 1` → 必红 |

**它们全绿 ⇒ `Awake` 确实被派发到了泛型基类里 ⇒ `C = 1`。**

额外收获：`SingletonMono_AfterDestroy` 里的 `DestroyCount == 1` 是由基类的 `private void OnDestroy()` 累加的，
所以 **`OnDestroy` 在泛型基类里同样被正常派发** —— 一次覆盖了两个生命周期消息。

> ✅ **结论：那个 Unity IssueTracker 条目（*"Awake methods of generic class children are not called"*）
> 在 Unity 2022.3.62f3c1 上不成立 / 不适用。`SingletonMono<T>` 与 `SingletonAutoMono<T>` 的写法无需改动。**

> 📌 **方法论收获（比结论更值钱）**：
> 我设计诊断实验时只想着"造 5 个对照去问一个问题"，
> 却忘了**已经写好的断言本身就是更强的实验** —— 一个会失败的断言，就是一次会自己喊出来的对照。
> 更省事的顺序本应是：**先看断言型测试红在哪，再决定要不要造观察型实验**；
> 观察型实验留到"全绿但仍然怀疑某件事"时再用，那时它才真正值钱。

### 11.4 两条被钉成契约的语义（这是 P-18 的真正修法）

| 情形 | 行为 |
| --- | --- |
| 派发中**新增**监听者 | **不会**收到本次事件；从下一次开始收到 |
| 派发中**移除**监听者 | **仍会**收到本次事件（本次名单在派发开始时就锁定了） |

两条都与 **C# 原生 `event` 一致** —— 选"和语言一致"是为了让人不必背新规则。
为什么要有测试：第 2 条容易被当成 Bug。**行为"有测试盯着"和"碰巧如此"是两回事**——
原版的问题不是"错了"，而是**没人知道它会怎样**。

### 11.5 三层防护（都是原版没有的）

| # | 防护 | 不做的后果 |
| --- | --- | --- |
| 1 | **未注册事件告警**（每个 id 只一次，可整体开关） | 原版静默，表现为"这个回调怎么不执行"，排查成本极高 |
| 2 | **派发深度上限（8 层）** | A 触发 B、B 触发 A 的无限递归 → **栈溢出**，而栈溢出的报错几乎无法定位 |
| 3 | **异常隔离** | 某个监听者抛异常时 catch 并 `LogException`，保证错误不被吞掉、也不破坏事件中心自身状态 |

### 11.6 一个热路径上的取舍（要能讲出来）

派发时**不调** `GetInvocationList()`（用它可以得到逐监听者的容错能力），
因为那会**每次派发都分配一个 `Delegate[]`** —— 在每帧几十次事件的热路径上是稳定的 GC 压力（需求 ⑩）。

代价：某个监听者抛异常会**中断本次派发**的后续监听者（与 C# 原生 `event` 行为一致）。
取舍理由：异常本身是 Bug，应当响亮地暴露；而 GC 是每帧都在付的成本。

### 12.1 两条设计主线

| # | 主线 | 具体做法 |
| --- | --- | --- |
| 1 | **宿主与门面合并** | 原版是"纯 C# 单例 + 另一个 MonoBehaviour 宿主"两个对象，宿主在构造函数里 `new` 出来、`DontDestroyOnLoad` 却要等 `Start` → **一帧未受保护窗口**（P-13）。改造后直接 `MonoManager : SingletonAutoMono<MonoManager>`：门面对象**本身就是**那个 MonoBehaviour，`DontDestroyOnLoad` 在创建那一刻就调用，**窗口消失**，还少一层转发 |
| 2 | **订阅 / 退订对称且可见** | 每个 `AddXxxListener` 都配 `RemoveXxxListener`；`OnBeforeDestroy` 清空全部回调；另提供三个 `XxxListenerCount` 计数接口接 PerfHUD —— "是否泄漏"从靠自觉变成**屏幕上有个数字**（P-05） |

### 12.2 为什么 A4 的测试全在 PlayMode

这个类存在的意义就是"**每帧被调用**"：`Update` / `LateUpdate` / `FixedUpdate`、定时器推进、协程。
这些**只有在播放模式下才真的会发生**。而 A1 已实测：EditMode 下连 `Awake` 都不会被调用（§9.7）。
**在 EditMode 测这些等于自欺** —— 这正是那条划分规则的实际应用。

### 12.3 派发语义：与 A3 保持一致（但实现手段不同）

| | A3 事件中心 | A4 MonoManager |
| --- | --- | --- |
| 契约 | 派发中新增 → 下次生效；派发中移除 → 本次仍执行 | **完全相同** |
| 实现手段 | 利用"委托不可变"，派发前读一次字段当快照 | 用**待处理队列**：派发中的增删先攒起来，本轮结束后统一应用 |
| 为什么手段不同 | 委托链天然不可变，快照零成本 | 这里是 `List`，遍历中增删会让下标错位，必须显式排队 |

**对外语义一致，学一套规则就够** —— 这是刻意设计，不是巧合。

### 12.4 关于"可暂停"的确切定义（需求 FW-M03 只写了"可暂停"，必须写死）

`IsPaused = true` 时：**定时器与延迟调用停止推进，每帧回调照常执行。**

- 为什么每帧回调不一起停：它们是"游戏的帧驱动"。真要把整个游戏冻住，应该用 `Time.timeScale = 0`
  （那是 Unity 的机制，物理、动画、协程都会跟着停）。
- 这个类里的 `IsPaused` 只负责"时间相关的东西"，语义单一、可预期。
- **协程不受 `IsPaused` 影响** —— 它们用 Unity 自己的时间。

### 12.6 一个诚实的细节：为什么这里做"逐回调容错"，A3 却没做

| | A3 事件中心 | A4 MonoManager |
| --- | --- | --- |
| 数据结构 | 委托链（`UnityAction` 的 `+=`） | `List<UnityAction>` 手动遍历 |
| 要做到逐监听者容错 | 必须调 `GetInvocationList()` → **每次派发分配一个数组** | 直接在循环里 `try/catch` → **零额外分配** |
| 结果 | 不做容错（异常中断本次派发），与 C# 原生 `event` 一致 | 做容错（一个回调抛异常不影响其它回调） |

**取舍取决于数据结构，不是随手定的。** 这条差异已记录为"已知的不一致"，如果将来更看重一致性，
可以把事件中心也改成 List 存储 —— 但那会增加它自身的复杂度，当前不值得。

### 13.1 一条主线：**框架不认识 YooAsset**

ADR-001 决策 3 要求"业务层绝不出现 YooAsset"，决策 6 又要求适配层独立成程序集。
于是把"底层怎么捞资源"抽成一个接口，形成**依赖倒置**：

```
业务层  ->  AssetManager  ->  IAssetProvider  <-  YooAssetProvider
(NBC.Game)  (NBC.Framework)     (接口)            (NBC.Framework.YooAsset)
```

框架侧只定义 `IAssetProvider` / `IAssetLoadOperation`，**一个 YooAsset 类型都不认识**。
依赖方向是 `适配层 -> 框架`，不是反过来。

### 13.2 这条设计带来的**可测性红利**（B2 能被验证的关键）

引用计数、缓存复用、失败重试、释放时机 —— 这些**最容易出错、也最值得测**的逻辑，
全都在框架侧，而且**与用哪个资源库无关**。

所以可以用一个**假加载器**（纯内存、完成时机由测试决定）把它们完整测掉：

| 好处 | 具体 |
| --- | --- |
| 不需要 YooAsset | 不需要包配置、不需要打包、不需要真资源 |
| **结果完全确定** | 完成时机由测试控制，不会 flaky（对比：等真实异步加载完成会有时序不确定性） |
| 跑得快 | EditMode，毫秒级 |

> 这不是"顺手得到的"，而是**把职责边界划在"可测的那一侧"**换来的。
> 如果引用计数写在适配层里，就必须连着 YooAsset 一起测。

### 13.4 三级释放（ADR-001 决策 1 的引用计数语义）

| 调用 | 做什么 | 为什么这样分 |
| --- | --- | --- |
| `handle.Dispose()` | 引用计数减一，**不立刻释放** | "放下又马上要用"很常见（关掉面板又立刻打开）。立刻卸载会反复加载，反而更慢 |
| `ReleaseUnused()` | 把计数已归零的条目**真正释放** | 给一个明确的回收时机（例如切场景前） |
| `UnloadUnusedAssets()` | 先 `ReleaseUnused`，再让底层做**引擎级卸载** | 引擎级卸载比释放句柄贵得多，所以要分开、要可控 |

`Dispose()` **幂等**（重复调用不重复减计数）—— 这是 ADR-001 约束 **C6** 的要求。

### 13.5 三个"原版没有、但不加会静默出错"的细节

### 13.9 测试踩坑：**把"进程级子系统"当成"每个用例都要重置的东西"**（2026-09-20，两轮才修对）

#### 第一轮：表象是"静默 no-op"

B3 冒烟测试首跑：**3 条里 2 条红**

```
Resource package 'DefaultPackage' is already initialized.
  at YooAsset.ResourcePackage.InitializePackageAsync (ResourcePackage.cs:101)
```

根因是 TearDown 里的顺序：

```csharp
SingletonRegistry.ResetAll();          // ← 先把 AssetManager 单例清掉了
YooAssetProvider.ShutdownInstalled();  // ← 再"通过单例"去找加载器 → 找不到了 → 静默 return false
```

`Init` 的幂等检查（`ResourcePackage.cs:100-101`）在 `_initializeOp != null` 时抛 `already initialized`。
所以第二个用例一初始化就撞上它。

**第一轮的修法**：顺序对调 + 加断言"装过就必须收得掉"（不许静默）。

#### 第二轮：**修好顺序之后，暴露出更深的问题**

```
YooPackageInvalidException : Active package manifest not found.
  at ResourcePackage.CheckInitialized (ResourcePackage.cs:1002)
```

注意这条**不是** "not initialized"。`CheckInitialized` 的分支（`ResourcePackage.cs:985-1003`）说明：
**`InitializeStatus == Succeeded`，但 `ActiveManifest == null`** —— 一个**畸形状态**。
日志里还留着证据：`DownloadSchedulerOperation has been aborted`（被我 TearDown 的 `Destroy()` 打断）。

也就是说：**"`YooAssets.Destroy()` 之后重新初始化"这条路在 v3 里不可靠**。

#### 最终修法：**改设计，不是改顺序**

| | |
| --- | --- |
| **① 产品代码：`InitializeAsync` 改成幂等** | 包已存在且 `InitializeStatus == Succeeded` 就直接复用、**绝不重复初始化**。这本来就应该有——引导流程被调两次时应当是安全的 |
| **② 测试：用例之间不再销毁资源系统** | 只在 `TearDown` 里 `ResetAll()`。PlayMode 结束时 `YooAssetsDriver.OnApplicationQuit()` 会自己 `Destroy()`（`YooAssetsDriver.cs:29-32`，仅编辑器） |
| ③ 三个用例都自己"装 + 初始化" | 因为有幂等，第一个真正初始化，其余复用 → **执行顺序不再影响结果** |

#### 两条可以带走的教训

| # | 教训 |
| --- | --- |
| 1 | **"每个用例都重置一切"这个习惯，对"进程级子系统"是错的。** 资源系统、网络栈、渲染管线这类东西天然是**一个进程一份**；硬要在测试之间拆掉重建，是在测试一个**真实运行中根本不存在的路径**。这次我就是在测那条路径，而且它还真的有 Bug |
| 2 | 但**第一轮的问题依然真实**：它和本项目反复在打的缺陷是同一类 —— `Clear()` 不清理（P-04）、订阅不退订（P-05）、拼错 key 静默不触发（FW-06）、`Destroy` 一帧窗口（P-13）—— **共同点都是"什么都没做，但也没说"**。所以"**收尾动作返回 `bool` 表示是否真的做了**"这个写法保留（`ShutdownInstalled()` 就是这么设计的，它仍是对外有用的 API，只是不该在用例之间调） |

> 📌 **诊断方法论上的一点**：第二轮错误信息里那个 `Active package manifest not found` 是**关键线索**——
> 它和第一轮的 `already initialized` **不是同一个症状**。如果我看到"又红了"就凭印象再改一次顺序，
> 会一直在原地打转。**每次都要重新读错误信息，而不是套用上一次的结论。**

### 13.10 已知局限

| # | 局限 | 影响 | 兜底 |
| --- | --- | --- | --- |
| 1 | 同一地址按不同类型加载会**各缓存一份**（缓存键含类型） | 极端情况下同一资源被底层加载两次 | 语义上更正确；YooAsset 自身也按地址去重，真正的重复加载有限 |

### 14.2 为什么场景要单独一套类型（不复用 `AssetHandle<T>`）

| # | 差别 |

### 14.3 FW-11 的修法：**把时间从 Unity 手里拿回来**

原版：

```csharp
while (!ao.isDone)
{
    EventTrigger("进度条更新", ao.progress);
    yield return ao.progress;          // ← float 不是合法的等待指令
}
```

`yield return` 后面跟的是**等待指令**，Unity 只认那 7 种；`float` 不在其中 →
这个 while 其实是**每帧轮询**，进度事件**每帧发一条**。

改造后的 `SceneLoader` **不写协程**，而是 `Tick(float deltaTime)` 驱动的状态机：

| 场景 | 谁调用 `Tick` |
| --- | --- |
| 游戏运行时 | `MonoManager`（A4）每帧调用（`OnInit` 里注册） |
| **单元测试** | **测试自己调**，可以精确控制"过了多少秒" |

**这条设计的价值很直接**：超时逻辑（30 秒）如果必须真等 30 秒才能测，那它**多半不会被测**。
抽成 `Tick` 之后，一次 `Tick(31f)` 就测完了 —— 而且完全确定，不 flaky。

`OnInit` 里用 `Application.isPlaying` 挡住 EditMode：EditMode 下 `Update` 不执行（A1 实测），
注册了也没用，反而会平白创建一个宿主 GameObject。

### 14.4 逐条对照

| 编号 | 原版 | 改造后 |
| --- | --- | --- |
| **FW-11** | 每帧广播进度（`float` 当成等待时长） | **只在进度真的变化时广播**（变化小于 0.001 不发）。一次加载的事件条数从"几百条"降到"几条到几十条" |

### 15.1 核心：**采集与命令必须分两层**

```
玩家按键 → 采集（IInputSource） → 生成"输入命令"（InputCommand） → 发给服务端
                                     ↑ 带帧号、可重放、确定性
```

| 层 | 关心什么 | 为什么必须分开 |
| --- | --- | --- |
| **采集** | 这一刻键盘/手柄是什么状态 | 与设备相关，**不可确定性重放** |
| **命令** | 这一帧玩家想做什么 | 与设备**无关**、可序列化、可发给服务端 |

帧同步要求"同样的命令序列 → 同样的结果"。如果逻辑层直接读 `Input.GetKey`，
**服务端根本没有键盘**，重放无从谈起 —— 所以这不是风格问题。

**这条分离还白捡了一个可测性红利**：真键盘在自动化测试里造不出来，
但注入一个假 `IInputSource` 可以 —— 于是命令层 27 条用例全部可测、完全确定。

### 16.4 池满的规则（**写死，不靠猜**）

`ActiveVoiceCount == MaxConcurrentVoices` 时再 `Play`：

| 步 | 动作 |
| --- | --- |
| 1 | 在正在播的里面找**优先级最低**的；**同级取最老的**（按发放顺序 `Sequence`） |
| 2 | 若它的优先级**严格低于**新请求 → **抢占**它（停掉、复用），`PreemptedCount++` |
| 3 | 否则 → **丢掉新请求**，返回 `AudioVoiceHandle.None`，`DroppedCount++` |

> ⚠️ 「**严格更低**」这四个字是关键：**同级不抢**。
> 否则两个同优先级的音效会互相踩，表现是"密集打击音时后一个把前一个吃掉" —— 比丢音效更难查。
> 推论：`Critical` **永远不会被抢占**（没有比它更高的），这正是它存在的意义（剧情语音不该被打击音吃掉）。
> 三条边界各有一个用例：`Preemption_SamePriority_DoesNotPreempt` / `Preemption_CriticalIsNeverPreempted` / `Preemption_SamePriorityVictims_TakesTheOldest`。

### 16.5 三个刻意的设计选择

| # | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 1 | **只收 `AudioClip`，不收资源地址** | `FW-M08` 的原文是"背景音乐 + 3D 音效池 + 音量分组 + 回池"，**没有**"按地址加载"。原版把加载和播放焊在一起，正是它不好测的原因之一（`ResMgr` 一调就得起整个资源系统）。拆开后 `AudioManager` 变成纯播放层，EditMode 里造一个 `AudioClip.Create(...)` 就能测。**加载策略（含素材句柄何时释放）留给调用方** | 调用方要多写两行：先加载、再播放、在 `VoiceEnded` 里释放句柄 |
| 2 | `Tick()` **不带 `deltaTime`** | A5 / A7 需要时间，所以把时间做成参数。这里**不需要**："播完了没有"由探针回答，不由"我们记的秒数"推算 —— 自己算时间会和 `AudioSource` 的真实进度**漂移**（改 pitch、暂停、编辑器卡顿都会偏）。**不引入第二份时间，就不会有不一致** | 无 |
| 3 | `IAudioPlaybackProbe` **只是测试缝**，不假装是架构 | `AudioSource.isPlaying` 在 EditMode 下永远是 false 且不推进，不注入就**根本测不了**"播完回池"。所以文件头**明说**它是 test seam，不像 `IInputSource` 那样是"将来换后端"的真抽象 | 多一个接口。换来的是"回池"这条逻辑可测，且能**数出探针被问了几次**（于是"刚起播那一帧不判定"也成了可断言的事实） |

**附**：`AudioEndReason` 分了 4 种结束原因（`Finished` / `Preempted` / `Stopped` / `Lost`）。
乍看过度设计，但调用方要靠这个事件**释放素材句柄**（选择 1 的代价）——
只在"自然播完"时通知的话，**被抢占**和**被停掉**的音效就会漏通知 → 句柄泄漏。

### 16.6 A8 自己的「W9 时刻」：两个被自己抓到的错误

**错误一：`Lost` 被报成了 `Finished`（静默错误，写的时候没发现）**

第一版的 `Tick()` 用一个 `List<AudioVoiceHandle>` 缓冲"本帧结束的播放器"，**只缓冲了句柄、没缓冲原因**，
然后在统一派发时**写死**传 `AudioEndReason.Finished`。后果：

```
宿主被销毁 → 上报 Finished   ← 调用方以为"这首自然播完了"，其实宿主都没了
```

第一版还配了注释说这是在防"监听者改列表"，**注释是对的，但掩盖了它同时丢掉了原因这个事实**。
修法：缓冲项改成 `private readonly struct EndedRecord { Handle, Reason }`，并在结构体上**写明这次踩坑**。
这和 FW-09 本身是同一类病：**看起来在正常运行，实际上信息已经丢了**。

**错误二：`Tick()` 的帧号自增位置**

`m_tickCount++` 原本放在 `Tick()` **开头**，于是"起播帧不判定"的 `StartFrame >= m_tickCount` 判断
在**同一帧**就会假掉 —— 精心写的保护**等于没写**。改成放在**结尾**自增，
这样 `StartFrame == m_tickCount` 只会在下一次 Tick 被跳过**一次**。

> 两条都不是编译器能抓的，都是"读自己的代码时发现逻辑和自己想的不是一回事"。

### 17.5 ⚠️ 本轮最重要的技术发现：**为什么内部坚持用回调而不是 `async/await`**

第一版 `UIManager` 内部用了 `async/await`。写到一半意识到：

> C# 的 `await` 在恢复执行时会把续体**投递回它捕获的 `SynchronizationContext`**；
> Unity 编辑器装了 `UnitySynchronizationContext`，它靠**帧循环**驱动；
> 而 **EditMode 测试没有帧循环** → 续体永远没人跑 → 测试**卡死**。

于是**整体重写为回调驱动**（`AssetHandle.OnComplete`）——回调在完成那一刻**直接调用**，不经过投递。
`ShowPanelAsync` 只作外层便利（`TaskCompletionSource`，回调触发时任务当场完成）。

> **这条也解释了本框架为什么一直是"回调 + 句柄"风格** ——
> 不是为了复古，是因为**回调在编辑器里可以被确定性地测**。

⚠️ **诚实边界**：这条判断**没有在 Unity 里实测过**（AI 不碰 Unity）。
证据是 228 条测试**全部通过且没有一条卡住** —— 如果判断错了，出现的会是"挂死"而不是"变红"。
所以**当前实测结果支持这个判断**，但严格说它是"**没被证伪**"，不是"**被证明**"。

### 18.3 ⚠️ 一处**刻意偏离需求签名**（已报负责人过目）

`FSM-02` 原文是 `OnEvent(e)`，**无返回值**。实现为 **`bool OnEvent(EventId)`**。

**理由**：分层派发需要知道"事件有没有被下层消化掉"。
没有返回值时两级只能**都收到同一个事件**，于是"按下闪避"可能被下层和上层各处理一次 ——
一种很难查的重复触发。

**这是扩展，不是偷偷改**；不同意则去掉返回值，代价是分层派发只能广播给两级。

### 18.4 三处"让它不可能发生"的设计

| 设计 | 理由 |
| --- | --- |
| **`StateTick` 没有"秒"字段**（只有 `Frame` / `DeltaFrames`） | FSM-04/09 要求逻辑只用帧计数器。给了秒字段就会有人写 `deltaTime > 0.3f`，那就**依赖真实时间** —— 单机看不出、帧同步时表现为"两端不同步"且极难定位。**不给，就写不出来** |
| **帧号倒退当场抛异常** | 倒退会让所有"持续 N 帧"的判断失效，而且很难查 |
| **`Fsm\` 目录零 `UnityEngine` 引用**（机械检查） | FSM-09。反过来说：**如果哪天 A10 的测试需要 PlayMode 才能跑，说明有人塞了 MonoBehaviour** —— 位置本身就是设计的一部分 |

### 18.5 四条写死的语义

| # | 语义 | 为什么写死 |
| --- | --- | --- |
| ① | `CanEnterFrom` 问**目标状态** | 规则集中在目标身上；问当前状态的话，每加一个状态都要改所有已有状态 |
| ② | 转移过程中再请求转移 → **排队**，只留一个槽位（后覆盖前） | `OnEnter` 里判断"该直接切走"是常见写法；递归执行会让顺序无法预料。只留一个槽位是因为状态机的语义是"**最终停在哪个**"，不是"按顺序播一遍" |
| ③ | 进退顺序固定为 **退下层 → 退上层 → 进上层 → 进下层** | 顺序会实际影响行为（如"退出跑步时停下移动"必须在"进入攻击"之前完成） |
| ④ | 分层：**下层属于某一个上层，不能跨上层乱跳** | 这是"分层"真正的约束，不是"两个状态机拼一起" |

事件与 `Tick` 的顺序统一为**先下层、后上层**（下层 `OnEvent` 返回 true 就停）—— 少一条要记的规则。

### 18.6 为什么状态切换**不走 `EventCenter`**

用普通 C# 事件（`StateChanged` / `TransitionRejected`）。理由与 A7 的"命令不走事件中心"一致：
**状态切换是每帧都可能发生的数据**，而事件中心（A3）是给**低频"游戏事件"**的工具。
需要进全局事件流的场合由游戏层自己转发。

另：**被拒绝的转移也广播** —— "按了跳跃却跳不起来"是最常见的 bug 报告，
只有成功事件的话根本不知道那次输入去哪了。

## 十九、D2 实施记录（确定性定点数学 · FW-M16 / DET-01 / DET-02）

| `Shared\Fix64.cs` | Q32.32 定点数：四则、比较、取整、开方、饱和溢出 |
| `Shared\FixVector3.cs` | 确定性三维向量 |

### 19.2 五条写死的语义

| # | 语义 | 为什么 |
| --- | --- | --- |
| ① | **溢出饱和**（不回绕、不抛异常），唯有除以 0 抛 | 回绕会让"变大"变成负数（位移里表现为"角色瞬移"且不报错）；逐帧仿真不该为数值溢出崩掉 |
| ② | **`Floor` 与 `ToInt` 是两个函数**（朝负无穷 / 朝零） | 网格对齐用前者、转整数下标用后者。**混用会在负数上错一格**，而正数上看不出来 |
| ③ | **零向量归一化返回零向量**；`Atan2(0,0)` 返回 0 | "没有方向"在游戏里是正常情况；抛异常会逼每个调用点判空，反而更容易漏 |
| ④ | **`FixVector3` 没有 `ToVector3` / `FromVector3`** | `NBC.Shared` 是 `noEngineReferences`（服务端没有 Unity）。转换由表现层**单向往外**做；反过来会把不确定性引回逻辑层 |
| ⑤ | **CORDIC 常量离线生成后硬编码** | 运行时用 `Math.Sin` 生成表会让两端得到**不同的表** —— 帧同步当场失效且几乎查不出来 |

### 19.3 四处"让错误不可能发生"的设计

| 设计 | 理由 |
| --- | --- |
| 加法/减法用**符号位判据**做饱和，不用 `checked` | `checked` 抛异常；饱和是确定性且可预期的 |
| **乘除法手写 128 位中间结果** | 两个 Q32.32 相乘是 Q64.64；`Math.BigMul` 在 netstandard2.1 / Unity 里**没有** |
| 除法用**二进制长除法**（每步只左移 1 位） | `(a << 32) / b` 里的 `a << 32` 会溢出。代价是 32 次循环，可接受 |
| `DeterminismGuardTests` 4 条**机械守卫** | "不许有浮点"编译器完全不管；改成读源码断言 + **阳性对照** |

**机械守卫的三条规则**：
1. 不许调用 BCL 的 `Math.Xxx(...)`（`(?<!Fix)` 负向环视排除自家的 `FixMath`）
2. `double` / `float` 只许出现在**转换边界**成员里（`ToFloat` / `ToDouble` / `FromFloat` / `FromDouble` / 显式运算符）
3. 真实代码里不许出现 `UnityEngine`（注释不算）

### 19.4 ⭐ 本轮最有价值的东西：**数值对拍探针**

定点数的 bug 有个共同特点：**在顺手写的几个用例上全对，在日常数值上错**。

### 19.5 探针抓到的 **3 个真 bug**（全部是"正数上正确、负数上错"或"局部正确"）

### 19.6 ⚠️ 探针的**覆盖盲区**（这条比 bug 本身更重要）

### 19.7 一次"值不值得"的**实测**决策

| --- | --- | --- |

| `asin` / `acos` | 1.365e-5 | **2.5e-9 / 2.2e-9** |

### 20.3 三条关键设计

| # | 设计 | 不这么做会怎样 |
| --- | --- | --- |

| ③ | `ILogSink` 把"记什么"与"记到哪"分开 | 过滤/滚动用内存 sink 测（不碰文件系统），落盘用真实临时目录测；**两个文件分开，红了立刻知道是哪层错** |

⚠️ 关于 ③ 要说实话：这道缝**主要价值是测试与将来的扩展**，不像 `IInputSource` 那样是明确的架构替换点。

### 20.4 ⚠️ 落盘滚动：**同一个测试两轮才对**

| 轮次 | 现象 | 根因 | 教训 |
| --- | --- | --- | --- |
| 第一轮 | 378 条 1 红（滚动之后 `nbc.log` 不在） | `Write` **写完再检查**长度 → 最后一次写触发滚动时，当前文件被归档却**不留新的当前文件** | **时序边界**："某个特定时刻状态不符合直觉"。代码上看不出来，朴素断言能抓到 |
| 第二轮 | 379 条 2 红（`RotationCount` 恒为 0） | 判断用 `BaseStream.Length`，而 **`StreamWriter` 带缓冲**，该值**落后于**实际写入量 → 改成"写之前检查"后缓冲还没 flush，永远不滚 | **缓冲让一个数值不可信**：依赖被中间层缓冲过的值做判断 = **赌它什么时候刷新** |

> 📌 **第二轮还暴露了一件事：第一版"能过"是侥幸。**
> 它只在"某次写恰好触发缓冲 flush"的那一刻才可能看到长度超标 ——
> 20 条日志刚好跨过一次 flush，于是**看起来能工作**。
> **这个 bug 一直都在，只是被"刚好合适的测试数据量"掩盖了。**

**最终修法**：自己记字节数，外加三个配套细节（缺一个都会出别的毛病）：
① `EnsureOpen` 时从**已有文件的真实长度**起步（否则追加到大文件永远不滚）；
② `Rotate` 时归零（否则下次写立刻又滚 → 无限滚动）；
③ 用**编码算字节数**而不是 `line.Length`（中文 1 个 char 是 3 字节）。

**验证**：PowerShell 复刻同一套逻辑跑 20 条（上限 200 字节）——
旧逻辑 **0** 次滚动，新逻辑 **6** 次滚动，当前文件存在、字节 177、归档正好 3 个。

### 21.3 显示侧的核心矛盾：**观测工具不能自己制造被观测的问题**

这是 E1 唯一值得单独讲的设计点。

看板要显示 **GC 分配**，而 `Text.text = ...` **每次赋值都分配字符串**。
如果按最直白的写法（每帧刷），那么：

| 写法 | 字符串分配（按 60 FPS、4 个文本算） |
| --- | --- |
| 每帧刷 | 4 × 60 = **240 次/秒** |
| 限频到 4 Hz（`DefaultRefreshInterval = 0.25`） | 4 × 4 = **16 次/秒** |
| | → **少 15 倍** |

> ⚠️ **记一笔自己的错**：第一版注释里我写的是"降了**两个数量级**"。
> 实际是 **15 倍**，一个数量级多一点。**"两个数量级"是我顺手写的，没算。**
> 本项目第 N 次栽在同一件事上：**凡是数字，先算再写。**

所以拆成两件事：**采样每帧都做**（FPS 需要每一帧的耗时），**文字限频刷**（人眼看数字也跟不上 60 Hz）。

还有一条同源的细节：**控件不存在时不能去拼那个字符串**。
第一版我写的是 `SetText(m_fpsText, snapshot.Fps.ToString("F1") + " FPS")` ——
C# 会**先把实参算出来**再进方法，于是 `SetText` 里那个 `if (target != null)` **拦不住分配**：
"没挂的控件"照样在拼字符串。现在是每个都**先判空、再拼**。

### 21.4 ⚠️ 本轮的"实测 vs 想象"：asmdef 到底要不要显式引用 UGUI

**背景**：E1 显示侧的 EditMode / PlayMode 测试都要 `using UnityEngine.UI;`（为了 `Text`），
但两个测试 asmdef 的 `references` 里**都没有** `UnityEngine.UI`。
按本项目已经付过学费的那条规矩（*asmdef 引用不传递*，B3 轮因此撞过 `CS0246`），这里**应该**编译不过。

**实测（Unity 自己生成的工程文件，不是我猜的）**：

| 文件 | 内容 |
| --- | --- |
| `Client\NBC.Tests.PlayMode.csproj`（Unity 生成，**晚于** `Tests_PlayMode.asmdef` 11 分钟） | **有** `<Reference Include="UnityEngine.UI">` → `Library\ScriptAssemblies\UnityEngine.UI.dll` |
| 同一个文件里 | **没有** `<Reference Include="YooAsset">` —— 而 `YooAsset.asmdef` 同样是 `autoReferenced: true` |
| `NBC.Framework.YooAsset.csproj` | **有** `<Reference Include="UnityEngine.UI">`（这个 asmdef **压根没提过 UGUI**）**且** 有 `<Reference Include="YooAsset">`（它显式列了） |
| `NBC.Tests.EditMode.csproj` | **有** `UnityEngine.UI`（asmdef 里也没写） |

**结论（分层写清楚，不硬凑一个说法）**：

| | 结论 | 依据 |
| --- | --- | --- |
| **事实** | `NBC.Tests.PlayMode` **不需要**显式列 `UnityEngine.UI` 也已经拿到引用 | Unity 生成的 `.csproj` 实测 |
| **排除的机制** | ❌ **不是 `autoReferenced` 的功劳**。`YooAsset.asmdef` 也是 `autoReferenced: true`，可它**没有被自动加上**（两个测试工程里都没有 `<Reference Include="YooAsset">`） | 上表第 2、3 行 |
| **剩下的解释** | `UnityEngine.UI` 的行为**像引擎模块**（`UnityEngine.UIModule` / `UIElementsModule` 也在每个工程里）——Unity 对自己的 UI 程序集做了特例，第三方包没有 | 上表第 3、4 行：连完全不碰 UGUI 的 `NBC.Framework.YooAsset` 也拿到了 |
| **处置** | **不改 asmdef**。改动零收益，而且"Unity 特例"这条如果哪天变了，正确的修法是**让 Unity 报错来告诉我们**，不是在能跑的时候先写一条冗余引用 | —— |

📌 **顺带得到一条可复用的方法**：**Unity 生成的 `*.csproj` 是 asmdef 接线的一手证据**。
以后怀疑"某个程序集的引用到底有没有接上"，先去看它生成的 `.csproj` 里有没有那条 `<Reference>` ——
**不用开编辑器、也不用靠"没报错"去推断**。

### 21.5 EditMode / PlayMode 的分工：A1 那条结论的**镜像**

A1 的结论是"**EditMode 不调 `Awake`**"。E1 显示侧撞上的是它的镜像：

| 面板**不注入也能自己活起来** | EditMode 下 `Application.isPlaying == false`，面板**故意不建采样器**（Profiler 没在跑，`ProfilerRecorder` 只会打噪音日志） |
| **每帧被驱动** | 面板靠 `MonoManager` 的每帧回调推进，而 EditMode 连 `Awake` 都不调，更没有帧循环 |
| 销毁时把回调摘干净 | `OnDestroy` 也是播放模式才有的事 |

→ 所以 E1 显示侧的证据必须是 **EditMode 13（纯逻辑）+ PlayMode 9（生命周期）**，**只看一边会漏一半**。

⚠️ 这里还有一个**测试隔离**上的坑：EditMode 里那 13 条**必须自己注入采样器**，
否则面板一旦自动建采样器，`ProfilerRecorder` 在编辑模式会往 Console 打噪音，
而**测试里任何一条没被声明的日志都会让用例失败**。所以 `OnInit` 里加的是
`if (m_sampler == null && Application.isPlaying)` —— 和 A5 / A8 / A9 用 `Application.isPlaying`
挡住编辑模式是同一个套路。

### 21.6 `PerfHudPanel` 的 `Start()` 自举：**一个只给调试看板的特权**

`PerfHudPanel` 覆写不了 `Awake`（A9 的 P-08 明确禁止面板自己初始化），
但它多了一个 `Start()`：发现 `IsInitialized == false` 就自己 `Initialize()` + `ShowMe()`。

**为什么它可以、别的面板不行**（这条边界要能讲出来）：

| | 调试看板 | 业务面板（`LoadingMaskPanel` 等） |
| --- | --- | --- |
| 什么时候该出现 | **随时** —— 排查问题时恰恰最不想先修资源系统 | 由玩法逻辑决定 |
| 谁来决定 | 谁把它拖进场景就归谁 | **必须**是 `UIManager` |
| 自举的代价 | 无（`Initialize()` 幂等） | 会把 A9 修掉的毛病（面板自己决定何时出现）引回来 |

⚠️ **它不会抢 `UIManager` 的活**，理由是一条**时序**：
`UIManager` 在 `Instantiate` 之后**同步**就调 `Initialize()`，而 `Start` 要等到**下一帧**才跑；
所以被管理的面板走到 `Start` 时 `IsInitialized` 已经是 `true`，**空操作**。
这条时序推论被 `ShowMe_TwiceAddsOnlyOneListener` 和 `Destroy_RemovesListenerAndReleasesSampler`
（都断言回调数**恰好是 1**）间接钉住。

### 21.7 为什么加这个自举（**它是被验收标准逼出来的，不是顺手加的**）

E1 的验收是"**屏幕上可见**"。而看板正常的上屏路径是
`UIManager.ShowPanel("PerfHud", ...)` → 需要 **YooAsset 打包（B4/B5）** 先做完。
于是会出现一个荒唐的局面：**"看得见数字"要等资源系统先跑通** ——
而排查问题时，最不想做的事就是先修资源系统。

`Start()` 自举把这条依赖**切断**了：把面板拖进任意场景、进播放模式就该看见数字。
普通面板**不该**有这条路（见上表），调试看板**必须有**。

### 21.9 ⚠️ 收关后发现的一处**我自己写错的说明**：`const` 与属性都不会出现在 Inspector 里

**怎么暴露的**：负责人在场景里照着 `Docs/16` §10.2.19 的 C 节第 10 步做，
回报"**这个没在 Inspector 面板显示，其他正常**"。

**我错在哪**：那一步写的是"把 `PerfHud` 的 `Refresh Interval` 在 Inspector 里改成 `0.1`"。
可当时 `RefreshInterval` 是个**属性**：

```csharp
public const float DefaultRefreshInterval = 0.25f;   // ← const：编译期常量，只活在代码里
private float m_refreshInterval = DefaultRefreshInterval;
public float RefreshInterval { get => m_refreshInterval; set => ... }   // ← 属性
```

**Unity 只序列化"字段"**（`public` 字段，或带 `[SerializeField]` 的私有字段）。
**属性是方法，不是数据，永远不进 Inspector；`const` 更是只活在编译产物里。**
所以那一格**本来就不可能存在** —— 我不是"忘了配"，是**写下了一句做不到的操作说明**。

**修法**（同时保住"能在 Inspector 里调"这个正当需求）：

```csharp
[SerializeField]
[Tooltip("文字刷新间隔（秒）。0.25 = 4 Hz；0 = 每帧都刷（不建议，看板会自己造 GC）。")]
[Min(0f)]
private float m_refreshInterval = DefaultRefreshInterval;
```

并补一条守门用例 `DefaultRefreshInterval_IsUsedWhenNothingConfigured` ——
因为字段初值现在同时被"常量"和"序列化数据"两个来源决定，
**两者一旦不同步，就会出现"新挂的组件和老实例刷新速度不一样"这种鬼故事**。

**顺带记一个 Unity 老坑**（写进代码注释了）：
**一旦某个值在预制体/场景里存过，改字段初始值不再影响它**（序列化数据盖掉初始值）。
想让已有实例回到新默认值，得在 Inspector 里点 `Reset`。

📌 **教训（和 W9 同源，但方向不同）**：
前面几次是"**校验器有 bug，导致检查空转**"；
这次是"**文档里承诺了一个平台根本做不到的操作**"。
两者的共同点是 —— **我都把"我以为"当成了"事实"**。
操作单里的每一步，**要么自己实测过，要么明确标"我没验过"**；
尤其涉及"某个东西会不会出现在 Inspector 里"这种**编辑器行为**，
它是可以**从类型系统推出来**的（属性/常量不序列化），所以没有理由写错。
