## 一、M4 是什么（范围一句话）

**M3 把"联机战斗"跑通了（状态同步 + 副本 + 掉落），M4 要把"玩得下去"补齐**：

| 方向 | 内容 | 优先级理由（Q4） |
| --- | --- | --- |
| **S1 事件下发与任务闭环** | 服务端把伤害/死亡事件也发下去；客户端接进 `EventCenter` → 任务进度能涨 | **M3 留下的断口**，不接上"联机打怪"对任务系统等于没发生 |
| **S2 成就** | 与任务**共用同一个 `ConditionTracker`**（`register(resetProgress:false)` = 一直生效） | Q4 把成就排在任务之后，且它与任务是同一套条件结构 |
| **S3 持久化** | MySQL 落库：条件进度 / 任务状态 / 掉落记录（`IConditionProgressStore` 换实现即可） | 需求 §5.2；也是"账号"的前置 |
| **S4 帧同步（2v2）** | PVP 小房间走帧同步（D2 定点数学），与状态同步并存 | Q2 的混合方案里"另一半"；规矩：**状态同步没稳之前不并行做帧同步** |

⚠️ **不做**（本阶段有意留下）：客户端预测/回滚、AOI/分线/分服（Q3 砍掉）、真正的账号系统。

### 3.3 三条**设计取舍**（都是有理由的，不是随手写）

1. **死亡按 `kind` 分派成两个事件**（`MonsterDied` / `HeroDied`），而不是"发一个带 kind 的、让订阅方自己判"。
   —— 沿用 M2 已经定下的理由（`BattleEvents.cs` 文件头）：合并会让"玩家死了"被当成"击杀了一个目标 0"，
   而 `targetId = 0` 是"任意目标" ⇒ **任何**击杀任务都会涨进度，**静默且看起来很正常**。S1 用一条回归用例把它钉住。
2. **掉落只在"归我"时发游戏事件**：`DropEvent.WinnerPlayerId` 是服务端算的归属（M3 = 击杀者）。
   别人的战利品若也当成"我获得了"，"收集 N 个物品"会被别人的掉落推进 —— 同样是静默的错。
   ⇒ 归属判断放在**产生事件的地方**（桥），订阅方拿到就是"我的"；而且**不重复判断**
   （`BattleSession` 那边只写 `payload => payload.ItemId`，同一规则两处实现迟早不一致）。
3. **`NetSession` 故意不解释 `kind`**（不写"1 就是怪"）：`Game\Net\` 是**引擎无关子集**
   （`Server\_net-probe` 直接编它），而 `EBattleAgentKind` 在 `Game\Battle\` ——
   引它会当场破坏探针的边界（实测见 §五.2）。分派是桥的活，桥住在战斗层。

### 3.4 与"服务端权威"的一致性

客户端**一个随机数都不掷、一次伤害都不算**：伤害多少、谁死了、掉什么，全部来自服务端事件。
`ServerEventBridge` 只做**翻译**（换事件类型、判归属），不做判定。这与 D3/D4 一致。

## 四、M4-S1 的验收（可复现的实测）

### 4.1 探针（`Server\_net-probe`）：83 → **88 全绿**

新增第【十三】节 5 条，全部跑在**真 socket + 两个客户端**上：

| 断言 | 证明什么 |
| --- | --- |
| 每次扣血都下发一条伤害事件，两端**逐字段一致** | 伤害事件确实发出去了，且是"同一份字节" |
| `applied` 是**实际扣掉的血**（打 3 次、每次 10，`remaining_hp` = 打之前 − 10） | 语义正确（不是"打出去的伤害值"） |
| 死亡事件带 `kind=1` / `config_id` / `killer_id`，两端一致 | 客户端有足够信息分派与归属 |
| 同一帧里**伤害在前、死亡在后** | 因果顺序契约（表现层不会先看到死、再看到挨打） |
| 服务端计数如实（伤害 = 扣血次数，死亡 = 死的单位数） | 统计不是装饰 |

> ⚠️ 断言里的数字全部是**算出来的**（`damage=10` ×3、`remaining_hp = hpBefore − 10`），不是手抄的。

## 五、本轮踩到的坑（都值得记住）

1. **`ServerEvent` 的 oneof 不叫 `Payload`**：信封 `ServerMessage` 是 `PayloadCase`，而事件是 **`EventCase`**
   （因为 `nbc_m3.proto` 里那个 oneof 叫 `event`，生成物加后缀就成了 `EventOneofCase`）。
   写错是 `CS0117`，闸门当场抓到 —— 已把这条写进 `NetSession.HandleServerEvent` 的注释里。
2. **`Game\Net\` 是引擎无关子集，不许引 `Game\Battle\`**：我给 `NetSession` 加了一行
   `using NBC.Game.Battle;`（为了 `EBattleAgentKind`），`_net-probe` 立刻 **CS0234**。
   ⇒ 桥搬到 `Game\Battle\ServerEventBridge.cs`，`NetSession` 只如实转发、不解释 `kind`。
   **判据同 D14：判"能不能进服务端 / 能不能进探针"要看整条依赖链。**
3. **`ToByteArray()` 要 `using Google.Protobuf;`**：新测试第一次编译报 `CS1061`（不是 CS0246）。
   —— 这是本项目第 10 次撞"第三方扩展方法/类型要自己引"这条规律。
4. **MSB3027/MSB3021 又来了**：负责人开着服务端 → Host 的 `bin` 被锁 → 解决方案级构建失败。
   处理办法（老规矩）：**不动他的进程**，用 `-t:Compile` 做只编译校验；整体构建与 Host 重启等他关掉服务端之后再做。

## 七、M4-S1b：可测性修正（2026-09-26，负责人实测反馈）

**反馈原话**：「668 全绿，**玩家老是被 boss 打死，且目标不在范围内，难以测试**」。
先量，再改 —— 量出来的账是这样的（都是真值，不是感觉）：

| 量 | 改前 | 含义 |
| --- | --- | --- |
| BOSS 索敌 | `NearestAliveHero`，**无范围** | 一进房就**全图锁定**你 |
| BOSS 移速 | 90mm/帧（2.7 m/s） | 从 3000mm 外走到你面前约 **1.5 秒** |
| BOSS 伤害 | `Monster.attack`=60 / 15 帧冷却 | **120 dps** ⇒ 1200 血 **10 秒左右**没了 |
| 英雄出生点 | `(-1000, 0)` | 距 BOSS（`-3000,0`）**正好 2000mm = 它的普攻射程** ⇒ **一进房就在它脸上** |
| 快照里的英雄 | 只有 `kind` | 两个客户端**分不出你我** ⇒ 调试工具可能操纵别人的角色 |

### 改了四处（每处都有可复现的验收）

| # | 改动 | 理由与验收 |
| --- | --- | --- |
| 1 | `BossBrain` 加**仇恨范围**（`DungeonBattle.BossAggroRangeMm = 2200mm`）：圈外的英雄视为"没看见" | 语义是"**够得着就追，够不着就回家**"，不是"全图仇恨"。2200 只比射程 2000 大一点 ⇒ 交战由玩家决定。探针：出生点距 BOSS 2500mm > 2200mm，站着不动 BOSS **不动**（状态站桩） |
| 2 | `BossBrain` 加 **leash（回位）**：没目标且离家 > `BossLeashSlackMm = 200mm` 就走回出生点 | 否则"甩掉它"只是让它停在原地，久了会漂到副本门口。探针：把它挪开 2000mm → 英雄跑出圈 → 60 帧后它**回到出生点**（离家 ≤ 200mm、状态站桩） |
| 3 | `HeroSpawnPoint` 的环半径 **1000mm → 500mm** | 四个席位距 BOSS 的最小距离从 2000mm 变成 **2500mm > 仇恨范围 2200mm** ⇒ 进房先安全。⚠️ 一个席位原本**正落在 BOSS 射程边界上**，这就是"老被打死"的直接原因 |
| 4 | 快照加 **`owner_player_id`**（`EntitySnapshot` 第 10 号字段，**兼容改动**，`CONTRACT_VERSION` 保持 1） | 客户端要认出"哪个英雄是我"。**没有它就只能靠 `kind == 0` 猜**，猜错的表现是"调试工具在操纵别人的角色"，**静默且看着正常**（同 M2 那两个事件取舍的教训）。同时把它做成 `SnapshotView.FindHero(playerId)`（纯 C#、可测），**表现层以后也要用** |

### 客户端调试窗（治"目标不在范围内"这个体感）

| 改动 | 为什么 |
| --- | --- |
| 目标改成**离我最近的活怪**（原 `FirstAliveMonsterId` 取"快照里第一只"，而快照顺序是创建顺序 ⇒ 常常指到地图另一头） | 你不用再手填编号、也不会"打了没反应" |
| **显示距离 + 是否在射程内**（`距离 2314mm ❌ 太远，打不到`） | 原来只有一个编号，得自己心算 —— 现象就是"打不出去且没有提示" |
| **「自动追击并攻击」开关**：不在射程就朝目标走，进圈就按一下普攻、再等冷却 | **只是替你按键**：位置/伤害/掉落照样全由服务端算（不是客户端预测）。面板上能看到"已按 N 次普攻 / 冷却剩余 N 帧" |
| 距离用**切比雪夫距离** | 与服务端 `DungeonBattle.DistanceMm` **同一种量法**；用欧氏距离会在四角误判成"还差一点"，于是永远不按攻击 |
| 射程与冷却改成读**共享层** `NBC.Shared.Battle.BattleRules` | 客户端也要这两个数（走到哪儿停、按键节奏）。在窗口里再写一份就会**静默漂移** —— 服务端改射程、客户端还在老位置按键。服务端那两个 `const` 现在是**指向共享层的别名**，只可能有一个真值 |

### 实测（探针 88 → **92 全绿**）

新增/改写的 6 条：出生点在仇恨圈外（用表里的 `spawnRadiusMm` 算）、圈外不追、进圈有反应、
出圈回家（leash）、走进射程才挨打、快照里英雄带 `owner_player_id`（怪是 0）。
EditMode：`SnapshotViewTests` 新增 1 条（**两个英雄时不能认错人**、自己的英雄死了返回 null）。

> ⚠️ **过程中我写错了 4 处用例**（都是断言而不是实现）：`MoveUntilInRange` 写死"往 +X 走"
> （当初是给右边的狼用的）却拿去追左边的 BOSS ⇒ 英雄反向跑；"进圈后距离一定变小"
> （其实英雄常常直接落进射程，那时 BOSS 是**打**而不是**走**）；leash 用例用"引怪"造位移
> （BOSS 一进射程就开打，只挪了 90mm）；`OwnerOfFirstHero` 取"第一个英雄的主人"
> （快照里两个英雄都在，第一个永远是先入职的那个）。
> ⇒ 又一条老教训的复现：**断言里的数字/前提必须算出来**，"看起来会那样"经常不是那样。

### 演示条件的目标**不写死**（2026-09-26 负责人实测："没办法达成 3 只狼的任务目标"）

窗口里那条演示条件是"接线对不对"的可见证据，但它原来写死 **`击杀野狼 × 3`**，
而副本 1001 的 `Dungeon.csv` 只有 `"6001,6001"` ⇒ **目标天生达不成**（我当时顺手写了个 3，
没去对阵容）。现在：

| 改动 | 做法 |
| --- | --- |
| 目标只数 | **从快照里的真实阵容算**：按 `config_id` 分组数怪，优先 `6001`（野狼），没有就取"出现最多的那种怪"。副本 1001 → `6001 × 2`；1002 → `6002 × 3`（平局按编号升序打破，确定性） |
| 为什么不需要"哪个是 BOSS" | BOSS 只有**一只**、小怪是**一批** ⇒ "出现最多的那种怪"天然就是小怪。**不用**给协议再加 `is_boss` 字段 |
| 手填覆盖 | 面板上 `目标只数覆盖（0 = 自动）` + 「按本副本阵容重设」按钮 —— 想测 3/5/10 都不用改代码 |

## 十、M4-S2 成就（2026-09-26）

### 10.1 一句话：成就与任务**只差三点**

| | 任务（`QuestRuntime`） | 成就（`AchievementRuntime`） |
| --- | --- | --- |
| 登记时机 | 玩家点「接取」时 | **构造时全部登记**（没有接取） |
| `Register` 的 `resetProgress` | `true`（接了才开始算） | **`false`（一直生效、跨局累计）** |
| 结束方式 | 玩家点「交付」才发奖 | **条件一齐当场解锁发奖**（没有交付） |

⇒ 所以本片**没有 `EAchievementState`** —— 成就只有"锁着 / 解锁了"两态。
多一个枚举只会多一处能不同步的状态（`ConditionTracker` 文件头第 ① 条同一个道理）。

### 10.2 本片最容易写错的一处：**登记顺序**（已写成能证伪的用例）

`ConditionTracker` 语义②：`resetProgress: false` 时，**如果注册的那一刻就已经达成，当场回调一次**。
这是**故意**的（"上次已经打了 10 只，这次登录就该解锁"）。但它意味着
**构造函数里的 `Register` 会重入到自己的 `OnConditionMet`**：

```
❌ 登记一条 → 记一条归属
   Register(4009, ..., false) 当场回调 → 回调查 m_ownerOfCondition[4009]
   → 还没记进去 → 认不出这是自己的条件 → 安静 return
   ⇒ 成就永远不解锁，而且一行日志都没有（"看起来像玄学"的典型）

✅ 三段：
   ① 先把全部归属记好
   ② 再逐条登记（此刻重入回调已经认得出来）
   ③ 全部登记完再统一评一遍
```

**第 ③ 步不是冗余**：`AreAllConditionsMet` 走 `m_tracker.IsMet`，
而**还没登记的条件 `IsMet` 恒为 false** ⇒ "两条都早已达成"的成就，
在 ② 的循环里每条单独触发时都凑不齐，只能靠 ③ 收尾。

**这条判据有能证伪的对照**（`Server\_condition-probe` 新增两条，45 → **47 全绿**）：
- `订阅晚了 -> 收不到那次『注册即达成』的通知`（⇒ "先订阅、后登记"是硬要求）
- `归属表要在 Register 之前就绪（否则当场回调会安静丢弃）`

### 10.3 CFG0023：一条条件只能被**一个**持有者引用

`ConditionTracker.Register` 对重复登记**当场抛 `InvalidOperationException`**
（它故意不静默覆盖：静默覆盖会让 bug 永远查不出来）。
⇒ "两个任务共用一条条件"与"任务与成就共用一条条件"都是
**数据单看全绿、炸在运行期**，而且成就**在启动时就登记**，
所以表现是"任务接不了 / 一接就闪退"，跟配置表"看起来"毫无关系。

**这条只有加了成就才完整**：以前只有任务时它就该存在，现在多了 `Quest`×`Achievement` 这一族组合。

### 10.4 顺带修掉 CFG0020 的两处**误报**（被真表逼出来的）

加了 `Achievement` 表之后，CFG0020 立刻在真表上报了两个错 —— 判据本身没错，错在**适用范围**：

| 排除 | 理由 |

### 11.4 核心设计：为什么**必须**是写回缓存（不是"每次 Set 就 UPDATE"）

看一眼调用点就明白（`ConditionTracker.Notify` 里）：

```csharp
foreach (已登记的条件) {
    int before = m_store.GetProgress(pair.Key);    // 每个条件读一次
    m_store.SetProgress(pair.Key, after.Current);  // 每个条件写一次
}
```

打死一只怪可能触发**十几次 Get + 十几次 Set**，30Hz 下每秒几百次。
一旦这里做同步查询 = "打一只怪卡一下"，而且卡在**逻辑线程**上，直接违反 **DB-03**。

⇒ **接口是同步的，实现就必须是内存的。** 这不是优化，是唯一能同时满足"接口好用"+"DB-03"的做法。

**落库时机**（DB-04：异步、脱离主循环线程、结果回投主循环队列）：

| 时机 | 为什么 |
| --- | --- |
| 进副本 / 登录时 `LoadAsync()` | 进度是跨局累计的，**必须先把全部读回来**（否则"这个成就早该解锁"会被漏掉） |
| 离开副本 / 成就解锁时 `FlushAsync()` | 成就解锁是"里程碑时刻"，值得立刻落盘 |
| 定时兜底（主循环低频调 `FlushAsync`） | 崩溃时最多丢一个周期 |
| 优雅关闭（SRV-17） | 等一次 `FlushAsync` 完成再退 |

**三条写死的线程语义**（都在文件头）：

1. **绝不持锁做 IO**：锁里只拷一份脏集快照，出了锁再发 SQL。持锁发 SQL = 主循环卡在等网络上（等于没写缓存）。
2. **单飞（single-flight）**：上一次没写完就不开新的。理由不是省事，是**正确性** —— 两次写若乱序落地，后落的那次会把**旧的**绝对值写进库 = **静默数据回退**。
3. **`Remove` 要写 0**（不是只删内存）：否则"内存删了、库里还在" ⇒ 下次登录又读回来，表现是"我明明重置过，怎么又有了"。

### 11.5 ⚠️ 本片最值钱的一条：持久化**自己制造了一个 bug**

`AchievementRuntime` 用 `resetProgress: false` 登记条件，而 `ConditionTracker` 的语义②是
**"注册时若已达成，当场回调一次"**（这正是"登录即解锁"要的行为）。

以前进度存内存、进程一重启就没了 ⇒ 永远不会重复解锁。
**一旦进度落库，服务端每重启一次就会把所有已完成的成就再发一遍奖。**

⇒ "解锁状态"能从 `condition_progress` 推导，但"**奖励发过没有**"推导不出来，**必须记账**。
所以有了 `reward_granted` 台账。

> 📌 这是"**加一个正确的东西，会暴露另一个地方的错误假设**"的典型样本：
> 持久化本身没写错，是原有代码隐含假设了"进度会随进程消失"。

⚠️ **台账的运行时守卫（`IRewardLedger` + `AchievementRuntime` 里查台账）是 S3 的下一步**，
本片先把**表**与**数据层**做完 —— 表已经建好，守卫不会需要第二次迁移。

#### ④ ⚠️ 一个**写反了**的 bug（我自己的注释先发现的）

`MySqlRewardLedger.FlushAsync` 第一版里，我写了注释"失败必须把这一批放回脏集"，
**但代码没做**（注释与代码互相矛盾 —— 读到那一段就该停下来）。

它的后果不轻：`MarkGranted` 是"内存里已经有它就**不再标脏**"，
所以脏集一旦被取走又没写成功，那个键**再也不会被标脏**
⇒ "发了奖但台账没落库"**永久丢失** ⇒ 下次重启**再发一遍**（等于台账白装）。

修法：`FlushAsync` 自己 `catch { RestoreDirty(batch); throw; }`。
**不用"让调用方补一刀"那种设计** —— 调用方手里没有那一批（它是内部的），
所以那种 API 只能靠"记得"来正确，而"靠记得"迟早会漏。

## 十三、修 Unity `CS0012` + 新增 asmdef 边界闸门（2026-09-26）

### 13.1 负责人实测的报错原文

```
Assets\_Project\Boot\M2DemoBehaviour.cs(521,29): error CS0012:
  The type 'IRewardLedger' is defined in an assembly that is not referenced.

```

### 13.2 根因：类型通过**「被调方法的签名」**泄漏，而调用方源码里一个字都没提它

我给 `BattleSession.FromConfigMgr` 加了一个**可选**的 `IRewardLedger` 参数
（类型在 `NBC.Shared`），而调用方 `M2DemoBehaviour` 在 `NBC.Boot`，它的 `references` 是
`NBC.Framework / NBC.Framework.UI / NBC.Framework.YooAsset / NBC.Game` —— **没有 `NBC.Shared`**。

C# **必须解析被调方法的完整签名（含可选参数的默认值）** ⇒ 需要那个程序集。

⚠️ 注意这一条的**新形态**：`M2DemoBehaviour.cs` 里**既没有** `using NBC.Shared...`，
**也没有**写出 `IRewardLedger` 这个词 —— 所以
`AsmdefReferenceGuardTests`（按 `using` 扫）**看不见**它。

### 13.3 修法：**不给那个方法加参数**（而不是给 Boot 加引用）

| 选项 | 为什么不选 |
| --- | --- |
| 给 `Boot.asmdef` 加 `NBC.Shared` | 编译器的确说"该加引用"，**但那个参数本来就没人用得上**：客户端这一侧没有持久化台账（进度还在本地），加了它就是"猜测性的通用" |
| ✅ **删掉那个可选参数** | ① 需求上不需要；② 更重要的：**一个"没人用得上"的参数，代价不只是多一行 —— 它会把一个程序集依赖钉进调用方的依赖图里** |

台账仍然通过 **10 参构造函数**注入（测试 / 服务端用）；
`FromConfigMgr` 内部传 `null`（= 内存台账），并在**调用点**写清了为什么。

### 13.4 新增 `Tools\Check-AsmdefBoundaries.ps1`（补上单程序集闸门的盲区）

把每个 asmdef 的**文件集合**与**引用集合**照抄成 csproj，一个个真编：

| 细节 | 为什么 |
| --- | --- |

### 14.1 这一片做了什么（依赖方向是刻意的）

```
RoomBattleService（Game，纯逻辑）  ——产出 `BattleRecordDraft`（中性草稿）——>  BattleRecordWriter（Data）
                                                                                    ↓ 后台线程
                                                                        BattleRecordDao → MySQL（一次事务）
```

| 关键决定 | 理由 |
| --- | --- |
| 战绩草稿 `BattleRecordDraft` 住在 **`Game`**，`Data` 引用 `Game` | 依赖方向 `Host → Data → Game → Core → Shared`，**不成环**：`Game` 仍然**不知道** `Data` 存在（"纯逻辑要能在没有数据库的环境里跑测试"这条依然成立）。📌 判据是**"谁不知道谁"**，不是"谁引用了谁" |
| `RoomBattleService` 用 **事件**（`BattleFinished`）而不是直接写库 | 同上：逻辑层不许认识 MySQL。由**组合根** Host 接线（与 M2 的 `IQuestRewardSink` 同一套路） |
| 战绩在 **`DungeonBattle.ApplyDamage` 里记账**（不是在广播出去的事件里反推） | `DamageEvent.attacker_id` 是**实例编号**，而战绩要按**玩家**记 —— `ApplyDamage` 里两个实体都在手上。⇒ **在信息最全的地方记账** |
| 写库**必须先入队**（`BattleRecordWriter`） | 它在 Tick 线程上被触发；直接 `await` 一次数据库往返 = **一局结束的瞬间卡住整个服务端** |
| **单飞排空**（一次只写一局）而不是每局 `Task.Run` | 保证 `record_id` 的顺序 = 入队顺序；代价是排队，而一局一次根本排不满 |
| 失败**只说一次**，恢复后再说 | 库挂了之后每局都失败 ⇒ 刷屏会把别的问题淹掉 |
| `_recorded` 去重 | ⚠️ `IsFinished` 一旦为真就**永远为真** ⇒ 不去重就是**每帧写一条战绩** |
| "房间没人了"**不算**一局 | 那种局没有"结果"，记下来只会污染统计（`DropBattlesOfDeadRooms` 直接回收） |
| 房间回收时**同时清 `_recorded`** | 房号是递增的（`r1`、`r2`…），留着旧记录会让"以后某个也叫 r1 的房间"被误判成交过了 |

### 14.2 ⚠️ 一个真实的欠账：`player_id` 还不是账号

`session.PlayerId` 现在是**会话计数器**（服务器第几个连上来的）。`ServerMessageRouter.cs:242` 原本就注明了：

⇒ 第 5 个连上来的人 id = 5 ⇒ 外键会拒绝那一行。

1. 写之前先问库里有哪些 `player_id`；

### 14.3 房号为什么是"转换"而不是"改列"

## 十五、握手绑真实档案（SRV-06 的最小可用版，2026-09-27）

### 15.0 ⚠️ 要你手动做的（**3 步**）

| # | 操作 | 成功判据 |
| --- | --- | --- |
| **1** | **先编译**：`dotnet build Server\NBC.Server.Host\NBC.Server.Host.csproj -m:1` | `0 个错误` |
| **2** | **重启服务端**（⚠️ 仍然**不要双击旧 exe** —— 双击永远不编译） | 横幅多出两行：<br>`[数据库] 已接：MySql root@127.0.0.1:3306/nbc_db（密码：已设，7 位）`<br>`[数据库] 档案槽位 4 个（占用 0、空闲 4；累计发放 0 次）` |
| **3** | **反复连开/关调试窗口 6 次以上**（每次都要"连接 → 加入房间"，然后关掉重来），**然后打一局** | ① 打完仍然出现 `[战绩] 战绩已落库：record#N、明细 M 条`（**没有"跳过无档案玩家"**）<br>② 查 `player_profile` 的 `total_kill` **继续涨** |

⚠️ **第 3 步就是在验这个修复**：**没有它的话**，"累计连过 4 次"之后每一局的战绩明细都会被外键拒绝、**静默跳过** ——
表现是"打完一局，`total_kill` 不涨了"，而且**控制台只有一条 ⚠️ 提示，不会报错**。

**怎么确认"复用"生效了**：Ctrl+C 停掉服务端，看最后那行统计：
```
[统计] 档案槽位 4 个（占用 0、空闲 4；累计发放 N 次）
```
- **占用 0** ⇒ 断开时都还回去了（对）
- **累计发放 N 次**（N 可以 > 4）⇒ 反复连接是在**复用** 1~4，而不是一路涨到 5、6、7（对）
- ⚠️ 如果出现 **`没有空闲 K 次`** ⇒ 有 K 次握手是在**没有可用档案**时发生的（那几次会退回计数器，
  仍然可能撞上"战绩明细被跳过"）—— 说明**同时在线的人数超过了档案数**。

### 15.1 修的是什么（一个会咬人的欠账）

`ServerMessageRouter` 原来这么分配：

```csharp
session.PlayerId = _nextPlayerId++;      // 第 1、2、3… 个连上来的
```

而 `battle_player_detail.player_id` 有**外键**指向 `player_profile`（只种了 1~4）。
⇒ **第 5 次连接**拿到 5 ⇒ 外键拒绝 ⇒ 那一局的战绩明细**静默跳过**。

⚠️ **注意它不是"最多 4 个人"**，而是"**累计连过 4 次之后就开始丢**" ——
调试时反复开关窗口很容易撞上（而且看起来像"战绩功能偶尔失灵"）。

### 15.2 做法：把会话绑到**一个真实存在的空档案槽位**

```
启动时：把 player_profile.player_id 全部读进内存（一次查询）
握手时：领一个**最小的空闲** id
断开时：还回去
```

| 决定 | 理由 |
| --- | --- |
| **领最小的空闲**（不是随便挑） | 确定性优先：调试时"我先进去所以我总是玩家 1"，比随机省掉一整类困惑 |
| **接缝 `IPlayerSlotProvider` 住在 `Core`**，实现 `PlayerProfileSlots` 住在 `Data` | 用它的地方是 `ServerMessageRouter`（在 Core）；让 Core 直接认 Data 的实现就把依赖方向反了，而且**网络层不该看见 MySQL**（`_net-probe` 要在没有数据库的环境跑 93 条）。⇒ Core **声明**、Data **实现**、Host **接线**（与 `ITransport` / `IAssetProvider` 同一套路） |
| **`slots == null` 时退回老计数器** | ⚠️ 这条**必须保留**：`_net-probe` 没有数据库，而它断言 `PlayerId == 1`、`== 2`。实测退回后 **93 条全绿** |
| **`Release` 对"不是自己发出去的 id"要无害** | 否则那个 id 会被后面的握手领走 ⇒ 又变成不存在的 `player_id`（同一个坑换个入口） |
| 档案列表**启动时读一次**，之后握手只查内存 | 握手跑在网络泵里，不该为一次分配去等一次 IO。新建/删除档案要重启 —— 刻意的取舍（本项目还没有注册流程） |

### 15.3 ⚠️ 这**不是**账号系统（说清楚，别让人以为 SRV-06 做完了）

**谁连上来都能领到「测试玩家一」** —— 它只是让"玩家编号"重新**落在一个真实存在的档案上**，
从而让战绩写得进去、累计涨得起来。

真正的 SRV-06（登录：用户名+密码 → `SHA256(salt+pwd)` 校验 → 绑定 `account` → 取 `player_profile`）
做完时，**换掉 `IPlayerSlotProvider` 的实现即可**，`ServerMessageRouter` 与调用方**一行都不用改**
—— 这正是把它做成接缝的理由。

## 十六、Host 真的读 `appsettings.json` 了（SRV-01，2026-09-27）

### 16.0 ⚠️ 要你手动做的（**4 步**）

| # | 操作 | 成功判据 |
| --- | --- | --- |
| **1** | **先编译**：`dotnet build Server\NBC.Server.Host\NBC.Server.Host.csproj -m:1` | `0 个错误` |
| **2** | **重启服务端**（⚠️ 仍然别双击旧 exe） | 横幅多出三行：<br>`[配置] 文件：…\appsettings.json`<br>`[配置] 监听端口 9000（来源：appsettings.json）`<br>`[配置] 数据库参数来源：Database 段（appsettings.json）；日志级别：Debug` |
| **3** | **改文件验证它真的生效**：把 `appsettings.json` 的 `"ListenPort": 9000` 改成 **`9100`** → 重启 | 横幅变成 `监听端口 9100（来源：appsettings.json）`，且 `[就绪] 已监听 9100` |
| **4** | **改回去**（`9100` → `9000`）→ 重启 | 恢复监听 9000 |

⚠️ **你现在不会看到行为变化** —— 因为文件里的值和代码默认值**恰好一致**。
**这一片的意义正是"以后改文件就会生效"**：在此之前，改 `appsettings.json` **什么都不会发生、也不会报**。

⚠️ **注意第 2 步的一个细节**：如果你看到的是 `[配置] 文件：**没找到**`，那说明 exe 旁边没有配置文件
（`csproj` 里 `CopyToOutputDirectory=PreserveNewest` 会拷过去；如果你手动搬过 exe，就要连它一起搬）。

**可选**：把 `Simulation.LogicTickRate` 改成 `20` → 重启会看到一段**大声警告**（见 §16.2），然后改回 30。

### 16.1 改了什么

| 文件 | 改动 |
| --- | --- |
| `Server\NBC.Server.Host\HostConfig.cs` | **新增**：按 `命令行 > appsettings.json > 内置默认值` 组装配置，并**记录每个值的来源** |
| `Server\NBC.Server.Host\Program.cs` | 用 `HostConfig` 取代 `ReadIntArg("--port")` 与"用默认值构造 `DatabaseOptions`"；横幅打印配置来源与提示 |
| `Server\NBC.Server.Host\appsettings.json` | 每个键标注**【已读】/【未读】**（因为现在真的会被读，标错的键会骗人） |

### 16.2 三个设计点

**① 优先级：`命令行 > 配置文件 > 内置默认值`，而且来源要印出来**

- 命令行优先：`--port=7778` 是**运维/自动化**用的（`_net-probe` 与手顺书都靠它），不能被配置文件悄悄盖掉。
- **来源必须印出来**（`监听端口 9000（来源：appsettings.json）`）—— 否则"我改的到底生效没有"又要靠猜，
  而那**正是这一片存在的理由**（"改了却没生效"是 `Docs\排查手册\06` 那条坑）。

**② 配置**读不出来**绝不让服务端起不来**，但**每一处降级都要说出来**

缺文件 / JSON 坏了 / 端口写成 `99999` —— 全都**忽略并继续启动**，只是往提示里写一条：

```
⚠️ appsettings.json 里的 `Server.ListenPort` = 「99999」不是合法端口，**已忽略**（用默认 9000）。
```

这与 DB-10（"数据库不可用时服务端仍能启动"）是同一条：**配置是辅助，不是前置条件**。

**③ ⚠️ 它顺手让一个"死掉的检查"复活了**（值得单独说）

`Program.cs` 里原来有一段"共享层 `LogicTickRate` 与协议 `TickRate` 不一致就警告"的运行时检查，
**被编译器用 CS0162（无法访问的代码）判死** —— 两边都是 `const`，比较在编译期就有结果，
那段代码**永远不执行**。（当时如实记下了这条，并把它挪去 `ProtocolTests` 做编译期断言。）

⇒ 现在 `Simulation.LogicTickRate` 是**运行期从文件读来的**，"文件里写的"和"协议常量"**真的可能不一致**了
—— 那个检查**重新有意义**。实测把它改成 20：

```
⚠️ appsettings.json 的 `Simulation.LogicTickRate` = 20，而协议常量 `NetContract.TickRate` = 30。
        服务端**用协议常量**（30Hz）—— 那个值会随 `HandshakeAck` 发给客户端，
        改它等于改协议（还要动 Shared\Net\NetContract.cs 并升 CONTRACT_VERSION）。
```

> 📌 **"走不到的分支"有两种下场**：一种该删，一种该**等它的前提变成真的**。
> 这一条是后者 —— 所以当时不该删，只是**不该放在那里**（该放测试）。现在它又有家了。
